# 可拓展创新方向 — AI Agricultural Assistant（AgriGPT）

## 项目定位与现有能力

本项目是一套**多模态、多智能体的农业咨询系统**：后端 FastAPI + LangChain/LCEL + Groq（Llama 3.3 70B 文本 / Llama 4 Scout 视觉），前端 React 18 + TypeScript + Vite + shadcn/ui，Docker 三服务一键编排。现有能力清单（全部已实现、有接口可验证）：

- **7 角色 Agent**：MasterAgent 主控 + Crop/Pest/Irrigation/Yield/Subsidy 五专家 + FormatterAgent，注册表模式（`core/langchain_tools.py`），职责边界写死在提示词内；
- **LLM 意图路由**：Pydantic 结构化打分（`core/router_schema.py`），主 ≥75 分、辅 ≥50 分、最多 3 个并行执行，图片强制注入 PestAgent；
- **多模态入口**：`/ask/text`、`/ask/image`、`/ask/chat`（图文混聊），JPEG/PNG ≤8MB 白名单校验；
- **RAG 防幻觉**：`services/rag_service.py` + `rag_chain.py`（LCEL 链）+ `guardrails.py` 政策名护栏，FAISS 384 维本地向量库（可脚本迁 Pinecone）；
- **会话记忆**：`core/memory_manager.py`，Redis List（TTL 7 天、上限 10 条），降级内存 deque；
- **工程闭环**：`token_tracker` 成本核算、`history_service` 原子写日志轮转、`/metrics/usage`、`/metrics/quality`、`/metrics/feedback` 满意度、`/weather/current` 天气、`/health` 健康检查、7 组 pytest 用例 + 容器化部署。

需要说明的事实基础：参考实现源于英文开源 AgriGPT，**当前 `prompts/prompts.yaml` 为英文，`data/subsidies.json` 是 20 条印度政策（PM-KISAN 等）**——以下方向均建立在这些真实代码与真实缺口之上。

## 主题一：功能增强——农户会用的"新入口"

### 方向1：中文农业语料本地化（难度：易）

**背景与痛点**：参考实现是英文 AgriGPT 的移植：提示词全英文，补贴数据是 PM-KISAN 这类印度政策，回答中出现 Aadhaar、₹ 符号——中国农户看不懂，答辩演示也说服不了评委。这不是小瑕疵，而是"产品给谁用"的根本问题。

**创新点**：不推翻架构，做"语言与数据双本地化"：提示词库按 locale 分版本管理，语料库从单一 subsidies.json 升级为中国政策条目。

**方案设计**：① `prompts/prompts.yaml` 增加 `locale: zh` 顶层键，Router 与五个 Agent 提示词各写一份中文版（先只写 SubsidyAgent 与 router 两个最影响观感的）；`core/prompt_loader.py` 增加按配置 `APP_LANG` 或请求参数加载的开关，不改调用方接口。② 数据侧：新建 `data/zh_subsidies.json`，字段沿用原 schema（scheme_name/eligibility/benefits/application_steps/documents），整理 15~20 条真实公开政策（耕地地力保护补贴、农机购置与应用补贴、大豆玉米生产者补贴等，出处写进 metadata 的 notes 字段）。③ 把 `rag_service.py` 的 `DATA_PATH` 常量改为可配置数据源路径，重建 FAISS 索引（复用现有脚本模式）。④ 护栏适配：`core/guardrails.py` 现按英文措辞判断"未找到"，需补充中文兜底关键词（"未查询到/暂无/请以官方发布为准"）与免责声明中文文案。

**落地步骤**：W1 完成 router + SubsidyAgent 中文提示词与 locale 开关，跑通既有 pytest 确认无回归；W2 整理中文政策语料、重建索引，端到端验证"查耕地补贴"回答含政策名且通过护栏；W3（可选）其余 Agent 提示词中文化 + 前端默认中文文案。

**实用价值**：这是本项目走向中国农户的"门槛级"改造；答辩时"我们补了 20 条中文真实政策语料并过了护栏测试"是扎实的创新证据，而非美化包装。

**风险与备选**：政策数据有有效期，写错会误导——对策：条目必须带发布日期与官方来源，回答中提示"政策以官方最新发布为准"；若时间紧，可只中文化提示词、把补贴数据保留为示例并注明"接入真实政策源"。

### 方向2：语音输入与语音播报（难度：易）

**背景与痛点**：农业 AI 助手最真实的目标用户是高龄农户，其中相当比例不会打字、甚至不识字；"拍照问病"能覆盖一部分，但"施什么肥"这类问题被输入门槛挡在门外。

**创新点**：纯前端、零后端改动、零成本接入浏览器原生 Web Speech API：长按麦克风说话 → 自动转中文文本 → 走现有 `/ask/chat`；回答返回后调用 SpeechSynthesis 中文朗读（可开关）。

**方案设计**：① `frontend/src/components/ChatInput.tsx` 输入框尾部加录音按钮：`SpeechRecognition`（`webkitSpeechRecognition`，lang=zh-CN，浏览器不支持时隐藏按钮并提示）；识别中间结果实时回填输入框，用户可编辑后再发送，避免识别错误直接进对话。② `ChatBubble.tsx` 增加"朗读"图标按钮，用 `speechSynthesis.speak(new SpeechSynthesisUtterance(text))`，中文需设置 `utterance.lang='zh-CN'`，播报中再次点击取消。③ `store/chatStore.ts` 加 `voiceEnabled` 偏好（localStorage 持久化）。

**落地步骤**：W1 接入 SpeechRecognition，语音→输入框→发送全链路可用；W2 播报按钮 + 朗读中打断逻辑；W3 选一台真实手机浏览器做真机测试并修兼容问题（Chrome Android 支持最佳）。

**实用价值**：一个 1 周 MVP 就能把产品从"给年轻人演示"变成"老人真的会用"，是演示时最打动人的功能；同时完全免费，符合教学预算。

**风险与备选**：中文识别依赖浏览器云端服务、方言识别率有限——备选：前端提供"快捷提问模板"（"今天适合打药吗？""番茄黄叶怎么办"）作为低识字用户的零输入入口；识别失败时引导用户点模板而非重说。

### 方向3：天气×农事联动（难度：中）

**背景与痛点**：天气数据现在只出现在页面顶部（`WeatherHeader` 用浏览器定位调 `/weather/current`），是"展示件"——而农业决策与天气强相关：明天下雨就不必今天浇水，雨前喷药等于白喷。用户问"我的番茄该浇水吗"时，Agent 并不知道窗外在下雨。

**创新点**：把天气摘要从 UI 层下沉到决策层：前端随请求带上坐标 → 后端取天气 → 以 `weather_note` 前缀注入 Agent 上下文，让灌溉/施药建议从"通用规程"变成"今天该不该做"。

**方案设计**：① 前端 `chatStore.ts` 保存 WeatherHeader 已拿到的 lat/lon，`agriApi.ts` 的 `askChat` FormData 增加 `lat`、`lon` 字段（沿用 FormData 既有传递机制）。② 后端 `routes/ask_router.py` 解析坐标后调用现有 `weather_service.get_current_weather`（无 key/失败时静默跳过，已有降级模式），把 `{location, temp, condition, humidity, wind}` 归一成一行中文摘要。③ 在 `master_agent.py` 的 `route_query` 中把摘要拼入 `chat_history_str` 之前（如 `[天气] 上海 多云 24°C 湿度 78% 风 3级，未来 12 小时无降水预报`），并在 `prompts.yaml` 的 Irrigation/Pest Agent 提示词中声明约束："若上下文含天气信息，必须基于它给出今天是否浇水/喷药的明确判断；若不含天气，禁止臆测天气"。④ 前端加两个问法引导按钮："今天适合打药吗？""今天要浇水吗？"降低使用成本。

**落地步骤**：W1 打通坐标传递 + 后端注入 weather_note（用日志验证注入生效）；W2 改造 Irrigation/Pest 两段提示词并各写 5 组"雨天/晴天/大风"示例做人工评测；W3 引导按钮 + 降级回归测试（无 API key 时行为与现在一致）。

**实用价值**：天气是农户每天真实打开手机的动机；"根据明天降雨调整今天灌溉"是农技站推广水肥一体化时的刚需话术，产品演示中一问一答即可展示差异化。

**风险与备选**：坐标定位到城区而非农田、预报数据只有当前值无未来 24h（OpenWeather 免费层限制）——备选：只做"当前天气 + 降水状况"的当下决策（雨后 2 天内不打药这类规则由提示词承载）；坐标错误时 weather_note 置空并约束 Agent 不提天气，避免强答。

## 主题二：智能升级——把"会说话"变成"说得准"

### 方向4：我的农场档案（难度：中）

**背景与痛点**：记忆只挂在随机 `session_id` 上（前端 `crypto.randomUUID()` 生成），关掉浏览器就归零；用户每次换会话都要重述"我种的是大棚番茄、三亩、四月移栽"。系统对"谁在种什么"毫无概念，个性化无从谈起。

**创新点**：新增"农场档案"持久化：作物类型/品种/移栽日期/种植方式（露地/大棚）随用户（先按设备档案 key）存储，问答前自动拼入上下文；叠加简单物候规则，主动提示"当前处于开花坐果期，注意补硼与控旺"。

**方案设计**：① 存储：`data/crop_profile.json`（原子写复用 `history_service` 的 os.replace 模式），key 为 device profile id；首版不做账号系统，用 localStorage 生成的 `profile_id` 传递，为方向10的用户体系预留 userId 字段。② 新路由 `routes/profile_router.py`：`GET/PUT /profile`（校验字段白名单：crop_type、variety、planted_at、mode、area）；不合法字段 400。③ 注入：`master_agent.py` 路由前读取档案，格式化为 `[档案] 大棚番茄，4 月 15 日移栽` 前缀；若查不到档案，FormatterAgent 在首次回答末尾提醒"告诉我你种什么，我能给更准的建议"（提示词加一条引导）。④ 物候日历：`core/crop_calendar.py` 静态表（10 种常见作物 × 移栽到各物候期的天数区间 + 关键农事提示），按 planted_at 推算当前阶段并注入。⑤ 前端新建"我的农场"小表单页（shadcn 表单组件已有），成功后 toast 提示。

**落地步骤**：W1 档案 CRUD 路由 + 原子落盘 + pytest；W2 profile 注入上下文 + 首次引导话术；W3 物候日历表 + 对话中阶段提醒评测。

**实用价值**：个性化 + 主动提醒是所有 AI 助手的价值叙事主线；答辩场景里"连续追问同一块番茄地"比每次冷启动的问答更能体现 Agent 记忆与推理的完整度。

**风险与备选**：档案可能填错（移栽日期输错导致物候判断全错）——对策：物候提示措辞加"若移栽日期不准会影响判断"；若静态日历表工作量大，MVP 可只做档案注入、把物候提醒列为 W3 可裁剪项。

### 方向5：农技知识中心（难度：中）

**背景与痛点**：系统唯一的 RAG 是补贴问答——`rag_service.py` 把数据路径写死为 `data/subsidies.json`、检索链只服务 SubsidyAgent。而农户问得最多的"番茄疮痂病用什么药、安全间隔期几天"反而全靠模型记忆，编造药名会直接害人。

**创新点**：把"补贴专用 RAG 链路"泛化为**多命名空间知识中心**：新增"农药/肥料安全使用"等知识库，让 Pest/CropAgent 在回答用药类问题时强制走检索、检索不到就明说"不在知识库内"，从源头防编造。

**方案设计**：① 泛化 `services/rag_service.py`：`DATA_PATH` 改为命名空间映射 `{namespace: (source_json, index_dir)}`，索引目录 `data/faiss_{namespace}/`；`rag_chain.py` 增加 `invoke_kb_rag(query, namespace, chat_history)` 通用链（复用现 LCEL 结构）。② 新增 `core/kb_registry.py`：注册 `subsidy`（现有）、`agrochemicals`（首批 15~20 条：通用名/登记作物/用法用量/安全间隔期/注意事项，来源注明公开植保手册）；给出每个命名空间的关键词（如"药、打、喷、间隔期"），供 Agent 判断是否触发检索。③ 挂接：PestAgent 与 CropAgent 的 `handle_query` 中，命中关键词先检索 `agrochemicals`，把结果（含来源条目标题）注入其提示词上下文，回答末尾列出"依据条目"。④ 黄金评估集：`tests/golden_qa.json` 建 20 条（10 条库内应命中、5 条库外应拒答、5 条越界应回落），`scripts/eval_kb.py` 输出命中/拒答/越界三项得分报告，加入 CI（GitHub Actions 现成流水线加一步），防止后续改提示词导致"编造率"回升。

**落地步骤**：W1 rag_service 泛化 + agrochemicals 语料整理；W2 检索触发挂接 + 依据标注；W3 黄金集与评估脚本接入 CI。

**实用价值**：农药建议是最高责任场景，能溯源的知识库直接支撑"我们敢承诺不编造药方"；运营方可不断上传新语料（新品种、新条例）而不改代码——这是向农技站/企业交付时的核心卖点。

**风险与备选**：农药登记数据版权/时效——对策：语料只收录省级植保站公开防治手册与教材内容并标注来源日期，加"请以当地植保站指导为准"免责；若合规评估不通过，首版命名空间改为低风险的"农时与栽培管理"知识（整地、轮作、密度），再逐步放开。

### 方向6：结构化诊断处方卡（难度：中）

**背景与痛点**：`/ask/image` 的诊断结论经 FormatterAgent 合成后是一大段 Markdown，关键信息（病名、用药、注意事项）淹没在文字里；农户拍完照最需要的是"这是什么病、怎么处理"一眼可读、可截图转发给家人/农资店的结果；且项目已证明 Pydantic 结构化输出可靠，却只用于路由，没用于业务输出。

**创新点**：为图像诊断新增"处方卡"结构化输出：病害名、置信依据、症状匹配项、处理建议（含安全间隔期）、复查提醒，落盘成诊断记录并允许多轮追问复查；前端以卡片渲染而非长文。

**方案设计**：① 新建 `core/consult_schema.py`：`DiagnosisCard(BaseModel)`——`disease_candidates: [{name, matched_symptoms[], basis_notes}]`、`severity`、`treatment: {action, product_generic_name, dosage_hint, safety_interval_days}`、`precautions[]`、`follow_up: {recheck_in_days, danger_signs[]}`；沿用 `router_schema.py` 的"结构化输出 + JSON 正则兜底"模式。② 新增视觉诊断链（仿 `rag_chain.py`）：vision 模型 + `with_structured_output(DiagnosisCard)`，失败时降级为现有长文路径。③ `PestAgent.handle_query` 图片分支改为先出卡片；卡片 JSON 存 `data/diagnoses/{session_id}_{ts}.json`（复用原子写模式），并作为下轮追问的引用上下文（"上次说 5 天后复查，现在叶背有白粉状物"）。④ 前端 `pages/ImageDiagnosis.tsx`：结果区用 shadcn Card 渲染字段表，`safety_interval_days` 用 Alert 高亮，附"转人工复核"占位按钮（承接方向12）。

**落地步骤**：W1 卡片 Schema + 视觉结构化链 + 兜底，pytest 覆盖合法/非法输出；W2 落盘 + 下轮追问引用；W3 前端卡片渲染 + 真机图片验收。

**实用价值**：把"AI 说了什么"变成"农户能照做"的处方形态，是产品从聊天工具走向"农事工具"的关键一跃；confidence 字段以"匹配到的症状清单"呈现而非伪造概率，既诚实又有说服力。

**风险与备选**：模型可能输出库外病害名或剂量措辞不当——对策：卡片 `product_generic_name` 只允许来自方向5知识库命中的通用名（未命中则 treatment 置为"咨询当地植保站"，不给剂量），两个方向互相成就；结构化失败率若高，保留长文降级并记录失败样本。

### 方向7：负反馈学习闭环（难度：高）

**背景与痛点**：`/metrics/feedback` 收集的点踩目前只被统计成满意度数字（`/metrics/quality`），从未被消费——系统不会因为被点踩而变好。学生辛苦积累的负样本是躺着的数据资产。

**创新点**：建一条"点踩 → 人工标注原因 → 生成修正 → 回归验证"的半自动闭环：负反馈不再只是指标，而是提示词与语料的训练信号。MVP 采用"人审半自动"而非全自动改写，规避质量漂移。

**方案设计**：① 数据管道：`metrics_router` 增加 `GET /metrics/feedback/top-negative?days=N`（按 query 聚合 negative 数与最近样本，含回答片段），负反馈落盘时同步把"回答 + 路由的 Agent 列表"写入样本字段（`feedback_service.py` 小改）。② 标注台：新前端页 `/quality`（运营菜单）：列出负样本，标注员选择原因标签（幻觉/政策过时/答非所问/语气生硬）并提交。③ 修正动作：对"政策过时/幻觉"类，自动建议写入 kb 纠错条目（复用方向5知识中心的新命名空间 `errata`，检索时置顶）；对"答非所问"类，把样本 query 追加到 `prompts.yaml` 该 Agent 段的 few-shot 修正节（yaml 已版本化，天然可回滚）——每次修正生成 diff 预览，须人工确认后落盘（半自动）。④ 回归：跑方向5的黄金评估集 + 负样本抽样复测，输出"编造率/满意度"变化报告。

**落地步骤**：W1 top-negative 明细接口 + 落盘样本字段；W2 标注台页面（复用表格/筛选组件）；W3 修正动作与确认流 + 回归报告；W4（可选）两周数据后输出一次"闭环改善前后"对比分析，作为项目结题素材。

**实用价值**：这是把演示项目推向"可运营产品"的分水岭：运营者每天能看见"今天被点踩最多的问题是什么、修正后同类问题占比下降多少"。农技站或企业评估该系统时，"数据越用越准的机制"比任何功能清单都值钱。

**风险与备选**：自动改写提示词可能漂移——对策已内建（人工确认 + 版本回滚 + 黄金集回归三防线）；样本量不足时指标波动大——对策：报告同时展示样本数，标注"样本 <10 时不下结论"。

## 主题三：架构工程化——扛得住、答得快、花得少

### 方向8：流式输出（难度：中）

**背景与痛点**：多 Agent 编排质量高但慢：路由打分 + 并行专家 + 合成，一次回答要等 5~15 秒整包返回（响应里已有 `elapsed_ms` 佐证等待时长），前端只有转圈 Loader，用户不知道系统在干什么，体感接近"卡死"。

**创新点**：加入 SSE 流式输出：聚齐专家结果后，Formatter 合成阶段逐字下发；前端逐字渲染并展示"正在由哪些 Agent 回答"的过程信息，让等待变得可感知、可打断。

**方案设计**：① 后端：新增 `POST /ask/stream`（FormData 同 `/ask/chat`），内部逻辑：路由与专家并行阶段完全复用 `master_agent.route_query` 的现有流程，仅将 Formatter 合成从 `LLMChain.invoke` 改为 `.stream`（LangChain 原生支持），用 `StreamingResponse(media_type="text/event-stream")` 下发事件：先发 `agents_routed` 事件（谁在答），再逐块发 `token`，最后发 `done`（含 token_usage 与 request_id）。**诚实的技术边界**：多 Agent 结果必须先聚齐才能合成，流式只能覆盖最后一段，但"转圈 8 秒 → 3 秒内看到文字开始流动"的体验差异已经巨大。② 前端：`agriApi.ts` 增加基于 `fetch` + `ReadableStream` 的流式请求（EventSource 不支持 POST，故用 fetch 流）；`ChatBubble` 支持增量文本渲染；AbortController 实现"停止生成"。③ 降级：流中断/超时自动切换为整包拉取，行为与现状一致。

**落地步骤**：W1 后端 stream 端点 + 事件协议 + 手工 curl 验证；W2 前端流式渲染与停止按钮；W3 降级与异常路径测试（断网、模型 5xx），并对比记录优化前后的 `elapsed_ms` 与首字时间。

**实用价值**：对 C 端演示是体感级的提升；对答辩，"我们量化了首字延迟从 ~8s 降到 ~2s"是工程能力的直接证据。无新增依赖、无付费服务。

**风险与备选**：Formatter 链若含非流式中间步骤会阻塞——对策：先跑通纯 LLM 段的流，复杂链后续再拆；若时间不足，备选"伪流式"：后端先返回路由信息（谁在答+预计结构），前端先渲染占位骨架，再整包渲染正文——成本 1 天，体验改善约五成。

### 方向9：多模型网关与语义缓存降本（难度：中）

**背景与痛点**：项目风险表里第一行就是"Groq 限流/欠费"。免费额度的 Groq 在演示/教学高峰时段经常 429，现有 3 次退避只能推迟失败；同时大量重复问题（全班同学问同一道题）在重复烧 Token。

**创新点**：在 `core/llm_client.py` 上加两层：① **Provider 网关**：抽象 `LLMProvider`（OpenAI 兼容协议），配置可声明主备 Provider 与失败切换顺序，主 Provider 连续失败 N 次自动切备用（接入硅基流动/阿里云百炼等免费额度的 qwen 系/glm 系模型，均 OpenAI 兼容、LangChain 现成封装，零成本）；② **语义缓存**：单轮无图问题先对历史"问题-答案"做语义命中（复用现有 384 维 embedding 做相似度 ≥0.97 判断），命中直接返回缓存答案并上报 `token_tracker` 的 savings 字段，未命中才调模型并写入缓存（键含 kb 版本号与缓存 TTL 防陈旧）。

**方案设计**：① `core/config.py` 增加 `LLM_PROVIDER`、`LLM_BACKUP_PROVIDER`、`SEMANTIC_CACHE_TTL` 等配置；`core/llm_client.get_llm` 改为工厂 + 探活切换（保留现有 retry_utils 的指数退避）；② 新增 `core/semantic_cache.py`：存储用 Redis（无 Redis 降级为 `data/cache.json` 原子写，复用轮转模式），查询归一化复用 `rag_service._clean_query`；③ 缓存仅对"文本、单轮、无图片"的请求生效（图片与多轮天然无法命中，避免上下文串味）；④ `/metrics/usage` 扩展返回 `savings_tokens`（`token_tracker` 加字段，前端看板承接）。

**落地步骤**：W1 Provider 工厂与配置化 + 手工模拟主 Provider 429 验证切换；W2 语义缓存 + 命中率日志；W3 savings 指标上报 + 一周用量对比报告。

**实用价值**：直接解决"演示现场 API 欠费"这种学生项目最常见的翻车事故；"缓存命中率 35%、省 Token 40%"是可写进结题报告的量化产出。

**风险与备选**：备用 Provider 质量不一、缓存误命中给出过时答案——对策：缓存键含模型名与 kb 版本、TTL 默认 24h；命中率与准确率双指标日志，低于阈值的命名空间自动关闭缓存（kill switch 一行配置）。

### 方向10：用户体系与配额（难度：高）

**背景与痛点**：系统现在完全匿名：`session_id` 前端随意生成，任何拿到 API 地址的人都能无限调用，无注册、无配额、无滥用防护；也无法区分"哪个农户、哪个渠道"在提问。这是项目从 demo 走向产品（无论免费公益还是订阅收费）的第一道工程门槛。

**创新点**：引入最小可用用户体系：注册/登录（JWT）+ 每日提问配额 + 会话归属用户；SQLite 起步零外部依赖，为后续方向11/12 提供 userId 维度。

**方案设计**：① 存储：`data/users.db`（SQLite，`sqlite3` 标准库，不引 ORM 不加依赖），表 `users(id, username UNIQUE, pass_hash, created_at)`、`usage_daily(user_id, date, cnt)`；密码用标准库 `hashlib.pbkdf2_hmac` 加盐（不依赖 bcrypt 兼容问题）。② 新路由 `routes/auth_router.py`：`POST /auth/register`、`POST /auth/login`（返回 HS256 自签 JWT，`pyjwt` 或手写 HMAC 均可，量级很小）、`GET /auth/me`。③ 配额：FastAPI 依赖注入在 ask 三个路由统一加 `require_user`；每请求对 `usage_daily` 计数，超限返回 429 + `detail` 文案（前端拦截器已有统一错误归一化，`client.ts` 补 401→跳登录、429→提示明日再试）。④ `ask_router` 生成/校验 session_id 时改为服务端绑定 `{user_id}:{uuid}`，Redis key 天然隔离多用户；`memory_manager` 无需改动。⑤ 前端：登录/注册页（shadcn 表单 + Card）、token 存 localStorage、axios 拦截器加 Authorization 头（拦截器已存在，只加逻辑）。

**落地步骤**：W1 用户表 + auth 路由 + pytest（注册/登录/错误密码/重复名）；W2 配额依赖注入 + session 绑定 + 429 联调；W3 前端登录流程 + 会话保持（刷新不丢登录）；W4（可选）把方向4档案 key 从 device 换成 userId，数据归户。

**实用价值**：用户体系是一切运营动作的地基：配额让免费 API 成本可控（全班共用一份 key 时尤其重要）、多用户隔离让记忆不串号；答辩叙事从"一个能跑的机器人"升级为"具备用户管理的产品"。

**风险与备选**：自研认证有安全边界（教学演示可接受）——对策：文档明示"生产环境需换 OAuth + HTTPS"，代码注释标注边界；若课时紧，砍配额只做登录与 session 绑定，3 周减为 2 周。

## 主题四：落地商业化——从 demo 到有人愿意用

### 方向11：运营可视化看板（难度：易）

**背景与痛点**：`/metrics/usage`（by_agent/by_type/by_day）与 `/metrics/quality`（满意度）的数据质量其实不错，但只能 curl 看 JSON；前端没有任何运营页面。数据躺在日志里，等于没运营。

**创新点**：新增一个"运营看板"页面，把现有指标 API 渲染成图：按天问答量折线、按 Agent 用量柱状、满意度趋势、Token 成本与估算费用、最近负反馈明细表——全部数据已有，主要工作量在前端。

**方案设计**：① 补一个明细接口 `GET /metrics/feedback/list?days=&limit=`（`metrics_router.py` 加路由，读 `feedback_log.json` 过滤近 N 天，返回 request_id/时间/正负/来源/关联 query 摘要）；usage 聚合若有性能顾虑加内存缓存（数据量小，首版可不做）。② 前端新页 `pages/Dashboard.tsx` 挂到 Navbar（`NavLink` 现成）；图表引入 recharts（npm 免费开源，与现有组件体系兼容），4 块：总览卡（今日问答/7 日满意度/估算成本）、按天折线、按 Agent 柱状（点击下钻到明细表）、负反馈表格（positive/negative 徽章用现成 Badge 组件）。③ 时间范围筛选（7/30/90 天）复用现有 `days` 参数约定。

**落地步骤**：W1 明细接口 + pytest；W2 前端图表页与筛选；W3 与方向7共用入口的"质量中心"菜单整合（可选）。

**实用价值**：面向运营者/教师评委——答辩时评委问"系统效果如何"，现场打开看板比口头解释有力十倍；运营者可据此决定"哪个 Agent 答得差要修、补贴季要不要加语料"。数据源已存在，是性价比最高的"易"方向。

**风险与备选**：JSON 日志量增大后聚合变慢——对策：按天分文件归档已在 `history_service` 5MB 轮转模式内，聚合改为按天文件读；看板首版只读近 30 天，避免全量扫描。

### 方向12：AI 初诊 + 植保专家人工复核通道（难度：高）

**背景与痛点**：AI 诊断再准，农户也不敢只信 AI 就买药打药；农技站专家的时间又宝贵。真实农技服务链条里，"AI 初筛 + 人复核"是已被验证的分工模式——AI 解决"大部分常见问题不用等人"，人解决"疑难杂症与责任背书"。项目现有 `feedback_log` 等 JSON 日志已证明"类状态数据落盘"可行，但没有一条"工单"数据流。

**创新点**：在方向6处方卡上增加"转人工复核"：农户一键把诊断卡（含图片与对话上下文）提交成工单 → 专家端待办列表认领 → 批注/修正回填 → 农户端看到"专家意见"标记，形成 open→assigned→resolved 状态机闭环。

**方案设计**：① 存储：`data/consults/` 目录，每单一个 JSON（id/status/image 副本/卡片快照/上下文摘要/专家批注/时间戳），复用原子写模式；`core/consult_store.py` 封装 create/claim/annotate/resolve 四个操作并做状态迁移校验（非法迁移报 400）。② 新路由 `routes/consult_router.py`：`POST /consults`（农户端，鉴权可先复用方向10用户或 demo 用 `source=demo`）、`GET /consults?status=open`（专家端待办）、`POST /consults/{id}/claim`、`POST /consults/{id}/annotate`。③ 前端两个页：农户端在 ImageDiagnosis 结果卡加"转人工复核"按钮 + 状态提示；专家端新页 `pages/ConsultQueue.tsx`（待办列表 + 详情 + 批注框，卡片渲染与诊断页共用组件）。④ 角色：MVP 不做权限系统，专家页链接放 Navbar 但注释标明"演示用"，接入方向10后再收紧。

**落地步骤**：W1 consult_store + 状态机 + 路由 + pytest（含非法状态迁移）；W2 农户端提交流与状态回显；W3 专家队列页与批注回填；W4 组内试运行一周：组员轮流当"值班专家"，记录平均响应时间与批注率，产出试运行数据。

**实用价值**：直接回答了"AI 诊断错了谁负责"这个所有农业 AI 项目都绕不开的商业问题：AI 做免费初筛、人工做付费背书，正是农技服务类产品的经典商业化路径；学生团队可借此对接真实农技站/合作社做试点，把实训项目变成有真实用户的课外实践。

**风险与备选**：专家供给不足、责任界定不清——对策：MVP 明示"专家意见仅供农事参考"，界面加免责文案；班级内试运行期用教师扮演专家验证流程；若对接外部失败，把该方向收缩为"诊断记录的分享/导出"（处方卡截图 + 文本分享），保留数据流骨架，后续随时扩展状态机。

## 落地建议（写给带队教师）

- **3 周内的稳妥组合**：方向1（本地化）+ 方向2（语音）+ 方向11（看板），三个"易"方向互不依赖、都可独立出成果，覆盖"中文/无障碍/运营"三条线。
- **冲刺获奖的组合**：方向3 + 方向6 + 方向5 打通"天气-诊断-用药溯源"一条完整农事链路，叙事是"从会聊到敢用药"。
- **工程深度组合**：方向9 + 方向8 + 方向10，量化指标多（首字延迟、缓存命中率、成本节省、配额拦截数），最适合写技术报告。
- 方向间的依赖关系已显式标注（6 依赖 5 的命名空间、10 是 12 的鉴权前置、7 依赖 5 的 errata 与评估集），排期时优先完成被依赖项的地基部分即可。
