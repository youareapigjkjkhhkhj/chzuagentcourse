# Kaleido AI 智能衣柜（AI Wardrobe）· 可拓展创新方向

## 项目定位与现有能力

**定位**：Kaleido AI 智能衣柜是一个面向 C 端用户的「AI 穿搭管理」微服务系统（Java 21 + Spring Boot 3.5 / Cloud 2025 + Spring AI 1.1.2，DDD + CQRS + 整洁架构），用户把真实衣物录入数字衣橱，由大模型驱动的穿搭 Agent 基于「我的衣橱」给出搭配与出行穿搭方案，金币激励与运营后台支撑用户活跃。**已实现**：服装/品牌/位置/穿搭(Outfit)四组 CRUD 与图片处理责任链（校验→压缩→EXIF 元数据）、穿搭穿着记录 API、标签体系（t_tag/t_tag_relation）、金币账户与流水（注册送币监听器先例）、AI 服务（Agent 管理：预设「穿搭助手」等 8+ 个 deepseek-v3 Agent，MEMORY/VECTOR_STORE/MCP 三类工具，会话管理，服装文档向量化 RAG 全链路：wardrobe 发 RabbitMQ clothing-event → kaleido-ai 消费 → embedding 入 Milvus → Chat 问答检索）、工作流引擎（definition JSON 的 steps 顺序执行，穿搭推荐/旅行规划两套示例）、衣橱 MCP Server（9021 端口 SSE，现仅天气工具）、RBAC 管理后台与 AI/工作流配置页面、可靠消息（t_mq_message）、短信通知（t_notice）与 XXL-Job 调度底座。前端为 Vue3 + Element Plus + Vite 管理端；用户侧仅有一份 H5 原型 HTML。模型走硅基流动（chat: deepseek-v3，embedding: bge-m3，可替换），向量库 Milvus，分表落 MySQL（t_user/t_recommend_record/t_user_operate_stream 按用户分片）。

> 难度图例：**易** = 复用现有模块与代码模式即可完成；**中** = 需新增接口/表/事件或跨服务改造，2~4 周；**难** = 需改动核心引擎或引入新模型协议，须拆里程碑。

## 一、功能增强 · 把已有基础能力做深做透

### 方向1：衣橱体检报告与闲置提醒

**背景与痛点**：项目已有「记录穿搭穿着」「查询穿搭穿着记录」API 与 t_user_operate_stream 行为流水，但穿着数据「只存不看」——用户不知道哪件外套一年没上身、哪条裙子只穿过一次。衣柜管理的真实价值不在于「存得多」，而在于「穿得值」。目前没有任何统计或提醒能力。

**创新点**：给衣柜装一块「体检仪」：按单品聚合穿着频次/最近穿着日期/季节分布，输出闲置清单；对 90 天以上未穿（且未过季）的衣物，经现有通知链路自动提醒用户「翻牌」或转赠，让沉睡库存重新进入穿搭循环。

**方案设计**：
- 新增明细表 `t_wardrobe_wear_log`（id、user_id、outfit_id、clothing_ids(JSON)、wear_date、weather、occasion、source），现有「记录穿搭穿着」接口同步补写此表（原表结构不动，兼容旧数据）。
- kaleido-wardrobe 新增聚合查询 `WearStatQueryService`：单品穿着次数、最近穿着日期、按颜色/风格(t_tag_relation)分布、闲置指数 = 90 天未穿 + 无未来季节穿着记录。
- 新增 XXL-Job 任务「衣橱体检扫描」：每日 9 点扫描闲置衣物 → 经 kaleido-message 可靠投递（t_mq_message 已有骨架）→ kaleido-notice 发站内信（t_notice 新增 IN_APP 类型，沿用现有发送与重试字段）；触发上限每日 1 条/人，避免骚扰。
- 前端（管理端/H5 原型均可）：新增「衣橱体检」页——Top 闲置榜、每件衣物的最近穿着时间线。

**落地步骤**：W1 建表并改造穿着记录接口 + 写单测；W2 聚合统计接口 + 体检报告页（先出 Top10 闲置清单）；W3 XXL-Job 定时提醒接入 notice，端到端演示「穿一次→第二天提醒消失」。

**实用价值**：真实使用者是「衣服多但总觉得没衣服穿」的都市用户与带娃家庭——闲置提醒直接换算成「省了买重复衣服的钱」，是可讲人话的卖点；对运营方，这是天然的高打开率触达位，后续可承载活动（见方向2 打卡激励）。

**风险与备选方案**：穿着记录低频，新用户冷启动无数据。备选：用 outfit 创建/穿搭助手采纳行为兜底计入使用率，并提供「演示数据一键生成」用于答辩；提醒可能被当成骚扰，必须可配置开关与频率上限。

### 方向2：穿搭打卡日历与连续激励

**背景与痛点**：穿搭本质是每日行为，但现有「穿着记录」是功能接口而非产品入口——没有日历视图、没有连续概念、也没有任何正反馈；金币系统目前只有「注册送币」一个来源（UserRegisteredCoinListener 与 t_user_coin_stream 已跑通），激励是单点的。

**创新点**：把穿着记录升级为「今日穿搭打卡」产品：穿哪套→拍一张→打上今日天气/场合，形成月历热力图与连续天数（streak）；打卡触发金币奖励事件，完全复用现有 coin 模块的监听器模式，让「坚持穿搭」成为可兑换的日常习惯。

**方案设计**：
- kaleido-wardrobe 新增打卡接口 `POST /wardrobe/checkin`（outfit_id + 今日照片走现有 MinIO 图片链），当日幂等（Redis setnx user_id+date）；打卡记录落方向1 的 `t_wardrobe_wear_log`（source=CHECKIN）。
- 新增 `CheckinStatQueryService`：月历数据（某天是否穿/穿了哪套）、连续天数（streak 按日扫描 wear_log 计算）。
- kaleido-coin 新增 `CheckinCoinListener`（对照 UserRegisteredCoinListener 写）：消费打卡事件 → 调用自身 CoinDomainService 发放奖励；规则存 t_dict（如连续 7 天奖励翻倍），改规则不动代码。
- H5 页面：日历热力图 + streak 徽标 + 「分享我的 7 天穿搭」卡片。

**落地步骤**：W1 打卡接口与幂等 + wear_log 落库；W2 日历与 streak 查询 + 简单 H5 页面；W3 金币监听器 + 字典规则 + 端到端（打卡→金币流水可见）。

**实用价值**：对用户，「记录+奖励」把整理衣柜从家务变成游戏化习惯；对平台，这是 pull 型每日回访入口（日历是天然留存钩子），也为运营大盘（方向3）提供日活口径。答辩故事完整：行为→事件→激励→留存。

**风险与备选方案**：可能被脚本刷金币。备选/缓解：单日单次 + 事件幂等键（事件 ID 落 t_mq_message 去重）+ coin 模块限流；若想压缩周期，金币奖励可先做「记账不发币」（流水可见即可演示），发币放二期。

### 方向9：家庭共享衣橱

**背景与痛点**：所有数据按 user_id 隔离、Sa-Token 单用户鉴权——但在真实场景中衣柜是家庭资产：夫妻互相看「今天你穿了什么」、帮孩子找校服、给老人备换季衣，这些需求现在完全没有承载。wardrobe 系列表未分表（仅 t_user/t_recommend_record 等分表），跨用户查询没有分片障碍，是做共享的有利条件。

**创新点**：引入「家庭组」作为 wardrobe 数据的第二归属维度：邀请码建组，成员分 OWNER/EDITOR/VIEWER 角色，组内共享服装/穿搭/打卡日历，主人在自己衣柜里「被看见」。

**方案设计**：
- 新表：`t_family_group`（id、owner_user_id、name、invite_code、status）、`t_family_member`（group_id、user_id、role）；wardrobe 各主表加 `family_group_id` 可空列（迁移脚本回填单人组）。
- 共享链路：邀请码（复用短信模板 t_notice_template 发送）→ 加入 → wardrobe 查询接口统一加组内数据范围条件（DAO 层注入 member 所在组集合，不动分表键）。
- kaleido-user/wardrobe 新增 RPC（参照 RpcCoinServiceImpl 出口模式）供组内读取；穿搭日历页支持「看家人的」视图（VIEWER 只读）。
- 权限：删除/改价等写操作仅 OWNER/EDITOR；组解散时衣物归属原 user_id 不转移（数据安全底线）。

**落地步骤**：W1 建表 + 邀请码建组/加组接口 + 单测；W2 查询层组范围过滤改造（先覆盖服装列表与穿搭列表两个主查询）；W3 共享穿搭日历页 + 组管理页；W4 联调与边界用例（退出/踢人/解散）。

**实用价值**：家庭是衣柜最自然的用户单位，共享后家庭版数据与活跃显著高于单人（可作演示对比）。答辩时能讲透「数据权限设计」与「单用户到多用户的架构演进」，是安全与架构话题的良好载体。

**风险与备选方案**：查询面广，逐接口加条件容易漏。备选路径：MVP 只共享「穿搭方案与打卡日历」（只读聚合视图，不改写主表），库存共享放二期——两周一版先演示。

## 二、智能升级 · 让 AI 真正「懂你的衣橱」

### 方向4：拍照一键录衣（视觉打标 + 表单预填）

**背景与痛点**：录入一件衣服要手填 10+ 字段（品类/颜色/季节/风格/品牌/场合…），是用户流失第一触点。现有图片责任链（ValidationHandler → ImageOptimizationHandler → MetadataExtractionHandler）只做了校验、压缩与 EXIF 提取，元数据信息对业务几乎无用——图片里最值钱的信息（衣服长什么样）没有被读取。

**创新点**：给图片链增加一个「视觉理解」Handler：调用多模态模型把服装照片转成结构化标签 JSON（品类/颜色/季节/风格/适用场合），自动预填创建表单的 90%，用户只点确认；识别结果对齐 tag 模块已有标签体系（t_tag/t_tag_relation），避免产生垃圾标签。

**方案设计**：
- kaleido-ai 新增 `POST /ai/clothing/vision-tag`（OpenAI 兼容多模态 chat，图片走 MinIO 临时 URL/base64），复用 AgentChatClientArmory 的装配模式新增 `TaggingChatClient`，prompt 强约束 JSON Schema（枚举值由 t_tag 字典下发，保证可对齐）。
- kaleido-wardrobe 图片处理链在 MetadataExtractionHandler 后追加 `VisionMetadataExtractionHandler`（开关由 Nacos 配置控制，失败降级跳过不影响主流程）；识别结果随创建接口返回给前端预填。
- 模型选型：硅基流动 Qwen2.5-VL-7B（免费额度即可用）；备选 GLM-4V。
- 前端「拍照录衣」流程：拍照→上传→展示识别草稿（可改）→确认创建→标签自动绑定。

**落地步骤**：W1 打通 vision-tag 接口（先 curl 出稳定 JSON）；W2 结果映射 tag 枚举 + 责任链 Handler 接入 + 降级开关；W3 前端拍照预填流程联调。

**实用价值**：录衣成本从「填表 2 分钟」降到「拍照 10 秒」，直接决定衣橱规模与 RAG 质量（衣服越多，穿搭助手越有用，方向5 才有戏）。视觉打标数据还能反哺方向1 的「重复购买提醒」（同品类同色 ≥3 件时提示）。

**风险与备选方案**：VLM 输出不稳定、中文服装品类可能跑偏。备选：schema 校验失败自动重试 1 次 + 置信度低时前端强制走人工确认；对输出做枚举白名单映射，白名单外一律「未识别」而不是乱造。

### 方向5：穿搭 Agent 长出「查真实衣橱」的工具

**背景与痛点**：现有穿搭助手（t_ai_agent 中 outfit-recommendation-id，deepseek-v3）的输出是「服装 ID 数组」，但它只能看到向量化摘要（ClothingVector，topK 100、无结构化过滤），看不到库存现状：会推荐已删除/已过季的衣物，也无法回答「下雨天能不能穿这件帆布鞋」「这件西装出席婚礼够不够正式」这类需要字段级查询的问题；且服装增删改目前只做了「新增→向量化」（ClothingEventListener 消费 clothing-event），删除/修改后的向量没有同步清理，向量库存在死数据。

**创新点**：给 Agent 装配一个真正的「衣橱查询工具」，把回答从「背书」变成「查库」：模型按需调用工具（按场合/温度区间/颜色/在架状态过滤），拿到字段级结果再组织答案；同时补齐服装修改/删除事件的向量同步，让 RAG 与库存一致。

**方案设计**：
- ToolType 枚举（现 MEMORY/VECTOR_STORE/MCP）新增 `WARDROBE_QUERY`；AgentChatClientArmory 的工具注册 switch 增加该分支，向 ChatClient 注册 Spring AI FunctionCallback（`QueryClothingFunction`，入参 occasion/temperature/color/onShelfOnly，出参为服装 id+名称+字段摘要）。
- 实现上复用 kaleido-wardrobe 的 ClothingQueryService（新增 RPC 出口，参照现有 Rpc*ServiceImpl 模式），响应直接进模型上下文而非向量检索，字段过滤精确。
- kaleido-ai 的 ClothingEventListener 扩展消费「更新/删除」两类服装事件（wardrobe 侧补发 MQ 消息，message 模块已有可靠投递兜底），执行 Milvus 文档 upsert/delete，保证向量与库存一致。
- 对话返回的服装 ID 增加「存在性校验」，引用已删除衣物时自动剔除并说明。

**落地步骤**：W1 枚举与 FunctionCallback 注册 + 查询函数 + 手工验证「模型会先问天气再查库」；W2 wardrobe 增改删事件补发与向量同步（重点做删除清理）；W3 对话端到端演示：新购羽绒服立即能被引用、删除后不再出现。

**实用价值**：这是从「AI 演示」到「AI 可用」的分水岭——用户真实诉求是「帮我从我的衣橱里选」，不是听模型编一套。答辩价值：讲清 RAG 局限（文本摘要检索）与 Function Calling 的互补，属于当下 AI 工程面试高频考点。

**风险与备选方案**：模型可能不调用工具或调用参数错。备选：prompt 与 system 中明示工具用途 + 温度降至 0.4（与现有 agent 配置一致风格）；如 FunctionCallback 链路调试成本高，先落「事件向量同步」独立交付，工具调用二期跟进。

### 方向10：工作流引擎支持条件分支与变量传递

**背景与痛点**：现有 WorkflowExecutionEngine 按 definition JSON 的 steps 顺序执行，每步只引用一个 agentId（见 travel-plan 7 步链与 OUTFIT_RECOMMEND 示例）。真实穿搭决策是分叉的：天气 25℃ 以上与以下应走不同方案；现引擎无法表达「如果…则跳过步骤/切换分支」，也拿不到上一步的输出作为下一步输入，多 Agent 编排只是「排队发言」。

**创新点**：给 definition 增加三类原语：step 条件（condition 表达式，命中为 false 则跳过）、输出变量（step 声明 outputSchema 并从 agent 回复中提取）、变量注入（后续 step 的 prompt/参数支持 `{{stepN.output}}` 占位符），让「夏装线 vs 叠穿线」真正由数据驱动。

**方案设计**：
- `WorkflowDefinition` 解析层扩展：step 增加 `condition`（JSONPath 式：`{{weather.maxTemp}} > 25`）与 `onFailNext`（失败跳过策略）；WorkflowExecutionEngine 执行循环改为「读取上下文 → 判定条件 → 选步执行 → 提取输出入上下文」，改造点集中在 `WorkflowExecutionEngineFactory` 与执行器（engine 目录已有良好分层，建议新增 `ConditionEvaluator` 与 `VariableResolver` 两个纯函数组件，先不改存储结构：definition 本就是 JSON，向后兼容）。
- 变量来源：执行入参（工作流执行 API 已支持传参）、上一步 agent 输出、MCP 工具返回值（天气）。
- 示例工作流「智能穿衣线」：Step1 穿搭协调 Agent → Step2 条件「若温度>25 走夏季场景 Agent；否则走叠穿 Agent」（同一 definition 内用 condition + nextStep 表达 if/else）→ Step3 汇总 Agent 引用变量拼装行李清单。
- 管理后台沿用 AI 工作流配置页，先支持 JSON 编辑 + schema 校验（monaco-editor 已在前端依赖中），图形化编排放二期。

**落地步骤**：W1 定义解析支持 condition/output 字段（纯解析 + 单测）；W2 执行引擎改造（条件判定 + 变量注入）+ 跑通「夏/冬分叉」最小 definition；W3 注册「智能穿衣」工作流并接入后台配置与执行记录页；W4 边界打磨（变量缺失报错文案、失败重试一次）。

**实用价值**：这是整个项目最有「架构含金量」的升级：工作流引擎从线性演示件变成可表达业务规则的产品能力，旅行规划等现有多 Agent 链立刻能复用。答辩时这是讲 Agent 编排深度最能打的素材。

**风险与备选方案**：引擎改造牵一发动全身，现有顺序执行必须回归通过（已有执行记录表可做对照）。备选：不碰引擎核心，先以「配置层约定」实现软分支——不同温度区间注册两条工作流，由外部调度（XXL-Job 查天气）选择执行，代价小、同样能演示分叉效果。

## 三、架构工程化 · 能力外放与系统治理

### 方向7：把衣橱发布成 MCP Server（衣橱即服务）

**背景与痛点**：项目里 MCP 已有两层沉淀——kaleido-mcp 是 MCP Server（9021 端口 SSE，现仅 WeatherService 一个工具），kaleido-ai 的 Agent 通过 agent_tool 配置以 MCP 客户端身份接入（baseUri/endpoint 即此 server）。也就是说「AI 会查天气」已经打通，但衣橱自身的数据（服装/穿搭/穿着统计）没有向 MCP 暴露，能力仍锁在自家对话里。

**创新点**：把衣柜核心查询能力以 MCP 工具形式外放：任何支持 MCP 的客户端（本项目的 Agent、外部桌面 AI 工具）都可以直接调用「查我 300 元内适合通勤的上衣」「我 3 月穿过几次这件外套」，衣橱从应用内数据变成可编程资产。

**方案设计**：
- kaleido-mcp 的 tool 包新增 `WardrobeMcpTools`（@Tool 注解，与 WeatherService 同风格）：先做三个只读工具——`query_clothing(filters)`、`query_recent_wears(days)`、`query_outfit_by_occasion(occasion)`。
- 数据获取：kaleido-mcp 通过 Dubbo RPC 调 wardrobe（在 kaleido-api 增补 RPC 接口，参照现有 RpcAiService/RpcCoinService 出口惯例），不直连库，保持服务边界。
- 鉴权：MCP Server 当前无鉴权，新增临时访问令牌（auth 服务签发 scope=mcp:wardrobe 只读、TTL 30 分钟，随客户端请求头/SSE 参数传入），server 端做校验与调用配额（Redis 计数，与方向8 的计量底座共用）。
- 演示场景：在 AI 对话客户端配置该 MCP Server 后，直接问「明天出差 3 天 20℃，帮我从我衣橱挑 3 套，列出要带的内搭数量」——答出的每件都是真实库存。

**落地步骤**：W1 定义 wardrobe RPC 只读接口 + MCP 工具注册 + 本地 SSE 联调；W2 令牌签发与校验 + 配额；W3 外部客户端接入演示 + 安全用例（越权 token 拒绝）。

**实用价值**：面向开发者与「AI 重度用户」，让衣橱像「天气插件」一样随处可用。对项目叙事，MCP 生态是当下热词，本方向复用零新增基建（MCP 框架、RPC、Redis、auth 全部现成），性价比高。

**风险与备选方案**：暴露个人数据有安全顾虑。备选/缓解：MVP 只做「工具内部按 token 映射 user_id 的只读视图」；若 Dubbo 跨服务调试成本高，可让 mcp 服务直接走 HTTP 调 gateway（写网关放行白名单），但需说明这是过渡方案。

### 方向8：AI 用量计量与免费额度治理

**背景与痛点**：AI 对话目前无任何计量：用户可无限调用 deepseek-v3，成本随活跃线性上涨；金币体系只有「送」没有「花」的出口，经济模型是断的。运营后台对 AI 成本既看不见也管不住。

**创新点**：给 kaleido-ai 装上「水表」：每次对话按 token 计费入库、每日免费额度（Redis 计数拦截）、超额后用金币兑换次数——把真实成本转成用户可感知的资源，同时给金币系统补上第一个有意义的消耗场景。

**方案设计**：
- kaleido-ai 对话链路（ChatServiceImpl 等核心执行点）统一计量：Spring AI ChatResponse 的 usage 字段取 prompt/completion token，按字典单价（t_dict 配每千 token 成本）折算，写入新表 `t_ai_usage`（user_id、agent_id、model、prompt_tokens、completion_tokens、cost、date 分区）——表结构照 t_user_coin_stream 的简洁风格。
- 免费额度：Redis `ai:quota:{userId}:{yyyyMMdd}` 计数（网关/对话入口双层校验），超限返回明确错误码 AI_QUOTA_EXCEEDED 并提示兑换。
- 兑换：`POST /ai/usage/exchange`（次数包 × N 金币）→ 调用 coin 模块 RpcCoinService 扣款 → 发放额度；coin 流水 type 记 AI_EXCHANGE。
- 管理后台「AI 用量页」：按天/按 Agent 的调用量与成本趋势（echarts），成本 Top 用户与 Top Agent，支撑运营决策。

**落地步骤**：W1 t_ai_usage 表 + 计量埋点 + XXL-Job 按日汇总；W2 免费额度拦截与兑换接口 + 前端引导弹窗；W3 后台用量看板（数据可与方向3 大盘页合并呈现）。

**实用价值**：对运营方，这是控制真实成本（模型 API 账单）的基础设施，任何商业化尝试（订阅/金币经济）的前提；对用户，额度把「AI 免费但不可控」变成透明规则。答辩可讲「成本治理」这个工程团队都认的痛点。

**风险与备选方案**：usage 字段在流式对话下需累加，易漏计。备选：先按「次数」而非 token 计量（最简单可演示），token 计量二期补；拦截必须可降级（Redis 挂了放行并告警），避免 AI 功能整体不可用。

## 四、数据与商业化 · 让数据长出新东西

### 方向3：衣橱运营大盘（跨服务数据可视化）

**背景与痛点**：管理后台已有 RBAC、Agent/工作流配置等管理页，但缺「业务视图」：服装/穿搭/用户/推荐/AI 会话的数据分散在 8+ 个服务与分表里（t_user_0/1、t_recommend_record_0/1、t_user_operate_stream_0/1…），运营方（管理员）对平台规模与健康度没有感知，答辩时「系统有多大的业务量」也答不上来。

**创新点**：用 XXL-Job 把各服务核心计数按日汇总进一张宽表，管理后台 Dashboard 展示服装/穿搭/活跃用户/AI 会话/金币发放/推荐采纳六大指标的趋势与构成——先有「数」，后续方向6/8 的运营判断才有依据。

**方案设计**：
- 新表 `t_stat_daily`（stat_date、metric_code、user_dim(ALL)、value、biz_service）——由 XXL-Job 总任务夜里跑子任务分别调用各服务只读汇总 RPC（user/wardrobe/coin/recommend/ai 各出一个 `DailyStatQuery` 出口），写库；admin 查询接口只读宽表 + Redis 缓存 1 小时。
- 避免跨服务直连库：每个服务自行出当日增量统计 RPC（复用各自 DAO），汇总任务只做编排——顺带检验各服务边界设计是否干净。
- 前端 Dashboard 增加「运营看板」页：指标卡片 + 30 天趋势折线 + 构成饼图（echarts 已在依赖）。

**落地步骤**：W1 建表 + user/wardrobe 两个服务先出统计 RPC；W2 XXL-Job 编排入库 + coin/recommend/ai 补齐；W3 看板页联调与缓存。

**实用价值**：直接服务平台运营者与答辩评委——用一张图证明系统「活着且有量」；且该看板是方向6（采纳率）、方向8（AI 成本）的公共底座，避免重复建设。

**风险与备选方案**：各服务统计口径不一致会闹笑话。备选：先只用「行为流水 + 分表汇总」由 admin 侧统一算最基础的 3 个指标（服装数/穿搭数/用户数），口径单一、2 周内必成，再做扩展指标。

### 方向6：推荐反馈闭环与个性化购衣建议

**背景与痛点**：推荐链路是单向的：AI 生成穿搭推荐 → OutfitRecommendCompletedEventListener 落 t_recommend_record 后即结束，采纳与否无人知晓；同时 brand（t_wardrobe_brand，含品牌）与 tag（风格/颜色）数据已足够刻画「这个人偏爱什么」，却从未被消费。用户「衣服多但不会买」与「总买重复的」两个需求都未被产品回应。

**创新点**：给推荐结果配「穿了 / 喜欢 / 不感兴趣」三键反馈，反馈进画像；周度生成「衣橱健康与购衣建议」：风格构成、重复购买预警（同品类同色 3 件以上提示停购）、缺口建议（常穿场合缺对应品类），把推荐从「一次推送」升级为「持续变懂你」的数据飞轮。

**方案设计**：
- t_recommend_record 增加 state 字段（PENDING/ADOPTED/LIKED/REJECTED），新增 `POST /recommend/records/{id}/feedback`；采纳标记同时触发 wear 数据（穿记录回写，与方向1/2 共享同一明细）。
- kaleido-recommend 新增画像聚合服务：按 tag_relation 统计用户风格/颜色偏好占比（近 90 天穿着口径）、按品牌统计偏好；新增「衣橱缺口」规则引擎（纯规则可实现：高频率场合 × 无对应品类标签的衣物 → 缺口项；同品类近色 ≥3 → 重复预警），规则可配在 t_dict。
- 周报生成：规则结果 + 简单模板拼装（可选由 kaleido-ai 润色文案，Prompt 只做改写不做决策），经 kaleido-notice 站内信推送「本周衣橱周报」。
- 商业化接口预留：购衣建议项带品牌与品类字段（无外部链接），为后续电商导流留位，不引入付费依赖。

**落地步骤**：W1 反馈接口 + 状态迁移 + 采纳回写穿记录；W2 画像聚合 + 缺口/重复规则 + 单测；W3 周报生成与站内信推送 + 前端「我的偏好」页展示画像。

**实用价值**：对用户，「别买重复的 + 缺什么买什么」是省钱级的实用价值；对运营，采纳率成为推荐质量指标（也是方向3 大盘的指标之一），偏好画像为将来的商业化（导购/品牌合作）提供数据资产。答辩可完整讲数据闭环：推荐→反馈→画像→更准的推荐。

**风险与备选方案**：反馈样本稀疏，画像失真。备选：画像兜底用「穿着记录 + 打卡」而非仅反馈；周报低频（每周 1 条）控打扰；规则先行保证 MVP 无 LLM 依赖，润色文案仅在有余力时开启。

## 执行建议

优先推荐学生团队按「功能增强 → 智能升级 → 外放/商业化」节奏落地前三个方向：**方向1 衣橱体检与闲置提醒**（2 周、纯复用现有模块、演示效果好）、**方向4 拍照一键录衣**（3 周、直击录衣痛点、视觉冲击强）、**方向5 穿搭 Agent 接通真实衣橱**（3 周、AI 深度最佳叙事，也可与方向4 合并演示「拍照入库→对话选衣」一条链）。方向10 引擎改造最有含金量，适合代码功底强、想冲高难度的组，务必先跑通现有顺序执行的回归用例再动引擎。
