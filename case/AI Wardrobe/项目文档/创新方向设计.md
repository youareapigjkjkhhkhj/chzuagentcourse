## 方向 1：多模态以图搜衣 + 视觉自动打标

**一句话**：用户拍照上传，系统自动识别品类/颜色/风格并入库，支持「以图搜同款」「以图找搭配」。

### 现有基础（代码依据）

| 已有能力 | 位置 |
|---|---|
| Spring AI 向量检索已跑通（`vectorStore.similaritySearch()`） | `kaleido-ai/infrastructure/adapter/repository/ClothingDocumentRepositoryImpl.java:66,94` |
| Milvus 已部署（v2.5.26） | `dev-ops/docker-compose.yml:258` |
| 服装图片已有责任链处理 | `kaleido-wardrobe/domain/image/` |
| MinIO 对象存储 + 文件服务 | `kaleido-common/kaleido-file`、`kaleido-file.yml` |

### 创新点

1. **文本向量 → 多模态向量**：当前服装文档走纯文本 embedding（BAAI/bge-m3），升级为图像+文本双塔（CLIP 类模型或多模态 embedding API），同一 Milvus collection 中并存文本列与图像列。
2. **VLM 结构化打标**：上传图片后用多模态大模型（Spring AI 支持 multimodal message）输出结构化 JSON（品类/颜色/季节/风格/适合场合），自动填充现有 `tag` 模块的标签体系——**录入流程从「手动填 10 个字段」变成「拍照即完成」**。
3. **同款识别**：图像向量近邻检索，把「我的衣橱里的相似款」聚合展示，为方向 3 的「重复购入提醒」埋点。

### 技术方案要点

- Milvus 建多向量字段 collection（text_vector + image_vector），Spring AI 的 `MilvusVectorStore` 不够用时直接用 `milvus-sdk-java` V2 客户端扩展 `ClothingDocumentRepositoryImpl`。
- 打标走现有 `AgentChatClientArmory` 的 ChatClient 装配模式，新增一个 `TaggingChatClient`，prompt 强约束 JSON Schema 输出。
- 图片走既有 MinIO 上传链路，向量入库挂在服装创建事件的 MQ 消费者上（`kaleido-message` 已有可靠投递骨架）。

### 涉及模块 / 工作量

`kaleido-ai`、`kaleido-wardrobe`（image 链路）、`kaleido-tag`；外部依赖 1 个多模态模型 API。约 2-3 周。

## 方向 2：场景感知的动态规划 Agent（当前架构的直接升级）

**一句话**：搭配推荐从「固定流程的工作流」升级为「根据天气/日程/场合动态规划步骤、自我评分迭代的 Agent」。

### 现有基础与明确的升级空间（代码依据）

| 现状 | 位置 | 问题 |
|---|---|---|
| 工作流引擎是**预定义 executor** | `kaleido-ai/application/command/executor/AbstractWorkflowExecutor`、`OutfitRecommendWorkflowExecutor`、`WorkflowExecutorFactory:41` | 流程硬编码，换个场景就要改代码 |
| 天气工具返回**硬编码字符串** | `kaleido-ai/types/tool/WeatherTool.java`（@Tool）；`kaleido-mcp` 的 WeatherService 同样是硬编码 | 「根据天气推荐」实际拿不到真实天气 |
| MCP 客户端能力已具备 | `AgentChatClientArmory.java:56,235,252`（McpSyncClient 动态装配） | 只缺真实 MCP Server 可接 |
| 多轮记忆已就绪 | `AgentChatClientArmory.java:206`（MessageWindowChatMemory + Mongo 持久化） | — |

### 创新点

1. **真实世界信号接入**：天气接高德/和风 API（顺便把 `kaleido-mcp` 从占位变成真 MCP Server，天气作为 MCP 工具被 Agent 动态发现加载）；日程接系统日历。
2. **Planner-Executor 模式**：新增 `PlannerWorkflowExecutor`，LLM 先输出「决策计划 JSON」（要查哪些维度：温度/降雨/场合/用户偏好），再按计划逐步调用工具与 RAG，替代硬编码流程——这是对现有 `AbstractWorkflowExecutor` 抽象的自然扩展。
3. **评分-自迭代闭环**：新增「搭配评审 Agent」，对推荐结果按色彩和谐度/场合匹配度/单品利用率打分，低于阈值自动重新规划，最多 N 轮——答辩时可以演示「Agent 自己发现自己推荐得不好并改进」。

### 技术方案要点

- `WorkflowExecutorFactory` 已用 prototype 作用域动态创建 executor（`:41-42`），新增 executor 类型零侵入。
- MCP Server 用 Spring AI 的 MCP server starter 实现，注册进现有 `t_ai_agent_tool` 工具表。
- 计划 JSON 用结构化输出（`BeanOutputConverter`），失败降级回 `GenericWorkflowExecutor` 保底。

### 涉及模块 / 工作量

`kaleido-ai`、`kaleido-mcp`（转正）；外部依赖天气 API。约 3 周，是**架构叙事最完整**的方向。

## 方向 3：个性化推荐与激励数据飞轮

**一句话**：把「推荐→行为→金币→更好的推荐」做成闭环，推荐排序从规则升级为用户画像驱动。

### 现有基础（代码依据）

| 已有能力 | 位置 | 现状短板 |
|---|---|---|
| 推荐服务（仅事件落库） | `kaleido-recommend`（18 文件），监听 AI 推荐完成事件 | 只记录、不学习，无个性化排序 |
| 金币体系完整 | `kaleido-coin`（账户+流水，监听注册发奖） | 激励与推荐行为未打通 |
| 通用标签关联 | `kaleido-tag`（AssociateEntityCommand） | 可直接作为画像标签源 |
| 行为流水表已分库分表 | `sharding.yaml`：t_user_operate_stream 2库×2表 | 说明行为数据量被认真对待过 |

### 创新点

1. **用户风格画像向量**：聚合「采纳的搭配」「穿着频次」「收藏/删除」行为，在 Milvus 中维护每个用户的画像向量，检索时与服装向量做个性化混合排序（向量相似度 × 行为权重 × 新颖度惩罚）。
2. **激励相容的数据收集**：用户「标记今天实际穿了这套」奖励金币——用金币体系换取高质量反馈标签（相比问卷/埋点，成本更低、数据更真），金币消耗场景（兑换）保证体系自洽。
3. **单品利用率报表**：基于穿着记录计算每件衣服「穿搭率」，联动方向 1 的相似款检索做「重复购入提醒」——可持续时尚叙事（少买多穿）。

### 技术方案要点

- 画像更新走 MQ 异步（复用 `kaleido-message` 可靠投递），避免同步拖慢请求。
- 排序层新增 `PersonalizedRankService`，插在现有推荐事件链路与 RAG 召回之间。
- 冷启动：注册信息 + 标签选择问卷生成初始画像，随行为衰减校正。

### 涉及模块 / 工作量

`kaleido-recommend`（从薄模块变核心）、`kaleido-coin`、`kaleido-tag`、`kaleido-user`（行为流）。约 3-4 周。

## 方向 4：AIGC 虚拟试衣

**一句话**：基于用户身材参数 + 选中单品组合，生成「穿上身」效果图，或上传全身照做 AI 换装。

### 现有基础（代码依据）

| 已有能力 | 位置 |
|---|---|
| Agent 工具表机制（可挂任意新工具） | `t_ai_agent_tool` 表 + `AgentChatClientArmory` 工具回调装配（`:268`） |
| 图片存储与外链 | MinIO（`kaleido-file.yml` 的 fileHost 出图链路） |
| 对话即入口 | AI 会话 + 流式输出已有（git log：ai对话改造为流式生成） |

### 创新点

1. **对话式试衣**：聊天里说「把这件白衬衫换成那双鞋看看」→ Agent 调用换装工具 → 返回效果图，工具化设计天然融入现有对话。
2. **双路线可选**：
   - 快路线：接商用 API（虚拟试衣/换装模型，如 OOTDiffusion 类开源方案私有化或云 API），1-2 周出效果；
   - 深路线：SD + ControlNet/试衣 LoRA 私有化部署（需 GPU，可复用你们平台的 GPU 虚拟化能力）。
3. **效果图反哺检索**：生成图再过方向 1 的图像向量，实现「看到效果→找相似更便宜单品」。

### 风险与对策

生成质量不稳定 → 提供多张候选 + 用户评分回流；GPU 成本 → 快路线用 API 起步，量大再私有化。

### 涉及模块 / 工作量

`kaleido-ai`（新 Tool）、`kaleido-wardrobe`（image 责任链扩展）、新增推理服务。快路线约 2 周。

## 方向 5：衣橱 MCP Server + 多智能体穿搭顾问团

**一句话**：把衣橱能力封装成标准 MCP Server 对外开放（让任何 AI 助手都能「看到」你的衣橱），内部则用多智能体分工做深度咨询。

### 现有基础（代码依据）

| 已有能力 | 位置 |
|---|---|
| MCP **客户端**已动态装配 | `AgentChatClientArmory.java:56,165-176,252`（外部 MCP 工具动态发现接入） |
| 多 Agent 意图路由经验 | `kaleido-interview`（LangChain4j，6 个 Agent 接口做意图识别路由） |
| 现成的领域 API 面 | `kaleido-api` 中 IRpcClothingService / IRpcOutfitService 等 11 组 Dubbo 接口 |

### 创新点

1. **能力外放（Server 端从 0 到 1）**：项目只有 MCP Client 没有 Server——新增 `kaleido-mcp-server` 模块，把 `查询衣橱/创建搭配/查穿搭记录` 封装为标准 MCP 工具。外部生态（Claude、桌面助手、微信 Bot）即可代管用户衣橱，衣橱从「一个 App」升级为「AI 生态的一个能力节点」。
2. **多智能体顾问团**：借鉴 interview 模块已验证的意图路由模式，拆「色彩顾问 / 场合顾问 / 预算顾问 / 品类补充顾问」四个子 Agent + 一个主持 Agent 汇总——对比单 Agent 输出，可做消融实验佐证价值。
3. **标准协议叙事**：MCP 是当前 Agent 生态主流协议，项目从「用协议」到「供协议」的完整闭环，技术前瞻性强。

### 涉及模块 / 工作量

新增 `kaleido-mcp-server`、`kaleido-ai`（顾问团编排）、复用 interview 的路由模式。约 2-3 周。

## 组合建议（按投入节奏）

| 阶段 | 建议 | 理由 |
|---|---|---|
| 第一步（2-3 周） | **方向 2** | 全部长在现有架构上，把硬编码 WeatherTool 转正为真 MCP 工具，叙事完整、风险最低 |
| 第二步（并行） | **方向 1** | 与方向 2 共用 Milvus/ChatClient 基建，解决录入痛点 |
| 第三步 | **方向 3** | 依赖方向 1/2 产生的行为数据，飞轮才有原料 |
| 演示冲刺 | **方向 4**（快路线） | 评委可见性最强，放最后做效果集锦 |
| 长线亮点 | **方向 5** | Server 端从 0 到 1，适合作为论文/答辩的「前瞻性」章节 |

> 五个方向共享同一套基建（Milvus / ChatClient / 工具表 / MQ / MinIO / 金币），不存在推倒重来——这是基于现有 DDD 分层设计的直接收益：每个方向基本只落在 1-2 个模块内。
