# RabbitMQ 面试题集锦（附参考答案）

---

## 🥉 基础题

### Q1. 为什么使用消息队列？MQ 有什么缺点？

**参考答案：**
**优点**：异步（提升响应速度）、解耦（系统间不直接依赖）、削峰（缓冲突发流量保护 DB）。
**缺点**（必答，体现全面性）：
1. **系统可用性降低**：MQ 挂了链路全断 → 需要集群高可用；
2. **复杂度提高**：要处理消息丢失、重复消费、顺序性、堆积；
3. **一致性问题**：A 系统成功了，B/C 系统消费失败怎么办 → 分布式事务/最终一致性方案。

---

### Q2. RabbitMQ 的核心概念有哪些？消息流转过程？

**参考答案：**
Producer → Connection/Channel → **Exchange**（按类型路由：direct/fanout/topic/headers）→ **Queue**（存储）→ Consumer → **ACK**。
Channel 是 TCP 连接内的轻量虚拟通道，避免频繁建 TCP；Vhost 做逻辑隔离。

---

### Q3. 四种 Exchange 类型的区别？

**参考答案：**

| 类型 | 路由规则 | 场景 |
|------|---------|------|
| Direct | RoutingKey 精确匹配 | 点对点精确投递 |
| Fanout | 无视 Key 广播所有绑定队列 | 日志广播、多端通知（最快） |
| Topic | 通配符匹配（`*`一个单词，`#`多个） | 按业务主题订阅，如 `order.#` |
| Headers | 按消息头属性匹配 | 性能差，基本不用 |

---

### Q4. RabbitMQ 怎么保证消息不丢失？

**参考答案（三段式，面试标准答案）：**
1. **生产者 → MQ**：开启 **Confirm 确认机制**（MQ 收到并落盘后异步回调），路由失败有 **Return 回调**；失败重发或落本地表定时补偿。
2. **MQ 自身**：**三重持久化**——Exchange、Queue 设置 durable，消息 deliveryMode=2（持久化到磁盘）；高可靠场景用仲裁队列（Raft 过半写入）。
3. **MQ → 消费者**：关闭自动 ACK，**业务处理成功后手动 ACK**；消费者宕机未 ACK，MQ 自动重投给其他消费者。

---

### Q5. 什么是死信队列？什么情况下消息会成为死信？

**参考答案：**
死信队列（DLX）是接收"无法正常消费的消息"的队列，三种来源：
1. 消费者 `basicReject/basicNack` 且 requeue=false；
2. 消息 TTL 过期；
3. 队列达到最大长度，早期消息被挤出。
用途：异常消息统一收殓、告警、人工补偿；配合 TTL 还能实现**延迟队列**。

## 🥈 进阶题

### Q6. 消息重复消费（幂等性）怎么解决？

**参考答案：**
重复消费不可避免（消费成功但 ACK 丢失、网络重传、MQ 重投），所以**消费者必须幂等**。方案：
1. **数据库唯一约束**：消息带全局唯一 ID（订单号），插入去重表，冲突即已消费；
2. **Redis setnx**：消息 ID 作为 key，setnx 成功才消费（注意设置过期时间防内存膨胀）；
3. **业务状态机**：如"订单状态=已支付则跳过"，天然幂等；
4. **数据库乐观锁/版本号**。

---

### Q7. 如何保证消息顺序性？

**参考答案：**
RabbitMQ 只保证单队列 FIFO。方案：
1. 需要严格顺序的消息进**同一个队列 + 单消费者**（牺牲并发）；
2. 实际生产多为**局部有序**：按业务 ID（如订单号）hash 分发到固定队列，同一订单的创建→支付→完成消息天然有序；
3. 消费者端加版本号/时间戳校验，丢弃乱序的旧消息。

---

### Q8. 消息积压（几百万条没消费）怎么处理？

**参考答案：**
1. **紧急扩容**：临时增加 N 倍消费者实例，提高消费速度；
2. **批量消费**：消费者一次拉取多条批量处理（注意幂等）；
3. **检查消费端是否有 bug**：是不是消费卡死/异常导致 ACK 失败堆积；
4. **降级方案**：极端情况写个临时程序把消息批量转发到更大的队列分流，或直接落库后续补处理；
5. **预防**：监控队列深度告警、设置队列最大长度 + 死信、消费端限流。
6. 如果消息不重要（如日志），可考虑设置 TTL 让过期消息自动清除。

---

### Q9. RabbitMQ 延迟队列怎么实现？

**参考答案：**
方案一（经典）：**TTL + 死信队列**。消息发往一个 TTL=30min 且无消费者的队列，过期后自动路由到死信队列被消费——实现"30 分钟未支付关单"。
缺陷：队头阻塞——队列级 TTL 时，排在后面的消息要等前面的过期。
方案二（推荐）：官方插件 `rabbitmq-delayed-message-exchange`，在交换机层面延迟，消息按各自延迟时间投递，更灵活。
方案三：用 Redis ZSet、时间轮（Netty HashedWheelTimer）、或 RocketMQ 原生延迟级别。

---

### Q10. 消费者的推（push）拉（pull）模式？

**参考答案：**
- **Push（basicConsume，默认）**：MQ 主动推送给消费者，实时性高；配合 **prefetch（QoS）**限制未确认消息数，防止消费者被压垮——比如 prefetch=10，消费者手里最多积压 10 条未 ACK 消息，处理不过来 MQ 就不再推。
- **Pull（basicGet）**：消费者主动拉取，按需消费但实时性差，用得少。

## 🥇 架构题

### Q11. RabbitMQ vs Kafka vs RocketMQ，怎么选型？

**参考答案：**

| 维度 | RabbitMQ | Kafka | RocketMQ |
|------|---------|-------|----------|
| 吞吐量 | 万级 | **百万级** | 十万级 |
| 延迟 | **微秒级（最低）** | 毫秒级 | 毫秒级 |
| 功能丰富度 | 路由灵活、延迟队列插件 | 功能简单、重吞吐 | 延迟级别、事务消息、消息回溯 |
| 典型场景 | 业务异步、复杂路由 | **大数据日志、流处理** | 金融级业务、事务消息 |
| 语言 | Erlang | Scala | Java |

选型：日志采集/大数据管道 → Kafka；业务系统解耦、需要灵活路由和延迟消息 → RabbitMQ/RocketMQ；需要分布式事务消息 → RocketMQ。

---

### Q12. RabbitMQ 集群模式对比？仲裁队列原理？

**参考答案：**
- **普通集群**：元数据（队列/交换机定义）全节点同步，但队列**数据只在创建它的节点**，其他节点路由转发——节点宕机该队列不可用。
- **镜像集群**（已弃用）：队列数据多副本镜像，可靠但同步开销大。
- **仲裁队列（Quorum Queue）**：基于 **Raft 共识协议**——队列有 Leader 和多个 Follower，写消息需**过半节点持久化**才返回成功；Leader 宕机自动选举新 Leader。兼顾可靠与性能，3.8+ 官方推荐用于关键队列。

---

### Q13. 设计一个"下单成功通知"场景：扣库存、加积分、发短信，怎么用 MQ 保证最终一致性？

**参考答案（本地消息表 / 事务消息思路）：**
1. **核心矛盾**：下单（DB 事务）和发消息（网络操作）无法同时保证成功。
2. **方案：本地消息表**——
   - 下单事务中，同时往"消息表"插一条待发送记录（同事务保证）；
   - 后台任务轮询消息表，发送到 MQ，成功后标记已发送；
   - 发失败重试，超过次数告警人工介入。
3. **消费端**：库存/积分/短信服务各自消费，幂等处理；失败则 nack 重试或进死信。
4. **对账兜底**：定时任务比对订单与下游状态，不一致则补偿。
5. 或用 RocketMQ **事务消息**（半消息 + 回查机制）替代本地消息表。

### Q14. RabbitMQ 为什么用 Erlang 开发？对你使用有什么影响？

**参考答案：**
- Erlang 天生为**高并发、分布式、软实时**系统设计（最初用于电信交换机）， actor 模型 + 轻量级进程，与 AMQP 协议的消息模型天然契合；
- Erlang 的"任其崩溃（let it crash）"+ 监督树机制让 RabbitMQ 具备很强的容错自愈能力；
- 对使用者的影响：二次开发和源码阅读门槛高（Erlang 小众）；交换机间数据交换延迟略高；运维排障工具生态不如 Java 系。

### Q15. 一条消息从发送到消费的完整生命周期？（综合串讲题）

**参考答案：**
1. 生产者建立 TCP 连接 → 创建 Channel → 声明 Exchange/Queue/绑定；
2. 发送消息（指定 routing key），开启 Confirm；
3. Exchange 按类型路由到队列，路由失败触发 Return；
4. 消息入队并持久化，MQ 回 Confirm；
5. 消费者 prefetch 拉取/push 接收消息；
6. 业务处理（幂等）→ 手动 ACK；失败 nack/reject；
7. 死信进 DLX 队列由补偿消费者处理；
8. 全链路配合监控：队列深度、消费速率、未确认数、死信数量告警。
