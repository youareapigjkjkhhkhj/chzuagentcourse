## 🥉 基础题

### Q1. MySQL 常见的存储引擎？InnoDB 和 MyISAM 的区别？

**参考答案：**

| 特性 | InnoDB（默认） | MyISAM |
|------|---------------|--------|
| 事务支持 | ✅ 支持 | ❌ 不支持 |
| 行级锁 | ✅ 支持 | ❌ 只有表锁 |
| 外键 | ✅ 支持 | ❌ 不支持 |
| 崩溃恢复 | ✅ 有 Redo Log | ❌ 易损坏 |
| 聚簇索引 | ✅ 数据即索引 | ❌ 索引和数据分离 |
| 全文索引 | ✅ 5.6+ 支持 | ✅ 支持 |
| 使用场景 | 99% 的业务场景 | 只读、历史归档 |

### Q2. 什么是索引？为什么用 B+树不用二叉树/Hash？

**参考答案：**
索引是帮助 MySQL 高效获取数据的数据结构，本质是**排好序的快速查找结构**。

**为什么用 B+树：**
- **vs 二叉树/红黑树**：树太高（千万数据 20+ 层），每层一次磁盘 I/O 太慢；B+树非叶子节点只存键值，一个 16KB 页能存上千个索引项，3 层就能存千万级数据。
- **vs Hash**：Hash 只能等值查询（`=`），不支持范围查询（`>`、`<`、`BETWEEN`）和排序；B+树叶子节点双向链表天然支持范围查询。
- **vs B-Tree**：B+树数据全在叶子节点，查询更稳定（都走根到叶子）；叶子节点双向链表利于范围扫描。

### Q3. 什么是聚簇索引和非聚簇索引？什么是回表？

**参考答案：**
- **聚簇索引**：叶子节点存**完整数据行**，一个表只能有一个（通常是主键）。查询主键时直接拿到数据，最快。
- **非聚簇索引（二级索引）**：叶子节点存**主键值**，查到主键后还要回聚簇索引再查一次拿完整数据，这叫**回表**。
- **覆盖索引**：查询的字段都在二级索引里，不用回表，性能极佳。

```sql
-- 假设有索引 idx_name(name)
SELECT * FROM user WHERE name = '张三';  -- 需要回表
SELECT id, name FROM user WHERE name = '张三';  -- 覆盖索引，不回表
```

### Q4. 什么是事务？ACID 分别靠什么实现？

**参考答案：**
事务是一组要么全成功、要么全失败的 SQL 操作。

| 特性 | 实现机制 |
|------|---------|
| 原子性 | **Undo Log**（回滚日志） |
| 一致性 | 由其他三个特性共同保证 |
| 隔离性 | **锁 + MVCC** |
| 持久性 | **Redo Log**（重做日志） |

### Q5. 事务隔离级别？默认是哪个？解决了什么问题？

**参考答案：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| 读未提交 RU | ❌ | ❌ | ❌ |
| 读已提交 RC | ✅ | ❌ | ❌ |
| **可重复读 RR（默认）** | ✅ | ✅ | ⚠️ 快照读解决 |
| 串行化 | ✅ | ✅ | ✅ |

MySQL 默认 RR，通过 **MVCC + Next-Key Lock** 解决了大部分幻读问题（快照读无幻读，当前读可能遇到）。

## 🥈 进阶题

### Q6. MVCC 是什么？怎么实现的？

**参考答案：**
MVCC（多版本并发控制）通过**数据多版本**实现读写不加锁的并发控制。

**三要素：**
1. **隐藏字段**：`DB_TRX_ID`（最近修改事务 ID）、`DB_ROLL_PTR`（回滚指针）。
2. **Undo Log 版本链**：每次修改生成新版本，旧版本通过回滚指针串联成链。
3. **ReadView**：事务读数据时生成的快照，包含当前活跃事务 ID 列表。

**可见性判断**：从最新版本沿版本链找第一个"由已提交事务修改"的版本。

**RC vs RR**：
- RC：每次 SELECT 都生成新 ReadView → 能看到别人刚提交的数据（不可重复读）。
- RR：事务开始时生成一次 ReadView → 整个事务期间读到的数据一致（可重复读）。

### Q7. 什么是幻读？MySQL 怎么解决的？

**参考答案：**
幻读：同一事务内两次相同条件查询，结果集行数不同（被其他事务 insert/delete）。

**MySQL 的解决：**
1. **快照读**（普通 SELECT）：通过 MVCC 的 ReadView 解决，RR 级别下整个事务看到同一快照。
2. **当前读**（SELECT ... FOR UPDATE）：通过 **Next-Key Lock**（记录锁+间隙锁）锁住范围，防止其他事务插入。

> ⚠️ 严格来说 RR 级别没有完全解决幻读：如果先快照读，再当前读（FOR UPDATE），可能读到新插入的数据。

### Q8. InnoDB 的行锁是怎么实现的？什么情况下锁全表？

**参考答案：**
**行锁锁的是索引项，不是物理记录**。

**锁类型**：
- **Record Lock**：锁单行记录。
- **Gap Lock**：锁间隙（如 id 在 10 和 20 之间），防止插入。
- **Next-Key Lock**：Record + Gap，RR 级别默认，锁住左开右闭区间，防幻读。

**锁全表的场景**：
```sql
-- name 列没有索引
UPDATE user SET age = 18 WHERE name = '张三';  -- 全表扫描，锁全表！
```

**避免锁全表**：WHERE 条件必须走索引。

### Q9. Redo Log、Undo Log、Binlog 的区别？

**参考答案：**

| 日志 | 作用 | 所属层 | 类型 | 写入方式 |
|------|------|--------|------|---------|
| **Redo Log** | 崩溃恢复 | InnoDB | 物理日志 | 顺序写，循环使用 |
| **Undo Log** | 回滚、MVCC | InnoDB | 逻辑日志 | 记录旧值 |
| **Binlog** | 主从复制、数据恢复 | Server 层 | 逻辑日志 | 追加写 |

**两阶段提交（2PC）**保证 Redo 和 Binlog 一致：
1. 写 Redo Log，标记为 prepare；
2. 写 Binlog；
3. 提交 Redo Log 为 commit。

### Q10. 什么是索引失效？常见场景有哪些？

**参考答案：**

**索引失效的常见场景：**
1. **最左前缀法则破坏**：联合索引 `(a,b,c)`，查 `c` 或 `b,c` 不走索引。
2. **索引列上做计算/函数**：`WHERE YEAR(create_time) = 2024` → 失效；应改为 `WHERE create_time BETWEEN '2024-01-01' AND '2024-12-31'`。
3. **隐式类型转换**：`phone` 是 varchar，但 `WHERE phone = 13800138000`（数字）→ 失效。
4. **LIKE 以 % 开头**：`LIKE '%张三'` → 失效；`LIKE '张三%'` 可以用。
5. **范围查询右边的列**：`WHERE a > 1 AND b = 2`，b 用不上索引。
6. **OR 条件**：`WHERE a = 1 OR b = 2`，b 无索引则全失效。
7. **!= 或 NOT IN**：通常不走索引。

## 🥇 架构题

### Q11. 如何优化慢查询 SQL？

**参考答案（系统化回答）：**

1. **定位慢查询**：开启慢查询日志（`slow_query_log`），设置阈值（如 1 秒）。
2. **分析执行计划**：用 `EXPLAIN` 看：
   - `type`：是否为 `ALL`（全表扫描），应优化到 `ref` 或 `range`。
   - `key`：是否用了索引。
   - `rows`：扫描行数是否过多。
   - `Extra`：是否有 `Using filesort`、`Using temporary`（需要优化）。
3. **优化手段**：
   - **加索引**：为 WHERE、JOIN、ORDER BY 字段加索引。
   - **覆盖索引**：避免回表。
   - **避免 SELECT ***：只查需要的字段。
   - **分页优化**：`LIMIT 1000000, 10` 改为 `WHERE id > 1000000 LIMIT 10`（游标法）。
   - **拆分大查询**：一个大 JOIN 拆成多个小查询。
   - **读写分离**：读请求走从库。
   - **分库分表**：数据量太大（单表 > 1000 万）考虑 ShardingSphere。

### Q12. 主从复制的原理？主从延迟怎么解决？

**参考答案：**

**复制原理**：
1. Master 写 Binlog；
2. Slave IO 线程拉取 Binlog 写 Relay Log；
3. Slave SQL 线程重放 Relay Log。

**主从延迟原因**：
- 大事务（批量 update/delete）；
- 从库机器性能差；
- 从库承担大量读请求；
- 网络延迟。

**解决方案**：
1. **强制读主库**：对实时性要求高的读（如下单后立即查询）直接读主库。
2. **半同步复制**：至少一个 Slave 确认后才返回，降低延迟概率。
3. **并行复制**：MySQL 5.7+ 支持基于逻辑时钟的并行重放。
4. **分库分表**：减少单库压力。
5. **业务层容忍**：写入后显示"处理中"，异步轮询结果。

### Q13. 死锁怎么排查和避免？

**参考答案：**

**排查**：
```sql
-- 查看死锁日志
SHOW ENGINE INNODB STATUS;
-- 查看当前锁等待
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```

**避免**：
1. **固定访问顺序**：所有事务按相同顺序访问资源（如都按 id 升序）。
2. **减少事务粒度**：大事务拆小，快进快出。
3. **降低隔离级别**：RR 改 RC，减少间隙锁。
4. **加索引**：避免全表扫描锁全表。
5. **设置超时**：`innodb_lock_wait_timeout`，超时自动回滚。
6. **乐观锁**：用版本号替代行锁（`UPDATE ... WHERE version = ?`）。

### Q14. 什么是分库分表？什么场景需要？

**参考答案：**

**垂直拆分**：
- **垂直分库**：按业务拆分（订单库、用户库、商品库）。
- **垂直分表**：大表按字段拆分，冷热分离（常用字段一张表，大字段一张表）。

**水平拆分**：
- **水平分库**：同一张表数据分散到多个库（user_0, user_1, user_2）。
- **水平分表**：同一张表数据分散到多表（order_2024, order_2025）。

**场景**：
- 单表数据量 > 1000 万，查询慢；
- 单库 QPS > 5000，扛不住；
- 单库磁盘 > 500G，备份恢复慢。

**中间件**：ShardingSphere-JDBC（客户端）、MyCat（代理层）。

### Q15. 一条 SQL 在 MySQL 中的完整执行流程？

**参考答案（综合串讲题）：**

1. **连接器**：建立连接、权限认证。
2. **查询缓存**（8.0 已删除）：命中直接返回。
3. **分析器**：词法分析、语法分析，生成解析树。
4. **优化器**：
   - 选择索引；
   - 决定 JOIN 顺序；
   - 生成执行计划。
5. **执行器**：
   - 调存储引擎接口；
   - 逐行扫描/索引查找；
   - 判断 WHERE 条件，组装结果集。
6. **存储引擎**：
   - 从 Buffer Pool 读数据页，miss 则从磁盘加载；
   - 返回结果。
7. **返回客户端**。

如果是写操作（UPDATE），还会涉及：
- 写 Undo Log（记录旧值）；
- 修改 Buffer Pool 中的数据页（脏页）；
- 写 Redo Log（prepare 状态）；
- 写 Binlog；
- 提交事务，Redo Log 改 commit；
- 后台线程异步刷脏页到磁盘。
