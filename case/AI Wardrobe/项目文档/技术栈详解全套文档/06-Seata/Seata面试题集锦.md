# Seata 面试题集锦（附参考答案）

---

## 🥉 基础题

### Q1. 什么是分布式事务？为什么需要 Seata？

**参考答案：**
分布式事务是指**跨多个服务、多个数据库**的事务操作，需要保证"要么全成功，要么全失败"。

**单机事务 vs 分布式事务**：
- 单机：一个数据库，用本地 ACID 事务即可。
- 分布式：多个独立数据库（订单库、库存库、账户库），本地事务无法保证全局一致性。

**Seata 的作用**：提供分布式事务解决方案，通过 TM/RM/TC 三角色协调，保证最终一致性。

---

### Q2. Seata 的三大角色？各自职责？

**参考答案：**

| 角色 | 全称 | 职责 |
|------|------|------|
| **TM** | Transaction Manager | 事务管理器，发起全局事务（开启/提交/回滚） |
| **RM** | Resource Manager | 资源管理器，管理分支事务（每个微服务一个） |
| **TC** | Transaction Coordinator | 事务协调器（Seata Server），维护全局事务状态，协调所有 RM |

**核心概念**：
- **全局事务**：一次完整的分布式事务，由 XID 唯一标识。
- **分支事务**：每个微服务的本地事务，是全局事务的一部分。

---

### Q3. Seata 有哪几种模式？默认是哪种？

**参考答案：**

| 模式 | 特点 | 侵入性 | 适用场景 |
|------|------|--------|---------|
| **AT**（默认） | 两阶段提交+undo_log自动补偿 | **无** | 90% 场景 |
| TCC | Try-Confirm-Cancel，手动控制 | 大 | 高并发 |
| Saga | 长事务，补偿机制 | 大 | 跨系统长事务 |
| XA | 强一致性，数据库原生支持 | 无 | 金融级强一致 |

## 🥈 进阶题

### Q4. AT 模式的原理？undo_log 是什么？

**参考答案：**

**AT 模式 = 两阶段提交 + 自动补偿**

**第一阶段（执行业务 SQL）**：
1. 查询修改前数据（before image）；
2. 执行业务 SQL；
3. 查询修改后数据（after image）；
4. 写入 undo_log 表（记录 before/after image）；
5. 注册分支事务，提交本地事务。

**第二阶段（提交或回滚）**：
- **全局提交**：异步删除 undo_log。
- **全局回滚**：根据 undo_log 的 before image 恢复数据，删除 undo_log。

**undo_log 表**：存储回滚信息的表，包含全局事务 ID、分支事务 ID、回滚数据（JSON 格式的 before/after image）。

---

### Q5. AT 模式怎么解决脏写问题？

**参考答案：**

**脏写场景**：两个全局事务同时修改同一行数据。

**解决方案：全局锁**
1. 全局事务 A 在第一阶段本地事务提交前，向 TC 申请**全局锁**（基于行记录）。
2. 全局事务 B 也想修改同一行，发现全局锁被 A 持有，等待。
3. A 全局提交后释放锁，B 才能继续。

**全局锁 vs 本地锁**：
- 本地锁：数据库行锁，只在本地事务期间持有。
- 全局锁：Seata 层面的锁，贯穿整个全局事务（第一阶段到第二阶段）。

---

### Q6. AT 模式的隔离级别？怎么解决脏读？

**参考答案：**

**默认隔离级别：读未提交（Read Uncommitted）**
- 全局事务 A 第一阶段完成（本地已提交），但全局还没提交。
- 全局事务 B 可以读到 A 的中间状态（脏读）。
- **原因**：为了提高性能，大概率会成功，不需要强隔离。

**需要强一致时**：
```sql
-- 使用 SELECT FOR UPDATE
SELECT * FROM order WHERE id = 1 FOR UPDATE;
```
Seata 会检查全局锁，如果有锁则等待，避免脏读。

### Q7. TCC 模式的原理？三大问题？

**参考答案：**

**TCC = Try（预留资源）- Confirm（确认提交）- Cancel（取消回滚）**

**示例：转账场景**
```java
// Try：冻结资金
boolean tryFreeze(userId, amount) {
    // 余额 -100，冻结 +100
}

// Confirm：确认扣款
boolean confirm(context) {
    // 冻结 -100，真正扣款
}

// Cancel：解冻资金
boolean cancel(context) {
    // 冻结 -100，余额 +100
}
```

**三大问题**：
1. **空回滚**：Try 没执行，Cancel 执行了（网络超时导致）。
   - 解决：Cancel 方法中判断 Try 是否执行过（记录状态）。
2. **幂等性**：Confirm/Cancel 可能被重复调用。
   - 解决：记录执行状态，重复调用直接返回成功。
3. **悬挂**：Cancel 执行了，Try 才执行（Cancel 先到，Try 后到）。
   - 解决：Try 方法中判断 Cancel 是否已执行，如果是则拒绝执行。

### Q8. Saga 模式的特点？适用场景？

**参考答案：**

**核心思想**：把一个长事务拆成多个本地短事务，每个短事务都有对应的补偿操作。

**示例：跨系统订单流程**
```
创建订单 → 扣库存 → 扣余额 → 发货
   ↓失败      ↓失败     ↓失败    ↓失败
取消订单 ← 恢复库存 ← 退余额 ← 无需补偿
```

**特点**：
- **优点**：不锁资源，适合长事务（跨天、跨系统）。
- **缺点**：不保证隔离性（中间状态可能被其他事务看到），补偿逻辑复杂。

**适用场景**：
- 跨多个系统的长流程（如电商订单：订单→支付→物流→发票）。
- 对实时性要求不高，允许中间状态。

### Q9. Seata 的高可用怎么实现？

**参考答案：**

**TC（Seata Server）集群**：
1. **无状态设计**：全局事务信息存储在共享存储（MySQL/Redis），TC 节点可水平扩展。
2. **Raft 选主**：TC 集群通过 Raft 协议选举 Leader，Leader 挂了自动切换。
3. **故障恢复**：TC 宕机重启后，从共享存储恢复未完成的全局事务，继续协调。

**配置示例**：
```properties
# 存储模式：db/redis/file
seata.store.mode=db

# 数据库配置
seata.store.db.url=jdbc:mysql://localhost:3306/seata
seata.store.db.user=root
seata.store.db.password=root
```

## 🥇 架构题

### Q10. AT 模式的性能瓶颈在哪？如何优化？

**参考答案：**

**性能瓶颈**：
1. **全局锁竞争**：高并发下，同一行数据的全局锁竞争激烈。
2. **undo_log 写入**：每次修改都要写 undo_log，增加 IO 开销。
3. **两阶段提交**：第二阶段需要 TC 协调，增加网络开销。

**优化方案**：
1. **减少锁粒度**：业务上避免热点数据（如库存拆分：一个商品拆成 100 个子库存）。
2. **异步删除 undo_log**：全局提交后，undo_log 异步批量删除。
3. **使用 TCC 模式**：对性能敏感的场景，用 TCC 替代 AT。
4. **读写分离**：读操作不走全局事务，只写操作走。
5. **批量操作**：合并多个小事务为一个大事务，减少全局锁竞争。

### Q11. Seata 和消息队列（MQ）实现分布式事务的区别？

**参考答案：**

| 维度 | Seata（AT/TCC） | MQ（事务消息/本地消息表） |
|------|----------------|--------------------------|
| 一致性 | 最终一致（较快） | 最终一致（较慢） |
| 实时性 | **高**（同步调用） | 低（异步消息） |
| 性能 | 中（有锁竞争） | **高**（无锁） |
| 侵入性 | AT 无侵入，TCC 侵入大 | 侵入中（需要本地消息表） |
| 适用场景 | 强实时性（如下单扣库存） | 弱实时性（如发通知、加积分） |

**选型建议**：
- 实时性要求高（用户等待）→ Seata AT/TCC。
- 实时性要求低（异步处理）→ MQ 事务消息/本地消息表。

### Q12. Seata 的全局锁是怎么实现的？会不会死锁？

**参考答案：**

**全局锁实现**：
1. TC 维护一个锁表（`lock_table`），记录哪个全局事务锁住了哪行数据。
2. RM 在第一阶段本地事务提交前，向 TC 申请全局锁。
3. TC 检查锁表，如果没被锁则授予锁，否则拒绝。

**会不会死锁？**
- **理论上会**：全局事务 A 锁住行 1，请求行 2；全局事务 B 锁住行 2，请求行 1 → 死锁。
- **Seata 的处理**：TC 有超时机制，申请锁超时（默认 60s）后自动回滚，释放已持有的锁。

**避免死锁**：
- 固定访问顺序（所有事务按相同顺序访问资源）；
- 减少事务粒度，快进快出；
- 设置合理的超时时间。

### Q13. Seata 回滚失败怎么办？（数据被其他事务修改了）

**参考答案：**

**场景**：全局事务 A 要回滚，发现数据已经被全局事务 B 修改了（B 在 A 之后修改了同一行）。

**Seata 的处理**：
1. 回滚时对比当前数据和 undo_log 的 after image。
2. 如果不一致，说明数据被其他事务改了，回滚失败。
3. 记录异常日志，需要**人工介入处理**（手动修复数据或强制回滚）。

**预防措施**：
1. **避免跨全局事务修改同一行**：业务上尽量避免。
2. **使用全局锁**：`SELECT FOR UPDATE` 保证强一致。
3. **监控告警**：回滚失败时及时告警，人工处理。

### Q14. 什么场景下用 AT，什么场景下用 TCC？

**参考答案：**

**AT 模式适用场景**：
- 业务逻辑简单，不想写补偿代码；
- 对性能要求不是极致（QPS < 1000）；
- 90% 的常规业务场景。

**TCC 模式适用场景**：
- 高并发场景（QPS > 1000）；
- 对性能敏感（如秒杀扣库存）；
- 需要精细控制资源（如冻结/解冻资金）；
- 业务方能接受写 Try/Confirm/Cancel 三个方法。

**示例**：
- 普通订单创建 → AT 模式；
- 秒杀扣库存 → TCC 模式（Try 冻结库存，Confirm 扣减，Cancel 解冻）。

### Q15. 设计一个分布式事务方案，你会考虑哪些点？

**参考答案（综合架构题）：**

1. **一致性要求**：
   - 强一致（金融级）→ XA 模式；
   - 最终一致（大多数场景）→ AT/TCC/MQ。

2. **性能要求**：
   - 高并发（QPS > 1000）→ TCC 或 MQ；
   - 一般并发 → AT 模式。

3. **实时性要求**：
   - 用户等待结果（同步）→ Seata AT/TCC；
   - 异步处理 → MQ 事务消息。

4. **业务侵入性**：
   - 不想改代码 → AT 模式；
   - 可以接受写补偿逻辑 → TCC/Saga。

5. **长事务 vs 短事务**：
   - 短事务（秒级）→ AT/TCC；
   - 长事务（跨天）→ Saga。

6. **高可用**：
   - TC 集群部署；
   - 共享存储（MySQL/Redis）；
   - Raft 选主。

7. **监控告警**：
   - 全局事务成功率；
   - 回滚失败告警；
   - 锁竞争监控。

8. **兜底方案**：
   - 定时对账任务；
   - 人工补偿接口。
