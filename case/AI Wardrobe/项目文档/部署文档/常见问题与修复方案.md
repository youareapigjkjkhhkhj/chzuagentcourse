# Kaleido 常见问题与修复方案（排错手册）

> 适用环境：单机 Docker Compose 部署，服务器 `192.168.52.133`，部署根目录 `/opt/kaleido/`。
> 排错总原则：**先看日志 → 定位容器 → 查挂载/配置 → 修复 → 重建容器**，不要盲目重启。

---

## 1. 通用排错流程

```bash
# 1. 看哪些容器不正常（重点看 Restarting / Exited）
docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Image}}"

# 2. 看异常容器的最近日志（--tail 控制 行数）
docker logs <容器名> --tail 200

# 3. 看容器的退出码（137=OOM被杀 / 134=abort(常见于OOM) / 100=权限或数据目录问题 / 1=应用错误）
docker inspect <容器名> --format '{{.State.ExitCode}} {{.State.Error}}'

# 4. 确认容器是否被系统 OOM 杀掉（搜 "Killed process"）
dmesg | grep -i -E "killed process|out of memory" | tail -5

# 5. 确认容器的实际挂载（权限问题的第一步）
docker inspect <容器名> --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
```

退出码速查：

| 退出码 | 含义 | 典型原因 | 处理方向 |
|---|---|---|---|
| 137 | SIGKILL | 内核 OOM（内存不足） | 加内存 / 限制 JVM 堆 / 加 swap |
| 134 | SIGABRT | 进程自检失败自杀（Milvus OOM 常见） | 同上 |
| 100 | 应用启动失败 | MongoDB 数据目录权限不足 | 修目录属主（见 §3） |
| 1 | 一般错误 | 配置错误 / panic | 看日志最后 50 行 |

## 2. 内存不足（8GB 机器必看）

**现象**：Milvus `Exited (134)` 并打印 Go 运行时堆栈（goroutine dump）；Java 服务随机被杀；`dmesg` 出现 `Out of memory: Killed process`。

**原因**：全套 29 个容器内存预算约 **13.6GB**（11 个 Java 服务 + Milvus + ELK + SkyWalking 等），8GB + 4GB swap 无法承载。

**内存预算参考**：

| 组件 | 建议内存 |
|---|---|
| Milvus standalone | ≥ 4GB |
| Elasticsearch | ≥ 2GB |
| 11 个 Java 服务（每个 512MB 堆） | ≥ 7GB |
| MySQL / Redis / Nacos / 其他中间件 | ≥ 2GB |

**方案 A（推荐）：升级到 16GB 内存。**

**方案 B：8GB 机器精简部署**——限制 JVM 堆并按需启动：

```bash
# 服务 compose 中给每个 Java 服务注入（示例 384MB 堆）
environment:
  - JAVA_OPTS=-Xms128m -Xmx384m
```

```bash
# 暂不用的组件先停掉（如 AI/向量功能不用时）
docker stop milvus-standalone milvus-etcd milvus-minio elasticsearch skywalking-oap skywalking-ui
```

注意：关闭 Milvus 后 `kaleido-ai` 的向量检索功能不可用，登录等基础链路不受影响。

## 3. 容器 Permission denied 反复重启（最高频问题）

**现象**：容器 `Restarting`，日志出现 `Permission denied` / `exitCode 100`。

**原因**：容器以非 root 用户运行，而宿主机数据目录被 Docker 以 root 创建，容器内进程无写权限。

**各镜像运行用户（实测）**：

| 容器 | uid:gid | 数据目录（宿主机） |
|---|---|---|
| elasticsearch | 1000:1000 | `/opt/kaleido/infra/elasticsearch/data` |
| grafana | 472:472 | `/opt/kaleido/infra/grafana/data` |
| mongodb | 1000:1000 | `/opt/kaleido/infra/mongodb/data` |
| prometheus | 65534:65534 (nobody) | `/opt/kaleido/infra/prometheus/data` |

**一键修复**：

```bash
cd /opt/kaleido/infra
mkdir -p elasticsearch/data mongodb/data mongodb/log grafana/data prometheus/data
chown -R 1000:1000 elasticsearch
chown -R 472:472 grafana
chown -R 1000:1000 mongodb
chown -R 65534:65534 prometheus
docker compose -f docker-compose.yml up -d --force-recreate elasticsearch grafana mongodb prometheus
```

**注意事项**：

1. MongoDB 不同镜像版本 uid 有差异（社区镜像曾出现 10001），不确定时让容器自报：
   ```bash
   docker run --rm --entrypoint sh mongodb/mongodb-community-server:latest -c "id mongodb"
   ```
2. `chown` 后容器仍报错时，检查**文件**本身的属主（不仅是目录），例如 Prometheus 的 `queries.active`：
   ```bash
   ls -ln /opt/kaleido/infra/prometheus/data
   ```
3. 日志是累计的：修好后 `docker logs` 里仍能看到历史报错行，以 `docker ps` 的状态和最新时间戳为准。

**验证 MongoDB 是否真正修好**（写入测试）：

```bash
docker exec mongodb mongosh -u root -p kaleido123 --eval 'db.test.insertOne({"ok":1}); db.test.findOne()'
```

## 4. Java 服务连不上 MySQL（127.0.0.1 陷阱）

**现象**：服务日志刷 `CommunicationsException: Communications link failure`，URL 形如
`jdbc:mysql://127.0.0.1:3306/kaleido_1`。

**原因**：数据源配置在 `kaleido-common/kaleido-ds/src/main/resources/sharding.yaml`（`kaleido_0`/`kaleido_1` 两个分片）。开发时 `127.0.0.1` 指向本机没问题；容器化后 `127.0.0.1` 指向**容器自己**，必须改为容器名 `mysql`。

**关键点**：该文件打包后嵌在 fat jar 内部（`BOOT-INF/lib/kaleido-ds-1.0.0.jar!sharding.yaml`），改服务器上的外部文件**无效**，必须重新打包或修补 jar。

**验证 jar 是否正确**（本地，任意一台装了 Python 的机器）：

```python
import zipfile, io
z = zipfile.ZipFile('kaleido-notice-1.0.0.jar')
inner = zipfile.ZipFile(io.BytesIO(z.read('BOOT-INF/lib/kaleido-ds-1.0.0.jar')))
print(inner.read('sharding.yaml').decode())
# 应输出 jdbc:mysql://mysql:3306/...；若出现 127.0.0.1 则该 jar 不能用于容器部署

# 1. 把本地 source code/deploy-output/backend/jars/ 整个目录重新上传覆盖
#    scp -r jars/* root@192.168.52.133:/opt/kaleido/backend/jars/

# 2. 重建 11 个服务镜像（Dockerfile 未变，只是 jar 变了）
cd /opt/kaleido/backend
for svc in gateway auth admin notice user wardrobe ai tag coin message recommend; do
  docker build -t kaleido/$svc:1.0.0 .
done

# 3. 重建服务容器
docker-compose -f docker-compose.services.yml up -d --force-recreate

# 4. 等 1~2 分钟后重发验证码（限流 60 秒 1 次）
curl -X POST http://192.168.52.133:9010/kaleido-auth/public/sms/verify-code \
  -H "Content-Type: application/json" \
  -d '{"mobile":"13066668888","targetType":"ADMIN"}'
# 成功时响应 data 里就有验证码，Redis 也会写入：
docker exec redis redis-cli -a kaleido123 --no-auth-warning \
  get 'kaleido:verify_code:sms:admin:13066668888'

```

**预防**：始终使用 `build-backend.sh` / `build-backend.bat` 打包，脚本会自动补丁数据源并在构建后自检（仍是 127.0.0.1 会直接报错退出）。**不要**直接 `mvn package` 后拿去部署。

## 5. 登录 / 短信验证码问题

### 5.1 登录机制

- 登录 = 手机号 + 短信验证码，**无密码**；短信发送是空实现（TODO，待接阿里云短信），验证码直接写入 Redis。
- 管理员手机号：`13066668888`、`13266668888`。
- Redis key 格式：`kaleido:verify_code:sms:admin:<手机号>`，有效期 5 分钟。

### 5.2 获取验证码并登录

```bash
# 1. 触发发送（网关 9010；限流：同一手机号 60 秒 1 次，失败别连点）
curl -X POST http://192.168.52.133:9010/kaleido-auth/public/sms/verify-code \
  -H "Content-Type: application/json" \
  -d '{"mobile":"13066668888","targetType":"ADMIN"}'

# 2. 成功时响应 data 字段就是验证码；也可从 Redis 取
docker exec redis redis-cli -a kaleido123 --no-auth-warning \
  get 'kaleido:verify_code:sms:admin:13066668888'
```

### 5.3 返回 `NOTICE_SERVICE_UNAVAILABLE` 怎么排

该错误是 auth 的统一包装，真实原因被屏蔽。调用链：

```
网关 → kaleido-auth → [Dubbo] → kaleido-notice → [Dubbo] → kaleido-system(取模板字典) → 查库 → 写 Redis
```

auth 收到 `success=false` 说明调用**已到达** notice，是 notice 内部抛了异常（被 `DubboExceptionFilter` 转成错误 Result）。按顺序查：

```bash
# 1. notice 日志里的真实错误（过滤业务/系统异常）
docker logs kaleido-notice --tail 300 2>&1 | grep -B2 -A8 -E '业务异常|系统异常|RPC异常|ERROR'

# 2. notice 连不上 MySQL？（见 §4，127.0.0.1 陷阱是最常见原因）
docker logs kaleido-notice --tail 100 2>&1 | grep 'jdbc:mysql'

# 3. kaleido-system 是否存活（notice 要 Dubbo 调它取验证码模板字典）
docker ps -a | grep system
```

| notice 日志表现 | 原因 | 处理 |
|---|---|---|
| `jdbc:mysql://127.0.0.1...` link failure | §4 数据源陷阱 | 重新打包（用打包脚本）→ 重建镜像 |
| `远程服务调用失败` (RPC异常) | kaleido-system 未启动/未注册 Nacos | 启动/重启 kaleido-system，等 1 分钟重试 |
| `VERIFICATION_CODE_TEMPLATE_EMPTY` | 字典或模板种子数据缺失 | 执行 §5.4 的 SQL 补数据 |

### 5.4 验证码模板种子数据检查

```sql
-- 字典（应返回 VERIFY_CODE_ADMIN）
SELECT dict_value FROM kaleido_0.t_dict
WHERE type_code='NOTICE_TEMPLATE' AND dict_code='VERIFY_CODE_TEMPLATE_ADMIN';

-- 模板（应有 template_code = VERIFY_CODE_ADMIN 的记录）
SELECT template_code FROM kaleido_0.t_notice_template;
```

缺失时补执行初始化脚本 `dev-ops/mysql/sql/kaleido.sql` 中对应 INSERT（t_dict 的 NOTICE_TEMPLATE 两条、t_notice_template 的 VERIFY_CODE_USER / VERIFY_CODE_ADMIN 两条）。

### 5.5 Redis 里没有 verify_code key

正常情况：没触发过发送就是空的。触发后仍为空，按 §5.3 排查——只有短信"发送成功"（当前恒成功）且写库成功后才会写 Redis，任何前置异常都会导致 key 不存在。

### 5.6 前端登录报 `POST /mock/user/login 405`

**根因**：管理端前端基于 vue-element-plus-admin 模板，登录页原为模板演示登录（硬编码调 `/mock/user/login`），从未接过后端；mock 关闭时 `/mock` 前缀也不会从实际请求中剥除，nginx 无此路由 → 405。

**现状**：前端登录页已改造为真实链路（手机号 + 短信验证码）：

| 功能 | 真实接口 | 说明 |
|---|---|---|
| 发送验证码 | `POST /kaleido-auth/public/sms/verify-code` | 60 秒限流；当前后端空实现，验证码直接在响应 `data.code` 返回并回显在页面提示中 |
| 登录 | `POST /kaleido-auth/public/admin/login` | 入参 `{mobile, verifyCode}`，返回 `{token, userInfo}` |
| 后续请求认证头 | `kaleido-admin-token: <token>` | sa-token 配置（`StpUtilConfig.java:11`） |
| 菜单路由 | 前端静态路由 | `app.ts` 的 `dynamicRouter` 已改为 `false`，不再依赖 mock 的 `/mock/role/list` |

改造涉及文件：`src/api/login/{index.ts,types.ts}`、`src/views/Login/components/LoginForm.vue`、
`src/axios/config.ts`（响应码适配后端 `Result{code:'SUCCESS', success}`）、`src/store/modules/app.ts`。

**注意**：登录后的 Dashboard/授权管理等页面仍是模板演示页，其数据接口仍为 mock（页面内会报接口错误），不影响登录链路与静态路由页面的展示。

## 6. 镜像相关问题

### 6.1 拉取超时（如 Sentinel）

`bladefed/sentinel-dashboard:1.8.6` 等小众镜像容易超时。重试即可；多次失败换网络环境或配置镜像加速器。

### 6.2 `docker save` 报 `reference does not exist`

镜像根本没拉下来（pull 失败后 save 必然失败）。先 `docker images | grep <镜像名>` 确认存在，不存在先 `docker pull`。

### 6.3 离线导入

```bash
docker load -i <镜像包.tar.gz>
docker images   # 核对 21 个镜像齐全（见 DEPLOY.md 离线镜像清单）
```

## 7. 网络与注册中心

### 7.1 服务间 Dubbo 调用失败 / 服务未注册

```bash
# 确认 Nacos 服务列表有对应服务（浏览器或 API）
curl -s "http://192.168.52.133:8848/nacos/v1/ns/service/list?pageNo=1&pageSize=20" | head
```

- 服务列表为空 → 看对应服务启动日志是否连上 Nacos（地址应为 `nacos:8848`，不是 127.0.0.1）。
- 服务时有时无 → 容器被 OOM 重启中，见 §2。

### 7.2 Seata 连接失败

`docker-compose.yml` 中 seata 的 `SEATA_IP` 预设为 `192.168.52.133`，服务器 IP 不同必须修改，否则客户端无法建立连接。

### 7.3 容器网络确认

所有基础设施与服务容器必须在同一网络 `kaleido-env-network`：

```bash
docker network inspect kaleido-env-network --format '{{range .Containers}}{{.Name}} {{end}}'
```

## 8. 前端/网关访问问题

| 现象 | 检查 | 处理 |
|---|---|---|
| 页面 404 / 白屏 | `docker ps | grep frontend` | 重建 frontend 容器；确认 nginx.conf 打包进镜像 |
| 接口 502/504 | 网关容器状态、目标服务是否 Up | `docker logs kaleido-gateway --tail 100` |
| CORS 报错 | Nacos 中 `kaleido-gateway-dev.yml` 的 allowedOrigins | 改为前端实际地址 |
| 接口 404（网关后） | 路由前缀，如 `/kaleido-auth/...` | 核对 Nacos 网关路由配置 |
