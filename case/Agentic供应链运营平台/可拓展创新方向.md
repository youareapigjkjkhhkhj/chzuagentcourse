# 可拓展创新方向 — Agentic 供应链运营平台

> 本文基于本仓库真实源码（`backend/src`、`frontend/src`、`scripts`）撰写，所有方向均是对现有模块"跳一步但够得着"的改造，可直接落到代码。

## 一、项目现状与能力清单

本项目是多智能体供应链运营平台：FastAPI 后端用 LangGraph 将 5 个智能体编排为线性 DAG（`orchestrator.py`：库存监控→需求预测→采购规划→供应商谈判→物流规划），各智能体以 OpenAI 兼容接口做 `json_mode` 推理、失败自动降级规则逻辑；WebSocket 按 `agent_started/agent_completed` 推送执行过程。前端 React 18 + Vite，含 Dashboard（控制塔）、WorkflowVisualizer、VendorNegotiation、ScenarioLab、GovernanceCenter 等页面。数据层为"PostgreSQL schema.sql + erp_simulator 内存兜底 + erp_gateway 双层降级"，不配库也能用内置 5 SKU 演示；MLflow/ClickHouse 追踪可开关；另有 deepagents CLI 控制室与评测脚本。

**已实现**：5 阶段智能体工作流与实时可视化、单 SKU 全链路分析、单次会话内 3~5 回合 LLM 谈判、控制塔/场景/治理三面板、KPI 汇总、LLM 降级、运行追踪。

**真实短板**：控制塔"优先建议"、场景影响百分比、审批队列与护栏规则是写死的展示数据，不随库存变化；`purchase_orders` 表建了但 Web 链路从不写单；`/api/negotiations` 与 `/workflow/state/{session_id}` 是空壳；谈判用户无法介入；预测无人复核准确率；会话状态只存内存、刷新即失联；只能演示内置模拟数据。

## 三、功能增强组：让系统真正"办成事"

### 方向1：自带数据接入——用你自己的进销存跑通平台（易，2 周）

**背景与痛点**：`erp_simulator.py` 全查询带内存兜底，演示只有内置 5 SKU、3 仓库、3 供应商；想换一套真实数据必须改代码，评委或客户无法自行尝试。

**创新点**：加"数据源适配层"：上传标准 CSV（products/inventory/sales_history/vendors 四表，模板对齐 `schema.sql` 字段）→ 解析写入本地 SQLite（stdlib sqlite3，零新依赖）→ `erp_gateway` 查询优先命中导入数据、未命中再走模拟。现有 5 个智能体与控制塔自动基于新数据工作，不动任何 agent。

**方案设计**：新 `db/import_store.py`（sqlite3+csv；如需 xlsx 加免费 openpyxl），支持中文表头→英文字段映射，校验必填字段、数值类型、SKU 引用完整性并返回错误行。改 `erp_gateway.py` 各查询先查数据源标记表 import_meta。接口：`GET /api/import/template`、`POST /api/import/csv`、`GET /api/import/status`。前端加"数据接入"页（下载模板/上传/预览/错误提示）。

**落地步骤**：W1 import_store+模板/上传/校验接口并用 curl 验证落库；W2 erp_gateway 走数据源路由，用自造 200 行销售数据跑通 `/api/analyze/{sku}` 全链路，补"数据概览"页。

**实用价值**：使用者为有自己商品与出入库流水、想试 AI 采购建议的中小商家及教学沙盘——"输自己的 SKU 就能算"比内置数据说服力强。

**风险与备选方案**：脏数据致导入失败——行级错误报告+默认值填充；备选：不做上传，CSV 放入 `backend/data_import/` 启动自动加载，工作量减半。

### 方向2：人机"续谈"式谈判——用户能真正插话砍价（易，2 周）

**背景与痛点**：`vendor_negotiation.py` 一次调用内由模型自导自演 3~5 回合，前端 NegotiationChat 只能回放；用户设定 initial_message 后便无法介入。

**创新点**：把谈判改造成有状态会话：用户每发一句话术，服务端以完整谈判史（含上轮报价、累计让步）为上下文，让智能体只生成"供应商下一轮回复"，并硬约束报价不偏离锚定基准价 ±5%；可随时换策略（压交期/压账期）。

**方案设计**：`vendor_negotiation.py` 新增 `run_turn(state, user_message)`，Prompt 注入上轮报价/让步史/`market_lowest_price` 锚点与价格约束；AgentState 增加 `negotiation_session`（vendor_id、sku、budget_line、transcript）。新 `services/negotiation_store.py`（内存 dict + JSONL 落盘 `logs/negotiations/`），把空壳 `/api/negotiations` 改为返回真实历史。接口：`POST /api/negotiation/session`、`.../session/{id}/reply`、`.../accept`（接受后回填 final_recommendation）。前端聊天框可发送、显示让步曲线与"已达预算线"提示。

**落地步骤**：W1 会话创建/续谈/接受接口+单轮生成（含无 Key 模板降级）；W2 前端输入交互+历史列表页。

**实用价值**：采购谈判是供应链岗位基本功，本系统可作"AI 扮供应商"的谈判训练器（教学/企业培训）；演示中"能跟智能体来回砍价"交互冲击力最强，同一话术换说法让步结果不同，天然有看点。

**风险与备选方案**：多轮后报价漂移——硬约束+让步曲线可视化暴露漂移；无 Key 降级规则回复（沿用现有 JSONDecodeError 分支模式）；备选：前端回传整段 transcript 续谈，不做服务端会话，更简单但不可跨设备。

### 方向3：采购单执行闭环——从"给建议"到"能下单、能收货"（中，2~3 周）

**背景与痛点**：工作流止于 `final_recommendation`；`purchase_orders` 表与 `erp_simulator.create_purchase_order()` 已存在但 Web 链路从不调用，推荐永远只是屏幕数字；KPI"待处理采购单"是 mock 常量。

**创新点**：每次全流程分析自动落一张待确认 PO，提供"确认→审批→发货→收货"状态机；收货时把数量回写 `inventory` 并记库存变动——下次 inventory_monitor 能"看到"补货生效，形成可循环的数据闭环；控制塔待办改为查真实 PO。

**方案设计**：新 `services/po_store.py`（本地 SQLite，沿用 purchase_orders 字段+warehouse_id/confirmed_at/received_at/negotiation_id），不配 PostgreSQL 也可跑。`orchestrator.run()` 末尾调 `po_store.create_from_recommendation(state)`；接口 `GET /api/orders?status=`、`POST /api/orders/{id}/confirm`、`.../receive`（回写目标仓库 inventory）；`get_dashboard_kpis()` 的 pending 值改真实查询（失败仍走原兜底）。前端新增"采购单"页（列表+状态流转+收货弹窗）。

**落地步骤**：W1 本地 PO 仓储+draft 自动生成+列表/详情接口；W2 状态流转与收货回写+KPI 真实化+页面；W3（可选）确认时带审批人与备注。

**实用价值**：采购主管要的是可跟踪的订单流而非建议报告；系统从分析工具变"能干活的小采购执行系统"，进销存补沙盘完整，也是方向 10 的数据来源。

**风险与备选方案**：状态非法迁移——枚举+白名单迁移函数+400 提示；备选：MVP 先只做 PO 生命周期、不做库存回写。

### 方向4：批量巡检与自动跑批——夜间智能体替你盯着（中，2 周）

**背景与痛点**：分析是"点一个 SKU 跑一次"，5 个 SKU 点 5 次；无定时机制，"实时风险预警"实际只在手动触发时发生。

**创新点**：加 `POST /api/analyze/batch`（全量或指定列表，`asyncio.gather`+信号量限并发 2），并叠加轻量定时巡检：每夜只跑"库存监控+需求预测"两节点（省 token），输出风险快照并与昨夜对比生成 delta，critical 级推送 WS 并写告警表，控制塔风险数据自此每日自动更新。

**方案设计**：routes 加 batch 路由；新 `services/patrol_service.py`：巡检编排、快照存 `patrol_snapshots` 表（日期、按 SKU 风险与库存）、delta 计算、`alert_events` 表告警去重（同 SKU 连续两夜同等级不重推）。定时用 asyncio 后台任务每小时检查到点即可，避免新增 APScheduler；另供 `scripts/patrol_daily.py` 由系统计划任务调用。前端 Dashboard 显示"最近巡检时间"，WorkflowVisualizer 加"一键全量巡检"按钮。

**落地步骤**：W1 batch 接口+并发控制+"巡检全部"按钮跑通 5 SKU；W2 定时任务+快照对比+告警去重列表。

**实用价值**：运营经理早晨打开即见昨夜巡检结果与新增风险，而非逐个手查；"7×24 自动值守"从宣传变为可验证事实，是答辩常问点。

**风险与备选方案**：费用与耗时——巡检只跑两节点+当日结果缓存；备选：先只做 `scripts/patrol_daily.py` 手动/计划任务触发，常驻任务留待稳定。

## 四、智能升级组：让决策"可度量、可推演、可比选"

### 方向5：预测要"考勤"——需求预测回测与自我修正（中，3 周）

**背景与痛点**：`demand_forecast.py` 无记忆独立调用，从无机制检验"上期预测准不准"；被问准确率只能语塞。

**创新点**：建立"预测-回填-评估-反馈"回路：预测落盘（sku、日期、预测值、置信区间），数天后用 sales_history 实际销量回填 actual 并计算 MAPE/高估低估方向；再次预测时把该 SKU 近期偏差注入 Prompt（如"过去 4 期平均高估 18%，请校准"）；控制塔新增预测准确率卡片与按 SKU 明细。

**方案设计**：新增 `forecast_runs` 表（本地 SQLite 或 PG：sku/run_date/horizon/forecasted/lower/upper/actual/mape）；`services/forecast_eval.py` 负责回填与指标计算；demand_forecast Prompt 增 `recent_accuracy` 块（数据来自新 `erp_gateway.query_forecast_history(sku)`，缺失则跳过保持兼容）；KPI 增 `forecast_accuracy`。不等真实天数：写 `scripts/backtest_forecast.py` 用 90 天历史切片"假装逐周预测"离线评测，产出开关自我修正的 A/B 两组 MAPE。

**落地步骤**：W1 预测落盘+回填+离线回放出基线 MAPE；W2 准确率卡片+SKU 明细；W3 Prompt 反馈通道+A/B 对比报告。

**实用价值**：运营/计划员需要知道"预测能不能信、误差多大、是否在改进"；这是少有的有量化指标支撑的智能增强，答辩含金量高。

**风险与备选方案**：样本期短指标波动大——离线回放放大样本、展示滚动 MAPE；备选：不做 LLM 自修正，先做统计兜底（指数平滑）+可视化对比。

### 方向6：场景实验室"真压测"——参数化冲击注入并重跑智能体（高，3~4 周）

**背景与痛点**：`get_scenario_lab()` 返回 3 个写死场景（"港口关闭库存影响 -18%"等固定数字），不随库存变化、不可调参，"14 天前向模拟"名不副实。

**创新点**：场景改为可运行模拟引擎：定义冲击算子（交期 ×k、需求 ×(1+s)+噪声、某仓库停用 capacity=0），基于**当前控制塔快照**构造扰动世界，在内存覆写 ERP 查询结果后重跑库存监控与采购规划智能体，输出**计算得出**的受影响 SKU 清单、断供时点（库存/日销推算可用天数）、建议补货量与预计损失——影响数字第一次来自代码。

**方案设计**：新 `services/scenario_engine.py`：`SimulatedWorld` 持扰动参数，`erp_gateway` 的 `query_inventory_levels`/`query_erp_sales_history`/`query_lead_times` 增加 contextvars 覆写机制；输出含 affected_skus[]（各含 days_of_supply、风险等级、建议动作）与基线 KPI delta。接口 `POST /api/platform/scenarios/run {shock_type, severity}`（静态列表保留为预设）。前端 ScenarioLab 改为选冲击/调强度/点运行/看结果表格与对比曲线（Recharts 已有）。

**落地步骤**：W1 冲击算子+查询覆写，用"交期翻倍"对 SKU-005 跑出符合直觉的结果；W2 覆盖 3 预设场景+结构化输出；W3 前端交互可视化。

**实用价值**：风险分析师每天要答"某港停摆两周我哪些 SKU 断供、提前备多少"；可调参实时压测把系统从监控台提升为决策推演台，差异化最强的演示点。

**风险与备选方案**：口径受质疑——输出中明示假设（需求不变、交期线性放大）；耗时——重跑限库存+预测两节点；备选：先做"固定 3 场景×自动重跑"批量报告，再上参数交互。

### 方向7：招标式竞价——多供应商并行谈判与比价（中，2~3 周）

**背景与痛点**：谈判只面向单个供应商，`alternative_vendors` 只是推荐字段没有真实报价；现实采购的核心是"货比三家"。

**创新点**：LangGraph 单链改"扇出-汇合"：采购规划后对 vendor_products 中供货该 SKU 的供应商（最多 3 家）并行各跑一轮谈判（同一 buyer 策略），新增 `vendor_comparator` 汇合节点综合 unit_price、lead_time、min_order_value、让步率与历史履约（query_vendor_history）打分排序，输出比价矩阵与推荐首选；用户可在前端改选首选，最终推荐联动更新。

**方案设计**：`orchestrator.py` 流程改 procurement→negotiation(fan-out N)→comparator→logistics（在单节点内用 `asyncio.gather` 并发即可，改动最小）；AgentState 增 `alternative_quotes`；vendor_negotiation 的 vendor_id 已参数化、可直接对每家执行；comparator 权重可配（价格 0.5/交期 0.3/历史履约 0.2），final_recommendation 的 vendor 由 comparator 决定。前端比价表每列一家供应商的报价/交期/让步曲线。

**落地步骤**：W1 并发多轮谈判跑通（多供应商 SKU 得 3 份报价与 transcript）；W2 comparator 打分+改选联动+前端比价表。

**实用价值**：采购员日常询价比价直接自动化，一次拿到 3 家可比报价与推荐；对评审则展示并行编排与多源汇合，LangGraph 深度用法的加分项。

**风险与备选方案**：token×3——限并发 2、同 SKU 同参数 30 分钟结果缓存；备选：串行跑 3 家（最简），比价价值不变。

## 五、架构工程化组：让运行"可信、可追、可恢复"

### 方向8：护栏从"展示品"变"执行闸门"——置信度不足的流程真实暂停（高，3~4 周）

**背景与痛点**：治理中心的护栏（"置信度低于 0.72 需审批"等）与审批队列是 `get_governance_hub()` 里的静态字符串，图上从不执行——置信度 0.3 也照样往下走，"人类监督式自治"名不副实。

**创新点**：护栏落地为图上真实条件闸门：demand_forecast 与 procurement 后各插一个 gate，命中规则（置信度<0.72、PO 金额超阈值或非首选供应商）时运行置 `approval_required` 并暂停在闸门，经 WS 推送审批事件；批准后流程继续，驳回生成记录并跳过下游。治理中心变成真审批工作台（待审来自真实运行、可批/驳、留备注）。

**方案设计**：AgentState 增 `approval {required, item, reason, status}`；orchestrator 增两 gate 节点与 conditional edge（LangGraph 原生支持）；新 `services/governance_engine.py`：先硬编码两条规则+`approval_records` 表+审计日志（谁、何时、对哪个 run、结果）。接口 `POST /api/approvals/{run_id}`、`GET /api/platform/governance/queue`；WS 增 `approval_required` 事件。MVP 用**阻断式**（审批通过后重放闸门之后两节点），规避 checkpointer 续跑复杂度。

**落地步骤**：W1 两闸门+判定+WS 事件（故意调差预测构造置信度 0.5 运行验证暂停）；W2 审批 API+GovernanceCenter 可操作化；W3 规则阈值前端可配+审计记录页。

**实用价值**：有资金审批要求的运营负责人是"敢不敢让智能体自动干活"的决策者，审批闸门是前提；把治理从 UI 做到执行层，是评审最关心的安全点，答辩最扎实。

**风险与备选方案**：审批卡住演示——超时 24h 自动驳回+手动恢复按钮；备选：先做"告警式护栏"（触发后重跑降级规则并标记人工复核，不中断），二期再升级为暂停闸门。

### 方向9：断线不丢现场——运行事件日志与回放（中，2~3 周）

**背景与痛点**：会话只存内存 `sessions` dict，前端刷新即丢流程；`GET /api/workflow/state/{session_id}` 恒返写死的 completed；长流程中间态无法找回，演示翻车无法复盘。

**创新点**：每次运行分配 run_id，把 WS 推送的每个事件（消息体已含每步完整 state 快照）追加落盘为事件日志；历史接口按游标回放；`useAgentSocket` 断线重连后按 `last_seq` 补齐错失事件；提供"回放某次运行"入口重播节点动画。

**方案设计**：新 `services/run_repository.py`：事件 JSONL 追加写 `logs/runs/{run_id}.jsonl`（每行 seq/type/agent/ts/state 快照，纯标准库）；接口 `GET /api/runs`、`GET /api/runs/{run_id}/events?after_seq=N`；websocket 的 send_event 处同步落盘（失败不阻塞推送）；`/workflow/state/{session_id}` 改为读日志返回真实最后状态。前端记录 last_seq，重连先补拉再订阅；WorkflowVisualizer 加回放模式。

**落地步骤**：W1 事件落盘+runs/events 接口（curl 模拟断线验证）；W2 前端断线续拉+回放入口与动画。

**实用价值**：演示者现场网络再差也不翻车（刷新可续看），每次运行可回放成答辩录屏素材；事件日志同时是方向 5/10 的数据底座，一份投入多处受益。

**风险与备选方案**：日志膨胀——按 run_id 分文件+保留近 N 天清理任务；备选：只做断线补拉与历史明细、不做回放动画，核心价值不变。

## 六、落地商业化组：让成果"看得见、交得出"

### 方向10：智能决策日报——自动生成管理层日报/周报（中，2 周，依赖方向4/3/5 数据）

**背景与痛点**：智能体每天干活，却没人向使用者汇报结果；系统没有"本周处理了哪些风险、预测偏多少、省了多少钱"的出口；evaluate_agent_suite 偏开发自测，产不出业务语言。

**创新点**：聚合巡检快照、预测回测、PO 状态等**代码算好的真实数字**，让 LLM 只做文案组织，生成 Markdown 日报/周报：①昨夜风险与处置状态 ②预测偏差 Top 3 与修正说明 ③本周下单/收货/补货进度 ④对标市场基准的估算节省 ⑤明日需人工关注的 SKU。报告页在线可看、可下载，可作周会材料或实训报告。

**方案设计**：新 `services/report_generator.py`：`aggregate(period)` 由代码聚合成结构化 JSON（无 LLM），`render(period)` 用单一 Prompt 生成文案拼装 Markdown；Prompt 明令禁止自造数字，渲染后做数值一致性断言，失败回退纯模板渲染。接口 `POST /api/reports/generate {period}`、`GET /api/reports`；前端新增"报告中心"页（列表/预览/下载 .md）；定时触发复用方向 4 调度。

**落地步骤**：W1 聚合模块+模板 Prompt+生成接口（手工触发出首份周报）；W2 报告中心页+下载+绑定时任务每日自动生成。

**实用价值**：运营负责人每周要向上汇报、学员需要可交付成果；一份"系统自己写的运营周报"是落地能力最直接的证据，也天然适合答辩结语材料。

**风险与备选方案**：文案注水或数字不一致——数字代码化+文案模板化+一致性断言兜底；备选：MVP 先做 CLI 生成 Markdown 文件验证闭环，再上前端与定时。

## 七、落地建议

- **首推组合（2 周 MVP）**：方向1（数据接入）+方向2（续谈谈判）+方向3（PO 闭环）——分别解决"真实数据、真实交互、真实执行"三个演示命门，彼此无强依赖、可并行。
- **进阶组合（+2 周）**：方向4（巡检）+方向5（预测回测）——让平台自动运转且可度量，为答辩备好量化指标。
- **王牌组合（+3 周，三人队）**：方向6（场景压测）+方向8（护栏闸门）+方向10（决策日报）——升级为"有人把关、可推演、会汇报"的决策平台，分别对应评审关注的推演深度、安全治理与落地价值。
- 所有方向遵循既有"先降级后增强"模式（新服务带内存/文件兜底），任何阶段都不破坏现有无 Key、无数据库的演示能力。
