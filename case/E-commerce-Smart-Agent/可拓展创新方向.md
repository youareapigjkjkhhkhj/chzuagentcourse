# 可拓展创新方向 —— E-commerce-Smart-Agent（灵犀客服 · 电商智能客服）

**项目定位**：基于 LangGraph + RAG 的电商智能客服，Supervisor 多智能体编排（Supervisor → Product Agent / Order Agent），FastAPI 提供 SSE 流式接口，Chroma 存商品说明书与政策文档，PostgreSQL 存订单与会话，前端为对话网页（含"灵犀客服"高保真原型）。

**现有能力清单**（据《项目设计方案.md》与原型核对）：多轮对话与 Checkpointer 会话持久化；意图路由（product / order / knowledge / fallback）；RAG 接地问答带引用脚标（docs 含 source 与 score）；order_lookup 订单工具（状态/运单号/ETA/物流节点卡片）；前端会话列表、快捷提问、agent 路径面包屑、开发者检查器（工作流图高亮、AgentState JSON 快照）；订单/会话/消息结构化表 + 模拟数据；对比实验框架（纯 LLM / 仅 RAG / 多智能体）。

> 说明：案例当前交付物为设计方案与高保真原型（`项目源码/` 等目录待开发填充），下文"现有模块"均指源码落地后即存在的范围；各方向不引入付费外部服务。

## 一、功能增强（买家可见的新能力）

### 方向1：售后工单办理链——从"讲政策"到"办售后"
**背景与痛点**：用户问完退货政策就断了——"能退吗"之后没有"那帮我退了吧"；方案第 9 节砍掉了退货执行，但这是客服最有价值的业务段。
**创新点**：政策问答与订单工具连成可办理链路：按签收日期与 7 天窗口当场判定，能退则生成申请单，覆盖"咨询→判定→申请→回填退货单号"，回复引用政策原文。
**方案设计**：新增表 `after_sale_applications(id, user_id, order_id, apply_type[return/exchange/refund], reason, status[applied/approved/return_shipping/refunded/rejected], reject_reason, created_at)`；Order Agent 注册两个工具：`create_after_sale(order_id, apply_type, reason)`（仅已签收且 7 天内可申请，超期引用政策条款拒绝；缺 reason 反问）、`submit_return_tracking(ticket_id, tracking_no)`；AgentState 增 `after_sale_ticket` 字段，工具先返回申请草稿、用户确认后才写库；前端复用原型 order-card 样式加工单卡。
**落地步骤**：W1 建表 + 两 tool + 判定规则单测；W2 接入对话流与确认机制、前端工单卡；W3 演示话术打磨（超期拒绝、质量问题运费两条分支）。
**实用价值**：售后咨询占比可达三成，"只答不办"的机器人会逼用户转人工；办成一件申请单即有可量化业务结果，答辩演示也更有说服力。
**风险与备选方案**：参数抽取出错——草稿确认机制兜底，写库前必须用户确认；备选：先做"生成预填申请单链接"的半自动版。

### 方向2：物流订阅与主动播报
**背景与痛点**：order_lookup 返回静态快照，物流更新后用户不问就不知道；原型订单卡片已有 node/ETA 数据，能力是现成的。
**创新点**：用户说"到了提醒我"即订阅订单，后台模拟物流推进，节点变化时系统主动给该会话发消息。
**方案设计**：新增表 `tracking_subscriptions(id, user_id, order_id, last_node, push_count, status[active/unsubscribed], created_at)`；AgentState 加 `source[user/system]`；新工具 `subscribe/unsubscribe_tracking`；写 mock 物流推进脚本（定时把在途订单节点/ETA 前移），检测到变化即以同一 thread_id 再入图，由 supervisor 路由 order agent 生成播报文案；前端显示主动消息与"已订阅·可退订"标记。
**落地步骤**：W1 订阅表与订阅工具；W2 mock 推进器与变更判定、主动消息节点；W3 前端订阅态 UI 与频控（同节点只推一次、每订单每日 ≤2 条）。
**实用价值**：物流提醒是电商标配体验而多数毕设系统没有，主动消息演示效果强，补齐"售前问商品、售中盯物流、售后办退换"三段链路。
**风险与备选方案**：推送打扰——频控 + 退订兜底；备选：不做主动推，改为用户再进会话时先给"离开后订单变更摘要"，省去定时任务。

### 方向3：多 SKU 对比与导购推荐
**背景与痛点**：知识库只有 X1 一款耳机 spec，只能答单品参数；"这俩怎么选"只能得到两段孤立回答，方案提过的"简单推荐"没有载体。
**创新点**：知识库扩为同店多 SKU（X1 / X1 Pro / X2），Product Agent 检索多商品文档块生成对比表卡片，并按使用场景标签做规则化推荐。
**方案设计**：写扩库脚本按 spec_x1.md 结构生成 spec_x1pro.md、spec_x2.md，metadata 补全 `product_id` 与 `audience[通勤/运动/游戏]`，检索加 `where={"product_id": ...}` 过滤即可；前端新增 compare-card 两列对照；Product Agent 判定对比类提问（区别/哪个好/怎么选）后每商品各做一次过滤检索，交由模型按表格字段组织；推荐按关键词→audience 标签匹配，比纯向量召回可控。
**落地步骤**：W1 扩库脚本与 metadata 补全；W2 对比检索逻辑与 compare-card 渲染；W3 标签推荐规则，quick chips 加"X1 和 X1 Pro 选哪个"。
**实用价值**：对比导购是客服促成转化的核心话术，系统从"被动答疑"变"帮用户决策"，也是 RAG 多文档组织回答的直观演示。
**风险与备选方案**：参数张冠李戴——metadata 过滤 + prompt 限制"只列检索到的行"；备选：先做 2 款 SKU，每款配一段"对比锚点"文档。

## 二、智能升级（质量与体验）

### 方向4：回答反馈回流与知识缺口自动上报
**背景与痛点**：RAG 答得好坏无人知晓：原型 citation 可点但无埋点，"没检索到就硬编"没有出口，知识库质量只能肉眼看。
**创新点**：引用点击与用户反馈变成数据，定期产出"知识缺口清单"指导补文档，让知识库越用越准。
**方案设计**：messages 表加列 `feedback(int,1/-1)`、`feedback_at`，接口 `POST /api/messages/{id}/feedback`，前端每条回答下加"有帮助/没帮助"按钮；埋点表 `doc_click_logs(message_id, doc_index, doc_source, clicked_at)`，原型已有的 citation 点击处加上报；`POST /api/conversations/{cid}/retry` 支持用户点"没帮助"后原问题重新入图追问澄清；周脚本聚合低分（score<0.7）或负反馈回答输出知识缺口清单（问题原文、doc_source、缺口关键词）。
**落地步骤**：W1 表与反馈接口、前端按钮埋点；W2 retry 链路；W3 周报聚合脚本（可先落 markdown 文件）。
**实用价值**：给运营一份明确的"哪里缺文档"作业清单，回答被纠正一次就少一次重复投诉，是可持续运营的质检机制。
**风险与备选方案**：真实反馈量少——demo 期用脚本批量生成模拟反馈；备选：缺口清单先只统计低分检索，不依赖用户点击。

### 方向5：情绪感知与升级策略
**背景与痛点**：Supervisor 只分意图不分情绪，催单、投诉的用户仍被同一话术硬答，原型 fallback 对焦躁用户是二次伤害。
**创新点**：路由前加情绪层：负面情绪先共情降级再作答，升级条件满足则转人工（对接方向7），降低差评。
**方案设计**：Supervisor 分类调用改一次输出 JSON：`{intent, sentiment[positive/neutral/negative/frustrated], risk_terms[]}`；条件边新增：negative/frustrated 先走 `de-escalation` 节点（先取 order/RAG 事实，再以安抚模板重述，可检索运费险等补偿政策，不承诺做不到的事）；State 记 `escalate_urgency`，同会话累计 2 次或命中"投诉/差评"类词 → 回答附转人工引导；复用现有模型调用，不新增服务。
**落地步骤**：W1 意图+情绪联合判定与字段扩展；W2 de-escalation 节点与三套模板（物流慢/售后纠纷/商品问题）；W3 升级规则与前端情绪标记。
**实用价值**：情绪识别是客服 AI 与搜索框的分水岭——一次愤怒未被识别可能带来一个差评，演示也易制造冲突剧情讲清价值。
**风险与备选方案**：误判致回复虚假——模板限定在既有事实内共情；备选：先用正则命中负面词起步，再对比 LLM 判定准确率。

### 方向6：评测集与三基线对比 harness
**背景与痛点**：方案第 8 节的对比实验若靠临时试问，结果不可复现，答辩"效果好"无数据支撑，改一次 prompt 后整体是否变差也无从察觉。
**创新点**：实验固化为工程资产：标注评测集 + 一键跑分 + 固定报告，改动可回归，答辩有真实数据图表。
**方案设计**：新建 `eval/dataset.jsonl`，每行 `{query, intent_gold, expect_doc_sources[], answer_must_contain[]}`，覆盖 5 意图 × 20 条（含政策边界与多轮追问）；`runner.py` 对同批问题跑三条链路（纯 LLM / 仅 RAG / 完整多智能体图）；评分含意图准确率、引用命中率与 LLM-as-judge 相关性打分（复用同一 DeepSeek/通义模型、固定温度，免费），输出 `report.md` 表格与柱状图。
**落地步骤**：W1 数据集编写（从原型内置 demo 问答整理首批 30 条）；W2 runner 与三链路封装；W3 评分函数、报告输出与基线记录。
**实用价值**：把毕设从"能跑"提升到"有验证"——评审必问"凭什么说多智能体更好"，跑分报告直接回答；团队里每次 prompt 改动跑一遍即防回归。
**风险与备选方案**：judge 有偏差——全量同模型打分并人工抽检 10%；备选：先上线纯规则指标（引用命中/意图准确），judge 后置。

### 方向7：会话摘要与人工坐席交接
**背景与痛点**：方案明确不做人工队列，但真实场景机器人答不了必须交人；且直接转人工时坐席要重读几十轮记录。
**创新点**：Agent 主动"交接"：生成结构化会话摘要（诉求、已完成动作、引用依据、情绪）并建档转人工；新增坐席工作台页面承接并双向回复。
**方案设计**：新表 `conversation_summaries(session_id, user_id, summary, topics[], unresolved[], updated_at)`，会话结束/转人工时由摘要节点 map-reduce 生成；新表 `tickets(id, session_id, user_id, reason, urgency, status[open/claimed/closed], assignee, created_at)`；不满足条件或用户要求转人工时 Order/Product Agent 调 `create_ticket`，附摘要与最终 AgentState；坐席工作台（Streamlit 或新页）：工单列表→接单→摘要卡 + 原文回放→快捷回复，坐席消息以 `source=human` 写同一会话。
**落地步骤**：W1 摘要节点与两张表、create_ticket 工具；W2 转人工触发规则与工单 API；W3 坐席工作台与双向消息；W4 状态流转与演示打磨。
**实用价值**：人机协同是客服落地的必经形态——没有商家敢全自动；坐席省下重读上下文的时间即省人力，摘要+轨迹可审计，是能讲商业化的故事。
**风险与备选方案**：摘要丢关键信息——固定字段模板 + 原文可查兜底；备选：MVP 只做摘要+工单，坐席回复走邮件占位。

## 三、架构工程化

### 方向8：Agent 注册表与路由插件化
**背景与痛点**：方案强调"预留新增 Agent 接口"，但路由写死后加一个优惠券 Agent 就要改条件边和分类 prompt，扩展成本高。
**创新点**：把"谁处理什么"从代码变数据：注册表集中声明各 Agent 职责、支持意图与工具，Supervisor 的分类 prompt 与路由表由其自动生成。
**方案设计**：新建 `agents/registry.py`：`REGISTRY = [{name, description, owns_intents[], tools[], entry_node, state_keys[]}]`（初始含 product/order，预留 after_sale/coupon 位）；Supervisor 分类 prompt 改 `build_router_prompt(REGISTRY)` 动态拼装，条件边改查注册表得 intent→agent 映射，删硬编码 if-else；图构建遍历注册表 `add_node` 挂子图，启动时校验每个 intent 有且仅有一个 owner。
**落地步骤**：W1 注册表结构与现有两 Agent 迁移；W2 prompt 动态化、条件边改造并用方向6 评测集回归；W3 加最小"优惠券 Agent"（知识库补 coupon_policy.md）验证只改注册表即可扩展。
**实用价值**：后续加 Agent 的成本从"看懂整张图"降为"填一行声明"，是方案可扩展性要点的实质兑现，架构分高。
**风险与备选方案**：小项目过度抽象——只抽象"意图→Agent 映射"一层，节点函数保持普通函数；备选：先写"新增 Agent 操作手册"验证流程再重构。

### 方向9：全链路状态回放——开发者检查器真化
**背景与痛点**：原型开发者视图（流程高亮、docs、AgentState JSON）是演示数据；真实会话跑过哪些节点、检索到什么、调了什么工具，只能翻日志。
**创新点**：每个真实会话产生可回放事件轨迹，前端检查器订阅后端事件流逐轮重放，"点开任何一条历史消息看它当时怎么答的"。
**方案设计**：事件表 `session_events(seq, session_id, event_type[agent_enter/agent_exit/retrieval/tool_call/tool_result/answer], payload JSON, ts)`，在各节点起止处插入统一事件发射器（节点装饰器包装即可）；接口 `GET /api/sessions/{id}/events?after_seq=`，与现有 SSE 流式共用通道但事件、文本分开命名；前端 inspector 改为拉真实事件：按 seq 点亮 flow 节点、追加 docs 分数条、滚动刷新 AgentState JSON。
**落地步骤**：W1 事件发射器与事件表；W2 events 接口与 SSE 融合；W3 前端回放 UI（先"选中消息→显示该轮完整状态"，播放动画后置）。
**实用价值**：开发者与答辩评委第一次"看见"LangGraph 每一步在做什么，排查检索空结果、路由错误从猜变看，教学演示价值高。
**风险与备选方案**：事件多拖慢流式——事件落库按需拉取、文本走 SSE 分道；备选：直接解析 checkpointer 历史回放，代码量更小。

### 方向10：运营后台与知识库管理
**背景与痛点**：加文档要手工改 md 再重灌 Chroma，会话记录散在库里没有检索入口，运营看不到"客户都在问什么"。
**创新点**：面向运营的轻后台，会话检索 + 文档可视化管理 + 统计报表三合一，全部复用选型内的 Streamlit。
**方案设计**：三个 tab：①会话检索：按 user_id/意图/日期/关键词过滤，点开看整段轨迹（联动方向9 事件表）；②知识库管理：上传 md/txt → 复用现有切分参数生成 chunk 预览 → 写 Chroma（metadata 记 source/版本），删除按 `where={"source":...}` 清理；③统计：意图分布、工具调用次数、平均轮次、当日 RAG 未命中 top 问题（联动方向4 缺口）。鉴权用环境变量里的简单口令，仅内网/演示。
**落地步骤**：W1 会话检索页与 SQL 封装；W2 文档上传与重灌/清理流程（复用现有 ingestion 函数）；W3 报表页与缺口清单展示。
**实用价值**：换退货政策、上新品不需要改代码，知识库归属从程序员还给运营；报表回答"机器人今天解决了什么、卡在哪"，是系统走向工具的标志。
**风险与备选方案**：重灌影响线上检索——先删 source 后写 + 版本字段；备选：MVP 只做文档管理 tab，报表沿用方向4 脚本产物。

## 四、落地商业化

### 方向11：订单数据适配层——从模拟数据到真实平台 API
**背景与痛点**：order_lookup 直读自建 orders 模拟表，数据自己造自己演；将来接真实店铺订单（淘宝/拼多多开放平台均有免费测试环境）时，改工具内部逻辑会污染 Agent 层。
**创新点**：工具与数据之间加订单源抽象接口，Agent 只见接口不见实现；演示用 MockOrderSource（现有模拟数据+状态推进），上线写 PlatformOrderSource 即可切换，Agent 与前端零改动。
**方案设计**：新建 `data/order_sources.py`：抽象基类 `OrderSource`：`fetch_by_id(order_id)`、`list_by_user(user_id)`、`on_tracking_change(cb)`（对应方向2 订阅）；重写 order_lookup 与订阅逻辑为依赖注入，启动时按配置选实现；MockOrderSource 包住现有模拟逻辑并保持输出字段（courier/track_no/eta/node/status）不变，前端 order-card 不动；附 `docs/platform_adapter_guide.md`：以淘宝订单查询与拼多多物流接口为例写清授权、签名与字段映射（沙箱免费，无需真实店铺），作真实接入施工图。
**落地步骤**：W1 抽象接口与 Mock 迁移、回归 order 用例；W2 配置化切换与错误处理（平台超时/未授权由 Agent 话术兜底）；W3 平台适配指引与字段映射文档。
**实用价值**：为演示系统留出唯一商用缺口——商家不在乎你用什么模型，只在乎能否查他家真实订单；抽象隔离让这项工作风险与工作量可控。
**风险与备选方案**：平台授权需商家资质，毕设未必拿得到——MVP 交付抽象层+Mock+适配文档，真实实现留待有商家时按文档落地；备选：接快递查询类公开 API 做只读演示（留意免费额度）。
