## 一、项目概述

### 1.1 产品定义

**CareerAgent** 是面向求职场景的多智能体协同职业发展平台，以"求职目标"为中心，通过多智能体（Multi-Agent）协同完成岗位分析、简历诊断、简历优化、岗位匹配、模拟面试、能力评估与个性化训练，形成完整的 AI 求职闭环。

**产品口号：**

> 岗位理解 · 简历优化 · 智能面试 · 能力评估 · 职业成长

### 1.2 核心理念

传统求职工具以单一功能点切入（简历生成、岗位检索、题库刷题、AI 问答），各环节彼此割裂，无法形成数据与能力的持续积累。

CareerAgent 的核心理念是：**以求职目标为中心，将求职全流程建模为多智能体协作任务**，通过统一的记忆系统与能力画像驱动，实现从"AI 帮你写简历"到"AI 帮你完成整个求职过程"的产品升级。

### 1.3 项目目标

| 阶段 | 目标 |
|------|------|
| 短期（MVP） | 打通"简历上传 → JD 解析 → 岗位匹配 → 简历优化"核心链路 |
| 中期 | 实现动态模拟面试、结构化评估与个性化训练推荐 |
| 长期 | 沉淀用户长期能力画像，演进为持续性 AI 职业成长系统 |

## 二、问题分析与解决思路

### 2.1 行业现状

```text
简历工具   →  生成简历
岗位网站   →  检索岗位
面试工具   →  刷题练习
AI 聊天    →  问答辅助
```

以上工具各环节相互独立，存在以下核心问题：

1. **数据割裂**：简历、岗位、面试记录分散在不同平台，无法互通复用；
2. **缺乏闭环**：简历优化与面试反馈、能力短板之间没有联动机制；
3. **无个性化**：所有用户使用相同的 Prompt 与题库，不感知个人能力差异；
4. **无成长性**：缺少对用户能力变化的长期跟踪与训练规划。

### 2.2 解决方案

系统以"求职目标"为输入，各智能体在统一编排下协同工作：

```text
                    用户
                     │
                     ↓
                 求职目标
                     │
              ┌──────┴──────┐
              │ CareerAgent │
              └──────┬──────┘
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
    岗位分析       简历分析       能力分析
       │             │             │
       └─────────────┼─────────────┘
                     ↓
                 岗位匹配 → 简历优化 → 模拟面试 → 面试评估
                     ↓
                 能力画像 → 个性化训练 → 下一轮求职
```

**产品核心价值主张：** 不是一个简历工具，而是一个覆盖求职全流程、具备长期记忆与个性化能力的 AI 求职系统。

## 三、系统总体架构

### 3.1 架构模式

采用 **"1 个 Supervisor + 8 个专业 Agent + 1 个 Agent Runtime"** 的分层协作架构：

- **Supervisor（主控智能体）**：负责任务分解、Agent 调度、流程编排与结果汇总；
- **专业 Agent**：各司其职，完成单一领域的分析或生成任务；
- **Agent Runtime**：为所有 Agent 提供统一的运行时基础设施（上下文、记忆、工具、治理、可观测性）。

### 3.2 架构总览

```text

                    ┌─────────┴─────────┐

        ↓                     ↓                     ↓
  Career Planner       JD Analysis Agent      Resume Agent
  求职规划智能体         岗位分析智能体          简历分析智能体
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              ↓
                        Match Agent
                        岗位匹配智能体
                              │
                              ↓
                Resume Optimization Agent
                     简历优化智能体
                              │
                              ↓

```

## 四、核心智能体设计

以下为 8 个核心智能体的职责、输入输出与处理流程定义。

### 4.1 Agent 01：Career Planner（求职规划智能体）

**职责：** 理解并结构化用户的求职目标，生成职业目标画像，作为后续所有 Agent 的任务上下文。

**输入：**

```text
期望岗位、工作经验、技能清单、期望城市、薪资期望、目标行业、职业方向
```

**输出：**

```text
职业目标画像：目标岗位、岗位级别、核心技能、能力要求、推荐岗位方向
```

**示例：** 用户输入"Java 后端开发 / 3~5 年经验 / 期望上海"，系统生成：

```text
目标岗位：Java 高级开发工程师

核心能力：Java、Spring Boot、MySQL、Redis、MQ、微服务、Docker

建议强化：Kubernetes、高并发、系统设计、性能优化
```

---

### 4.2 Agent 02：JD Analysis Agent（岗位分析智能体）

**职责：** 对招聘 JD（Job Description）进行结构化解析，生成标准化岗位画像。

**处理流程：**

```text
JD 文本 → 文本解析 → 岗位职责提取 → 技能提取
→ 经验要求 → 学历要求 → 关键词提取 → 能力模型
```

**输出示例（岗位画像）：**

```text
技术能力                 软能力
Java          ★★★★★    沟通能力    ★★★★☆
Spring Boot   ★★★★★    团队协作    ★★★★☆
Redis         ★★★★☆    问题解决    ★★★★★
MySQL         ★★★★☆
K8s           ★★★☆☆
```

---

### 4.3 Agent 03：Resume Agent（简历分析智能体）

**职责：** 多格式简历解析与多维度质量分析。

**支持格式：** PDF / Word / Markdown / TXT / 图片（OCR）

**解析维度：**

```text
个人信息、教育经历、工作经历、项目经历、技能、证书、成果
```

**分析维度：**

| 分析项 | 说明 |
|--------|------|
| 结构分析 | 简历结构完整性、模块组织合理性 |
| 内容分析 | 描述具体性、信息密度 |
| 技能分析 | 技能覆盖度与深度 |
| 项目分析 | 项目复杂度、角色贡献度 |
| 成果量化分析 | 是否有可量化的业务成果指标 |
| ATS 关键词分析 | 与 ATS（简历筛选系统）关键词的匹配情况 |

**诊断示例：** 对"负责公司后台系统开发。"这类描述，系统识别：

```text
❌ 缺少具体职责    ❌ 缺少技术栈
❌ 缺少业务背景    ❌ 缺少成果
❌ 缺少量化指标
```

---

### 4.4 Agent 04：Match Agent（岗位匹配智能体）

**职责：** 系统核心模块之一。将岗位画像、简历内容与用户能力画像进行多维匹配计算。

**输入：** 岗位 JD + 用户简历 + 用户能力画像

**输出 1：匹配度总分与分项得分**

```text
岗位匹配度：82%

技术能力 88%   项目经验 79%   工作经验 91%
技能匹配 86%   岗位关键词 93%  软技能 71%
```

**输出 2：结构化差距分析**

| 类别 | 内容 |
|------|------|
| 优势 | Java、Spring Boot、Redis、MySQL |
| 短板 | Kubernetes、高并发、系统设计 |
| 简历缺失项 | 未体现性能优化、未体现架构设计、未体现团队管理 |

---

### 4.5 Agent 05：Resume Optimization Agent（简历优化智能体）

**职责：** 基于差距分析的定向简历优化。

**设计原则：** 不采用"LLM 直接重写简历"的简单方案，而是执行"分析 → 规划 → 分维度优化 → 评估迭代"的受控流程：

```text
原始简历
    ↓
Resume Analysis（简历分析）
    ↓
JD Analysis（岗位分析）
    ↓
Gap Analysis（差距分析）
    ↓
Optimization Plan（优化方案）
    ↓
┌──────────┬──────────┬──────────┐
结构优化     内容优化     关键词优化
└──────────┴──────────┴──────────┘
    ↓
Resume V2（优化版本）
    ↓
Evaluation（匹配度复评）
    ↓
Resume V3（迭代版本）
```

**版本管理：** 支持以下版本链路与版本间对比（Diff）：

```text
原始简历 → 优化版本 → 岗位定制版本 → 最终版本
```

---

### 4.6 Agent 06：Interview Agent（面试智能体，含编排与三类面试官）

**职责：** 系统核心模块之二。提供**动态模拟面试**能力，而非固定题库。

**面试编排结构：**

```text
Interview Orchestrator（面试编排智能体）
    │
    ├── Technical Agent（技术面试官）
    ├── HR Agent（HR 面试官）
    └── Stress Agent（压力面试官）
```

#### 4.6.1 动态追问机制（核心能力）

系统根据用户回答实时评估回答深度，动态规划下一问题：

```text
用户回答 → 回答分析 → 能力判断 → 动态生成下一问题 → 继续追问
```

**追问示例：**

> **面试官**：你在项目中负责高并发系统开发，请介绍一下你的设计。
>
> **用户**：使用 Redis 做缓存。
>
> **Agent 判断**：回答深度：中 → **追问**："为什么使用 Redis？"
>
> **用户**：为了提高访问速度。
>
> **Agent 判断**：深度不足 → **追问**："如果出现缓存击穿，你会怎么处理？"
>
> **继续追问**："缓存雪崩和缓存穿透有什么区别？"

#### 4.6.2 三类面试官职责划分

| 面试官 | 考察重点 |
|--------|---------|
| 技术面试官 | 技术基础、项目经验、系统设计、算法、技术深度 |
| HR 面试官 | 职业规划、离职原因、薪资期望、沟通能力、团队协作、稳定性 |
| 压力面试官 | 压力承受、临场反应、逻辑能力、应变能力 |

**压力面试示例：**

> "这个项目团队只有 3 个人，为什么简历上写的是你主导了整个项目？"

---

### 4.7 Agent 07：Evaluation Agent（面试评估智能体）

**职责：** 面试结束后输出**结构化评价体系**，而非简单的定性结论。

**评估输出示例：**

```text
面试综合评分：82 / 100

技术能力 88    表达能力 72    项目能力 84
逻辑能力 79    应变能力 76    岗位匹配 91
```

---

### 4.8 Agent 08：Career Coach（职业教练智能体）

**职责：** 汇总前序所有 Agent 的结果（简历分析、岗位匹配、面试评估、历史训练数据），生成个人能力画像（Career Profile），并输出可执行的训练计划。

#### 4.8.1 能力画像示例

```text
Java 后端开发

技术能力 86    项目能力 82    架构能力 74
表达能力 68    沟通能力 79    系统设计 71
算法能力 63
```

**Top 3 优势：** ① Java 技术基础　② 项目经验　③ 数据库能力

**Top 3 短板：** ① 算法　② 系统设计　③ 面试表达

#### 4.8.2 训练计划生成示例

基于近 5 次面试数据分析：

```text
技术能力 ↑12%    表达能力 ↑3%    系统设计 ↓2%

主要问题：
① 项目描述不够具体
② 技术追问容易卡顿
③ 系统设计回答结构不完整
```

自动生成未来 7 天训练计划：

| Day | 训练内容 |
|-----|---------|
| Day 1 | Redis 专项 |
| Day 2 | 高并发专项 |
| Day 3 | 项目表达训练 |
| Day 4 | 系统设计 |
| Day 5 | HR 模拟面试 |
| Day 6 | 综合面试 |
| Day 7 | 最终模拟 |

**产品价值：** 该 Agent 使产品从"求职工具"升级为"AI 职业成长系统"。

## 五、Agent Runtime 设计

Agent Runtime 是整个项目的技术核心，作为独立子系统设计，为所有智能体提供统一基础设施：

```text
Agent Runtime
│
├── Agent Manager        # Agent 生命周期管理
├── Supervisor           # 任务编排与调度
├── Planner              # 任务规划
├── Context Manager      # 上下文管理
├── Memory Manager       # 记忆管理
├── Tool Manager         # 工具注册与调用
├── MCP Manager          # MCP 协议接入管理
├── Workflow Engine      # 工作流引擎
├── Multi-Agent Engine   # 多智能体协作引擎
├── Guardrail            # 安全护栏
└── Trace                # 全链路追踪
```

## 六、记忆系统设计

记忆系统是本项目实现"个性化"与"成长性"的关键，分为三层：

### 6.1 记忆分层

| 层级 | 内容 |
|------|------|
| 用户记忆 | 求职目标、技能、职业偏好、历史简历 |
| 面试记忆 | 问过的问题、回答记录、错误记录、知识薄弱点 |
| Agent 记忆 | 最近面试情况、优化记录、能力变化趋势 |

### 6.2 长期记忆驱动示例

```text
第 1 次面试：Redis 缓存击穿回答不佳 → 系统记录薄弱点
第 2 次面试：自动增加 Redis 专项追问
第 3 次面试：掌握情况改善 → 自动提高问题难度
```

该机制即**长期记忆驱动的自适应 Agent**，是区别于普通对话式面试工具的核心能力。

## 七、知识中心设计

知识中心为各 Agent 提供 RAG 检索支撑，采用多库分类组织：

```text
Knowledge Center
│
├── 技术知识库（Java / Python / MySQL / Redis / Kubernetes ...）
├── 面试知识库（技术面试 / HR 面试 / 行为面试）
├── 岗位知识库（Java / AI / 前端 / 产品 ...）
└── 企业知识库
```

**面试 Agent 的 RAG 调用链路：**

```text
Question → Knowledge Retrieval → Context → Interview Agent → Dynamic Question
```

## 九、客户端设计（UI / UX）

### 9.1 产品形态与交互范式

产品为跨平台桌面客户端（Windows / macOS / Linux），交互范式参考 Claude Code Desktop：**对话为中心（Chat-first）+ 三栏式布局 + 求职项目管理**。

- **左栏**：会话与求职项目管理（按求职方向分组的会话列表）；
- **中栏**：与 Agent 团队的主对话区，用户以自然语言下达求职任务；
- **右栏**：上下文面板，实时展示简历预览、匹配度、能力画像、Agent Trace 等结构化结果。

**桌面端独有能力：**

| 能力 | 说明 |
|------|------|
| 本地文件直通 | 简历 PDF / Word 拖拽进窗口即可解析，文件不上传 |
| 数据本地化 | 简历、面试记录等敏感数据全部存储于本地 |
| 离线可用 | 历史会话、简历版本、能力画像本地可查，断网可回顾 |
| 系统级集成 | 全局快捷键唤起、系统通知（面试提醒 / 训练计划打卡）、托盘常驻 |
| 多方向并行 | 多个求职方向（如 Java 后端 / AI 工程）各自独立会话与上下文 |

### 9.2 信息架构（左侧导航）

```text
CareerAgent
│
├── 💬 会话            # 与 Agent 团队的所有对话，按求职项目分组
├── 🎯 求职项目
│   ├── 求职目标
│   ├── 目标岗位列表
│   └── 求职进度
├── 📄 简历
│   ├── 我的简历
│   ├── 简历优化
│   └── 版本对比（Diff）
├── 💼 岗位
│   ├── 岗位分析
│   ├── 岗位匹配
│   └── 岗位收藏
├── 🎤 面试
│   ├── 模拟面试
│   ├── 面试记录
│   └── 面试报告
├── 📊 能力中心
│   ├── 能力画像
│   ├── 能力雷达
```

## 十、安全与治理机制

虽然是本地客户端形态，Agent 自主调用工具与本地敏感数据驻留的特性，仍要求完整的治理机制：

### 10.1 权限控制（Permission）

```text
Agent → Permission → Tool
```

Agent 对工具的每次调用均经过权限校验。

### 10.2 风险分级控制（Risk Control）

| 风险等级 | 处置策略 |
|---------|---------|
| 低风险 | 自动执行 |
| 中风险 | 用户确认 |
| 高风险 | 人工审批 |
| 禁止操作 | 直接拦截 |

### 10.3 审计日志（Audit）

全量记录操作行为：

```text
User、Agent、Task、Tool、Input、Output、Time、Token、Cost、Result
```

### 10.4 本地数据安全

| 项 | 策略 |
|----|------|
| API Key 存储 | 使用系统密钥链（Windows Credential Manager / macOS Keychain）加密存储，不明文落盘 |
| 敏感数据 | 简历与面试记录仅存本地数据目录，支持一键导出与彻底清空 |
| 云端同步 | 默认关闭，开启需用户显式授权并明示同步范围 |

## 十二、技术架构与选型

### 12.1 总体技术架构（桌面客户端）

采用 **"Electron 客户端壳 + 本地 Python Agent Runtime + 云端 LLM API"** 的本地优先（Local-first）架构：

```text
┌────────────────────────────────────────────────┐
│              Electron 桌面客户端                 │
│  ┌──────────────────────────────────────────┐  │
│  │  渲染层：Vue 3（三栏式 UI）                 │  │
│  └───────────────────┬──────────────────────┘  │
│  ┌───────────────────┴──────────────────────┐  │
│  │  主进程：窗口 / 文件系统 / 系统通知 / 自动更新 │  │
│  └───────────────────┬──────────────────────┘  │
└──────────────────────┼─────────────────────────┘
                       │ IPC / localhost HTTP
┌──────────────────────┴─────────────────────────┐
│     本地 Python Agent Runtime（Sidecar 进程）     │
│                                                │
│  Supervisor / Multi-Agent Engine / Workflow    │
│  Context Manager / Memory Manager              │
│  Tool Manager / MCP Manager                    │
│  Guardrail / Trace                             │
└───────┬───────────────┬───────────────┬────────┘
        │               │               │
        ↓               ↓               ↓
   本地数据层        RAG 检索层        模型接入层
   SQLite          Milvus Lite       OpenAI / Qwen /
   本地文件目录      （内嵌向量库）      DeepSeek / Claude
   （简历原件）      bge-m3 本地嵌入    （用户配置 API Key）
```

### 12.2 架构说明

| 层 | 技术栈 | 职责 |
|----|--------|------|
| 客户端壳 | Electron + Vue 3 | 三栏式 UI、本地文件访问、系统通知、托盘、自动更新 |
| 智能运行层 | Python（Sidecar 本地常驻进程） | Agent、LLM 编排、RAG、Memory、Tool Calling、Multi-Agent、Evaluation |
| 数据层 | SQLite + Milvus Lite + 本地文件目录 | 会话、简历、面试记录、知识库、记忆全部本地存储 |
| 模型层 | 云端 LLM API | 用户自备 API Key，按用量计费，无服务器成本 |

**该架构的关键决策：**

1. **不设业务服务器**：求职场景是单用户个人工具，用户系统、权限、API 网关等企业级组件在 MVP 阶段全部裁剪，客户端直连本地 Runtime；
2. **Spring Boot 降级为可选演进项**：仅当未来推出"云端同步 / 团队版 / 企业版"时，再引入 Spring Boot 作为云端服务（账号、多端同步、组织管理），客户端架构无需重构；
3. **数据主权在用户**：简历与面试记录属于高敏感个人数据，本地存储天然规避隐私合规风险，同时构成相对 Web 版产品的核心卖点；
4. **向量库选用 Milvus**：MVP 阶段使用 **Milvus Lite**（`pymilvus` 内嵌模式，随客户端分发、零外部依赖）；未来云端版可无缝切换为 Milvus Standalone / 分布式集群，接口协议一致，无换库与数据迁移成本；
5. **技术栈备选**：若对安装包体积敏感，客户端壳可替换为 Tauri 2（Rust，约 10MB），渲染层与 Python Sidecar 方案不变。

### 12.3 可选云端扩展（Phase 3 之后）

```text
桌面客户端（保持本地优先）
    │  可选登录 / 可选同步
    ↓
Spring Boot 云端服务（可选）
├── 多端数据同步（PC ↔ 移动端）
├── 云端知识库与岗位数据更新
└── 团队版 / 企业版（组织、权限、审计）
```

### 12.4 打包与分发

| 项 | 方案 |
|----|------|
| 客户端打包 | electron-builder：Windows（NSIS）/ macOS（DMG）/ Linux（AppImage） |
| Python Runtime 打包 | PyInstaller 打包为独立可执行文件，随客户端分发，用户免装 Python 环境 |
| 自动更新 | electron-updater |
| 分发渠道 | 官网下载 / GitHub Releases |

## 十三、实施路线规划

MVP 分三阶段交付：

### Phase 1：基础能力

```text
客户端骨架（Electron 壳 + Python Sidecar 进程管理）、
简历导入（拖拽 / 文件选择）、JD 解析、简历分析、岗位匹配
```

### Phase 2：智能体能力

引入多智能体协作，实现核心 Agent 闭环：

```text
Supervisor、Resume Agent、JD Agent、Match Agent、
Resume Optimizer、Interview Agent、Evaluation Agent
```

本阶段完成后，系统具备真正的多 Agent 协作能力。

### Phase 3：平台化能力

```text
Memory、Knowledge、MCP、Tool Center、Workflow、
Agent Trace、Guardrail（权限 / 审批 / 审计）、Cost 统计、
自动更新、多平台安装包分发、可选云端同步
```

本阶段完成后，产品成为完整的**本地 Agent 工作站（Local Agent Workstation）**，并具备接入云端服务（账号、多端同步、团队版）的扩展能力。
