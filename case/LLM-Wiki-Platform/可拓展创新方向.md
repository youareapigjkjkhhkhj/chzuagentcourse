# LLM-Wiki-Platform 可拓展创新方向

## 一、项目定位与现有能力

本项目是面向企业运维团队的 LLM Wiki 知识管理平台：Flask 3 + SQLAlchemy + MySQL 8 后端，Vue 3 + TS + Element Plus 前端，Milvus 向量库承载 RAG。RAG 链路为「文档发布时用 RecursiveCharacterTextSplitter（chunk 1000/overlap 200）切块 → text-embedding-3-small 向量化入 Milvus（collection: wiki_embeddings，metadata 仅 document_id/chunk_index）→ 提问时 similarity_search top_k=5 → LCEL 链注入 PromptTemplate 生成回答，来源在聊天页展示」。

已实现功能（据代码核实）：JWT 登录注册与 RBAC 三角色（admin/editor/viewer，`require_permission` 装饰器）；文档 CRUD、多级分类树、标签、软删除、文档版本快照（DocumentVersion，每次更新存旧版）；问答三条接口（/qa/ask、/qa/history、/qa/feedback），qa_records 完整记录 document_ids/confidence/model_used/tokens_used/session_id；文档检索（SQL LIKE）；首页统计 4 项计数。同时存在大量"只搭了一半"的资产：comments、audit_logs、document_versions 表与模型齐备但无任何 API；Celery 已完整配置（docker-compose 已起 worker、`app/tasks/celery.py` 就绪）但零任务，向量化仍在 HTTP 请求线程里同步执行；LangGraph、Redis 已装未真正使用；confidence 为硬编码 0.85。这些是以下方向最扎实的抓手。

## 三、功能增强类（现有技能即可快速落地）

### 方向1：文档评论区与讨论

- **背景与痛点**：`comments` 表、`Comment` 模型、`allow_comment/comment_count` 字段、前端文档详情的评论期望全都存在，但后端没有任何评论路由——知识库是单向"发布-阅读"，读者对文档的疑问（如某命令版本过时）只能回到 IM 群聊，问题与答案无法沉淀。
- **创新点**：零迁移成本补齐讨论闭环，并把"文档 ID"作为问答与评论的共同锚点，为后续"问答结果可转评论"留好位置。
- **方案设计**：新建 `backend/app/api/comments.py` 并注册进 `api/__init__.py`：`GET/POST /documents/<id>/comments`（分页）、`POST /comments/<id>/reply`（复用 parent_id）、`PUT/DELETE /comments/<id>`（作者可改，admin 可隐藏，status 置 'hidden'）；写服务层 `CommentService`，新增评论时 `document.comment_count += 1`。前端在 `DocumentDetailView.vue` 底部插入评论组件（新建 `components/comment/CommentList.vue`），复用现有 types 风格补 `types/comment.ts`。
- **落地步骤**：第 1 周完成后端 CRUD + 权限（viewer 可读，editor+ 可写）与计数维护；第 2 周前端评论组件、楼中楼回复、空态与权限隐藏；第 3 周可选：管理员隐藏接口 + 列表接口按创建时间排序，写 3 条 pytest。
- **实用价值**：知识库最大的流失是"不敢改文档的人发现问题"——读者一句话评论让编辑按需修订，评论即更新信号。运维值班人员确认某个 SOP 失效时的即时指正，是最廉价的质量反馈源。
- **风险与备选方案**：评论易水化（"赞""顶"）——备选限制：仅 editor 以上可见全部评论或按文档开关；无需全文检索评论，本期只做按文档拉取。

### 方向2：版本历史 Diff 与一键回滚

- **背景与痛点**：`DocumentVersion` 每次更新都把旧版整份存档（version、change_summary、author 都有），但全站无一处能查看历史——误改后只能手动找回，版本表成了只进不出的死数据。
- **创新点**：不引入任何第三方 diff 服务，直接用 Python 标准库 difflib 做版本对拍，低成本把"存了没用的版本"变成可用功能。
- **方案设计**：后端加 `GET /documents/<id>/versions`（分页列表，含 change_summary/author/created_at）与 `GET /documents/<id>/diff?v1=N&v2=M`——用 `difflib.HtmlDiff` 生成行级增删对比并附差异行数；`POST /documents/<id>/revert` 取目标版本内容写回并走 `DocumentService.update_document`（自然生成新版本号并同步触发向量更新，链路完全复用）。前端在详情页加"历史版本"抽屉：时间线列表 + 版本间对比预览 + "回滚到此版本"二次确认。
- **落地步骤**：第 1 周两个查询接口 + diff 接口（先单测 difflib 输出）；第 2 周 revert 接口与前端抽屉；第 3 周打磨：diff 视图空态、超长文档仅返回前 200 差异行（防页面卡死）。
- **实用价值**：企业 wiki 被误改后"找回原文"是刚需；运维手册常因一次变更事故被回滚，配合 change_summary 能直接看出谁在何时改了什么，也是责任追溯的最小实现。
- **风险与备选方案**：大文档 diff 耗内存——限制单文档 500KB 内可 diff，超出只提供整版下载；前端高亮冲突可退回「左右分栏纯文本 + 后端返回 unified diff 文本」。

### 方向3：中文全文检索增强（ngram 方案）

- **背景与痛点**：列表搜索与 `/documents` 搜索都走 `content ILIKE '%关键词%'`，中文不分词导致「故障排查」搜不到「排查故障」，且全表扫描无相关性排序，关键词明明精准命中却排在浏览量高的无关文档后面。
- **创新点**：MySQL 8 自带 ngram 全文解析器（免安装、免外部服务），给 documents 建 FULLTEXT 索引后改用 `MATCH...AGAINST` 布尔检索，标题命中加权、返回命中片段，让关键词通道真正可用。
- **方案设计**：新增迁移 SQL `docs/迁移脚本/03-add-ft-index.sql`（`ALTER TABLE documents ADD FULLTEXT INDEX ft_doc_search (title, content, summary) WITH PARSER ngram;`）；`DocumentService.get_documents/search_documents` 中当 keyword 非空且库已建索引时走 `MATCH(title, content, summary) AGAINST(:kw IN BOOLEAN MODE)`，按 `MATCH 得分*1.5（title）+ 匹配字段数` 排序，回退逻辑保留 LIKE；接口在返回项中补 `match_snippet`（命中位置前后 80 字）。管理端提供"重建/检查全文索引"说明页。注意 ngram_token_size 默认 2，单字词会查不到——可在 SQL 里按需声明。
- **落地步骤**：第 1 周导入索引 SQL、改造查询与排序、pytest 断言"关键词顺序优先于浏览量"；第 2 周前端把列表页搜索与搜索框升级（高亮命中词、显示片段），首页新增关键词搜索入口；第 3 周可选：搜索历史落 Redis 与热词 TOP10。
- **实用价值**：检索是 wiki 使用频率最高的动作，运维排障时"搜得准、排得对"直接决定平台口碑；零新依赖、一周见效，是所有方向中性价比最高的一笔。
- **风险与备选方案**：线上库表结构需手动执行迁移（项目无 flask db migrate 流程，需在启动文档写明）；备选不引外部引擎，最坏情况下保留 LIKE + 增加 `summary` 列权重排序，效果降级但可控。

## 四、智能升级类（吃透现有 RAG 再做深）

### 方向4：多轮会话与流式输出（LangGraph 上场）

- **背景与痛点**：`qa_records.session_id` 建表就存了但从未被读取，聊天页刷新即失忆，追问"那回滚呢"只能重述上文；`/qa/ask` 是同步整包返回，最慢时用户盯着 spinner 十几秒。requirements 里 langgraph>=0.2.0 已装却一行未用。
- **创新点**：让依赖物尽其用——用 LangGraph 的 StateGraph 编排「意图→检索→（有依据才）生成→（附来源）」，把会话历史作为 State 注入，实现真正多轮；输出改 SSE 流式，首字秒出。
- **方案设计**：`ai_service.py` 新增 `build_graph()` 构建问答图（检索节点调现有 `search_similar_documents`，生成节点用流式 `llm.stream()`，可加"无命中直接拒答"条件边）；`qa_service` 按 session_id 从 `qa_records` 取最近 10 轮 Q/A 拼入 system prompt（无需新表）；`/qa/ask` 改流：Flask 返回 `text/event-stream`，逐 token 推送并最终补 sources 与 record_id；前端 `QAChatView.vue` 用 `fetch` + `ReadableStream` 边收边渲染，打字效果 + 停止生成按钮；会话列表左侧栏（读写 session_id，复用现有字段）。
- **落地步骤**：第 1 周 LangGraph 图 + 历史注入 + 非流式回归测试；第 2 周 SSE 改造 + 前端流式消费与打断；第 3 周会话列表、复制/分享答案、超时与断线重连。
- **实用价值**：值班人员在事故处置中连续追问（"这个报错什么原因→我们的版本是多少→那怎么回滚"）是最典型场景；流式让首字 <1s，问答从"搜索工具"质变为"可对话的排障搭子"。
- **风险与备选方案**：LangGraph 调试曲线陡——MVP 可先用 LCEL `RunnableWithMessageHistory` + Redis 存会话（同样达到多轮），图编排作为第二阶段；SSE 在 Nginx 后需关缓冲（部署手册补充 proxy_buffering off）。

### 方向5：权限感知的混合检索

- **背景与痛点**：`visibility`（public/private/department）与 `department` 字段设计完备但检索层完全不感知——语义搜索会把 private 文档内容捞进任何人的回答上下文；且 RAG 只有向量一路召回，关键词精确匹配（版本号、报错码）往往比语义更准却排在后面。
- **创新点**：把"数据安全"与"召回质量"一起解决：向量命中按文档可见范围二次过滤（两级过滤优于在 Milvus 建复杂 expr），并与关键词通道做 RRF（倒数排名融合）。
- **方案设计**：发布文档时向量 metadata 追加 `visibility` 与 `author_department`（在 `process_document_for_embedding` 传入）；`qa_service` 检索改为：① 从 MySQL 一次查出当前用户可见的 document_id 集合（public 全量 + 本部门 department + 本人 private/作者），② 向量 top_k=10 召回后按白名单过滤，不足 5 条时用方向 3 的全文检索补召回到 top_k=5，③ 两路结果按 `1/(rank+60)` 计分融合排序，重排后进上下文；`answer.sources` 保持原格式，仅多带 visibility 标记。后台文档接口同步按可见范围过滤（现有接口目前对 private 无强制）。
- **落地步骤**：第 1 周可见性查询工具 + 向量召回过滤 + 白名单单测；第 2 周全文补召回与 RRF 融合、重排开关；第 3 周接口级可见性收紧、跨部门问答盲测 10 组对比。
- **实用价值**：企业内部 wiki 最先被挑战的就是"AI 会不会把我部门的内部预案答给外人"；权限过滤上线前，智能问答根本不敢对全员开放——这是从演示系统到可进生产的安全分水岭。
- **风险与备选方案**：两级过滤可能让冷门问题召回不足——备选改为"过滤后仍不足即拒答并提示扩大文档公开范围"，比硬凑上下文更诚实。

### 方向6：答案质量门卫与反馈闭环

- **背景与痛点**：`confidence` 字段写死 0.85，等于没有；检索零命中时模型仍可能硬答（prompt 说了"不知道就说不知道"，但没有兜底逻辑验证）；用户点过的不满意反馈（qa_records.feedback）只躺在库里，没有任何机制把它变成知识库改进动作。
- **创新点**：做"事实门卫 + 缺口回流"：低分/零命中直接拒答并给出原因，把"not_helpful 的问题"聚合成"待补文档清单"交给编辑——问答系统第一次能把知识库的洞反馈给补洞的人。
- **方案设计**：`qa_service.ask_question` 改造：① 最高分 < 阈值（如 0.45）或召回为 0 时进入拒答分支（回答"知识库暂无相关内容，建议：1. 扩大文档公开范围 2. 提交补充需求"），confidence 写入真实分；② 拒答与 low-score 提问落新表 `qa_gaps`（question、doc_ids 空、计数、状态 open/fixed，每周定时任务按同义归一合并——先按文本归一，后续可加 embedding 去重）；③ 新增 `GET /api/v1/qa/gaps`（editor+ 可见）与 `PUT /gaps/<id>/close`，前端给编辑加"知识缺口"任务页，一键把问题转成待写文档草稿（title 预填问题）。
- **落地步骤**：第 1 周拒答分支 + 真实置信度 + 单元测试（造零命中场景）；第 2 周 qa_gaps 表 + 聚合任务 + 缺口 API；第 3 周编辑端任务页 + 反馈率统计（not_helpful 数/总问答数）进运营看板。
- **实用价值**：知识库管理员最需要的不是"AI 答得漂不漂亮"而是"哪块知识是空的"——缺口清单直接指导内容采购；对使用者，诚实的"我不知道"比一本正经的编造更能建立信任，运维场景下错误答案的代价是事故等级。
- **风险与备选方案**：阈值调参玄学——MVP 阶段提供后端配置开关与三档阈值，留一周 A/B 手动比对；拒答过频会劝退用户，故缺口页同时展示"未答问题数"让管理员尽快补文档。

### 方向7：文档入库智能增强（摘要/标签/相似提醒）

- **背景与痛点**：documents.summary 大多为空（发布时没人填），列表页与搜索展示全靠全文截断；tags/categories 靠人工，多级分类常选错或漏选；新人整理二手资料时常与已有文档重复，问一遍才知道撞车。
- **创新点**：把已有 LLM 能力用到"写文档之前/之时"：编辑器内一键生成摘要与标签建议，发布时用现有向量检索提示相似文档——AI 从"出口"（问答）延伸到"入口"（写作）。
- **方案设计**：`ai_service.py` 新增 `summarize_document(content)`（LLM 输出 ≤100 字摘要 + 3~5 个标签 + 关键词）与 `find_similar(document_id/content, top_k=3)`（直接复用 `search_similar_documents`，排除自身）；后端 `POST /api/v1/ai/doc-augment`（editor+，接收 content 返回三件套）与 `GET /documents/<id>/similar`；前端编辑页右侧 AI 助手卡片：点击填充 summary 字段与标签勾选、展示相似文档链接；发布校验：summary 为空时提示一键生成（不强制）。所有 AI 调用异步化后可搬进方向 8 的任务队列。
- **落地步骤**：第 1 周摘要/标签 prompt 与接口、prompt 效果 10 篇手工抽检；第 2 周前端 AI 助手卡片 + similar 展示；第 3 周把增强结果写入 meta_data JSON（该字段闲置已久，正好启用）供后续统计。
- **实用价值**：编辑省去每篇几十字的摘要撰写（批量导入旧文档时尤其值钱）；auto-tag 提升检索与问答的分类质量；相似提醒让"一人一版的重复文档"在源头被拦下。
- **风险与备选方案**：LLM 生成的标签可能漂移——限制从现有 tags 表候选 + 新词须人工确认；摘要质量不稳时降级为"抽取式"（取首段 3 句），不阻塞发布流程。

## 五、架构工程化类（把演示工程推向可运维）

### 方向8：向量化异步任务化（激活闲置 Celery）

- **背景与痛点**：docker-compose 里 celery-worker 与 `app/tasks/celery.py` 早已就绪，但目录下零任务——向量化仍在 `create/update/delete` 请求线程同步执行（切块 + embedding API 网络往返，接口从 200ms 拖到数秒，embedding 供应商抖动时发布直接超时）；更新文档"先删后写"若中途失败，旧向量已删新向量没进，该文档在问答中永久缺席且无任何告警。
- **创新点**：把已部署的 Celery + Redis 从摆设变成索引流水线：embedding 全异步 + 幂等 + 失败重试 + 对账工具，发布接口回归秒级。
- **方案设计**：新建 `app/tasks/indexing.py`：`@celery.task(bind=True, max_retries=3)` 的 `embed_document(doc_id)`（内部先按 document_id 清旧 chunk 再写入，保证幂等）与 `delete_document_vectors(doc_id)`；`document_service` 三处调用改 `.delay()`，并给 documents 表加 `vector_status` 枚举列（pending/indexed/failed，model 同步），任务成功/失败回写；删除时用 Redis 记录任务状态便于看板；提供 Flask CLI 命令 `flask index rebuild [--ids]` 供全量/增量重建（遍历 published 文档重投队列）。docker-compose 无需改动（worker 命令已指向 `app.tasks.celery`，任务文件同模块自动被发现）。
- **落地步骤**：第 1 周任务文件 + service 改造 + vector_status 字段与回写；第 2 周重试/死信（失败队列 Redis list 单独兜底）+ 重建 CLI + 手工对账脚本（MySQL 已发布数 vs Milvus 去重 document_id 数）；第 3 周索引状态页（admin 查看 failed 列表与一键重投）。
- **实用价值**：文档量上百篇后同步 embedding 必然卡死发布体验；异步化后批量导入 1000 篇文档也能秒回。worker 与向量库的健康状态终于有人看着——这是演示项目被运维团队接手时的第一道体检。
- **风险与备选方案**：单机学生环境 Celery 部署略重——备选先用 `threading`/进程池降级（接口内投递不等待），但 worker 已在 compose 里，鼓励直接上 Celery；embedding API 限速时可调低 worker concurrency。

### 方向9：审计链路补全（补上从未发生的"记录"）

- **背景与痛点**：audit_logs 表、AuditLog 模型、请求钩子（`register_request_hooks` 里 `before_request` 是 pass）一应俱全，但没有一行代码往审计表写数据——"谁在何时改了什么"完全不可查，与权限体系的严谨度极不匹配。
- **创新点**：改动最小、收益即时的工程补全：用请求钩子统一落库，按资源与动作给编辑/删除/导出等写操作生成审计事件。
- **方案设计**：`utils/audit.py` 提供 `log_action(resource, resource_id, action, details)`（读 current_user/request 自动带 ip、user_agent、path、耗时）；在 `api/documents.py`、`categories.py`、`tags.py`、`users.py` 的写操作处埋点（或直接写进 service 层，覆盖更稳）；删除历史：只软删文档，审计里留硬关联。新接口 `GET /api/v1/admin/audit-logs`（admin 限定，按 user/action/resource/时间过滤分页），前端管理区加"操作日志"页（复用现有表格组件风格）。
- **落地步骤**：第 1 周埋点 + 落库自测（增删改各 3 条场景）；第 2 周管理查询接口与页面；第 3 周可选：登录/登出与 JWT refresh 也入审计、超过 90 天日志归档。
- **实用价值**：任何企业知识库上线评审必问"谁能改、改了有记录吗"；审计 + 版本历史（方向 2）组合即完整可追溯链——回答不了这两个问题的系统进不了生产网段。
- **风险与备选方案**：全量埋点易漏——备选先覆盖"写操作 + 登录"四类高危动作，读操作一律不记（量大且无价值）；表增长可控（日增万条以内，保留 90 天）。

### 方向10：问答运营质量看板

- **背景与痛点**：`/stats` 只回 4 个数字；但 qa_records 里躺着 response_time、feedback、tokens_used、document_ids、session_id 一堆金矿从未被分析——负责人不知道问答用得多不多、答得好不好、花多少钱。
- **创新点**：把现有数据表变成决策依据：问答质量、热门缺口话题、token 成本估算三个维度，全部从现有表聚合，不加新采集。
- **方案设计**：`stats.py` 扩展：`GET /api/v1/stats/qa-quality` 返回——问答总量/日均、平均与 P95 响应时间、helpful/not_helpful/neutral 占比、拒答率（方向 6 上线后）、零引用回答数、按 model_used 聚合的 tokens 估算成本（按 $/M tokens 配置单价）；`GET /stats/hot-questions`：问题按 embedding 去重聚类后 TOP20（复用方向 6 的归一逻辑）；前端新增 DashboardView 路由（admin/editor 可见）：ECharts 或原生 SVG 折线/柱状（不引重依赖，Element Plus 已有基础，画图可用 echarts——免费开源可引）。每 10 分钟任务预聚合到新表 `stats_daily`（按天归档，避免大表实时扫）。
- **落地步骤**：第 1 周聚合 SQL + qa-quality 接口；第 2 周 hot-questions + stats_daily 预聚合任务；第 3 周前端看板 + 管理员周报邮件（纯文本模板，走免费 SMTP 或跳过）。
- **实用价值**：给领导看"问答解决了多少问题、堵了多少文档洞"比截图聊天记录有力得多；成本数字让团队敢把模型从 gpt-5-mini 往上试——所有数字都能解释，AI 预算不再是黑盒。
- **风险与备选方案**：问题归一去重做不准会污染 TOP 榜——MVP 先按关键词集合聚类 + 人工确认；看板只读不写，纯查询无并发风险。

## 六、落地商业化类（把平台能力打包对外）

### 方向11：内嵌问答小组件（嵌入企业门户）

- **背景与痛点**：平台只在独立域名可用，而运维值班的场景在监控大屏、工单系统、企业微信/门户里——用户不会为了问一个问题再开一个系统登录一次。
- **创新点**：把问答能力打包成"一行 iframe 即用"的组件，并设计免登录短期 ticket 机制——知识库从"一个网站"变成"可嵌入各处的问答服务"。
- **方案设计**：后端新增 embed 蓝图：`POST /api/v1/embed/ticket`（带主站 JWT 换取 10 分钟有效、只读 QA 权限的短 ticket，Redis 存 `embed:{ticket}`）、`GET /api/v1/embed/chat?ticket=`（校验后放行子集接口：ask + 流式输出 + 历史三条）。前端新增独立入口（Vite 多页构建 `embed.html`，独立轻量组件，不含主布局，样式只依赖 markdown 渲染片段，复制 QAChatView 的只读精简版）；提供 `<iframe src="https://wiki/embed/chat?ticket=..." />` 与一个 ticket 生成小工具页面，门户管理员复制即用。SSO 对接留待方向 12 的 API Key 方式。
- **落地步骤**：第 1 周 ticket 签发/校验 + 精简问答接口；第 2 周 embed 独立页面与流式适配、iframe 自适应高度消息；第 3 周在 2 个真实场景（模拟监控大屏、工单页）内嵌演示 + 安全走查（ticket 泄漏吊销）；第 4 周使用统计与埋点。
- **实用价值**：排障发生在监控屏前而不是 wiki 首页——"在哪里遇问题，哪里就能问"，嵌入工单系统后提问与工单上下文天然结合，这是把知识库日活做起来的最短路径。
- **风险与备选方案**：ticket 安全边界是核心——只授权 QA 读接口、10 分钟过期、Redis 主动删除；iframe 跨域由 CORS 与同源限制兜底；若门户禁用 iframe，备选输出为站内"链接直达页"，降级但不失效。

### 方向12：QA 开放接口与 IM 群机器人接入

- **背景与痛点**：问答接口只服务本站 UI；运维同学问问题最多的场所其实是工作群。系统没有"对外 API 身份"——第三方想调要么裸奔要么借账号，不可控也不可计量。
- **创新点**：提供带配额与计量的开放 QA 接口，先落一个真实场景（飞书/钉钉群机器人），让"群聊里@机器人即问答"跑通，并把 key 维度用量（tokens_used 已在记录）变成可续费治理的资源。
- **方案设计**：新表 `api_keys`（key 哈希、名称、owner_id、quota_per_day、tokens_budget、status、created_at），签发/吊销接口（admin）；`/qa/ask` 开放通道：支持 `Authorization: Bearer <api_key>` 方式，Flask-Limiter（已依赖、已初始化，只是未配规则）按 key 加配额限制；每次调用把 key_id 写入 qa_records（加一列或复用 ip/audit）；飞书机器人适配层 `services/im_bot.py`：接收事件回调 → 调 QA 通道 → 回卡片消息（附来源标题链接），给出本地 ngrok/内网穿透调试说明。前端管理页"开放接口"：创建 key、用量曲线、吊销。
- **落地步骤**：第 1 周 api_keys 表 + 签发/校验/配额中间件；第 2 周机器人适配（先挑一个 IM，用 webhook 免费额度）与卡片消息；第 3 周管理页与用量统计；第 4 周安全走查（key 泄露吊销、限流压测）与调用文档。
- **实用价值**：群机器人让问答触达"从不去 wiki 的人"；对校内外做 demo 时，"接入你们自己的群"是最有说服力的展示；配额与计量是未来向其他团队"售卖知识问答能力"的最小计价模型（每个部门一个 key、按月用量报表）。
- **风险与备选方案**：IM 平台回调签名校验复杂且各有差异——MVP 只做飞书（签名验证代码最少），钉钉留 TODO；若平台风控严格，退化为"webhook 手动粘贴问答结果"的运维机器人模式，同样不引入付费服务。

## 七、推荐落地优先级（学生团队视角）

1. **方向 3（中文全文检索，1 周）**：零依赖、见效最快，是检索体验的立竿见影项，适合作为热身与团队磨合。
2. **方向 8（向量化异步化，2~3 周）**：工程价值最高且基础设施已备好（Celery/Redis/worker 全在 compose 里），做完后 4/6/7 的 AI 增强都能安心挂异步。
3. **方向 6（质量门卫与反馈闭环）**：让问答从"看起来能答"变成"知道自己不会什么"，配合方向 10 看板即是完整的演示叙事：AI 问答 + 知识缺口治理 + 数据运营。
