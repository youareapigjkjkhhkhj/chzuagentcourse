- ⚠️ **三条链路的线上编码互不相同**：TTS 与 ASR 是**二进制帧**，实时语音是**纯 JSON 文本帧（音频 Base64）**。三套编解码器各自封装在独立 Provider 内，**不抽公共基类、不共用解析函数**（TTS 的 payload 区比 ASR 多一层 `session_id` 长度前缀，照抄必错）

**动手前必读（六条容易踩的坑）**：

1. **两套音色池互相独立，不能混用**：
   - 实时对话音色（后缀 `_jupiter_bigtts`）**全平台只有 4 个**，端到端实时语音只能从这 4 个里选；
   - TTS 2.0 音色（后缀 `_uranus_bigtts`）90+ 个，只能用于大模型 TTS（资源 `seed-tts-2.0`）；
   - 选错池子直接报 `InvalidSpeaker`。**→ 6 个角色拿不到 6 个实时音色，这是硬约束，不是配置问题。**

2. **音频必须按实时节奏送，且不能断流**：上行 PCM 16k / int16 / 单声道，**20ms 一包 = 640 字节**，发送速率偏离实际节奏（过快或过慢）都触发服务端错误。模型依赖上行音频流保活 —— 麦克风关闭后若不再发帧，服务端会判超时（错误码 `52000042 DialogAudioIdleTimeoutError`）。
   **三种保活解法的优先级**（首日实测取生效者，详见 `技术实现方案.md` §5.3-B5）：
   | 优先级 | 机制 | 说明 |
   |---|---|---|
   | ① | `extension.dialog.extra.input_mod = "keep_alive"` | **官方错误码直接点名的解药**，声明式配置，代码最简 |
   | ② | `input_audio_mute.commit` / `input_audio_unmute.commit` | 3.0 协议上行事件，大概率与 ① 是同一机制的新旧表达 |
   | ③ | 持续发静音帧 `b"\x00" * 640` | 官方 Demo 的做法，能跑通但空占带宽配额，仅兜底 |

3. **打断事件不可省**：收到 `conversation.item.input_audio_transcription.started`（识别到首字）时**必须立即停播并清空本地缓冲** —— 这是「可打断」体验的实现点，不是可选优化。对应到火山是 `response.cancel`（上行）。

4. **关闭必须优雅**：先发 `session.close` 并**收到 `session.closed` 回执**再断开 WebSocket，直接断连触发 `ContextCanceled`（错误码 `55000001`）。建议等待超时 3 秒。

5. **会话可能被服务端主动释放，必须写重连**：**超过 10 分钟没有对话交互，服务端释放连接**（错误码 `45000003 Abnormal silence audio`）。一节课 45 分钟，学生长时间不提问是常态 —— 这不是异常分支，是**必然发生的正常路径**。`providers/tts/volc_realtime.py` 必须监听该错误并**自动按 `session.create` 重建会话**，对前端透明（字幕与播放队列不中断）。
   > 好消息：官方文档明确 WebSocket 连接**可复用** —— 会话结束后不必重连 WS，只需重发 `session.create` 即可恢复。这把重连成本压到很低。
   > ⚠️ 待实测：`keep_alive` 保活期间是否仍被计为"无交互"（决定保活心跳间隔与重连触发阈值）。

6. **TTS 必须显式关掉 Markdown 解析**：`additions.disable_markdown_filter` 默认为 `false`，此时 `**你好**` 会被**照念成"星星你好星星"** —— LLM 生成的讲稿带 markdown 是常态，不设这个参数课堂里就会出现"星星"。**这是必设项，不是优化项**（见 `技术实现方案.md` §5.3-A4）。
   > 顺带两个同族参数：`latex_parser: "v2"` 是官方为**教育场景**做的公式朗读，但启用会增加时延，且**必须同时 `disable_markdown_filter: true`** —— 建议按课程类型开关（数理化开，文史不开）。`max_length_to_filter_parenthesis: 30` 可让讲稿里的 `（停顿）` 一类标注不被朗读。

## 1. 阶段目标

一句话：**打开课堂演示页，AI 教师按讲稿逐句发声、字幕与语音同步；学生按住空格提问，教师用语音作答；教师说话时学生插话，教师 300ms 内停下。**

本阶段**只做语音链路**，不做多智能体讨论编排（那是 P3）。P2 结束时应能演示「单教师有声课堂」的完整闭环。

## 2. 关键设计决策

### 2.1 三条路径（A 与 B 必须都做，C 是降级与辅助）

| 路径 | 用途 | 技术 | 特点 | 文档状态 |
|------|------|------|------|---------|
| **路径 A：TTS 念稿**（默认，主） | AI 教师按已生成的 `narration` beat 逐句朗读 | 火山大模型 TTS 2.0（**双向流式** `/api/v3/tts/bidirection`） | 可预生成并缓存 → **零等待、零推理成本、可回放**；`enable_subtitle` 返回**字级时间戳**，字幕可逐字高亮 | ✅ 已核对 |
| **路径 B：实时语音对话**（按需） | 学生自由提问、AI 同学即兴发言、研讨辩论 | 豆包端到端实时语音 3.0 全双工（Speech-to-Speech） | 双向流式、低延迟、可打断；成本高，仅对话时开启 | ✅ 已核对 |
| **路径 C：流式 ASR**（降级 + 辅助） | ① B 不可用时的语音输入兜底；② 「按住说话」快捷提问，边说边上屏 | 大模型流式 ASR（`bigmodel_async`） | 只转文字，回答仍走 LLM + TTS；比 B 便宜、比 B 简单 | ✅ 已核对 |

**切换规则**：
- 课堂讲解 → A
- 学生举手提问 / 自由问答 / 研讨模式 → B（不可用时降级到 C）
- 实时语音未配置或连接失败 → **自动降级**为 A + 文字回答；若 ASR 可用，则走 C + LLM + TTS
- 全部不可用 → 纯文字 + 浏览器 `speechSynthesis`

**路径 B 的会话生命周期（据官方输入模式与保活机制确定）**：
一节课**只建一个实时语音会话**，全程复用，用 `input_mod` 声明当前处于哪种输入状态：

| 课堂状态 | `input_mod` | 行为 |
|---------|------------|------|
| 教师讲授 / 学生听讲（麦克风空闲） | `keep_alive` | 不上传音频，**服务端不会判音频流超时** |
| 学生按住空格提问 | `push_to_talk` | 推流；**服务端 VAD 被屏蔽**，由客户端发结束信号决定何时判停 |
| 学生用文字提问 / AI 同学点名发言 | `text` | 服务端自动补静音，链路与麦克风模式对齐 |
| 课程结束 | — | `session.close` → 等 `session.closed` → 再断 WS |

- 为什么不「一问一建」：每次 `session.create` 都要付建连与模型预热成本，且每次关闭都暴露在 `ContextCanceled` 风险下；官方专门为「暂时不说话但会话要留着」提供了 `keep_alive` 模式，**这个设计决策得到了官方 API 的正面印证**。
- **`push_to_talk` 是官方为「按住说话」量身定制的模式**（屏蔽服务端 VAD + 客户端控制判停），比用 `input_audio_buffer.commit` 去抢 VAD 更可靠，避免环境噪声导致误判停。
  > ⚠️ `input_mod` 出自旧版 S2S 协议，3.0 端点是否原样接受待首日实测；不生效则回退到 `input_audio_mute.commit` / `input_audio_buffer.commit` 组合（见动手前必读第 2 条）。
- 代价：会话期间持续占用并发时长配额（错误码 `ExceededConcurrentDurationLimit` 即此项）。课堂是连续场景，这个代价可接受；若未来要控成本，可加「静默 N 分钟自动收起会话」策略。
- 🔴 **但"持久会话"不等于"永不断线"**：10 分钟无交互会被服务端释放（`45000003`），**重连逻辑是必需品而非可选项**，见动手前必读第 5 条。

### 2.2 为什么不全用端到端实时语音

1. **成本**：端到端实时语音按会话时长计费，25 分钟课堂全程开启成本不可接受；讲稿是**已知文本**，用 TTS 更划算且音质可控。
2. **可控性**：讲稿预先合成后可缓存、可干跑、可反复回放，课堂体验稳定；实时生成每次结果不同。
3. **可测性**：TTS 产物是文件，可做验收；实时语音只能人工听。

### 2.3 音频数据流

```
路径 A（念稿）                                        —— 默认链路，文档已齐，可开工
  讲稿 beat ──► 火山 TTS 2.0(双向流式 WS，**二进制帧**) ──► mp3
                 └─► enable_subtitle 返回字级时间戳 ──► assets/audio/{courseId}/{beatId}.json
                 └─► 音频落盘 ──► assets/audio/{courseId}/{beatId}.mp3
                                        └─► 前端 <audio> 顺序播放 + 字幕逐字高亮

路径 B（实时对话，学生提问/研讨）                      —— 文档已齐，可开工
  浏览器麦克风 ─(PCM 16k, 20ms/640B)→ 前端 WS /ws/voice/realtime
       └→ Flask 代理 WS ─→ 火山实时语音（JSON 文本帧 + Base64）
  火山返回音频(Base64) ─→ Flask 转二进制帧 ─→ 前端 Web Audio 播放
                └─► 同时回传识别文本/回复文本 ─→ 课堂消息流 + 字幕

路径 C（ASR，降级 + 按住说话）                         —— 文档已齐，可开工
  浏览器麦克风 ─(PCM 16k, 200ms/包)→ 前端 WS ─→ Flask 代理
       └→ 火山流式 ASR（二进制私有帧，见 §5.3-C3）
  识别结果 ─→ 前端「边说边上屏」(fixed_prefix_result) ─→ 交 LLM 生成回答
```

**关键点**：
- Flask 端只做**帧中转 + 鉴权 + 事件旁路记录**，不做音频编解码以外的处理。但注意：**路径 B 的上游是 Base64 JSON、下游给浏览器是二进制帧，中间必然有一次编解码转换** —— 这次转换发生在 `providers/tts/volc_realtime.py` 内，是唯一允许的位置。
- **两条链路的音频分包规格不同**（B 是 20ms/640B，C 是 100~200ms），各自由自己的 Provider 负责，service 层不感知。
- 鉴权凭据只存在服务端，浏览器不直接持有火山密钥。

| F2-11 | 语音设置页真实化 | 音色卡片点击可**试听**（合成固定示例句），选中的音色全局生效 |

## 4. 接口设计

### 4.1 HTTP

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/voice/voices` | 可用音色列表：`{id, name, gender, style, provider, sampleUrl, builtin}` |
| POST | `/api/voice/voices/{id}/preview` | 试听：合成示例句返回 mp3 流（带缓存） |
| POST | `/api/voice/tts` | 单句合成：`{text, voiceId, speed, tone}` → 返回音频 URL 或流 |
| POST | `/api/courses/{id}/narrate` | 整课预合成：入队后台任务，可查询进度 |
| GET | `/api/courses/{id}/audio-manifest` | 音频清单：`{pageNo, beatId, textHash, url, durationMs}` —— 前端播放器的输入 |
| POST | `/api/voice/asr` | 上传音频（wav/webm）→ 返回文本（P2 兜底路径） |
| GET | `/api/voice/usage` | 用量：字符数 / 会话时长 / 估算费用 |

### 4.2 WebSocket

| 路径 | 方向 | 说明 |
|------|------|------|
| `/ws/voice/realtime` | 双向 | 与火山实时语音模型的双向音频通道（透传） |

客户端上行消息（JSON 文本帧，音频用二进制帧）：

```jsonc
{ "type": "start",  "sessionId": "s_…", "roleCode": "teacher", "voiceType": "<火山音色ID>",
  "mode": "voice_chat", "systemPrompt": "你是沈老师…", "context": { "courseId": "…", "pageNo": 7 } }
{ "type": "audio",  "seq": 12 }          // 随后跟二进制帧为 PCM 16k/int16/单声道，20ms/包
{ "type": "barge_in" }                    // 学生插话，请求模型停止当前输出
{ "type": "stop" }
```

服务端下行：

```jsonc
{ "type": "ready",   "sessionId": "…", "dialogId": "<火山 session.id>", "ttsFirstFrameMs": 820 }
{ "type": "asr",     "text": "老师，学习率为什么要衰减？", "final": true }
{ "type": "reply",   "text": "好问题……", "final": false }     // 逐句返回，供字幕用
{ "type": "audio",   "seq": 3 }                                // 随后跟二进制音频帧
{ "type": "barge_in_ack", "latencyMs": 210 }
{ "type": "error",   "code": "upstream_closed", "fallback": "tts_text_only" }
{ "type": "done",    "usage": { "durationMs": 12400, "asrChars": 22, "replyChars": 96 } }
```

**契约要点**：
- 二进制音频帧与 JSON 文本帧交替发送，用 `seq` 关联；前端必须按 `seq` 顺序播放。
- **两段链路的音频编码方式不同，这是刻意的**：
  - 浏览器 ↔ Flask：**二进制帧**（省 33% 体积、省前端编解码）；
  - Flask ↔ 火山：**纯 JSON 文本帧，音频 Base64 内嵌**（协议强制，音频不进独立二进制通道）。
  - 转换在 `providers/tts/volc_realtime.py` 一处完成，**上层与前端完全不感知**。这正是把协议细节收敛到 Provider 层的意义。
- 任何 `error` 事件都必须携带 `fallback` 字段告知前端降级策略，前端**不得**自行猜测。
- 以上是**本项目自定义的语义层**，与火山原生事件是映射关系而非等同 —— 前端不应出现任何火山事件名。映射表（对标 3.0 全双工事件名）：

  | 本项目消息 | 火山原生事件（3.0 全双工） | 说明 |
  |-----------|--------------------------|------|
  | `start` | `session.create` → 收 `session.created` | 建连即开会话，鉴权头 `X-Api-Key`；`model` 固定 `1.2.6.1` |
  | `stop` | `session.close` → **等 `session.closed`** → 再断 WS | 不等回执直接断连会触发 `ContextCanceled`(55000001) |
  | `audio`（二进制 → Base64） | `input_audio_buffer.append` 上行 / `response.output_audio.delta` 下行 | 上行 PCM 16k/int16 单声道 **20ms=640B，须按实时节奏**；下行**必须配 `pcm_s16le`**（`pcm` 是 32bit，浏览器播不了） |
  | `audio` 结束 | `input_audio_buffer.commit` | 松开按键 = 强制判停（`input_mod: "push_to_talk"` 生效时由客户端决定判停时机） |
  | （麦克风空闲保活） | `extension.dialog.extra.input_mod = "keep_alive"` **或** `input_audio_mute.commit` / `input_audio_unmute.commit` | **不按键时必须保活，否则报 `52000042` 音频流超时**；两种机制首日实测取生效者 |
  | `asr` | `conversation.item.input_audio_transcription.delta` / `.completed` | 中间结果 `final:false`，最终 `final:true`；`.started` 用于打断 |
  | `reply` | `response.output_text.delta` / `.done` | 用于字幕与课堂消息落库 |
  | `barge_in` | `response.cancel`（上行）；下行由 `...transcription.started` 自然触发 | 见下 |
  | `ready` | `session.created` | 同时保存 `session.id`（= `dialog.id`）供接续历史（服务端默认留 20 轮） |
  | `done` | `response.output_audio.done` + `response.done` | `response.done` 携带用量 → `usage_records`；`status_code="20000002"` 表示识别到退出意图 |
  | `error` | `error` 事件 | 必须映射为可读原因 + `fallback`；**4xx 停止重试，5xx 触发重连** |

- **打断的两种模式**：
  - 模式 1（本项目默认，按住空格说话）：会话以 `input_mod: "push_to_talk"` 建立，未按键时**不推流**（`keep_alive` 保活），按键才发 `input_audio_buffer.append`，松开发 `input_audio_buffer.commit` —— 逻辑简单、不会误触发、节省配额；**服务端 VAD 被屏蔽**，判停时机完全由客户端掌握；打断由学生松开后教师立即停播实现。
  - 模式 2（持续麦克风，研讨模式可选）：麦克风常开并持续推流，由服务端 `conversation.item.input_audio_transcription.started` 驱动打断 —— 体验更自然，但需处理回声与配额占用。
  - 两条路径的服务端接口一致，用 `mode` 参数切换，便于后续升级。（模式 2 在官方 demo 中已示范：`play_worker` 收到 started 即 `clear_queue(audio_queue)`）

## 6. 前端设计要点

- **播放器内核**：`useNarrationPlayer` composable 统一管理 beat 队列、当前 beat 索引、音频元素、播放速率、seek。路径 A 播放中、路径 B 触发时先暂停 A，结束后回到 A 的下一页。
- **字幕**：当前 beat 文本以打字机效果在字幕区高亮，`narration[i].estSec` 用于无音频时的节奏估算。
- **按住空格说话**：keydown 开始录音、keyup 结束并提交（松开即发送）；录音中界面显示波形与「松开发送」提示。**注意与播放器快捷键冲突**：编辑输入框中禁用该快捷键。
- **打断**：教师发声时学生按空格 → 立即发 `barge_in` → 本地立即压低/暂停教师音频（乐观 UI），收到 `barge_in_ack` 后确认。
- **降级提示**：实时语音不可用时，顶部显示黄色提示条「实时语音不可用，已切换为文字问答」，不弹错误弹窗打断课堂。

| P2-A10 | 倍速不变调 | 1.5x 播放时人声无明显变调失真（人工听辨 3 个音色） |
| P2-A11 | 用量可查 | 设置页显示本次课堂「TTS 字符数 / 实时语音时长 / 估算费用」，与 `usage_records` 求和一致 |
| P2-A12 | **麦克风空闲保活** | 建立实时会话（`input_mod: "keep_alive"`）后 60s 不按空格说话 → 会话仍存活，随后按空格提问能正常得到回答；日志中**不出现** `52000042 DialogAudioIdleTimeoutError` |
| P2-A13 | **优雅关闭不报错** | 会话结束时先发 `session.close` 并等到 `session.closed` 再断连 → 日志中**不出现** `ContextCanceled`(55000001)；对比：不等回执直接断连能在日志中复现该错误码（用于证明用例有效） |
| P2-A14 | **流式 ASR 边说边上屏** | 调 `/api/voice/asr`（或对应 WS）持续推流 8 秒语音 → 期间至少收到 3 次中间结果且文字**单调增长不回退**（用 `fixed_prefix_result` 校验）；松开后拿到 `definite:true` 的最终分句 |
| P2-A15 | **ASR 二进制帧编码正确** | 单测：构造 full client request 帧 → 断言 4 字节 header 各字段（version/header size/message type/flags/serialization/compression）与**大端** payload size 均符合 §5.3-C3 规格；对 audio only request 与「最后一包」（flags=`0b0010`）同样断言 |
| P2-A16 | **ASR 与实时语音的分包规格不串用** | 断言：实时语音上行单包恒为 640 字节（20ms）；ASR 上行单包为 100~200ms 对应字节数。两者由不同 Provider 产生，**service 层不得出现任何分包常量** |
| P2-A17 | **会话被释放后自动重建** | 用 Mock 让上游返回 `45000003 Abnormal silence audio` 并关闭会话 → `volc_realtime.py` 自动重发 `session.create` 重建会话 → **前端无感**（不弹错、字幕与播放队列不中断），随后提问仍正常作答。**这是必然发生的正常路径，不是异常分支** |
| P2-A18 | **按住说话用官方 `push_to_talk` 模式** | 会话以 `input_mod: "push_to_talk"` 建立，在环境噪声中按住空格说话 → 判停完全由松开按键触发（不因背景音被 VAD 提前截断），对照：不加该参数时噪声可导致提前判停 |
| P2-A19 | **Markdown 不被照念** | 合成讲稿 `**重点**：梯度下降` → 音频中**不出现"星星"二字**，只念"重点：梯度下降"。反向对照：关闭该参数时能复现"星星"（证明用例有效） |
| P2-A20 | **术语纠音生效** | 讲稿含多音字（如"卷积""重整化"）→ 配置 `pronunciation_dict` 后人工听辨读音正确；且**该术语表与 ASR 热词表来自同一份课程术语表**（同一数据源两处消费） |
| P2-A21 | **TTS 二进制帧编码正确** | 单测：① 帧头字节断言（`byte0=0x11`、`byte1` 高低位拆出 message type 与 flags、`byte2` 拆出序列化与压缩）；② 带事件号帧能正确解析出 `350`/`351`；③ **`TTSResponse` 无事件号帧**（flags 不含 `0b0100`）能正确跳过扩展字段直接读 `session_id` 长度；④ 造一个 gzip 压缩帧，断言解压后再解析成功；⑤ 所有长度字段按**大端**读 |
| P2-A22 | **TTS 与 ASR 编解码器不通用** | 断言：拿 ASR 的真实响应帧喂给 TTS 解析器**必须抛异常**（反之亦然）—— 用于防止后续重构时"顺手抽公共基类"把两套协议混在一起 |

| ~~TTS 接口文档缺失~~ | — | **已解除**：`/api/v3/tts/bidirection` 双向流式，`X-Api-Key` 单头，`req_params` 全字段已核对，见 `技术实现方案.md` §5.3-A |
| ~~TTS 帧编码格式未确证~~ | — | **已解除**：V3 二进制帧规范已确认（4 字节帧头 + 可选 4 字节事件号 + `session_id` 长度前缀 + payload；`TTSSentenceStart=350`、`TTSSentenceEnd=351`），见 `技术实现方案.md` §5.3-A7 |

| **三条链路线上编码互不相同**（TTS/ASR 二进制帧 vs 实时语音 JSON+Base64） | 误把编解码器写成通用件 | 三套编解码器**各自封装在独立 Provider 内**，不抽公共基类、不共用解析函数。TTS 的 payload 区比 ASR **多一层 `session_id` 长度前缀**，照抄 ASR 解析器必错。验收 P2-A16 / P2-A21 |
| 讲稿含 Markdown 被照念出"星星" | 课堂质量事故 | `additions.disable_markdown_filter=true` **必设**；写进 Provider 默认参数，不给调用方关闭的机会 |
| **会话超 10 分钟无交互被服务端释放**（`45000003`） | 课上学生提问突然无响应，演示事故 | **不是异常分支而是必然路径**：`volc_realtime.py` 内实现在线重建会话（WS 连接可复用，只需重发 `session.create`）；验收 P2-A17 必须通过 |
| `input_mod` 保活机制在 3.0 端点是否生效未确证 | 麦克风空闲时易报 `52000042` | 首日实测 `keep_alive` vs `input_audio_mute.commit`，取生效者；官方 Demo 的静音帧方式作兜底 |
| 两套音频分包规格不同（实时语音 20ms/640B，ASR 100~200ms） | 分片逻辑写错导致服务端报错 | 在 `providers/` 层各自实现，**不得在 service 层统一**；两边都写单包字节数断言 |
| 上行音频节奏偏离（过快/过慢）触发服务端错误 | 会话不可用 | 发送端用固定 20ms 定时器驱动（非「尽快发送」循环）；开发期加断言：单包必须为 640 字节 |
| 端到端实时语音延迟不达 2s | 体验差 | 优先就近接入区域；音频用 PCM 直传不转码；必要时降级为「ASR + TTS」两步式 |
| 音色 ID 变更或下线 | 演示中断 | `voice_profiles` 存 ID + 名称，启动时校验可用性；不可用时回退到内置默认音色并告警 |
| 库里内置音色行的 ID 与 `.env` 对不上（先 seed 后改配置） | 设置页三张卡片全「未配声音 ID」，合成悄悄降级 | **已消除**：`seed` 对 builtin 行改为**按 config 刷新**（ID/展示字段以当前 `.env` 为准），非 builtin 行维持只补缺 —— 内置行唯一的事实来源就是配置，用户自己建的行不碰。改了 `.env` 里的音色 ID 要重跑 `flask seed` **并重启后端**（provider 在启动时读一次配置） |
| 浏览器自动播放策略 | 无声 | 首次进入课堂需用户点击「开始上课」手势解锁音频上下文（必须显式实现） |
| 回声/啸叫（麦克风采集到扬声器） | 无法对话 | 默认启用 `echoCancellation: true` + `noiseSuppression`；教师发声时暂停 ASR 采集（半双工），端到端模式依赖模型内建打断能力 |

### 10.2 有意差异与已知缺口（保留）

| 条目 | 规格怎么写 | 我们怎么做 | 为什么 |
|------|-----------|-----------|--------|
| P2-A9 后半句「提问仍能得到**文字**回答」 | 降级后接着提问，文字作答 | 降级提示、课照常上、页面照常读，**文字作答那一步留给 P3** | 课堂里的文字问答是 P3 运行时（多智能体）的职责，`ClassroomView` 上就写着「文字提问也由它作答」。P2 这一轮把它验到「路是通的」为止，不越界造一个假的作答 |
| P2-F3 的「课堂录音」开关 | 默认不落盘，**除非开启开关**；开启时路径与保留期在设置页明示 | 只做了默认那一半（含「实时语音的音频不落盘」那条断言）；开关没做 | 开关不是一个按钮：一开就要连带设计落盘路径、保留期、设置页文案与清理策略（§8 的隐私口径）。没有需求就先不引入一个会默默录下学生的开关 |
| P2-C2 的「删除课程」 | 删课即清理音频 | `DELETE /api/courses/{id}` 是**软删**（置 `deleted_at`），故意把页面与音频都留着；真删是 `store.purge_course` | P1 §4 的口径：用户的手滑要能撤回。验收因此直接驱动那个函数，并且把「软删之后库和盘都还在」也钉成了一条断言 —— 免得哪天有人把软删改成真删，学生点一下「删除」就把花了钱的音频丢了 |
| P2-B2 的「返回 40201」 | 返回 `40201` 且带 `fallback` | 业务码 40201，**HTTP 状态是 400** | P0-B3 定的：4xxxx 段表示「去设置页补一下就好」，不是服务端故障（不是 402 —— 这里没有要付钱的东西）。验收按业务码判，只额外要求它落在 4xx |
| P2-F4 的「未带票据拒绝（4401）」 | WS 关闭码 4401 | **HTTP 401 + 40101**，客户端连 `101` 都见不着 | 票据在 `Server.accept()` **之前**校验：没票的握手根本没升级成 WebSocket，自然没有 WS 关闭码可发。这比 4401 更靠前一步，不是打了个折扣 |
| P2-F5 的「单用户并发上限 1，重复 start 返回 42901」 | 重复 `start` 返回 `42901` | 名额认的是**归属人**（`X-Owner-Id`，与 HTTP 一路同源），不是连接：同一个人**第二条通道**的 `start` 得 `42901` + `fallback=text`；同一条通道上重复 `start` 是**幂等忽略**（那条通道本来就只有一个会话） | 「两条实时语音」的现实样子是一个浏览器开了两个标签页 —— 那正是两条连接，所以键只能取人。占用凭据由服务端生成，不取前端给的 `sessionId`：那个值客户端说了算，两条连接报同一个号就都算「同一次会话」，上限形同虚设 |
| P2-A6 的重合成时机 | 该页 beat 标记 `stale` 并自动重合成 | 标记随那次改动同步做完，重合成**排进后台任务**，而且只带这一页 | 一页也是十几秒的活，不能卡在「保存讲稿」那次请求里（所以是后台）。只带 `page_no`：别的页按内容哈希命中缓存，一句都不会白合。这一步失败只记日志 —— 语音是课程的**下游**，改讲稿不该因为标记音频出错而失败；真出错最坏也只是这一页留着旧音频，下一次预合成会按哈希判出来 |
| 字级时间戳（A3） | 用 TTS 返回的字级时间戳驱动逐字高亮 | 数据结构与解析都有（`subtitles`），但**离线替身不给时间戳** → 前端退回整句切换 | ≤150ms 那条要真上游才量得出来；离线这一半验的是「48 句都带 url/时长/文本/状态」 |
| ASR 上传格式闸门 | — | 格式白名单在**接口层**（`UPLOAD_FORMATS`），不在 Provider | 上游要的是 PCM，浏览器给的是 webm/ogg；转码在 service 层做，Provider 只管「推给上游的那串字节」。MockASR 的时长是按字节估的，不代表真识别的时长 |

### 10.3 接真 Key 那天撞出来的两件事（2026-09-13）

试听、课堂语音提问、实时语音三条路一起报「服务器内部错误」（业务码 50001）。
拆开看是两件独立的事叠在一起：一件在账号侧，一件在我们这边。

**一、账号侧：这把 Key 只开通了实时语音大模型。** 把 WS 升级请求当普通 HTTP
发出去（握手失败的原因只在响应体里，协议层只留下一个状态码），四组资源 ID
逐个撞：

| 服务 | 上游地址（`/api` 之后） | 试过的资源 ID | 结果 |
|------|------------------------|--------------|------|
| 流式语音识别 | `/v3/sauc/bigmodel_async` | `volc.seedasr.sauc.duration`、`volc.seedasr.sauc.concurrent`、`volc.bigasr.sauc.duration`、`volc.bigasr.sauc.concurrent` | 全部 403 `requested resource not granted` |
| 语音合成 | `/v3/tts/bidirection` | `seed-tts-2.0`（→`volc.seedtts.default`）、`seed-tts-1.0`（→`volc.service_type.10029`） | 全部 403 同上 |
| 端到端实时语音 | `/v3/duplex/realtime/dialogue` | 不需要资源头 | **通**：握手 101，`session.created` 回执正常，`ttsFirstFrameMs` 500ms |

网关会**原样回显**我们发的资源 ID（发个假值也能在报错里看到它），所以这不是
「ID 写错了」，是账号没开通那两项服务 —— 语音合成大模型与流式语音识别大模型
是**两项独立服务**，要各自在火山控制台开通。开通之前，设置页试听给 50201 与
那句提示，课堂语音提问退到文字（`fallback`），实时语音那条路不受影响。

**二、我们这边：上游握手失败被当成了「我们崩了」。** `simple_websocket` 握手
被拒时抛的是**它自带的** `ConnectionError`，而它继承 `SimpleWebsocketError
(RuntimeError)` —— 跟内建 `ConnectionError`（`OSError` 的子类）没有亲缘关系。
`transport.default_connector` 当初写的正是 `except ConnectionError`：接不住，
异常从连接层一路漏到路由层，被 Flask 兜成 500「服务器内部错误」。用户拿到的
是一句无从下手的话，而真因是上游一句「resource not granted」。现在按库自己的
类接住，并按状态码补一句可排障的提示（401 凭据 / 403 开通 / 404 地址），
业务码 50201、HTTP 502；`wsproto` 的 `ProtocolError`（网关插了一页 HTML 那种）
同样接住。顺手订正一处**说错了的注释**：上游的响应体拿不到 —— 握手的拒绝在
协议层是个 `RejectConnection` 事件，wsproto 只留状态码与响应头，所以提示只能
按状态码写，别指望透出上游文案。回归钉在
`tests/unit/test_provider_transport.py`（不联网，全程 monkeypatch 连接入口）。

### 10.4 服务开通之后：三条路各自还差什么（2026-09-13 晚）

控制台把「录音文件识别 2.0 / 语音合成 2.0 / 端到端实时语音」都开通之后，三条路
仍然各有毛病。**都不是账号问题了**，是 §10.3 那两件事之外、被 403 挡在后面没
机会暴露的代码问题。逐条记结论与实拍口径，省得下次再从字节流反推。

**一、TTS（`/v3/tts/bidirection`）——通了，出的是真 mp3。**

- **错误帧的排布和响应帧不同**：`头 + 错误码(4B) + 载荷长度 + 载荷`，**没有事件
  号、没有 session_id**。按响应帧的布局去读，错误码会被当成 id 长度，报出来的是
  `session_id 长度不合理：45000000` 这种谁也看不懂的话（上游真正想说的是
  `sequence mismatch`）。
- **连接类回执（50/51/52）里那段 id 是 connect_id，不是 session_id**；只有会话类
  事件才带 session_id。官方示例里 `_read_session_id` 跳过这三个事件、
  `_read_connect_id` 专读它们，就是这个原因。
- 握手之后：`StartConnection` → 等 50；`StartSession` → 等 150；`TaskRequest` 之后
  **必须立刻发 `FinishSession`**，否则尾音与 351（字级时间戳）不会回来，而且
  没读完的帧会**毒化同一条连接上的下一次会话**。读到 152 才算一次会话结束。
- **`enable_subtitle` 属于 `audio_params`**，不是 `req_params` 的同级键。写错位置
  **不报错**，只是字级时间戳永远为空 —— 我们因此白排查了一轮「为什么没有字幕」。

**二、流式 ASR（`/v3/sauc/bigmodel_async`）——通了，真机识别出完整句子。**

- **资源 ID 用 `volc.seedasr.auc`**（录音文件识别 2.0 那个），不是文档写的
  `volc.seedasr.sauc.duration`：后者在这把 Key 上仍 403 `requested resource not
  granted`，而 `auc` 能服务这个端点（握手 101 + 完整协议往返）。判定依据见 §10.3
  那张表 —— 网关会原样回显资源 ID，所以报错里的值可信。
- **末包的序号必须取负**（写几就写几的相反数）。写正数上游当场回
  `autoAssignedSequence (-7) mismatch sequence in request (7)` 并掐连接。
  取负这件事放在构造器里做：忘了必错，且错得很难懂。
- **「会话已建立」那一帧的 flags 是 `0b0000`**（不带序号），载荷只有
  `{"result":{"additions":{"log_id":...}}}`。把它当非法帧拒掉，表现是「上游明明
  回话了，我们却说这不是 ASR 帧」。
- **响应信封和文档不一致**：实拍是 `{"audio_info": ..., "result": {"text": ...,
  "utterances": [...]}}` —— `result` 直接挂顶层，**没有 `payload_msg` 那一层**。
  只认文档那版的后果不是报错，是**静默返回空文本**（帧解析得好好的、业务码是 0，
  就是取不到字）。
- **`result_type` 用 `full`（默认值），不要用 `single`**。上游会把**已经出过的字
  回改**：实拍里 `同学们。` 的下一帧是 `同学们好。`。用 `single`（不返回之前分句）
  配上这个行为，累计逻辑就得去猜「这帧是新句子还是同一句的修订」，猜错就出现
  「同学们。同学们好。」。用 `full` 则每帧就是「到目前为止的整段转写」，
  累计 = 整段替换，规则只有一条。
- 错误帧布局与 TTS 那边**一样**（错误码 + 载荷，无序号）—— 两条链路共用同一套
  V3 帧壳，不是巧合。

**三、端到端实时语音（`/v3/duplex/realtime/dialogue`）——通了，回字幕也回语音。**

- **`session.model` 是必填**，缺了整个 `session.create` 不被受理。值取官方 demo
  （`项目文档/材料/python3.7_duplex_demo/config.toml`）的 `1.2.6.1`，落到
  `VOLC_REALTIME_MODEL`。
- **下行增量事件的字段名是 `delta`**，不是 `text`；只有 `.completed` / `.done`
  才给 `text`。**音频下行也是 `delta`**（和上行 `input_audio_buffer.append` 的
  `audio` 不对称）。只读 `text` 的表现是「事件一直来、字幕全空白、一个音频字节
  都收不到」—— 真机踩过，两个处理器一起改。
- **不要发 `input_audio_buffer.commit`**。官方 demo 从头到尾不发，它只是按 20ms
  的节奏持续推流（语音之后接着推静音），由服务端的 VAD 判停。我们先前「推一段
  就 commit」的写法，服务端**不回话**；改成持续推流之后，开场白、识别、字幕、
  语音四样全到齐（实测一轮：`barge_in` → 3 条 `asr` → 8 条 `reply` → 8 段音频
  共约 133KB → `done` + `usage`）。
