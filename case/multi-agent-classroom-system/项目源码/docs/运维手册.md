# EduAgentX 运维手册

给人看的日常手册：怎么启停、数据在哪、怎么备份和恢复、日志怎么查、
钱花在哪、出事从哪下手。部署姿势见 [部署文档](部署文档.md)。

一条贯穿全篇的事实：**这台机器的全部状态就是 `backend/data/` 这一个目录**。
库里只存相对路径，材料/音频/产物都在这棵树里 —— 所以「迁移」「备份」「清空重来」
这三件事的最小单位都是它。见 §2。

---

## 1. 日常操作

容器那档：

```bash
make ps                 # 容器状态 + 健康检查
make logs               # 跟 app 日志（等价 docker compose logs -f --tail=100 app）
make down               # 停掉（数据不动）
make up                 # 起来（改过 .env 后也用它：重建容器才会读新配置）

docker compose restart app                    # 只重启，不重建
docker compose exec -T app flask providers    # 进容器跑后端 CLI
```

物理机那档：`systemctl restart eduagentx` / `journalctl -u eduagentx -f`。

**改配置的三种代价**，别搞混：

| 改了什么 | 要做什么 | 为什么 |
|---------|---------|--------|
| `.env`（供应商、端口、访问码…） | 重启 | 配置在启动时读一次 |
| 前端源码 | `make build` 再重启 | 后端托管的是构建产物，读的是 `dist/` |
| 后端源码 | 重建/重启 | 没有热重载（`APP_ENV=production`） |

设置页里改的东西（服务商、音色、生成参数、预算）**不走重启** —— 那些改的是数据库。

## 2. 数据目录

```
backend/data/
├── eduagentx.db              # SQLite（WAL 模式，同目录会有 -wal / -shm 边车文件）
├── uploads/                  # 用户上传的原始文件（课件附件）
├── materials/                # 解析后的材料（切片/向量/中间产物）
├── audio/                    # 合成出来的语音（默认只在用到时才落）
├── exports/                  # 导出产物（PPTX / HTML / PDF），到期即删
└── backups/                  # 备份归档（BACKUP_DIR，默认保留 7 份）
```

三个目录可以通过 `UPLOAD_DIR` / `MATERIAL_DIR` / `AUDIO_DIR` / `EXPORT_DIR` /
`BACKUP_DIR` 挪到别的盘；`DATABASE_URL` 挪库。**挪哪个都要记得它也在备份范围里** ——
备份只认「配置里那五个路径」，不认「我以为它在哪」。

体积的第一个来源是 `audio/` 和 `exports/`；`exports/` 有自动清理（§4），
`audio/` 没有 —— 它是教学资产，删了就没了，要腾空间先看这里再决定。

## 3. 备份与恢复

别用 `cp data/eduagentx.db`。SQLite 在 WAL 下直接拷贝会拿到一个**看起来正常、
其实少一截**的文件，而这正是备份最不该有的一种失败方式：它不报错。
后端的备份命令走的是 SQLite 的在线备份 API，取一致快照：

```bash
make backup                                   # 容器在跑也能跑，不需要停机
cd backend && .venv/bin/python -m flask --app "app:create_app()" backup
docker compose exec -u app -T app flask backup    # 在容器里打（文件属主是 app）
```

归档里是：DB 快照 + `uploads/` `materials/` `audio/` `exports/` 四棵逻辑目录 + `manifest.json`。
**写的是逻辑名**，所以换机器、换挂载路径也恢复得回去 —— 恢复时按**当前配置**的路径落盘。

保留策略：打完自动删旧归档，只留最近 `BACKUP_KEEP`（默认 7）份。

### 恢复

```bash
make restore FILE=backend/data/backups/backup-20260913-030000.tar.gz          # 只打印预告
make restore FILE=... ARGS=--yes                                             # 真的恢复
```

不带 `--yes` 时它**只打印计划**（会覆盖哪些文件、多少个），这是刻意的：
恢复是这套系统里唯一会覆盖用户数据的动作。

带 `--yes` 时它的顺序是：

1. 先读归档里的 DB 快照，跑一遍 `PRAGMA integrity_check` —— **验不过就什么都不写**。
   备份的全部意义是「以后还读得回来」，而这是唯一能当场回答这个问题的一步；
2. 把现有 DB 原样复制一份成 `eduagentx.pre-restore-<时间戳>.db` 留在原地
   （不是 `rename`：Windows 上正被打开的库改不了名，而这个文件必须在原地留着）；
3. 删掉旧的 `-wal` / `-shm` 边车文件 —— 留着它们等于让新库去接旧库的 WAL；
4. 按逻辑名把四棵目录写回去。

第 2 步那份 `pre-restore-*.db` 是**你最后一道保险**，恢复完确认没问题了再手工删。

**恢复后要重启服务**：进程里还握着旧库的连接，不重启就会看到「恢复完了但页面还是老的」。

### 演练

恢复流程**必须练过**，否则它只是一段没跑过的代码。练法（不动生产数据）：
另找一台机器或一个空目录，把归档拷过去，用环境变量把五个路径都指向那个空目录，
再 `flask restore <归档> --yes`，然后开页面看课程在不在。

季度做一次就够。真正要防的不是「备份文件坏了」，而是「我们以为它能恢复」。

## 4. 导出产物的清理（P5-C1）

产物是**到期即删**：默认 `EXPORT_TTL_HOURS=24`，到期后文件与记录一起清掉
（下载链接本身更短命 —— 一次性票据 600 秒失效，见 §8）。不做这件事，`data/exports/`
只会一直涨。

```bash
make clean-exports
docker compose exec -T app flask exports-cleanup
```

容器那档 `entrypoint.sh` 已经挂了一条每小时的循环，不用再配。物理机那档要自己挂 cron：

```cron
0 * * * * cd /srv/eduagentx/项目源码 && make clean-exports
17 3 * * * cd /srv/eduagentx/项目源码 && make backup
```

清理是**幂等**的，多跑几次没关系；它顺手还会收掉上传中断留下的临时文件。

## 5. 日志

默认只出 stdout/stderr，由容器运行时/journlad 收 —— 容器里建议就用这个：

```bash
docker compose logs -f --tail=200 app      # 跟着看
docker compose logs --since 30m app | grep -i error
journalctl -u eduagentx -f --since "30 min ago"
```

要落文件（物理机那档常见）就在 `.env` 里开：

```bash
LOG_FILE=/var/log/eduagentx/app.log
LOG_MAX_BYTES=52428800      # 50MB
LOG_BACKUP_COUNT=5
```

轮转是**按大小**自动做的，不需要 logrotate。写不进去时它只警告、不会让服务起不来 ——
日志记不下不该是一个服务停摆的理由。

**脱敏**（AGENTS §24）：日志里不会有 API Key 原文（异常栈里也不会）、完整提示词、
材料正文、音频帧。想确认自己加的日志是否漏了东西，看
`app/common/logging.py` 里的 `RedactingFilter`。

**按 requestId 串一次请求**：响应体里有 `requestId`，前端每请求也带 `X-Request-Id`。
出问题时让用户把那个 id 给你，日志里一搜就是整条链路：

```bash
docker compose logs app | grep <requestId>
```

注意 `gunicorn.conf.py` 里自定义的访问日志格式**去掉了查询串**：一次性下载票据就在
查询串里，而对拿到日志的人来说那张票就是钥匙。要排「谁在什么时候打了哪个接口」不受影响。

## 6. 审计日志

`audit_logs` 表记的是**会让状态改变的动作**，一共六类：

| action | 什么时候写 | target / detail |
|--------|-----------|-----------------|
| `course.create` | 生成任务入队 | 标题、jobId、页数 |
| `course.delete` | 删课程 | `course:<id>` / 标题 |
| `provider.update` | 改服务商配置 | **只记改了哪几个字段名**（值里含 Key） |
| `provider.enable` | 启用/停用服务商 | 服务商名 |
| `export.create` | 创建导出 | courseId / 格式 / 范围 |
| `access.grant` | 访问码验证通过 | 站点 |

查最近的动作：

```bash
cd backend && .venv/bin/python -c "
import sqlite3, json
c = sqlite3.connect('data/eduagentx.db'); c.row_factory = sqlite3.Row
for r in c.execute('select created_at, action, target, owner_id, ip, ua, detail from audit_logs order by id desc limit 20'):
    print(dict(r))
"
```

四条要知道的：

- **IP 是从哪来的**：默认取 `request.remote_addr`。只有在反代后面、且
  `AUDIT_TRUST_PROXY=true` 时才去读 `X-Forwarded-For` —— 那个头是调用方自己填的，
  直连暴露端口时开了它，等于让写日志的人自己填 IP；
- **输错访问码不落库**，只写一行日志（防爆破的写放大）；成功才记 `access.grant`；
- **审计写失败不会影响业务**：失败只写日志，不让这次请求跟着 500。
  代价是「审计可能缺行」，所以别把它当作账本用；
- **detail 里不写提示词、材料正文、材料摘录、Key 的取值**（AGENTS §19）。加新动作时
  照这条办：写「谁在什么时候对什么做了什么」，不写内容。

审计表同样**只增不减**，涨得慢（一行一个动作），常年不清理也没事。真要归档，
先备份再 `delete ... where created_at < ?`。

## 7. 成本与用量

- 每次模型调用都会落一行 `model_calls`（token、耗时、归属人、课程、用途），
  用量看板读的是按天聚合的 `daily_usage` 缓存。
- **缓存可能是旧的**：午夜之后才写完的那笔账会落在昨天，而昨天的缓存前一天就生成好了。
  看板数字对不上时先重算：

```bash
docker compose exec -T app flask usage-refresh                    # 最近两天
docker compose exec -T app flask usage-refresh --day 2026-09-12  # 指定某天
docker compose exec -T app flask usage-refresh --owner user_demo_teacher
```

- **预算**（设置页 → 预算，或 `GET/PUT /api/settings/budget`）：按 `global` / `course` /
  `day` / `month` 设上限，超限后**新任务直接被拒**（老任务不受影响），到告警比例
  （`alert_ratio`，默认 0.8）时页面提示。改了模型价格要同步改定价表，
  否则看板的金额是拿旧价算的。

## 8. 安全巡检

| 项 | 怎么查 | 期望 |
|----|--------|------|
| 进程不是 root | `docker compose exec -T app id` | `uid=10001(app)` |
| `.env` 没进镜像 | `docker history --no-trunc eduagentx:latest \| grep -i "env\|secret"` | 无输出 |
| 库里没有明文 Key | `grep -a -c "sk-" backend/data/eduagentx.db` | `0` |
| 依赖漏洞 | `make deps-audit`（**要联网**） | 无 high/critical 未处理项 |
| 访问码 | 见部署文档 §2 | 公网/局域网必开 |
| SSRF | 设置页填一个内网地址的自定义 `base_url` | 被拒 |
| 审计 IP | 反代档下看 `audit_logs.ip` | 是真实客户端 IP，不是 `127.0.0.1` |

`make deps-audit` 的两个坑写在 Makefile 里了：npm 的漏洞库接口只在**官方 registry**
上有（配了镜像源时要显式 `--registry=https://registry.npmjs.org`，否则报
`[NOT_IMPLEMENTED]`，看着像错，其实是源没实现）；`pip-audit` 要自己装
（它是运维工具，不在 `requirements.txt` 里）。

本仓库实测（2026-09-13）：前端 `npm audit --audit-level=high` 为
**2 moderate / 0 high / 0 critical**，两条都在 `@vitest/mocker`（仅开发依赖，
修它要跨 vitest 大版本，暂不处理）。后端 `pip-audit` 那一半**还没跑过** ——
开发这套代码的机器装不上 `pip-audit`（源里没有这个包），所以它只留了命令。
第一次部署时请自己跑一遍，把结果记在这里。

一次性下载链接（票据）**600 秒失效、用过即废**，且不进任何访问日志。产物本身 24 小时
到期删除。所以「把链接发给别人」这件事的窗口很短，超时让他重新点导出。

## 9. 故障排查

### 容器起不来 / unhealthy

```bash
docker compose logs --tail=100 app       # 先看这个，八成有答案
docker compose exec -T app id            # 起得来的话
```

entrypoint 是 `set -e` 的，停在哪一步日志里那一句就是原因。最常见的是**迁移失败**
（跑的是哪个库、有没有写权限）与**挂载目录不可写**。

### 页面打得开，接口全 500

先看有没有「数据库 is locked」：SQLite 是单写者，多进程写同一个库会互相等。
**确认没有起第二个实例**（`docker compose ps` 只该有一个 app；物理机上 `ps aux | grep gunicorn`）。
`workers` 必须保持 1（理由写在 `gunicorn.conf.py` 开头）。

### 生成进度条不动 / 一会儿就断

- 走了 nginx → 检查 SSE 那一段有没有 `proxy_buffering off` 与足够长的
  `proxy_read_timeout`（`docker/nginx.conf` 里第 1 段）；
- 没走 nginx → 看应用日志里还有没有事件在发。心跳是 15s 一次，日志里看不到心跳
  就说明 worker 卡住了，`docker compose restart app` 之后再看 §7 的用量有没有异常。

### 课堂里说话没声 / 举手没反应

WebSocket 没连上。浏览器控制台的 `ws://` 那条连接会直接告诉你原因；
走 nginx 时是 Upgrade 头没转发或者超时太短（`docker/nginx.conf` 第 2 段）。
另外确认 5000 端口这条链路上没有别的反代把 `Connection` 头吃掉了。

### 磁盘满

按顺序看：`exports/`（该被自动清理，没清就是定时任务没了）、`audio/`（教学资产，
别盲删）、`backups/`（`BACKUP_KEEP` 调小或挪到别的盘）、日志文件。
`docker system df` 里镜像层也会占一两个 G，`docker image prune` 能回收旧层。

### 恢复之后数字不对 / 页面还是旧的

**重启服务**。进程握着旧库的连接，不重启看到的就是恢复前的状态。

### 怎么确认「现在这套是好的」

```bash
cd 项目源码 && python scripts/accept_p0.py     # 会自己起服务、跑完关掉、不改你的数据
```

它跑的是跟开发态同一套接口。生产上更该看的是 §10 的那几条业务动作。

## 10. 日常该盯什么

- **每天**：`docker compose ps` 是否 healthy；磁盘余量；
- **每周**：`make backup` 有没有真在跑（看 `data/backups/` 里最新那份的时间）；
  导出产物目录在不在正常涨落（只涨不落 = 清理没跑）；
- **每月**：`make deps-audit`；用量看板对一遍账；
- **每季度**：**恢复演练**（§3）；`audit_logs` 翻一翻有没有不该出现的动作。
