# Ragent AI 开发规范

## 1. 核心原则

Ragent 是面向 Agentic RAG 演进的生产级 Java AI 应用平台。

开发必须遵循以下优先级：

1. **正确性**
2. **安全性**
3. **简单可读**
4. **职责清晰**
5. **最小修改**
6. **复用已有能力**
7. **必要时再抽象**
8. **避免过度设计**

核心原则：

> 能简单解决的问题，不要复杂化。

> 能修改已有模块，不要无意义地创建新模块。

> 能复用已有代码，不要重复实现。

> 当前需求不需要的能力，不要提前实现。

---

# 2. 开发前必须先理解项目

涉及代码修改时，必须先进行项目侦察，不允许直接开始写代码。

至少完成：

1. 查看项目目录结构。
2. 定位与需求相关的模块。
3. 阅读相关代码。
4. 理解现有模块之间的调用关系。
5. 判断功能应该属于哪个已有模块。
6. 确定最小修改范围。
7. 检查是否已经存在可复用的函数、服务、组件或类型。
8. 再开始修改。

如果无法判断现有架构，应优先阅读代码，而不是直接创建新的抽象。

---

# 3. 架构原则

Ragent 当前采用：

```text
Ragent AI
├── framework          # 通用基础设施
│   ├── 统一响应与异常
│   ├── 认证上下文
│   ├── 幂等控制
│   ├── 分布式 ID
│   ├── MQ 适配
│   ├── Trace
│   └── SSE 与跨节点流式取消
│
├── infra-ai           # AI 基础设施
│   ├── ChatClient
│   ├── EmbeddingClient
│   ├── RerankClient
│   ├── 模型档位
│   ├── 路由
│   ├── 首包探测
│   └── 健康状态与降级
│
├── system             # 系统支撑域
│   ├── 用户认证
│   └── 审计日志
│
├── rag                # RAG 核心业务
│   ├── 问答链路
│   ├── 知识库管理
│   ├── 入库 Pipeline
│   ├── 意图树
│   ├── 检索通道
│   ├── 会话管理
│   └── 管理端 API
│
├── agent              # Agent 执行架构
│   ├── ReAct 骨架
│   └── 工具调用
│
├── bootstrap          # 启动装配层
│   ├── 启动类
│   └── 主配置
│
└── mcp-server         # MCP 工具服务
    ├── 天气查询
    ├── 票务查询
    ├── 销售数据
    └── 联网搜索
```

必须保持以下边界：

### framework

负责：

- 统一响应封装
- 全局异常处理
- 认证上下文透传
- 幂等控制
- 分布式 ID
- MQ 适配
- Trace
- SSE 与跨节点流式取消

不要在 framework 中实现：

- 具体业务逻辑
- AI 模型调用
- RAG 检索
- MCP 工具

---

### infra-ai

负责：

- Chat / Embedding / Rerank / VLM 模型客户端
- 模型档位管理
- 模型路由
- 首包探测
- 健康状态检查
- 熔断降级

不要在 infra-ai 中实现：

- 具体业务逻辑
- RAG 检索策略
- 会话管理

---

### rag

负责：

- RAG 问答链路
- 知识库 CRUD
- 文档解析与分块
- 入库 Pipeline
- 意图识别
- 检索通道管理
- 会话管理
- 管理端 API

不要在 rag 中实现：

- 模型客户端细节
- 通用基础设施
- Agent 执行逻辑

---

### agent

负责：

- Agent 执行架构（v2 ReAct）
- 工具调用抽象
- 执行上下文管理

不要在 agent 中实现：

- 具体工具实现
- 检索逻辑
- 会话管理

---

# 4. 模块边界

## 模块间依赖

```text
bootstrap
    ↓
agent → rag → infra-ai → framework
    ↓
system → framework
    ↓
mcp-server（独立）
```

必须保持：

- 下层模块不能依赖上层模块
- 同层模块之间尽量避免循环依赖
- 新增依赖必须有明确理由

---

## 接口隔离

模块对外暴露接口，内部实现隐藏。

例如：

```java
// rag 模块对外暴露
public interface SearchChannel {
    List<SearchResult> search(SearchRequest request);
}

// 具体实现隐藏在 rag 内部
@Component
public class MilvusSearchChannel implements SearchChannel {
    // ...
}
```

不要让外部直接依赖实现类。

---

# 5. 代码规模控制

Ragent 强调"小而清晰"的代码。

默认参考标准：

| 对象 | 建议上限 | 超过后 |
|---|---:|---|
| 普通 Java 文件 | 300 行 | 检查是否需要拆分 |
| Java 文件 | 400 行 | 原则上应拆分 |
| Java 文件 | 500 行 | 原则上禁止继续堆积 |
| 方法 | 50 行 | 检查拆分 |
| 方法 | 80 行 | 原则上必须拆分 |
| 单个 Class | 300 行 | 检查职责 |
| 单个模块 | 单一职责 | 多职责必须拆分 |

以上是**设计警戒线，不是机械规则**。

判断标准优先于行数。

---

# 6. 什么时候必须拆分代码

出现以下任意情况，应考虑拆分：

### 6.1 一个文件出现多个明显职责

例如：

```text
RagService.java
├── 问答逻辑
├── 检索逻辑
├── 会话管理
├── 知识库管理
└── 入库逻辑
```

应拆分为职责明确的模块。

---

### 6.2 一个方法承担多个阶段

例如：

```java
public void processQuestion(String question) {
    // 1. 意图识别
    // 2. 问题重写
    // 3. 检索
    // 4. Rerank
    // 5. 生成回答
    // 6. 保存会话
}
```

必须拆分。

---

### 6.3 需要大量注释才能解释代码

如果代码必须写大量注释才能理解，优先考虑重新设计。

目标：

> 让代码结构本身表达意图。

---

### 6.4 出现大量 if/else

如果一个方法出现大量 if/else，应判断是否存在：

- Strategy 模式
- Map 映射
- Handler 处理器
- 独立方法

但禁止为了消灭 if/else 而过度设计。

---

# 7. 禁止过度抽象

不要为了"看起来高级"而创建：

```text
AbstractXXX
BaseXXX
XXXFactory
XXXManager
XXXService
XXXRegistry
XXXProvider
XXXStrategy
```

除非确实存在多个实现或明确的扩展需求。

优先：

```text
简单实现
```

等出现真实需求后再抽象。

---

# 8. 禁止无意义创建文件

新增文件前必须回答：

1. 为什么不能放入现有模块？
2. 新文件是否承担独立职责？
3. 是否会被多个地方复用？
4. 是否能够降低复杂度？

如果只是几十行一次性逻辑，不要为了"模块化"强行创建新文件。

---

# 9. 优先复用已有能力

新增功能前必须搜索：

```text
已有接口
已有实现
已有工具类
已有配置
已有常量
```

禁止重复实现。

---

# 10. 最小修改原则

修复 Bug 时：

> 只修改解决问题所需要的代码。

禁止：

```text
修一个 Bug
↓
顺便重构整个模块
↓
修改 20 个文件
↓
新增 5 个抽象
```

优先：

```text
定位问题
↓
最小修复
↓
测试
↓
完成
```

---

# 11. 新功能开发原则

新增功能必须优先判断：

```text
是否可以扩展现有模块？
        ↓
可以 → 修改现有模块
        ↓
不可以
        ↓
是否需要独立职责？
        ↓
需要 → 新模块
```

不要：

```text
一个需求
↓
Controller
Service
Manager
Factory
Adapter
Repository
```

---

# 12. 检索通道开发约束

检索通道是 RAG 系统的核心。

必须保持：

```text
SearchChannel 接口
    ↓
具体实现（Milvus / ES / LightRAG / You.com）
    ↓
并行调度器
    ↓
后处理链（去重 → 融合 → Rerank → 富化）
```

不得将具体通道逻辑硬编码进调度器。

---

# 13. 模型调用规范

模型调用必须经过：

```text
ChatClient 接口
    ↓
模型档位选择
    ↓
候选路由
    ↓
首包探测
    ↓
熔断检查
    ↓
实际调用
```

禁止绕过模型档位和熔断机制。

---

# 14. 入库 Pipeline 规范

入库 Pipeline 必须支持：

- 节点配置存储在数据库
- 条件执行
- 输出链式传递
- 独立执行日志
- 失败定位

禁止将 Pipeline 逻辑硬编码。

---

# 15. 错误处理

错误必须：

```text
可识别
可恢复
可展示
```

不要：

```java
try {
    // ...
} catch (Exception e) {
    log.error("error", e);
}
```

然后静默失败。

工具失败应结构化返回：

```text
ToolResult
├── ok
├── text
├── error
└── metadata
```

---

# 16. 日志规范

日志必须：

- 有明确模块
- 有错误上下文
- 不记录 API Key
- 不记录完整敏感环境变量
- 不打印无意义的大段数据

禁止输出：

```text
API Key
Token
密码
MCP Secret
```

---

# 17. 测试原则

新增功能必须至少验证：

```text
正常情况
异常情况
边界情况
```

涉及核心模块时必须补测试。

重点模块：

```text
检索通道
模型路由
熔断降级
入库 Pipeline
MCP 工具调用
```

---

# 18. 开发完成后的强制自检

完成任务后必须主动检查：

### 架构

- 是否破坏模块边界？
- 是否增加不必要的依赖？
- 是否产生新的重复逻辑？
- 是否出现职责混乱？

### 代码

- 是否存在巨型方法？
- 是否存在巨型文件？
- 是否可以进一步简化？
- 是否有重复代码？
- 是否有无意义抽象？

### 安全

- 是否绕过认证？
- 是否存在 SQL 注入？
- 是否可能泄露 Key？

### 测试

- 是否验证正常流程？
- 是否验证异常流程？
- 是否验证边界条件？

---

# 19. 优先选择简单方案

当存在多个实现方案时：

```text
方案 A：100 行 + 3 个抽象
方案 B：50 行 + 1 个类
```

如果两者都满足需求：

> 优先方案 B。

---

# 20. MVP 原则

Ragent MVP 的目标不是：

> 功能最多。

而是：

> 用最少的代码形成稳定的 RAG 问答闭环。

核心闭环：

```text
用户提问
    ↓
意图识别
    ↓
多路检索
    ↓
融合排序
    ↓
模型生成
    ↓
流式输出
    ↓
会话保存
```

优先保证这个闭环稳定。

其他能力：

```text
Agent
MCP
管理后台
Trace
审计
```

按照实际需求逐步增加。

---

# 21. 最重要的规则

如果本规范与"快速堆功能"发生冲突：

> 优先保持架构清晰和代码简单。

如果本规范与实际需求发生冲突：

> 先理解需求，再选择最小、最安全、最容易维护的实现。

最终目标：

```text
少代码
低耦合
低复杂度
职责清晰
容易理解
容易修改
容易回滚
容易测试
```

**Ragent 不追求代码多，而追求每一行代码都有必要。**
