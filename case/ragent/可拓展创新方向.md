# Ragent AI 可拓展创新方向

## 项目定位与现有能力速览

Ragent 是面向 **Agentic RAG 演进的生产级 Java RAG 平台**：Spring Boot 4 + Java 17 模块化单体（framework / infra-ai / system / rag / agent / bootstrap / mcp-server 七个 Maven 模块），前端 React 18，PostgreSQL(pgvector) + Milvus + ES + Redis + RocketMQ + Sa-Token，后端约 6.1 万行 Java、30+ 张业务表。已实现能力：多路混合检索（向量、ES 关键词、LightRAG 图谱、You.com 联网，Scope 范围 + 去重/RRF 融合/Rerank/证据门控/富化后处理链）；意图树 + 查询词映射 + 问题重写拆分路由；Tier 模型档位、首包探测与三态熔断；Redis ZSET 公平排队限流；可编排入库 Pipeline（HTTP/飞书 Fetcher → MIME 解析/Tika/Excel/VLM/MinerU → 分块 → 嵌入 → 索引，支持远程文档定时刷新与分布式锁状态机）；会话 N 轮 + 持久化摘要、回答溯源 + 推荐追问 + 用户反馈；Trace/变更审计/幂等/事务消息；Agent v2 ReAct 骨架（KnowledgeSearchTool / MCP 桥 / 长短记忆压缩管线，Agent Profile 与 Prompt Slot 已落库可动态激活）；独立 MCP Server（天气/票务/销售/请假/资产/联网执行器）；完整管理后台（知识库/意图树/图谱/迁移词/样例问题/摄取/Agent/Trace/变更日志/用户）与 `ragent.eval` 离线评测开关。项目阶段规划明确列出**后置候选**：子 Agent、MCP SSE/HTTP 传输、多租户隔离——正是下方方向的富矿。

## 一、功能增强：让已有闭环更顺手

### 方向 1：会话资产化——收藏、标签、匿名分享与导出（难度：易｜2 周）

**背景与痛点**：项目已有完整的会话/消息/溯源/推荐追问（`ConversationController`、`t_conversation`、`t_message`），但会话是「用完即走」的日志：用户查到的关键结论无法沉淀，想把某段带来源的结论发给同事只能截图。

**创新点**：把会话升级为可管理资产——收藏分组、打标签、一键生成**匿名只读分享链接**、导出带来源引用的 Markdown 文档。

**方案设计**：不改动问答主链，纯增量。
- 新表 `t_conversation_mark`（id、user_id、conversation_id、folder、tags、note），收藏与分组；
- 新表 `t_share_link`（id、type=conversation/kb、target_id、creator、token、expire_at、max_views、created_at）；
- `ConversationController` 新增：收藏/取消、分组列表、生成分享、`GET /api/conversations/share/{token}`（只读 + Sa-Token 匿名跳过，按 token 查归属做越权校验）；
- 导出：后端拼装 Markdown（问题 + 正文 + sources 引用列表），复用前端现有来源数据结构，无需新 PDF 依赖；
- 前端 ChatPage 会话栏增加「收藏夹/标签」Tab 与「分享/导出」按钮，管理分享链接列表页（可吊销）。

**落地步骤**：第 1 周建表 + 收藏/分组后端 CRUD 与单元测试；第 2 周分享链接与导出接口，前端收藏栏与分享弹窗；第 2 周末联调验收。

**实用价值**：知识库场景（行政制度、考试答疑、内部 FAQ）中「把一份带出处的好答案发给同事/客户」是最高频诉求，分享链接比截图专业且可吊销；导出 Markdown 可直接进知识库反哺内容建设。

**风险与备选**：分享链接易被爬取——默认 7 天过期 + 到期吊销即可；若不想建表，可先做「收藏 + 导出」两个轻功能，分享后置。

### 方向 2：入库质量自检——文档质量评分卡与失败根因归类（难度：易｜2 周）

**背景与痛点**：摄取链路（Fetcher → Parser → Chunker → Embed → Index）具备节点日志与失败定位（`t_ingestion_task_node`、`t_knowledge_document_chunk_log`），但数据是「散点日志」：管理员不知道哪些文档解析后是空壳、哪些嵌入失败、为什么批量失败，只能一条条翻日志。

**创新点**：给每份文档生成**质量评分卡**（分块数、空块率、嵌入失败数、正文长度分布、解析耗时），并自动把失败消息聚成根因类别，形成「一眼看出先修谁」的运营视图。

**方案设计**：不改摄取引擎，只做**读侧聚合 + 新页面**。
- `ingestion` 包新增 `QualityReportController` + `QualityReportService`：Mapper 聚合 SQL 直接查 `t_knowledge_document_chunk_log` / `t_ingestion_task_node`，输出文档级画像（文档数/分块数/空块/失败数/平均耗时/最后状态），无需新表（量大再加物化聚合表）；
- 失败归类：新增 `ErrorClassifier` 工具，按错误消息特征（fetch 超时、MIME 不支持、embedding 失败、连接拒绝）归一化为 `err_type`，聚合出 Top 根因 + 受影响文档清单；
- 管理端「摄取」页新增「质量中心」Tab：库级筛选、质量分排序、根因饼图、点击文档直达重试入口（复用已有任务重跑）。

**落地步骤**：第 1 周后端聚合接口与单元测试（用已有 84 个测试模式）；第 2 周前端质量中心 Tab + 根因视图 + 验收。

**实用价值**：企业库动辄上千文档，管理员靠「质量中心」按分数倒序修文档，比翻日志快一个数量级；也是后续「检索空洞运营」方向 5/8 的数据基础。

**风险与备选**：日志字段不足时无法区分失败阶段——风险低，`task_node` 已按节点记录；备选：聚合口径先行，页面二期再可视化。

### 方向 3：远程文档版本化刷新——变更摘要、差异高亮与失败通知（难度：中｜3 周）

**背景与痛点**：已有远程文档定时刷新（`HttpUrlFetcher` / `FeishuFetcher`，`t_knowledge_document_schedule` / `_exec`，分布式锁 + 状态机），但刷新后「内容变了什么、什么时候变的」完全不可见，失败也只存在于 exec 记录里——用户问的问题答案悄悄过期没人发现。

**创新点**：把每次刷新变成**可追溯的版本**：内容哈希比对生成变更摘要与差异段，失败与重大变更通过站内信/飞书机器人（Webhook）主动通知维护者。

**方案设计**：
- 新表 `t_knowledge_document_revision`（id、doc_id、schedule_exec_id、content_hash、change_summary、changed_chunks_json、fetched_at）与 `t_doc_change_notice`（可选合并）；
- 摄取管线的 `FetcherNode` 之后新增轻量 `VersionCheckNode`（实现 `IngestionNode` 接口注册，遵守「节点配置存库」约束）：比对上次 `content_hash`，差异走文本 diff（引入免费 `io.github.java-diff-utils:diff-utils`，与现有 hutool 同属零成本依赖），用 LLM（走现有 `ChatClient` 档位）把 diff 压成 3 条以内的中文变更摘要；
- 通知：新增 `ChangeNoticeService` 与 `NoticeChannel` 接口，首版实现「站内信（复用 t_message 或新表）」+ 可选飞书 Webhook（配置项注入，无 key 即关闭），在 `schedule_exec` 状态机收尾处回调触发；
- 管理端摄取页新增「刷新记录」Tab：版本列表、变更摘要、旧版本原文预览。

**落地步骤**：第 1 周建表 + VersionCheckNode + diff 摘要；第 2 周通知通道与 exec 回调；第 3 周前端版本时间线与验收、补单测。

**实用价值**：制度文档、产品手册定期更新，维护者订阅「变更播报」后不用再逐篇人工核对；回答溯源时可提示「该来源 3 天前更新过」，显著提升可信度。

**风险与备选**：LLM 摘要每轮刷新消耗 token——只对内容哈希变化的文档调用；备选：不接 LLM，纯规则抽取差异首段；飞书不可用则只做站内信。

### 方向 4：内置 QAGA 回归评测——把 eval 开关变成可跑的报告流水线（难度：中｜3 周）

**背景与痛点**：项目已预留评测能力：`ragent.eval.enabled=true` 时注册 `EvalController`（sync 问答入口）与检索捕获切面，供外部评测项目调用；但没有「题集管理、批量运行、指标报告」——改一次检索预算/重排逻辑，效果是变好还是变坏全凭手感。

**创新点**：在服务内落地 **QAGA 回归评测**：题库落库，批量跑「问 → 检 → 答」，产出 Chunk 命中率、引用准确率（Grounding 覆盖）与 LLM 相关度打分，输出 Markdown 报告并对比基线，作为每次检索改动的回归关卡。

**方案设计**（全部复用现有能力，不引新中间件）：
- 新表 `t_eval_case`（id、question、expected_kb_id、expected_chunk_ids、golden_answer、tags）与 `t_eval_run` / `t_eval_result`（run_id、case_id、recall@k、cited_hit、llm_score、latency_ms）；
- `rag/eval` 包扩展：`EvalRunnerService` 复用 `EvalController` 的 sync 链路调用并读取捕获的检索上下文；`EvalJudge` 走 `ChatClient` 档位（与生产同一路由/熔断），Prompt 只判「是否基于给定引文作答、有无幻觉」；
- 指标与报告：`EvalReportGenerator` 输出 Markdown（按题集汇总表 + 失败样例 + 与上次 run 的 diff）；
- 管理端「设置」下加简易评测页：上传题集 CSV / 查看历史报告（可选，后端接口先行）；
- 项目阶段规划要求的「每期结束回归」从此有客观依据，可与 `mvn test` 同 profile 共存。

**落地步骤**：第 1 周表结构 + 批量执行器跑通 1 条 golden case；第 2 周三个指标计算与报告生成；第 3 周题集管理接口/CSV 导入 + 用方向 2 的模板 15 问做首批基线、验收。

**实用价值**：任何 RAG 项目改检索都怕「拆东墙补西墙」，一套 30~100 题的回归集把「凭感觉」变成「看数字」，是答辩与简历里最有说服力的工程证据。

**风险与备选**：LLM 打分有抖动——取同题 2 次平均、分数只看趋势；备选：先把检索类硬指标（recall、引用命中）做扎实，LLM 打分后置。

## 二、智能升级：让问答更聪明

### 方向 5：路由自学习——从真实会话挖掘意图节点与查询词映射建议（难度：中｜4 周）

**背景与痛点**：意图树与查询词映射（`t_intent_node`、`t_query_term_mapping`）是手工配置的知识，而真实流量中「检索空窗 + 证据门控拦截 + 用户反馈差评」的问题天天产生（方向 4 的 trace 里全有），却没有任何机制把它们回流成配置改进建议。

**创新点**：**让系统从自己的失败中学习**——定时把低质问题聚类，产出「建议新增意图节点 / 建议查询词映射 / 建议补充哪份文档」，管理员点一下确认即写入现有配置表。

**方案设计**：
- 数据源：近 7 天 `t_rag_trace_run`（空检索/被证据门控的查询）+ `t_message_feedback`（差评消息的问题）+ `t_message`；
- 聚类：问题文本过 Embedding（复用 `EmbeddingClient`）后在 pgvector 上做近似分组，或直接按已映射意图归组——优先简单方案；
- LLM 提炼（`ChatClient`）：每组输出「代表问题、意图节点建议名称、建议查询词、关联知识库」；
- 新表 `t_intent_suggestion`（id、status=pending/applied/ignored、payload_json、created_at）；管理端意图树页新增「学习建议」Tab，一键调用现有 `IntentTreeController` / `QueryTermMappingController` 创建接口落库；
- 触发：`@Scheduled` 每日低峰执行 + admin 手动按钮，全程可关。

**落地步骤**：第 1 周数据抽取 + 聚类跑通；第 2 周 LLM 提炼与建议表、落库流程；第 3 周前端「建议」Tab 与确认/忽略；第 4 周对模板 15 问做端到端自证（构造 N 个故意未配置的问题验证建议质量）。

**实用价值**：知识运营者每周花 10 分钟点「采纳」就能让路由覆盖率持续增长，是「RAG 越用越准」最朴素可信的落地形态，也直接补齐项目当前「配置靠人、无反馈回路」的短板。

**风险与备选**：LLM 建议质量不稳——置信度低于阈值不进建议列表，全部建议默认不自动生效；备选：先只做「未命中问题 Top 榜」不做自动提炼，第二期再上 LLM。

### 方向 6：轻量个性化问答记忆——抽取用户事实并注入重写与重排（难度：高｜4 周+）

**背景与痛点**：RAG 会话侧记忆目前只有「最近 N 轮 + 持久化摘要」（`rag/core/memory`），agent 侧已有复杂的用户记忆管线（`AgentMemoryJudge`/`Consolidator`/`t_agent_memory`），但两侧未打通——用户天天问「我们部门」的休假规则，系统始终不懂「我们」是谁。

**创新点**：给 RAG 问答加**跨会话的轻量用户记忆**：从对话中异步抽取「用户身份/偏好/常用对象」事实（引用 agent 侧记忆提示词思路但大幅简化），存储后在问题重写与重排两处注入。

**方案设计**：
- 新表 `t_user_memory`（id、user_id、category=org/dept/preference/fact、fact_text、source_conversation_id、confidence、updated_at、deleted），按用户缓存于 Redis 控制读取成本；
- `MemoryExtractionService`：问答完成后异步（复用 framework 线程池）调 `ChatClient` 从本轮消息抽取事实，`MemoryJudge` 只做「确定性事实、无个人隐私敏感词」白名单过滤，规避合规风险；
- 注入点 1——问题重写：`rag/core/rewrite` 的重写 Prompt 追加记忆上下文（如「用户所在部门：市场部」），让「我们」被显式限定；
- 注入点 2——个性化重排：新增 `PersonalPrefPostProcessor` 注册进 `postprocessor` 链（实现现有 `SearchResultPostProcessor` 接口），按用户关注对象给命中结果加权；均带开关，默认按用户关闭；
- 用户端「我的记忆」设置页：查看/删除（`UserMemoryController`），删除即永久不注入。

**落地步骤**：第 1~2 周事实抽取 + 存储 + 设置页（先只做生成阶段注入，不碰检索）；第 3 周重写注入与效果对比（方向 4 评测集对照）；第 4 周重排加权 + 测试 + 验收。

**实用价值**：企业内部知识问答里「团队上下文」是体验分水岭；长期使用用户的回答命中率与个性化是 RAG 产品留住 C 端/组织内用户的差异化点，答辩演示效果好。

**风险与备选**：记忆注入错误会系统性带偏回答——高置信过滤 + 用户可见可删 + 默认关闭按需开启；备选：只做「生成阶段注入」，不做检索加权，难度降至中。

### 方向 7：Agent「深度研究」模式——多子任务并行检索 + 多工具聚合（难度：高｜4 周+）

**背景与痛点**：agent 模块已有 v2 ReAct 骨架、`KnowledgeSearchTool` / `McpToolBridge`、`t_agent_state` 状态持久化与上下文压缩中间件，但执行仍以「单步工具调用」为主；面对「对比 A 库与 B 库口径差异」这类跨库复杂问题时，主链路会检索分裂、答案浅薄。

**创新点**：新增 **Plan-and-Execute 研究模式**（正是项目规划标注的「子 Agent」后置候选的方向）：先规划拆解 3~6 个子问题 → 并行执行（多库检索 + 联网 + MCP 工具）→ 证据级聚合，输出带完整来源的研究报告式答案，全程复用 agent 会话/状态/压缩能力。

**方案设计**：
- `agent` 模块新增 `ResearchPlanner`：由 Agent Profile 新增「research-plan」Prompt Slot 驱动（Profile/Slot 已落库，天然支持运行时调参）；拆解结果写 `t_agent_state`；
- 新增 `SubtaskExecutor`：子问题并行调度（复用框架线程池），每个子任务内部仍走 ReAct；工具调用上把 `KnowledgeSearchTool` 扩展为可携带 **kb scope 参数**（当前检索链路 Scope 已支持按知识库限范围，直接透传）；
- `EvidenceSynthesisTool`：收集各子任务带来源引用的结论，去重引文后按「结论—依据—来源」结构生成最终流式回答，引用复用现有 Grounding/来源数据结构，前端 AgentChatPage 可直接展示；
- 上下文控制：子任务结果入 `t_agent_context_compaction` 现有压缩管线，防止长研究爆 token。

**落地步骤**：第 1 周规划器 + 状态落库 + 单子任务串行跑通；第 2 周并行执行与 kb scope 透传；第 3 周聚合器与引用结构化输出；第 4 周对照实验（普通模式 vs 研究模式回答同一复杂问题）、压测与验收。

**实用价值**：「给我一份对比结论」是企业知识库最高价值也最难的问题形态；研究模式让平台从「单轮问答工具」升级为「可交付结论的助手」，是向 Agentic RAG 定位的关键一步。

**风险与备选**：成本与耗时上升（数倍 token、分钟级响应）——限制子任务数、超时与档位走低配模型；备选：不做并行，先做「串行深度追问」版本降低实现与调试难度。

## 三、架构工程化：更稳、更可见、更可交付

### 方向 8：检索漏斗与性能看板——把 Trace 变成运营数据（难度：中｜3 周）

**背景与痛点**：系统已把每次问答写成 `t_rag_trace_run` / `t_rag_trace_node`（阶段、耗时、输入输出），管理端有 Trace 列表与详情，但**缺一页聚合分析**：检索预算在三段（recall/rerank/final）里哪层最浪费？哪个 channel 最慢？证据门控拦掉了多少检索结果？

**创新点**：把分散的 Trace 聚合成**检索漏斗看板**：意图→召回（各通道候选数）→去重融合→Rerank→证据门控→生成，逐层展示数量流失与耗时，并给出慢会话 Top 榜直达 Trace 详情。

**方案设计**：
- `RagTraceController` 扩展聚合接口（或在 admin 侧新增 `TraceAnalyticsService`）：按 kb/intent/时间段做 SQL 分组聚合（COUNT、AVG、P95 用窗口函数或取数内存分位），阶段量从 trace node 名称与记录值规格化提取（若缺字段，则本方向第一步是补打 trace 指标，属小改）；
- 管理端 dashboard 新增「检索漏斗」Tab：漏斗图 + 通道耗时对比 + 慢会话列表（点击复用现有 Trace 详情页）；
- 阈值告警（可选）：平均首包耗时超过配置值时在变更日志页提示（复用 `t_biz_change_log` 或站内信）。

**落地步骤**：第 1 周梳理 trace 数据、补打缺失的漏斗计数指标；第 2 周聚合 SQL + 接口；第 3 周前端漏斗可视化与验收。

**实用价值**：检索预算怎么调、Rerank 该不该上、哪条 channel 该降级，从此有数据说话；对「每期结束回归」（方向 4）提供性能侧对照，两个方向天然互补。

**风险与备选**：老数据缺指标无法回溯——只对新产生的 trace 生效，说明即可；备选：先做「接口级 P95 + 慢会话榜」最小版，漏斗图二期。

### 方向 9：交付体检套件——一键检查 + 生产编排 + 演示脚本（难度：易｜2 周）

**背景与痛点**：中间件多达 6 个（PG/Redis/Milvus/etcd/ES/RocketMQ），部署手册齐全但**没有自动化手段**：新人部署失败只能逐个 `psql`/`telnet` 排查；`scripts/` 目前仅一个 SSE 排队压测脚本；生产编排（docker-compose.prod）仍停留在手册示例。

**创新点**：交付三件套——`ragent-check.sh` 环境体检（一次输出 15 项检查的红绿灯报告）、`docker-compose.prod.yml` 生产编排（应用 + 依赖 + 健康检查 + 日志卷）、`demo` 一键脚本（建库 → 灌模板 → 预热问答，复用 initializer）。

**方案设计**：
- `scripts/` 新增 `ragent-check.sh`：检查 JDK/Maven/Node 版本；`docker compose ps` 中间件状态；TCP 探测 5432/6379/19530/9200；`curl actuator/health`；读取 `application.yaml` 关键配置项一致性（模型档位与候选能力启动校验逻辑已有，脚本只做冒烟）；
- 新增 `docker-compose.prod.yml`（参考手册 9.x 补齐服务健康检查与资源限制）与 `.env.example`（占位符，不落真实密钥）；
- `scripts/demo-up.sh`：初始化库 → 执行 `resources/initializer` 模板 → 打印演示账号与示例问题清单。

**落地步骤**：第 1 周体检脚本 + 环境矩阵验证（本机 macOS/Windows 各跑一遍）；第 2 周编排文件 + demo 脚本 + README「3 分钟跑起演示环境」章节。

**实用价值**：任何人（老师、评委、客户）都能在 10 分钟内从零跑起完整演示环境——比赛答辩与商业化 POC 的硬门槛；体检报告在部署排障时省下大量沟通成本。

**风险与备选**：各中间件版本差异导致探测误报——脚本只报「探测结果 + 期望值」不做自动修复，宁可保守；备选：先只交付体检脚本，编排文件后续再补。

### 方向 10：知识库协作权限 → 多租户演进（难度：高｜4 周+）

**背景与痛点**：当前数据归属是「一人一库」的单用户模型（数据归属校验在 framework 认证上下文层），项目规划把多租户列为后置候选；但真实团队使用第一个撞上的就是「知识库不能共享给同事」。

**创新点**：分两期演进——**第一期做 ACL 团队协作**（周期短、立即可用），**第二期做租户化**（借助已有的 `VectorSpaceSpec`/`VectorSpaceId` 向量空间隔离能力，避免数据混洗）。

**方案设计**：
- 第一期（2 周）：新表 `t_knowledge_base_acl`（kb_id、user_id、role=owner/editor/viewer）；`rag` 的 Scope 解析（`RetrievalScopeResolver`）与知识库 CRUD 增加「我可见的库」过滤；管理端知识库详情新增成员管理；所有读写校验收敛到现有归属校验过滤器上扩展一个 `AclCheck`，避免散落各处改；
- 第二期（2 周+）：`t_user` 增加组织维度；framework 认证上下文扩展 tenant 透传（TTL 已能跨线程传 Trace 上下文，同机制）；核心业务表（kb/doc/chunk/conversation）加 `tenant_id` 与索引；向量侧按现有 `VectorSpaceId` 每租户独立 Collection/partition；缓存 key、MQ 消息头统一补租户字段；存量数据迁移脚本；
- 明确边界：审计/Trace 等日志表可不做隔离（只读归平台），降低工作量。

**落地步骤**：第 1 周 ACL 表与读写校验收敛；第 2 周 Scope 过滤 + 前端成员管理 + 验收；第 3 周 tenant 上下文与建表迁移；第 4 周检索/会话/缓存逐项过租户字段 + 回归（用方向 4 评测集双租户各跑一遍）。

**实用价值**：第一期直接解锁「部门共用一个知识库」的真实场景；第二期让平台具备向企业私有化交付的资格——多租户是商业合同里的常见硬性条款。

**风险与备选**：改动面大、易漏——务必先收敛校验入口再铺字段，宁可第二期只做到「应用层隔离 + 向量空间隔离」而不拆物理库；备选：若周期紧，只交付第一期 ACL，并在文档中把第二期作为架构演进方案保留。

## 四、场景落地：从平台到产品

### 方向 11：行业开箱模板市场——初始化器模板化与一键演示（难度：易｜2 周）

**背景与痛点**：`resources/initializer` 已有一套成熟的「一键重置 + 灌库 + 预热」模板（企业知识库：2 库、10 文档、23 意图节点、15 条预热问题，预热后答案与追问均已落库），演示效果已被验证——但只有一套行业模板，换场景就要重做模板；且模板数据藏在目录里，管理端不可见。

**创新点**：把「一套模板」变成「模板市场」：沉淀模板结构与目录规范，新增 2~3 个行业模板（高校教务、电商客服、项目研发 FAQ），每个模板自带文档集、意图树、查询词映射与预热题；管理端新增「模板中心」页展示与一键导览。

**方案设计**：
- 梳理 `enterprise-knowledge-base` 目录结构与模板元数据（模板名、行业、简介、库清单）→ 抽出 `template.yaml` 规范并补一份模板编写指南放 `resources/initializer/README.md`；
- 新增模板目录（文档用自生成样例内容避免版权风险），复用现有 `common/*.java` 初始化骨架，尽量零代码只填数据；
- 管理端「模板中心」：列模板、看预热问题样例与回答效果（可直接点开历史会话），执行仍走 CLI（不开放生产环境写库），页面给出可复制命令；
- 配套：模板之间共享的「文档集打包/导出」工具脚本，方便后续低成本新增行业。

**落地步骤**：第 1 周模板规范与新增 1 个行业模板并跑通初始化+预热；第 2 周第二个模板 + 管理端模板中心 + 验收。

**实用价值**：售前/答辩「换行业 5 分钟出演示」的杀手锏；也是教学训练营按行业分组做课设的现成底座；模板生态让平台具备「解决方案」而非「demo」的观感。

**风险与备选**：模板内容质量参差——预热环节已有 VerifyMain/WarmupMain 校验，可再加「问题—答案命中」断言；备选：先只做规范文档 + 1 个新模板，页面二期。

### 方向 12：可嵌入 Chat Widget——知识问答嵌入任意业务站点（难度：中｜3 周）

**背景与痛点**：平台问答体验完整但**只存在于自己的前端**：企业的 OA/官网/工单系统用户遇到问题要另开标签页登录平台。RAG 产品的常见商业化形态正是「把知识库问答嵌入客户自己的系统」。

**创新点**：提供「分享问答」能力——管理员选定知识库/意图范围生成分享令牌，任何人通过 `iframe` 或链接在**任意站点**直接提问，匿名 + 限流 + 可吊销，SSE 流式体验不变。

**方案设计**：
- 新表 `t_share_chat`（id、name、kb_scope_json（复用 Scope 结构，可限定意图白名单）、creator、token、expire_at、daily_limit、enabled）；
- `rag` 侧新增 `ShareChatController`：签发/吊销令牌（仅登录用户）；`POST /api/share-chat/{token}/ask` 走**现有 RAG 问答主链**，鉴权层换为「令牌校验 + Redis 计数限流」（轻量实现，无需进公平队列），命中 kb 范围用现有 `RetrievalScope` 拦截，天然无法越权读库；
- 前端新增 `share-chat` 迷你页：`/s/{token}` 直接复用 ChatPage 组件与 SSE 逻辑（不做登录态），附带 `<script>` 嵌入片段与样式参数（主题色）；
- 安全：令牌只读、可到期、可按日限次，问答记录以 `share` 用户身份入库便于审计，敏感知识库不允许被分享（配置开关）。

**落地步骤**：第 1 周令牌表 + 签发/吊销接口与主链接入；第 2 周匿名问答与限流、审计适配；第 3 周 `/s/{token}` 迷你页 + 嵌入示例页（在本地另起静态页演示）与验收。

**实用价值**：把「企业内部系统旁边挂一个会答制度问题的悬浮问答」变成 5 分钟接入的事——这是 RAG 平台对外售卖/对内推广时最常被要求的能力，也是展示 SSE 与限流功底的好材料。

**风险与备选**：匿名入口被刷/被恶意提问——日限次 + 异常频率熔断（复用熔断器思路）即可控；备选：首版只支持「整库只读分享」，意图白名单与主题定制二期再做；若不想新开前端工程，用现成 ChatPage 加 query 参数免登录态渲染即可。

## 落地优先级建议

- **首推（易、快、演示效果强）**：方向 1（会话资产化）、方向 2（入库质量自检）、方向 11（行业模板市场）——均不改主链路、2 周内出 MVP，直接提升日常使用与演示体验。
- **次推（中难度、工程含金量高）**：方向 4（QAGA 回归评测）与方向 8（漏斗看板）配合使用，构成「改检索 = 跑报告」的闭环，是答辩与简历中最硬的证据。
- **冲刺（高难度、最能体现 Agentic 方向）**：方向 7（深度研究模式）单点突破即可覆盖「Agentic RAG」叙事；方向 5（路由自学习）则是「越用越准」产品故事的最小可信实现。
