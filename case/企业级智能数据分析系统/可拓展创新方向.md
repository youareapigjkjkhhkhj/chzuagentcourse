# 可拓展创新方向 —— 企业级智能数据分析系统（ChatBI 问数平台）

## 项目画像与现有能力

本项目是 ChatBI 智能问数平台（由 DataEase 开源项目 SQLBot 重构）：自然语言提问 → RAG 语义召回表/字段/术语 → Text2SQL 生成 → 多引擎执行 → 图表渲染 → 智能分析与预测。技术栈：Python 3.11 + FastAPI + SQLModel + PostgreSQL（Alembic 72 迁移）、LangChain 0.3 + LLMFactory（openai/tongyi/vllm/azure 四类 12+ 服务商）、text2vec + pgvector、13 种数据源（含 Excel 上传建表）、Vue3.5 + Element Plus + AntV、g2-ssr 服务端出图、MCP 服务、Web 嵌入/弹窗。

现有能力：① 完整对话链路（`apps/chat/task/llm.py` LLMService：多轮上下文、推荐问题、失败错误回传下一轮）；② RAG 表/字段/术语三路召回；③ `apps/template/` 全套生成器（SQL/图表/分析/预测/选源）；④ 工作空间隔离 + 行列权限 + CWE-89 注入转义；⑤ 术语库 + SQL 示例训练（data_training，Excel 导入/启停）；⑥ ChatLog 执行日志与 token 用量、智能分析、数据预测；⑦ 表关系手工维护接口（table_relation）；⑧ 审计日志、API Key 管理、4 语 i18n、Docker 部署。

## 组 A：功能增强

### 方向1：问数结果反馈闭环——差评自动沉淀为训练样本 【易】

**背景与痛点**：用户问错只能刷新重问，管理员不知道哪类问题质量差，术语库与训练集优化靠感觉——而系统已备好训练闭环全部接口，只缺"入口"。

**创新点**：每条 ChatRecord 支持好/差/一句话修正；差评经管理员确认后写入现有 data_training 训练流水线，"用户一次纠错"变成"全平台校准样本"。

**方案设计**：`ChatRecord`（chat/models/chat_model.py）加列 rating INT、feedback_text TEXT，新表 chat_feedback（record_id、原 SQL、修正 SQL、status），走 Alembic 迁移；`api/chat.py` 加 `POST /chat/record/{id}/feedback`，system 加管理员处理接口；采纳时调 data_training 现有 `create_or_update`（修正 SQL 与原始 SQL 同存，便于模型对比学习）；前端 ChatRow 组件加反馈按钮 + system/training 页旁加"反馈处理"Tab。

**落地步骤**：W1 建表迁移+反馈接口+前端按钮；W2 处理页与写回训练集；W3 按问题域差评率看板，形成闭环。

**实用价值**：业务用户"错一次纠正一次"，管理员从此有准确率数据驱动调优——ChatBI 运维的真实刚需。**风险与备选**：反馈有噪音，修正可空、采纳权归管理员；最简版先只做统计看板（1 周）。

### 方向2：SQL 白话解释 + 失败自动修复 【中】

**背景与痛点**：`llm.py` 已把上次执行错误注入下轮提问的 error_msg，但用户当次只拿到一句报错；非技术用户看不懂"这数怎么算出来的"。

**创新点**：① execute_sql 失败即把错误拼入提示词让模型当轮重生成（上限 2 轮，全程记 ChatLog），不再等下一轮；② 结果渲染前用轻量模型把 SQL+口径翻译成 3 条业务语言摘要，随答案展示。

**方案设计**：复用 execute_sql（llm.py:1184）、check_sql 白名单校验、ChatLog 与 generate_analysis 的 LLM 调用写法；`run_task` 执行分支包 retry 循环，模板放 templates/（与现有 yaml 同目录）；ChatRecord 加 repair_rounds、final_sql 列；解释任务走 `no_reasoning` 轻模型路径并行返回。

**落地步骤**：W1 失败重试循环+日志；W2 白话解释接口与前端折叠展示；W3 对"修复仍失败"做统计并决定是否收敛。

**实用价值**：同时降低"报错即放弃"与"看不懂不信任"两个流失点。**风险与备选**：重试烧 token——限 2 轮、仅语法/权限类错误重试；备选：只做解释不做自修复（降为易）。

### 方向3：图表上的探索式追问——点击即下钻 【高】

**背景与痛点**：拿到"各区域销售额"柱图后，下一问九成是"华东呢？按月呢？换成本率呢？"，每次都要完整重述，模型重新理解上下文。

**创新点**：G2 图表可点击：点柱体/扇区即自动生成带维度值过滤的追问并立即执行；提供下钻/上卷/换指标三条快捷链，把多轮探索变成点鼠标。

**方案设计**：前端图表组件挂点击事件，产出结构化续问参数（base_record_id + filter 维度=值 + 意图 down/rollup/switch）；`ChatQuestion` 扩展 filter_context，后端复用 `build_table_filter`（llm.py:898）把点击值编译成 WHERE 条件附加到新 SQL；上卷/换指标由模板给改写指令，续问沿用原 Chat（origin 复用已有字段保上下文）。

**落地步骤**：W1 前端捕获点击值传参；W2 后端 filter 注入执行，先支持单值下钻；W3 上卷/换指标快捷链；W4 20 条探索路径回归+点击埋点。

**实用价值**：追数从打字变点击，是 QuickBI/Tableau 同款标配交互，答辩演示最直观。**风险与备选**：点击值到条件映射易错——用结构化参数让模型只补条件不重写全句；前端复杂可先做"选中值+预设追问模板"半自动版（降为中）。

## 组 B：智能升级

### 方向4：个性化"猜你想问"+点击率自学习 【中】

**背景与痛点**：现有 generate_recommend_questions_task 与 recommended_problem.py（管理员维护）对所有用户推同一批问题，财务与销售看到的一样。

**创新点**：以用户最近 N 轮对话涉及表/字段的 embedding 均值刻画兴趣向量，与候选推荐问题重排加权；埋点点击率，用指数移动平均持续调权，越用越准。

**方案设计**：新表 recommend_question_log（user_id、record_id、question、clicked）；前端 QuickQuestion/RecommendQuestion 组件上报曝光与点击；新服务 `recommend_rank.py`：冷启动=现有排序，有历史后=候选 embedding×兴趣相似度×（1+α·点击率），管理员置顶权重最高；embedding 工具链直接复用 `apps/datasource/embedding/`。

**落地步骤**：W1 埋点表与上报；W2 重排服务+开关（可 A/B）；W3 对比改版前后点击率出报告。

**实用价值**：业务用户每天第一动作是点推荐问题，推荐准=留存高。**风险与备选**：冷启动退化为现状；兴趣向量仅用于本空间排序不做跨用户画像；备选：不做学习只做"最近常用表优先"启发式（1 周）。

### 方向5：指标口径注册中心 【中】

**背景与痛点**：术语库只解释名词，回答不了"销售额=订单金额还是含税实收？去不去退货？"；同词两口径答案都对却互相矛盾，这是企业不敢放开 ChatBI 的头号原因，目前口径散落在提示词与 SQL 示例里。

**创新点**：新增指标注册中心：指标=名称+口径定义+可执行 SQL 公式+适用表+负责人；生成 SQL 前按语义召回指标并注入提示词；同名多口径触发澄清追问，答案标注口径来源。

**方案设计**：新表 metric_registry（oid、name、alias jsonb、definition、formula、scope_table、owner、version）；`LLMService.filter_metric_prompt` 仿 `filter_terminology_template`（llm.py:367）在生成前召回，generate_sql 模板加"口径约束"区块，要求输出引用指标名、禁止臆造口径；写入时 name embedding 近义检测，撞名提示新增或合并；前端 terminology 页加"指标"Tab。

**落地步骤**：W1 表+CRUD+管理页；W2 生成注入+答案口径角标；W3 冲突检测与澄清追问；W4 10 个真实指标过方向7 评测集验收。

**实用价值**：口径唯一事实源，答得可解释、口径可追责，政企客户硬需求。**风险与备选**：注入后生成变保守——评测集监控防回退；冷启动提供从术语库批量导入向导；备选：先做只读口径字典注入（降为易）。

### 方向6：表关系自动推断——手工 JSON 升级为 JOIN 智能 【高】

**背景与痛点**：`CoreDatasource.table_relation` 与 `/api/v1/table_relation/save|get` 已存在，但关系全凭管理员手工维护 JSON，几十张表后即失维护，多表 JOIN 只能靠模型猜。

**创新点**：自动推断候选表关系（主外键线索+列名/类型/embedding 相似+采样值重叠度打分）生成置信度，管理员勾选确认写回 table_relation；生成 SQL 召回多表时，先用关系图求最小连接树、把 JOIN 顺序与连接键建议注入提示词，再用 sqlglot 解析生成 SQL 的 join 树做后验校验。

**方案设计**：新增 analyzer.py 采集打分（复用表清单与字段元数据）；数据源详情页"表关系"Tab 改候选勾选确认，仍走 save_relation 写回不破坏旧数据；`choose_table_schema`（llm.py:446）选表后加 resolve_join_path 一步；低置信度不进提示词。

**落地步骤**：W1 元数据采集与打分；W2 候选确认 UI 与写回；W3 JOIN 路径注入提示词；W4 后验校验+10 条多表问题回归。

**实用价值**：把手工画关系图变成"系统给答案人来盖章"，直接提升多表问数成功率。**风险与备选**：同名异义误连——确认制+置信度兜底；采样开销限量并行并缓存 Redis；备选：只做 JOIN 条件建议单点（降为中）。

## 组 C：质量与架构工程化

### 方向7：Text2SQL 回归评测集——改模型先跑分 【易】

**背景与痛点**：换模型、调提示词后"感觉变准了"没有证据；data_training 的问题-SQL 示例本可当 Golden Set，却从未被用作评测。

**创新点**：把启用的训练示例作 Golden，搭"生成→比对→报告"流水线：sqlglot 解析归一化做语义比对，再执行结果集（顺序无关）比对，产出准确率/可执行率/延迟/失败 Top10 报告，作为一切改动的回归门禁。

**方案设计**：复用 generate_sql/generator.py（纯生成）、execute_sql_with_db（llm.py:1744）、data_training CRUD、sqlglot；独立 sqlbot_eval 库用 Excel 建表能力灌种子数据，绝不对生产数据源执行；`tests/test_eval_regression.py`（pytest，风格同 test_cwe89_escape_fix.py）+ scripts/eval_report.py 输出报告。

**落地步骤**：W1 评测库与种子数据+Golden 读取；W2 双级比对器单条跑通；W3 全量报告与失败样例列表；W4 沉淀进"模型/提示词变更"流程。

**实用价值**：调优从玄学变工程，答辩可现场演示"加术语后准确率 62%→78%"的量化证据。**风险与备选**：样本少方差大——报告带分错误类型（语法/权限/语义）；种子数据先覆盖单表聚合/过滤/排序/分组/多表 5 类；备选：只做 sqlglot 归一化比对（量减半）。

### 方向8：模型路由与成本护栏 【中】

**背景与痛点**：平台已支持多模型（LLMFactory、工作空间级模型配置、ChatLog 记 token_usage），但所有请求默认同一模型，简单"查个数"也烧旗舰 token；管理员不知花了多少、无预算闸门。

**创新点**：① LLMFactory 上层加 Router，按复杂度（召回表数、问题长度、示例命中数、是否多表）分流，SQL 生成用精确模型、解释/分析用轻量模型（no_reasoning 路径已有）；② 工作空间日/月 token 预算，超限自动降级轻模型并提示；③ 用量看板（模型/空间/日期聚合，token_usage 为 JSONB，一条聚合 SQL 出数）。

**方案设计**：路由特征在 choose_table_schema 与 filter_training_template 后已有状态可取，无需新采集；model_factory 加 create_router_llm，默认关闭并跑"影子日志"2 周，用方向7 评测集对比后再放开；看板页复用 system 列表页风格（chat_record_usage 同源数据）。

**落地步骤**：W1 用量聚合接口+看板；W2 路由器+影子模式；W3 预算闸门+降级+评测回归；W4 灰度放量。

**实用价值**：把"模型账单"与上限交给管理员——采购 LLM 的第一预算关切，且路由质量有评测背书。**风险与备选**：误判降准——影子模式+评测集双保险；多服务商计费单位不一——统一折算 token，汇率表放系统参数；备选：先只看板+告警（1~2 周）。

## 组 D：开放与商业化落地

### 方向9：把一次问数变成定时报表——问数订阅与推送 【中】

**背景与痛点**：用户问出"近 7 天各渠道 GMV"后数据每天在变，不想天天重问；给老板推日报全靠手工。SQL 保存、执行、xlsxwriter、Redis 全已具备，只缺"定时器+推送"。

**创新点**：对话"订阅化"：对某次问数点订阅、配周期，系统以创建者身份与行权限定时重放该 record.sql，产出 xlsx 推送到企业微信群机器人（免费，无需 SMTP）或邮件。

**方案设计**：新模块 apps/subscription：表 report_subscription（chat_id、record_id、cron、recipients jsonb、next_run_at）+ report_run_log（结果/失败原因/文件路径）；lifespan 启动轻量调度线程（单进程轮询，借鉴仓库 test_distributed_lock 的锁思路防重入）；到期以创建者上下文重放 SQL（execute_sql_with_db，行权限照常生效）→ xlsxwriter 出表 → webhook 推送，失败重试并通知；对话工具栏加"订阅"入口+订阅管理列表。

**落地步骤**：W1 建表+调度器+重放执行；W2 xlsx+推送+重试；W3 管理 UI 与手动执行；W4 运行历史与告警。

**实用价值**：个人问数升级为组织数据服务，老板在群里看日报是最易讲清商业价值的场景。**风险与备选**：SQL 随表结构变更失效——运行日志记录并通知、停用不静默；备选：不做 cron 只做每日定时（更简）。

### 方向10：开放通道计量化——API Key 配额与用量账单 【中】

**背景与痛点**：平台已有 Web 嵌入/弹窗/MCP 8001 与 apikey 管理，向 OA、n8n/Dify 开放能力只差计量：谁在用、用多少、如何限流防滥用。

**创新点**：为 Key/通道补"计量+配额+报表"：请求链路记录 Key 维度 token/次数/耗时，Redis 计数做日配额限流（超额 429+额度提示），管理端看任意 Key 用量趋势并导出——最小计费底座。

**方案设计**：计量点设在 chat/api 与 MCP mcp_question 处，中间件统一注入 key 上下文（参照 common/audit/schemas/request_context.py 现成模式）；ChatLog.token_usage 已有明细，新表 api_usage_daily 由每日聚合落表，报表毫秒级；Redis INCR+EXPIRE 计数，阈值存系统参数（settings 参数体系已有）；system 页加"开放集成"Tab（用量图+CSV 导出，xlsxwriter 现成）。

**落地步骤**：W1 计量点+日聚合表；W2 配额限流中间件；W3 报表 UI 与导出；W4 嵌入/MCP 全链路验证+配额告警。

**实用价值**：集成方与运营有了量/额契约；演示"外部系统经 MCP 调用、配额耗尽自动熔断"是完整商业化体验。**风险与备选**：误伤正常调用——配额默认宽松先统计后收紧；聚合任务复用方向9 调度器；备选：先只做计量报表（1 周）。

## 落地优先级建议

- **最推荐先做**：方向7（评测集，为一切改动提供度量尺）→ 方向1（反馈闭环，让质量数据持续流入）→ 方向5（指标口径，体现企业级差异化）。
- **答辩演示效果最好**：方向3（点击下钻）、方向9（企业微信日报）、方向6（自动 JOIN 技术深度足）。
- **风险对冲**：改动先跑方向7 评测集防回退；新表一律走 Alembic 迁移；LLM 调用一律经 LLMFactory，不绕过模型管理。
