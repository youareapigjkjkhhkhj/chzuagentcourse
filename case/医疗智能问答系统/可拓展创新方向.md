# 医疗智能问答系统：可拓展创新方向

## 项目现状速览

本项目是一个面向眼科糖尿病视网膜病变（DR）辅助筛查场景的「医学知识问答 + 眼底图像分级」平台：后端为 Flask + SQLAlchemy，元数据存 SQLite、向量存 PostgreSQL/pgvector；前端为 React 18 + TS + Vite + Tailwind/TDesign。已实现能力包括：JWT 三角色认证（admin/doctor/user）、多知识库与多格式文档管理（PDF/Word/Excel/PPT/HTML 解析、批量与 zip 上传、向量化与重同步）、混合检索（向量 + 关键词，相似度阈值等参数全局可配）、RAG 问答（OpenAI/Ollama/通义千问三 provider、SSE 流式、回答带 sources 引用并落库）、会话历史/统计/导出、LLM 与 Embedding 模型在线配置与连通性测试、眼底图像 6 模型加权集成分级（0-4 级，权重 0.25/0.20/0.20/0.15/0.10/0.10）、结构化诊断报告（风险分级 + 随访建议）。整体代码约 1.2 万行，模块边界清晰（models/routes/services/utils 分层），扩展基础良好。

> 通用合规前提：以下所有涉及诊疗内容的方向，均按「AI 辅助建议 + 免责声明常驻展示 + 关键节点人工复核/人工介入」设计，定位为教学演示与院内辅助工具，不构成诊疗行为。接入真实数据前需脱敏并取得授权。

## 主题一：问答与知识功能增强

### 方向1：引用即证据——回答溯源卡片与原文定位

**背景与痛点**：`ChatMessage.sources` 已把每次 RAG 回答的引用（文档 id/标题/片段/相似度）完整存库，但前端只把它当普通文本展示，医生无法确认"这句话出自知识库哪里、原文怎么写的"，溯源成本高，直接影响对 AI 回答的信任度。

**创新点**：把 sources 升级为可交互的证据链——引用卡片带相似度徽标，点击可跳转到对应文档并定位到命中段落原文（关键词高亮），回答正文与来源一一对应，形成「AI 结论 → 知识库证据 → 人工核对」闭环。

**方案设计**：① `routes/chat.py` 构建 sources 时补充 `kb_id`、`doc_id`、`chunk_id`、片段在文档中的顺序号，sources 结构向后兼容；② `routes/kb.py` 新增 `GET /api/kb/<kb_id>/documents/<doc_id>/chunks?query=xx`，返回该文档命中片段及前后文（query 为空则按 chunk 顺序分页）；③ 前端 `AIAssistant.tsx` 渲染引用卡片列表（标题 + 相似度），点击打开侧滑面板调上述接口展示原文并高亮命中的关键字（后端返回命中词位置或前端用相似片段做简单高亮）；④ 会话历史页复用同一组件，历史回答的引用同样可点开；⑤ 页面底部常驻一行免责声明「AI 回答仅供参考，请以专业医生判断为准」，引用面板内提供「引用有误」反馈按钮。

**落地步骤**：第 1 周——后端 sources 补字段 + chunks 查询接口，前端展示引用卡片与侧滑原文；第 2 周——历史会话复用、反馈按钮落库（可直接写一张 `source_feedback` 表：user_id、message_id、source_id、is_useful、note），若时间紧反馈可挪到方向4一并做。

**实用价值**：让知识库问答"敢被引用"。医院场景里医生愿意使用 AI 的首要条件是能快速核验出处；对带教场景，引用溯源本身也是 RAG 原理最好的教学切片。该方向可支撑竞赛答辩中的"可解释性"提问。

**风险与备选方案**：切块与原文定位可能因分块重叠出现偏移，MVP 阶段接受"定位到块级原文"即可，不做字符级对齐；若文档已被删除，引用跳转时给出友好提示。备选：不做跳转页，只在回答下方展开引用全文（前后 200 字），实现更简单。

### 方向2：真·多轮对话与追问改写

**背景与痛点**：代码检查发现 `send` 与 `send-stream` 每次只把"当前这一条用户消息"发给大模型（system prompt + 当前 message），会话历史虽然完整存入了 `chat_sessions`/`chat_messages` 却没有参与生成——医生连续追问"那复查频率呢？""这个药有什么禁忌？"时，模型并不知道前文指的是哪个病、哪份指南。此外 RAG 检索也只用当前句，"它""这个方案"这类指代会让向量检索完全跑偏。

**创新点**：① 组装消息时从 `chat_service` 取出该会话最近 N 轮对话拼入上下文，窗口长度按 token 估算裁剪（`tiktoken` 已在依赖中，免费）；② 检索前增加「追问改写」：把最近一轮用户对话压缩成一条独立、完整的检索 query（复用已配置的 chat 模型做一次小调用，Ollama 本地部署时零成本）；③ 可在会话设置里给出"记忆轮数"开关。

**方案设计**：`services/chat_service.py` 新增 `get_recent_messages(session_id, limit=6)`；`routes/chat.py` 中 send/send-stream 共用一个新的 `build_messages(model, session, current_message, context)` 组装函数（system prompt + 历史（user/assistant 交替，来自 message_type） + 当轮）；改写函数 `rewrite_query_for_search()` 失败时降级为"用当轮消息原样检索"（try/except 兜底，不影响主流程）。在回答的 sources 之外追加 `rewrittenQuery` 字段便于前端展示"本次检索的问题"，让医生理解检索依据。

**落地步骤**：第 1 周——历史消息拼装 + token 窗口裁剪（先固定 6 轮/4000 token 内，观察模型报错即缩减）；第 2 周——追问改写接入检索链路并做 10 组"指代问法"对照测试（改写前 vs 改写后命中对比），前端展示改写后的检索问题。

**实用价值**：多轮是医生真实提问方式（一个病例连问 5-8 个问题是常态），当前实现"有会话形、无会话神"，该方向把产品从"单轮问答器"变成"会诊对话助手"，是演示效果提升最明显的一步。

**风险与备选方案**：历史污染（模型把前面的错答带进后续回答）——方案：只拼用户问题与 AI 回答，且 AI 回答截断保存最近 300 字；改写增加一次额外模型调用可能变慢——备选：改写失败直接用原句、或先用规则（检测疑问词）决定是否改写。

### 方向3：一键导出标准化随访文书

**背景与痛点**：医生完成一场知识问答或一份 DR 筛查后，要口头/手动整理成随访记录或筛查意见；`/api/chat/sessions/<id>/export` 虽然已存在，但只是原始对话导出，不能直接进病历或随访档案，`python-docx` 已在依赖中却未用于文书生成。

**创新点**：新增「随访文书导出」：把一次问答会话（或一份诊断报告）排版成带页眉页脚、签名栏、免责声明的 docx/md 文书，供医生补充意见后打印存档。

**方案设计**：① 新建 `utils/report_exporter.py`：`export_chat_session(session)` 提取会话要点——问题/要点回答（按 sources 标注引用）、结论句、AI 建议、参考文献清单；`export_diagnosis_report(report)` 输出筛查信息、患者基本信息、DR 分级与置信度、风险等级、随访计划、生活方式建议；② docx 模板内置标题「AI 辅助筛查/问答记录（教学演示用途）」+ 声明段落「本记录由 AI 生成并仅供参考，须经执业医师审核签字后方可归档」；文末固定留出「医师意见」与「签名/日期」手写栏；③ `chat_history.py` 的 export 接口增加 `format=docx` 分支（保留 json 兼容），`reports.py` 增加 `/api/reports/<id>/export`；④ 前端 ChatHistory 与 ReportDetail 各加导出按钮。

**落地步骤**：第 1 周（易）：会话导出 docx + 报告导出 docx + 两处前端按钮，全流程可跑通；第 2 周（可选）：增加 md/打印友好视图，把导出记录写入 `export_logs` 表（谁在何时导出了哪份文书，便于合规留痕）。

**实用价值**：真实使用者是科室教学秘书与规培医生——做病例汇报、教学查房准备、随访提醒记录都需要"可打印、可签字"的载体；同时"AI 生成 + 医师签字"正是医疗 AI 演示项目最标准的合规表达，答辩时是加分亮点。

**风险与备选方案**：文书格式返工——先在团队内约定固定模板再写代码；docx 依赖在 Windows 服务器上已安装。备选：若评审更看重轻量，可先只做 Markdown 导出再扩展 docx。

## 主题二：RAG 与图像智能升级

### 方向4：检索质量评估工作台

**背景与痛点**：知识库的相似度阈值 0.7、top-5、chunk 1000/200 都来自默认设置，没有任何机制知道"检索到底准不准"；医生答错时通常归因模型，实际问题常在检索。没有评估数据就无法调参，这是 RAG 系统从"能跑"到"可信"的最大瓶颈。

**创新点**：做一个面向维护者的「检索测试台 + 评估集」：输入一组问题（人工构造或来自真实会话），逐个展示当前检索命中的片段与相似度，由操作者标注"相关/不相关/缺失"，系统自动汇总 Recall@k、命中率、平均相似度，并支持参数对照实验（改阈值/改 top_k 后重跑对比），让调参从拍脑袋变成看数据。

**方案设计**：① 新模型 `RetrievalEvalItem`：id、kb_id、query、参数快照（threshold/top_k/chunk 设置）、检索 JSON 结果、人工标签（relevant/irrelevant/missing）、created_by、created_at；② 新路由 `routes/retrieval_eval.py`：`POST /api/eval/items`（运行一次检索并保存快照，内部调 `VectorManager.hybrid_search`，不重复实现检索逻辑）、`PUT /api/eval/items/<id>/label`（标注）、`GET /api/eval/report?kb_id=`（按参数快照分组统计：样本数、相关命中数、Recall@1/@3/@5、无命中率）；③ 前端新页面 `RAGEval.tsx`：左侧问题输入与参数面板，中部命中列表带相似度条与"相关/不相关"按钮，右侧报表卡片；④ 与方向1 的"引用有误"反馈表共享：把真实问答中的负反馈（医生点踩）自动回流成一条待标注样本，形成评估数据自增长。

**落地步骤**：第 1 周——模型与路由（运行检索 + 标注 + 简单计数报表）；第 2 周——前端工作台页面，导入 20 条来自 DR 常见问题的种子样本，跑出第一份 Recall 报表并据此调整默认阈值；第 3 周（可选）——参数 A/B 对照视图。

**实用价值**：使用者是知识库管理员/带教老师。学校答辩中"我们如何证明检索质量"常被追问，本方向给出数据答案；对真实医院试点，评估集也是上线前的验收物。

**风险与备选方案**：标注工作量大——种子样本控制在 20-40 条即可说明方法；避免引入人工成本争议，文案定位为"教学与演示用途的检索质检工具"。备选：不做独立页面，先在 chat 回答末尾收集"这个回答有帮助吗"并将负反馈样例列成待审列表。

### 方向5：命中片段邻段扩展与冗余去重

**背景与痛点**：文档按 1000 字/200 字重叠切块后，同一知识（如"糖尿病视网膜病变分期标准"）可能被切在两块之间，向量命中只是"半个答案"；top-5 命中里同一文档相邻块反复出现，浪费上下文窗口且引用重复。全局设置只有单一 chunk 参数，无法针对检索后处理调优。

**创新点**：检索后处理管线：① 对命中块按文档分组，若同文档命中块序号相邻则拼接为完整段落（块表补充 `chunk_index`/`start_char` 后即可判断连续性）；② 拼接后按相似度去重 + 最大块数/字符数上限（如拼接后单篇最多 1500 字、全文最多 3 篇），既给模型更完整的知识片段，又控制 prompt 长度。

**方案设计**：`utils/vector_manager.py` 在 `hybrid_search` 之后新增 `expand_and_dedupe(results)`：依赖 `document_vectors` 表中补齐的 `chunk_index`（SQLite 元数据 + pgvector 均有迁移脚本机制，加一列并写一个回填脚本即可）；命中块携带其原文档 id、chunk 顺序与所在文档的标题；拼接后的片段在返回前重新标相似度（取组内最高值），保证前端引用排序正确。`KnowledgeBaseSettings` 增加 `enable_neighbor_expand`、`expand_max_chars` 两个可选字段，设置页加开关。方向1 的引用定位可直接复用扩展后的片段信息。

**落地步骤**：第 1 周——chunk_index 迁移与回填 + `expand_and_dedupe` 实现与单元测试（构造一个被切开的文档验证拼接）；第 2 周——接入 chat 与 kb search 链路、设置开关 + 前端设置页两项、用方向4 的评估集做拼接前后 Recall 对比。

**实用价值**：直接提升答案完整度与连贯性，减少"模型一本正经地把半个知识点讲完"的情况；对医生来说表现为回答更少断章取义，引用更像"原文"而非"碎片"。

**风险与备选方案**：拼接会引入跨块噪声（两块主题不同却被拼在一起）——用块间文本相似度阈值（≥0.75 才允许拼）控制；备选：不做拼接，仅做"取命中块所在文档前 200 字 + 后 200 字"的简单窗口扩展，改动量减半。

### 方向6：眼底图像 Grad-CAM 病灶热力图

**背景与痛点**：集成分级（0-4 级 + 置信度）目前是纯黑盒——医生看到"3 级、置信 0.83"却看不到模型依据哪里（微动脉瘤？出血点？渗出？）。`grad-cam`、`timm`、`ttach` 都在 requirements 中，`train_model/` 下有现成 6 套权重，具备做可解释性输出的全部依赖，但尚未使用。

**创新点**：对分级置信度最高的模型生成 Grad-CAM 热力图，与原图叠加输出，随分析结果与报告一起展示，让"AI 看见的病灶区域"可视化，辅助医生快速定位可疑区域——定位为辅助核对工具而非诊断依据。

**方案设计**：① `services/model_manager.py` 增加 `generate_cam(model_name, image_tensor) -> heatmap_path`：复用已加载模型，对 `model.features`（EfficientNet/ResNet 均为 `features` 层）之后的层做钩子取梯度，无 GPU 时在 CPU 上对单张图计算（单次约 1-3 秒，可接受）；② 热力图以 jpg 存入 `instance/uploads/heatmaps/`，`image_analysis` 相关表增加 `heatmap_path` 列；③ `routes/image_analysis.py` 在 results 与报告接口中返回 heatmap 路径；④ 前端 ImageAnalysis/ReportDetail 用左右对照或透明度滑条展示原图/叠加图；⑤ 图上固定水印「AI 热力图仅辅助定位演示，不构成诊断，请结合临床复核」。

**落地步骤**：第 1 周——选定 densenet121（层结构简单稳定）实现单模型 CAM 生成与保存；第 2 周——接入分析流程与接口返回、前端对照展示；第 3 周——在典型阳性样本（数据集自带标注）上做 10-20 例目视核对，确认热力图大致落在病变区域后写进演示脚本；可选加分：把热力图缩略图一并写入诊断报告导出。

**实用价值**：真实价值在信任与教学：医生示范课、论文配图、答辩演示中，"模型定位到了黄斑区渗出"远比"置信度 0.9"有说服力；也是衔接方向7「报告解读问答」的图像证据基础。

**风险与备选方案**：钩子写错或模型结构差异导致 CAM 报错——先只支持 densenet121，其他模型逐个适配；CPU 推理热力图慢——分析任务本身已异步，热力图作为后处理阶段串行执行并提示"生成中"。备选：不做梯度，用输入遮挡法（把图像分块遮挡后看输出变化）生成显著性图，纯 numpy 实现，无框架依赖。

### 方向7：诊断报告「AI 解读 + 追问」

**背景与痛点**：诊断报告结构完整（分级、置信度、风险等级、随访建议、生活方式建议等字段），但解读文本目前依赖调用方（前端）组织后经 `POST /api/reports` 提交，后端仅落库；报告页没有"为什么是这个风险等级""下一步怎么办"的解释能力，非眼科专业的使用者（如基层医生、患者家属）读起来吃力。

**创新点**：把报告变成可对话对象——报告详情页提供「AI 解读」与「继续追问」：后端按报告 JSON + 对应图像分析结果组装上下文，走统一 chat 链路生成解读，回答可再结合院内指南知识库检索（复用方向1/5 的 RAG 管线），并逐条标注"建议来源 = 报告字段 / 知识库 X / 模型推断"。

**方案设计**：① `routes/reports.py` 新增 `POST /api/reports/<report_id>/explain`：内部调 `call_chat_model` + 可选 `hybrid_search`，把 report.to_dict()（分级、置信度、risk_level、follow_up_plan 等）序列化进 system prompt，约定输出三段式：结论概述 / 依据说明（字段引用 + 文献或知识库条目）/ 明确边界声明；② 数据库不变（解读随会话存 `chat_messages` 即可复用历史能力）；③ 前端 ReportDetail 增加「智能解读」按钮与对话面板，所有解读气泡带统一免责声明；④ admin 可在模型设置里为解读场景配置独立 system_prompt（如更保守的语气）。

**落地步骤**：第 1 周——explain 接口 + 三段式 prompt 调通（用 3 份历史报告人工比对解读质量）；第 2 周——前端面板、会话化（追问形成小会话）、边界声明与字段引用展示。

**实用价值**：直接使用场景是基层医院转诊沟通与教学：全科医生拿到眼底报告后向眼科会诊前，先获得一份结构化的"解读草稿"帮助理解与准备问题；对演示项目则是"图文双模态能力闭环"的叙事核心。注意在界面显著声明「解读不替代阅片诊断，最终结论以执业医师复核为准」，并设计"转人工咨询"按钮跳转报告归属医生。

**风险与备选方案**：报告字段结构变化导致 prompt 失效——解读逻辑读取 to_dict()，与表结构解耦，改表时同步改示例即可；LLM 过度解读置信度——prompt 强制要求输出"模型内部置信度不等于诊断可靠性"的提醒。备选：MVP 先只做"一键生成固定模板解读"（不开放追问），成本最低。

## 主题三：架构与工程化

### 方向8：统一异步任务中心

**背景与痛点**：文档批量向量化（upload-zip/batch/sync-vectors）与图像批量分析目前都在请求线程内执行（部分靠启动后台线程 + status 轮询硬撑），存在三类真实问题：任务中途失败无记录、无重试入口；并发大任务挤占请求线程；前端无法看到"总进度/失败项明细"。

**创新点**：引入轻量任务表 + 进程内队列的执行模型：所有耗时操作提交为 job，后台 worker 顺序/小并发执行，job 记录状态机与失败明细，前端统一轮询进度；不引入 Celery/Redis（避免部署复杂度，保持 Dockerfile 单容器可用）。

**方案设计**：① 新模型 `Job`：id、type（vectorize_doc/batch_upload/image_analysis）、params(JSON)、status（pending/running/success/failed/partial）、total/done、error_summary、result_summary、created_by、created_at/finished_at；② `app/__init__.py` 启动时拉起 worker（`threading.Thread` + 内置 `queue.Queue`，daemon 线程，单进程部署模型下够用）；③ `routes/kb.py` 的 zip/batch/vectorize 接口改为「提交 Job + 返回 job_id」并保持旧同步接口为可选参数（`?sync=1`）以兼容现有前端页面，同时把 image_analysis 的 start 也纳入同一体系；④ `routes/jobs.py`：`GET /api/jobs?type=&status=`、`GET /api/jobs/<id>`（含子项进度明细）；⑤ 前端做一个通用 `JobProgress` 组件（进度条 + 失败项列表 + 重试按钮），先挂在 DocumentManagement 的批量上传上。

**落地步骤**：第 1 周——Job 模型 + 提交/查询/列表接口 + 简单串行 worker 跑通单文档向量化任务；第 2 周——把 zip 批量导入迁入任务体系（子项明细：每个文件成功/失败原因），前端进度组件；第 3 周——图像批量分析迁入，重试与"partial 失败可单独重试失败文件"。

**实用价值**：让"导入 200 个文件 / 一次分析 50 张眼底图"成为稳定能力，而不是演示到一半卡死；失败的逐文件原因（格式不支持、超时、向量化报错）对维护者是排障关键信息。这也是学生团队能讲清楚的工程亮点（任务状态机、失败重试、前后端进度协议）。

**风险与备选方案**：线程模型在生产多进程部署（如 gunicorn 多 worker）下会重复消费——文档与部署脚本明确"当前面向单进程教学部署"，并预留 `JOB_WORKER_ENABLED` 开关；备选：不做后台队列，仅把现有同步调用包上"任务记录 + 失败重试按钮"，先解决可观测性，队列化后置。

### 方向9：模型用量与问答运营看板

**背景与痛点**：`chat_messages` 已记录每个回答的 `tokens` 与 `model_response_time`，`/api/analysis/stats`、`/api/chat/statistics` 各有单用户口径统计，但缺少管理端全局视图：模型配了多个，哪个快、哪个贵、哪个常出错？知识库哪些文档被高频引用？问答量趋势如何？这些数据全部已在库里，只差聚合与展示。

**创新点**：新增管理端「运营看板」：按日聚合问答量、平均响应延迟、token 消耗估算（`tiktoken` 免费精确计数，成本按配置的可选单价表估算）、各模型错误率、知识库命中分布（从 message.sources 解析）、最近 N 条失败/超时会话的抽样列表——全部只读查询 + 前端图表（recharts 已装）。

**方案设计**：① 新路由 `routes/stats.py`（admin 角色限定）：`GET /api/stats/overview?days=30`（总量/延迟/token 趋势，按日）、`GET /api/stats/models`（按 ModelConfig 分组：消息数、平均延迟、平均 token、错误计数——错误计数需在 chat 路由失败分支补一条 `chat_messages` 的 system 类型占位或独立 `chat_errors` 计数表）、`GET /api/stats/kb`（按 kb_id 聚合引用次数，含文档级 top10）；② 前端 `Dashboard.tsx` 扩展或新增 `OpsDashboard.tsx` 页，recharts 画 4 张图 + 2 个表；③ 单价表做成系统设置 JSON（`ModelConfig` 加 `price_per_1k` 可选字段），无单价时只显示 token 不显示金额。

**落地步骤**：第 1 周——三条统计接口（纯 SQLAlchemy 聚合查询）+ 错误计数埋点；第 2 周——前端看板页与导航接入，用真实使用数据核对各口径后固定展示模板。

**实用价值**：使用者是实验室管理员/带教老师：答辩与验收时需要"系统真实被用过、用量可量化"的数据支撑；对接真实医院试点时，token 成本估算表能直接回答"这套东西跑一年要多少钱"的预算问题。全部基于已有字段，几乎零侵入。

**风险与备选方案**：历史数据中 `tokens` 字段可能大量为 0（早期未统计）——报表中标注"部分历史数据缺失"，并以新数据为主；备选：跳过成本估算，只做问答量与延迟两张图，半天即可完成。

## 主题四：医疗合规落地与教学价值

### 方向10：患者科普问答门户与风险语预警

**背景与痛点**：系统目前的问答、图像分析均面向医生，无法直接演示"面向公众的健康科普"这一最有传播力的场景；而直接放开医生端 AI 给患者又违反安全边界。糖尿病视网膜病变的公众知晓率低、筛查依从性差，恰好需要"低门槛科普问答"这一载体。

**创新点**：在现有体系上外扩一个隔离的「科普门户」：患者/访客只能选择标记为 `public` 的科普知识库进行问答，不可触达内部临床库与图像分析；内置风险语检测——当问题命中"视力骤降/突然看不见/剧烈眼痛/胸痛"等紧急词时，回答被强制替换为「就医提示」并阻断诊断性生成；所有回答附固定免责声明与"转人工咨询"留言入口，留言由 doctor/admin 角色在管理端回复。

**方案设计**：① `KnowledgeBase` 增加 `visibility` 字段（internal/public），`kb.py` 查询与 `chat.py` 检索按角色过滤，public 库的检索与生成走同一 RAG 链路（复用全部现有能力，新增量很小）；② 新模型 `PortalMessage`：id、visitor_name(可选)、contact(可选)、content、reply、status、assigned_to；新路由 `routes/portal.py`：`POST /api/portal/ask`（问科普问题，先过风险词表）、`POST /api/portal/messages`（留言）、doctor 侧 `GET/PUT /api/portal/messages`（列表/回复）；③ 风险词表做成本地 JSON 规则文件（正则 + 关键词，约 30 条种子词，可扩展），命中返回结构化 `emergency_alert`，前端渲染红色就医提示卡（附就近就医建议文案但不提供具体医院排名）；④ 前端新页面 `PortalChat.tsx`（或复用 AIAssistant 组件只读模式）+ 管理端「患者留言」页；⑤ 入口处常驻横幅「本门户用于疾病科普与健康教育，不提供诊断与治疗建议」。

**落地步骤**：第 1 周——visibility 字段与权限过滤 + portal/ask（含风险语检测）；第 2 周——留言表与回复管理 + 前端门户页与留言页，用 15 条种子问题（含 3 条紧急词测试）走查全流程。

**实用价值**：使用场景清晰——校园义诊、社区健康日、医院科普角放一台触屏机即可演示；答辩与宣传中"AI 守住安全边界"（紧急语阻断 + 人工复核留言 + 权限隔离）是最打动评委的合规叙事。整个方向只复用现有 RAG/聊天/权限代码，学生可在 2 周内做出可演示成品。

**风险与备选方案**：风险词表必然不完整（漏判）——设计上"漏判最多给出不严谨的科普回答，且回答自带免责声明"，而"误判只多弹一次就医提醒"，误判方向的代价可接受；备选：不做独立门户页，在现有 chat 里加"游客模式"（免登录 + 自动限定 public 库 + 开启风险词检查），改动更小。

### 方向11：医生投稿→专家审核→自动向量化入知识库

**背景与痛点**：`knowledge_articles` 表（title/content/category/tags/author/views/status：draft/published）早已建好，但它是早期遗留模型，与当前 pgvector 的 RAG 流程脱节：医生有价值的一线经验（本地 DR 筛查 SOP、随访话术）没有正式渠道沉淀成知识库内容；知识库内容只靠 admin 手工上传文档，版本更迭也无从追溯。

**创新点**：把遗留的文章表激活成「投稿-审核-发布-向量化」工作流：doctor 角色在线撰写"临床小贴士/FAQ"草稿；专家/admin 在审核页查看正文与查重预览（与库内现有内容的相似度对比，防止重复入库）；审核通过后自动向量化进入指定知识库并置 published，修订时产生版本记录、旧向量原子替换；来源为"医生投稿"的引用在回答中带作者名。

**方案设计**：① 复用 `KnowledgeArticle`（补 `kb_id`、`version`、`reviewed_by`、`reviewed_at` 字段），新增 `ArticleVersion`（article_id、content 快照、change_note、created_at）用于追溯；② 新路由 `routes/articles.py`：医生 `POST /api/articles`（draft）、`PUT /api/articles/<id>`（改稿/提交审核）；专家/admin `GET /api/articles?status=pending`、`POST /api/articles/<id>/review`（approve/reject + 意见）——审核动作里调 `vector_manager` 把正文切块向量化写入该 kb 的向量表（复用 `process_document` 同款逻辑），拒绝则仅保存意见；`GET /api/articles/<id>/duplicates`（查重：对全文做 hybrid_search 返回近似条目）；③ 前端新增 `Articles.tsx`（投稿/我的稿件）+ `ArticleReview.tsx`（待审列表/正文对照/查重结果/通过按钮）；④ `chat.py` 构建 sources 时若命中文章型文档，带上 author 展示。

**落地步骤**：第 1 周——模型字段扩展与迁移 + 投稿/审核/查重接口（审核通过先同步向量化打通端到端）；第 2 周——版本表、驳回重提流程、前端两页与导航、聊天引用展示作者；第 3 周——邀请 3-5 位成员各投 2 篇真实 DR 科普稿完成一轮审核发布，验证知识库内容质量闭环。

**实用价值**：审核环节本身就是设计好的人工复核机制——比任何"AI 自查"更符合医疗内容合规；对知识库运营者，内容从"管理员手动搬文档"变成"医生共建、专家把关"，知识库会越用越贴合本院/本课程实际；答辩时可讲"知识生产流程 + RAG 内容质量治理"的完整故事。

**风险与备选方案**：审核通过后向量化失败导致状态不一致——用方向8 的 Job 体系承接向量化并标记 published 为"待入库/入库失败"两态；备选：MVP 砍掉版本追溯与查重，只做「投稿-审核-发布入库」，周期压缩到 1 周半。

## 落地优先级建议（给学生的建议顺序）

1. **先做方向1 + 方向2**（可合并为一个 2 周冲刺）：改动集中、风险低，但让问答体验从"单轮黑盒"变成"多轮可溯源"，演示观感提升最大，且方向2 补的是代码里真实存在的缺口。
2. **再做方向4 或方向6 选一**：前者给 RAG 调参提供数据依据（配合方向2 的改写效果对比，答辩素材好），后者是图像侧最能展示"AI 能力"的可视化亮点，可按队伍更擅长后端检索还是视觉模型来选择。
3. **冲刺方向10 作为压轴演示场景**：科普门户 + 紧急语预警 + 人工留言，是 2 周可交付、合规叙事完整、面向公众可展示的收官模块；若时间允许再补方向3（导出文书）作为附属功能。

> 说明：以上方向均未引入付费外部服务；涉及图像/嵌入/对话的算力需求可全部由已配置的 Ollama 本地模型与现有 PyTorch 权重承担。任何进入真实医疗流程的尝试，请在带教老师与伦理审查指导下进行，并始终保留"人工复核为最终裁决"的机制。
