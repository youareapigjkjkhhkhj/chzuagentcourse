# 用户认证与授权模块功能报告

## 一、模块概述与功能定位

### 1.1 模块概述
用户认证与授权模块是糖尿病视网膜病变诊断系统的安全核心，负责用户身份验证、权限管理和会话控制。该模块采用基于JWT（JSON Web Token）的无状态认证机制，支持多角色权限体系，确保系统数据安全和操作合规。

### 1.2 功能定位
- 提供用户注册、登录、登出等基础认证功能
- 实现基于角色的访问控制（RBAC）
- 管理用户信息和权限状态
- 支持用户信息查询、修改和导出
- 提供密码管理和安全验证机制

## 二、核心功能说明

### 2.1 用户认证功能
- **用户注册**：支持管理员创建新用户账户，包含用户名、邮箱、密码等基本信息
- **用户登录**：支持用户名或邮箱登录，验证用户身份并生成访问令牌
- **用户登出**：客户端清除本地存储的token实现登出
- **Token验证**：自动验证请求头中的JWT token，确保请求合法性

### 2.2 用户授权功能
- **角色管理**：支持三种用户角色
  - `user`：普通用户，仅能访问个人数据
  - `doctor`：医生角色，可进行图像分析和诊断
  - `admin`：管理员角色，拥有系统最高权限
- **权限控制**：通过装饰器实现接口级别的权限控制
- **会话管理**：基于JWT的24小时有效会话管理

### 2.3 用户信息管理
- **个人信息查询**：用户可查看自己的详细资料
- **个人信息修改**：用户可更新姓名、电话、科室、职称等信息
- **密码修改**：支持当前密码验证后修改新密码
- **用户列表查询**：管理员可查看所有用户信息，支持分页和搜索

### 2.4 用户管理功能（管理员）
- **创建用户**：管理员可创建新用户并分配角色
- **更新用户**：管理员可修改任意用户的属性和角色
- **删除用户**：管理员可软删除用户（设置为非活跃状态）
- **用户导出**：支持将用户列表导出为Excel文件

## 三、技术实现细节

### 3.1 数据模型
用户数据模型（User）包含以下字段：
- `id`：主键，自增整数
- `username`：用户名，唯一索引
- `email`：邮箱，唯一索引
- `password_hash`：密码哈希值（使用werkzeug.security加密）
- `full_name`：用户姓名
- `phone`：联系电话
- `role`：用户角色（user/doctor/admin）
- `department`：所属科室
- `title`：职称
- `hospital`：所属医院
- `is_active`：账户状态（活跃/非活跃）
- `is_verified`：验证状态
- `created_at`：创建时间
- `updated_at`：更新时间
- `last_login`：最后登录时间

### 3.2 认证机制
- **JWT Token生成**：使用HS256算法签名，包含用户ID、用户名、过期时间等载荷
- **Token验证**：解析并验证JWT签名和有效期
- **密码加密**：使用werkzeug.security的generate_password_hash和check_password_hash
- **认证装饰器**：login_required和admin_required装饰器实现接口权限控制

### 3.3 数据验证
- **用户名验证**：长度3-20字符，仅允许字母、数字、下划线
- **邮箱验证**：标准邮箱格式验证
- **密码验证**：最少8字符，必须包含字母和数字
- **角色验证**：仅允许user、doctor、admin三种角色

### 3.4 安全措施
- 密码哈希存储，不保存明文密码
- Token有效期24小时，过期需重新登录
- 敏感字段修改需要管理员权限
- 软删除机制，保留用户历史数据
- 请求频率限制（通过分页参数控制）

## 四、API端点列表及参数说明

### 4.1 认证相关接口

#### POST /api/auth/register
**功能**：用户注册（管理员权限）

**请求参数**：
```json
{
  "username": "string",    // 必填，用户名
  "email": "string",       // 必填，邮箱
  "password": "string",    // 必填，密码
  "name": "string",        // 必填，姓名
  "role": "string"         // 可选，角色，默认doctor
}
```

**响应示例**：
```json

      "id": 1,
      "username": "doctor1",
      "email": "doctor1@example.com",
      "name": "张医生",
      "role": "doctor"
    }
  }
}
```

## 五、数据流程

### 5.1 用户登录流程
1. 客户端发送用户名/邮箱和密码到登录接口
2. 服务器验证必填字段和字段格式
3. 查询用户记录（支持用户名或邮箱登录）
4. 验证用户存在、密码正确、账户活跃
5. 更新用户最后登录时间
6. 生成JWT token（包含用户ID、用户名、过期时间）
7. 返回用户信息和token给客户端
8. 客户端存储token并在后续请求中携带

### 5.2 请求认证流程
1. 客户端在请求头中携带`Authorization: Bearer {token}`
2. 服务器从请求头中提取token
3. 验证token格式和有效性
4. 解码token获取用户信息
5. 将用户信息添加到请求上下文
6. 执行业务逻辑
7. 返回响应结果

### 5.3 用户信息更新流程
1. 客户端发送更新数据
2. 服务器验证用户身份和权限
3. 验证字段格式和唯一性
4. 更新用户记录
5. 保存到数据库
6. 返回更新后的用户信息

## 六、错误处理机制

### 6.1 错误码定义
| 错误码 | 说明 | HTTP状态码 |
|--------|------|-----------|
| MISSING_REQUIRED_FIELDS | 缺少必填字段 | 400 |
| INVALID_USERNAME | 用户名格式无效 | 400 |
| INVALID_EMAIL | 邮箱格式无效 | 400 |
| INVALID_PASSWORD | 密码格式无效 | 400 |
| INVALID_ROLE | 角色格式无效 | 400 |
| USERNAME_EXISTS | 用户名已存在 | 400 |
| EMAIL_EXISTS | 邮箱已被注册 | 400 |
| USER_NOT_FOUND | 用户不存在 | 404 |
| INVALID_CURRENT_PASSWORD | 当前密码错误 | 400 |
| INVALID_AUTH_FORMAT | 认证格式无效 | 401 |
| MISSING_TOKEN | 缺少认证token | 401 |
| INVALID_TOKEN | token已过期或无效 | 401 |
| ACCESS_DENIED | 没有权限 | 403 |
| ADMIN_REQUIRED | 需要管理员权限 | 403 |
| ACCOUNT_DISABLED | 账户已被禁用 | 403 |
| CANNOT_DELETE_ADMIN | 不能删除管理员账户 | 400 |

### 6.2 错误响应格式
```json
{
  "success": false,
  "message": "错误描述",
  "error_code": "ERROR_CODE",
  "details": {}
}
```

### 6.3 异常处理
- 数据库操作异常：捕获并返回通用错误信息
- Token解析异常：返回token无效错误
- 字段验证异常：返回具体的验证错误信息
- 权限验证异常：返回权限不足错误

## 七、性能与安全考量

### 7.1 性能优化
- 数据库索引：在username和email字段建立唯一索引
- 分页查询：用户列表支持分页，避免一次性加载大量数据
- 查询优化：使用SQLAlchemy的查询优化功能
- 缓存策略：用户信息可考虑缓存（当前未实现）

### 7.2 安全措施
- 密码安全：使用werkzeug.security进行密码哈希
- Token安全：JWT签名验证，防止token伪造
- 权限控制：基于角色的访问控制，接口级别权限验证
- 输入验证：所有输入字段进行格式和长度验证
- SQL注入防护：使用ORM（SQLAlchemy）防止SQL注入
- XSS防护：前端输入过滤和转义
- HTTPS传输：生产环境强制使用HTTPS

### 7.3 审计日志
- 记录用户登录时间
- 记录用户信息修改时间
- 记录用户创建和删除操作
- 可扩展：记录关键操作日志
