第三章 系统需求分析与设计
3.1 系统需求分析
在构建基于机器学习的糖尿病辅助诊断系统之前，有必要对系统的整体需求进行明确分析，使系统设计和开发过程具有清晰的目标和可行的实现路径。系统需求主要包括功能性需求和非功能性需求两个方面，分别从用户角度和系统性能角度阐述系统应具备的能力和特性。
3.1.1 功能性需求分析
功能性需求主要由系统的预期使用场景决定。本系统面向医生、医技人员以及管理人员等用户群体，旨在为糖尿病视网膜病变的辅助筛查提供便捷、高效的工具。主要功能需求如下：
（1）用户管理功能
系统应提供基本的用户注册、登录和权限管理功能，不同类型的用户根据其身份拥有不同的操作权限。系统需确保用户信息的合法性和安全性，支持用户信息的修改与维护。
（2）患者信息管理
系统应支持患者基本信息的录入、查询和更新，包括姓名、性别、年龄、病史等内容。同时，系统需能够关联患者的图像记录和诊断结果，以便医生进行持续跟踪和复查。
（3）图像上传与管理
作为诊断的重要输入数据，系统应提供便捷的眼底图像上传接口，支持常见医学图像格式。上传完成后，系统应对图像进行统一管理，包括列表查看、分类整理和历史记录存档等。
（4）图像预处理与模型分析功能
系统应能够自动对上传的眼底图像进行预处理操作，如亮度校正、归一化和裁剪等。随后调用训练好的诊断模型，对图像进行自动分析，并给出预测结果，如病变等级评估、风险提示等。
（5）诊断结果展示与报告生成
系统应以清晰直观的方式展示分析结果，包括模型输出、概率分布、可视化标注等信息。同时，系统应支持生成诊断报告，并可将报告与患者档案进行关联。
（6）数据记录与查询
系统应提供诊断记录的保存与检索功能，使医生能够查看诊断历史、浏览过往图像以及分析发展趋势，便于长期随访与临床管理。
（7）AI助手与知识库功能
系统应提供基于大语言模型的AI智能问答功能，支持医生或患者咨询糖尿病视网膜病变相关知识；构建医学知识库，支持文档上传、语义检索和知识管理，为AI助手提供专业知识支撑。
3.1.2 非功能性需求分析
非功能性需求是保证系统可用性和可靠性的重要方面，涵盖性能、安全性、可扩展性等内容。
（1）系统性能需求
系统应能够在合理时间内响应用户操作，尤其在调用深度学习模型进行推理时，应确保推理延迟不影响医生使用体验。对于并发使用场景，系统应具备一定的处理能力，保证多用户同时访问时仍保持稳定运行。
（2）系统安全性需求
由于系统涉及患者隐私信息和医疗数据，必须具备严格的安全防护措施，包括数据传输加密、访问权限控制以及服务器端数据保护机制。此外，系统需遵循相关医疗数据管理规范，确保数据不会被未经授权的人员获取或篡改。
（3）可扩展性需求
随着模型的更新和功能需求的变化，系统应具备良好的扩展能力。如模型接口可替换、数据表结构可扩展、功能模块可增加等，以便未来支持更多疾病类型或更多分析功能。
（4）维护性需求
系统应具备良好的可维护性，包括模块化设计、清晰的代码结构和规范的文档记录。便于后续维护人员对系统进行更新、优化和调试。
3.2 系统总体架构设计
在明确系统需求之后，为确保系统各功能模块能够稳定、高效地协同工作，需要对系统总体架构进行合理规划。本系统采用典型的 B/S（Browser/Server）架构，通过浏览器作为主要访问入口，服务器负责业务逻辑处理、数据管理和模型推理服务。该架构具有部署简便、更新集中、跨平台性强等优势，适合医疗辅助诊断系统的应用场景。
3.2.1 技术架构选型
系统整体采用分层架构思想，将前端展示层、后端业务层、数据存储层以及智能模型层进行分离，使各模块职责清晰、结构稳定。
（1）前端展示层
前端主要负责用户界面的呈现与交互逻辑，包括图像上传、分析结果展示、报告列表、AI对话等功能。本课题采用 React 18 框架，配合 TypeScript、Vite、Tailwind CSS 和 Framer Motion 构建现代化用户界面。前端通过 HTTP/HTTPS 与后端 RESTful API 进行数据通信，确保界面响应迅速、操作流畅。
（2）后端业务逻辑层
后端是系统的核心部分，负责处理用户请求、管理业务流程以及与数据库和模型服务的通信。本课题采用 Flask 轻量级 Python Web 框架，统一处理用户认证、图像分析、报告生成、AI助手对话等所有业务逻辑。Flask 结合 SQLAlchemy ORM 进行数据库操作，通过 RESTful API 与前端交互，实现结构清晰、扩展灵活的数据通信方式。
（3）数据存储层
系统采用混合数据存储方案。结构化数据（用户信息、患者档案、图像记录、诊断结果、对话历史等）使用 SQLite 嵌入式关系型数据库存储；向量数据（医学知识库文本的向量表示）使用 PostgreSQL 配合 pgvector 扩展存储，支持语义相似度检索，为 RAG-based AI 助手提供知识检索能力。
（4）模型服务层
模型服务层负责智能诊断模型的加载和推理。系统基于 Flask 统一提供模型推理接口，接收图像输入后调用训练好的 CNN 模型（EfficientNet、ResNet、DenseNet）进行预测，返回疾病分级、概率值、Grad-CAM 可视化标注等结果。模型层与业务层紧密集成，支持多模型选择和动态加载，便于模型更新和扩展。
3.2.2 系统架构分层设计
为了提升系统的可维护性和扩展性，系统采用分层架构设计，各层如下：
（1）展示层（Presentation Layer）
负责界面展示与用户交互。主要任务包括：
图像上传页面的呈现；
分析结果的图形化展示（如图像标注、分级结果）；
用户登录和信息管理；
诊断历史记录列表的呈现。
展示层不直接处理业务逻辑，只负责与后端进行接口通信，使浏览器成为轻量化的访问终端。
（2）业务逻辑层（Application Layer）
对展示层的请求进行处理，同时协调数据存储层和模型服务层。主要功能包括：
用户认证与权限验证；

图像信息记录、报告生成等业务流程管理；
调用模型服务接口并处理返回结果；
对前端请求进行合法性校验与响应格式化。
通过模块化设计，使系统逻辑清晰、易于维护。
（3）数据层（Data Layer）
负责系统中所有数据的存储与管理，包括：用户信息数据表、患者基本资料表、图像记录与诊断结果表、模型版本信息表等。数据层通过SQL 与业务层交互，保证系统数据的完整性、安全性与可追溯性。
（4）模型层（Model Layer）
负责辅助诊断模型的加载、推理与结果返回。其主要功能包括：快速响应来自业务层的推理请求、对输入图像进行进一步预处理（如尺寸调整）、返回预测标签、置信度和可视化结果。模型层独立运行能够实现高效计算，并可根据实际需要灵活扩容，如部署多个推理实例以支持高并发访问。
3.3 功能模块详细设计
根据系统需求与总体架构，本系统主要由用户管理模块、患者信息管理模块、图像管理模块、图像分析模块和报告管理模块等组成。各模块相互协作，共同完成糖尿病视网膜病变的辅助诊断流程。本节将对各功能模块的设计思路、主要功能及交互关系进行说明。
3.3.1 用户管理模块设计
用户管理模块主要负责系统用户的身份认证和权限控制。
用户管理模块包括用户注册、登录、密码验证以及权限分配等功能。不同角色（如医生、管理员）在系统中拥有不同操作权限，以确保系统的安全性与规范性。用户可根据系统规则创建账号，并填写必要的身份信息；系统通过账号与密码验证用户身份；系统根据角色设定可访问的功能范围，例如医生可查看患者记录，管理员可进行系统配置与用户管理；系统允许用户修改联系方式、密码等信息。
3.3.2 患者信息管理模块设计
患者信息管理模块实现患者基本资料及其相关诊断信息的系统化管理。模块承担患者信息的录入、编辑、查询和历史数据维护，为图像管理与诊断结果展示提供基础数据支持。
主要功能点包括：
患者基本信息录入：记录患者姓名、性别、年龄、病史等信息；
患者资料查询与搜索：支持按姓名、编号或其他条件快速定位患者信息；
信息维护与更新：支持对患者资料的修改；
诊断记录关联：每位患者可关联多次图像上传与诊断记录，支持长期跟踪与复查。
该模块通过数据库表结构设计实现数据的关联性与完整性。
3.3.3 图像上传与管理模块设计
模块负责用户上传眼底图像并对其进行统一管理。模块支持多种图像格式的上传，并对图像进行分类管理与历史存档，确保图像数据的可追溯性。
主要功能点包括：
图像上传接口：支持本地文件选择上传；
格式校验与预处理触发：对图像格式与大小进行初步检查，上传后自动触发预处理流程；
图像列表管理：医生可查看所有历史上传记录；
图像与患者关联：每张图像需与对应患者信息建立关联，避免数据混淆；
图像删除与恢复（可选）：支持图像管理的基本维护操作。
3.3.4 图像分析模块设计
图像分析模块负责调用深度学习模型对眼底图像进行自动诊断，接收来自图像管理模块的图像输入，并通过模型服务完成病变识别与分级任务，最终将分析结果返回业务层并展示给用户。
主要功能点包括：
图像预处理：包括CLAHE对比度增强、图像归一化、尺寸调整等；
模型推理：调用已部署的CNN深度学习模型（EfficientNet、ResNet、DenseNet系列）生成预测结果；
结果解析：包括病变等级（0-4级）、风险指数、各类别概率值；
可解释性可视化：基于Grad-CAM技术生成注意力热力图，展示模型关注的病变区域；
错误处理机制：如模型加载错误、图像质量不足等情况给出提示。
3.3.5 报告管理模块设计
报告管理模块为医生提供诊断结果的汇总与呈现功能，使诊断过程更加正规化。模块将图像分析结果与患者信息结合，生成结构化诊断报告，并支持历史报告的查询与管理。
主要功能点包括：
报告生成：自动整合患者信息、图像分析结果、生成时间等内容；
报告浏览与下载：允许医生查看历史报告并导出；
报告与患者档案关联：所有报告均与对应患者信息关联，以便长期保存与跟踪。
3.3.6 AI助手与知识库模块设计
AI助手与知识库模块为系统提供智能问答和医学知识管理功能，基于RAG（检索增强生成）技术构建。
主要功能点包括：
AI智能问答：支持医生或患者就糖尿病视网膜病变相关问题进行咨询，系统基于大语言模型生成回答；
对话历史管理：保存多轮对话记录，支持上下文理解和连续对话；
知识库文档管理：支持医学文献、诊疗指南等文档的上传、解析和存储；
语义检索：基于向量相似度实现知识库内容的语义检索，为AI助手提供精准的知识支撑；
模型配置：支持配置不同的大语言模型供应商（OpenAI、Ollama、Qianwen等）和参数。
3.4 数据库设计
数据库设计是系统实现过程中的基础工作，其质量直接影响系统的运行效率和数据管理能力。基于系统需求分析，本系统需要存储用户信息、患者基本资料、眼底图像数据、诊断记录、模型版本、AI对话历史以及知识库内容等。系统采用混合存储方案：结构化数据使用 SQLite 嵌入式关系型数据库存储，向量数据使用 PostgreSQL 配合 pgvector 扩展存储。本节将从概念结构设计、逻辑结构设计以及主要数据表设计三个方面进行说明。
3.4.1 概念结构设计
在概念结构层面，通过使用实体—联系模型（E-R 模型）对系统中的主要实体及其之间的关系进行抽象。系统主要涉及以下实体：
用户实体（User）：记录系统使用者信息，如医生、管理员等；
患者实体（Patient）：存储患者基本资料；
图像实体（Image）：保存上传的眼底图像及其相关属性；
诊断记录实体（Diagnosis）：记录每次图像分析的结果；
模型信息实体（ModelInfo）：保存当前使用的诊断模型版本及参数信息。
主要实体之间的关系如下：
用户与诊断记录之间为 一对多关系（医生可生成多个诊断记录）；
患者与图像之间为 一对多关系（同一患者通常有多张眼底图像）；
图像与诊断记录之间为 一对一或一对多关系（同一图像可对应一次或多次诊断结果，视系统需求而定）；
模型信息与诊断记录之间为 一对多关系（不同版本的模型可能对应不同诊断结果）；
用户与对话记录之间为 一对多关系（一个用户可创建多个AI对话会话）；
会话与消息之间为 一对多关系（一个会话包含多条对话消息）；
知识库文档与文档块之间为 一对多关系（一个文档被切分为多个文本块）。
3.4.2 逻辑结构设计 
根据概念结构设计，将各实体转化为相应的关系模式如下：
SQLite 结构化数据表：
User（UserID, Username, PasswordHash, Role, ContactInfo, CreateTime）；
Patient（PatientID, Name, Gender, Age, MedicalHistory, CreateTime）；
Image（ImageID, PatientID, FilePath, UploadTime, ImageType, Resolution, UploaderID）；
Diagnosis（DiagnosisID, ImageID, PatientID, UserID, ModelID, DiagnosisResult, Confidence, Notes, CreateTime）；
ModelInfo（ModelID, ModelName, Version, Description, DeployTime）；
ChatSession（SessionID, UserID, Title, ModelProvider, CreateTime, UpdateTime）；
ChatMessage（MessageID, SessionID, Role, Content, CreateTime）；
KnowledgeDoc（DocID, Title, FilePath, FileType, UploadTime, Status）；
PostgreSQL + pgvector 向量数据表：
DocumentChunk（ChunkID, DocID, Content, EmbeddingVector, ChunkIndex）；
在逻辑结构设计中，需要考虑实体之间的外键关系，例如：
Image 表中的 PatientID 作为外键与 Patient 表关联；
Diagnosis 表中的 UserID、ImageID、ModelID 分别与对应表关联；
ChatMessage 表中的 SessionID 与 ChatSession 表关联；
DocumentChunk 表中的 DocID 与 KnowledgeDoc 表关联。
通过外键约束机制能够确保数据库内部的数据一致性与完整性。
3.4.3 主要数据表设计
根据关系模式，进一步明确各数据表的字段结构及其设计目的。
（1）用户表（User）
用于存储系统使用者的账户信息。
字段名	类型	说明
UserID	主键	用户唯一标识
Username	字符串	用户名
PasswordHash	字符串	加密后的密码
Role	整型或字符串	用户角色（如医生、管理员）
ContactInfo	字符串	联系方式
CreateTime	时间	账号创建时间
（2）患者信息表（Patient）
用于记录患者基本资料，以便后续图像与诊断结果的关联。
字段名	类型	说明
PatientID	主键	患者唯一标识
Name	字符串	姓名
Gender	字符串	性别
Age	整型	年龄
MedicalHistory	文本	既往病史等信息
CreateTime	时间	录入时间
（3）眼底图像表（Image）
记录每张上传的图像数据与属性。
字段名	类型	说明
ImageID	主键	图像唯一标识
PatientID	外键	对应的患者
FilePath	字符串	图像存储路径
UploadTime	时间	上传时间
ImageType	字符串	图像格式（JPEG/PNG 等）
Resolution	字符串	图像分辨率
UploaderID	外键	上传用户
（4）诊断记录表（Diagnosis）

字段名	类型	说明
DiagnosisID	主键	诊断记录标识
ImageID	外键	对应图像
PatientID	外键	对应患者
UserID	外键	操作医生
ModelID	外键	使用的模型版本
DiagnosisResult	字符串	分级结果或类别标签
Confidence	浮点数	预测概率或可信度
Notes	文本	医生备注

（5）模型信息表（ModelInfo）
用于管理当前系统使用的模型版本及相关描述。
字段名	类型	说明
ModelID	主键	模型唯一标识
ModelName	字符串	模型名称
Version	字符串	模型版本号
Description	文本	模型结构介绍或训练说明
DeployTime	时间	部署时间
（6）对话会话表（ChatSession）
用于存储AI助手对话会话信息。
字段名	类型	说明
SessionID	主键	会话唯一标识
UserID	外键	创建用户
Title	字符串	会话标题
ModelProvider	字符串	使用的模型供应商
CreateTime	时间	创建时间

（7）对话消息表（ChatMessage）
用于存储对话中的消息记录。
字段名	类型	说明
MessageID	主键	消息唯一标识
SessionID	外键	所属会话
Role	字符串	角色（user/assistant）
Content	文本	消息内容
CreateTime	时间	发送时间
（8）知识库文档表（KnowledgeDoc）
用于存储上传的医学知识库文档信息。
字段名	类型	说明
DocID	主键	文档唯一标识
Title	字符串	文档标题
FilePath	字符串	文件存储路径
FileType	字符串	文件类型（PDF/DOC/TXT等）
UploadTime	时间	上传时间

（9）文档块向量表（DocumentChunk）
用于存储文档切分后的文本块及其向量表示（PostgreSQL + pgvector）。
字段名	类型	说明
ChunkID	主键	块唯一标识
DocID	外键	所属文档
Content	文本	文本块内容
EmbeddingVector	向量	文本嵌入向量（1536维）
ChunkIndex	整型	块在文档中的序号
通过以上数据库设计，系统可以有效管理用户信息、图像数据、诊断结果、AI对话历史和知识库内容。混合存储架构（SQLite + PostgreSQL/pgvector）兼顾了结构化数据的完整性和语义检索的灵活性，为后续系统扩展提供了良好基础。
