# 可拓展创新方向 —— 智能笔记助手

## 项目现状速览（写作依据）

「智能笔记助手」是面向个人知识管理场景的轻量 RAG 问答系统：用户上传 `.md/.txt/.pdf` 笔记，`note_service.build_index()` 经 `loader → splitter → embedding → FAISS` 全量重建本地向量索引（`data/vector_store`）；`qa_service.ask()/ask_stream()` 先 `similarity_search(top_k=4)` 召回，再由 `chain.py` 中"仅依据笔记作答、禁止编造、标注来源"的提示词驱动 `gpt-5-mini`（经 `OPENAI_BASE_URL` 代理）流式回答并带溯源。技术栈：Flask + LangChain 1.3 + faiss-cpu + text-embedding-3-small + Vue3/Vite，单 Flask 进程同托管 API 与前端 dist，配置集中在 `config.py/Settings`（.env 可调 chunk=800/overlap=120/top_k）。已实现：笔记上传/列表/读取/删除、索引重建与状态（`/api/index/*`）、问答与 SSE 流式问答（`/api/qa*`）、端到端与 HTTP 冒烟测试。明确边界：单用户无鉴权、索引仅支持全量重建、问答无历史记忆、不能编辑笔记。

以下 10 个方向均从上述真实接口与文件出发，注明改动模块、新增接口与存储结构，按主题归组；难度按"现有技能 + 现有依赖即可动手"标注，高难方向均给出可拆分的 MVP 路径。

## 一、功能增强：把"能问答"变成"好用到离不开"

### 方向1：多轮对话与会话记忆（中）

**背景与痛点**：`qa_service.ask/ask_stream` 每次都是孤立问答——用户问完"第3点展开讲讲"，模型并不记得第3点是什么，只能把问题重新描述得很完整；`ChatPanel.vue` 的消息列表也没有会话边界，混在一起无法回溯。

**创新点**：引入"会话（session）"概念与滑动窗口历史：后端把最近 N 轮对话拼入 Prompt，回答才有"连续性"；前端支持新建/切换多个会话，各会话独立记忆。这是从"问答工具"到"对话助手"最关键的一跳，且完全可复用现有 `build_prompt() | get_llm()` 链式调用，只需给 Prompt 增加一节。

**方案设计**：
- 后端：新增 `services/chat_store.py`，用 Python 标准库 `sqlite3`（零新依赖）建表 `conversations(id INTEGER PK AUTOINCREMENT, session_id TEXT, role TEXT, content TEXT, ts REAL)`，按 `session_id` 建索引；`chain.py` 的 `PROMPT_TEMPLATE` 增加 `【历史对话】{history}` 段（放在用户问题之前），`format_docs` 之外再写一个 `format_history`（仅保留最近 6 轮、超长截断）。
- `QAService.ask/ask_stream` 增加参数 `session_id`：先查历史 → 拼装 `{context, history, question}` → 回答后把 user/assistant 两条写入库。
- 路由（`routes.py`）新增：`POST /api/sessions`（建会话）、`GET /api/sessions`（列表含最后提问时间与消息数）、`DELETE /api/sessions/<id>`；`/api/qa`、`/api/qa/stream` 请求体加可选 `session_id`。
- 前端：`ChatPanel.vue` 左侧/顶部加会话栏（新建、切换、删除），发送与 SSE 解析逻辑把 `session_id` 透传（改 `api.js` 的 `askQA/streamQA` 签名即可）。

**落地步骤（MVP 2~3 周）**：第 1 周：`chat_store.py` + 建表，`qa_service` 串历史跑通非流式（先内存后落 sqlite）；第 2 周：`/api/qa/stream` 带历史 + 会话增删查接口；第 3 周：前端会话栏与切换 UI，并按 `tests/test_full_flow.py` 模式补"追问上下文是否生效"的断言。

**实用价值**：学生复习某门课、研究者追踪某篇论文时可以连续追问而不必重复描述语境——这是知识类 AI 产品留存率最高的使用形态。真实使用者即现有 RAG 教学与个人笔记用户群，属"问卷答得越顺越离不开"的基础能力。

**风险与备选方案**：历史越长上下文越贵且易跑题 → 只保留最近 6 轮 + 每轮长度上限；历史中的旧信息与当前检索冲突时模型可能采信历史 → 提示词中注明"历史仅供参考，事实以笔记上下文为准"；若单测中发现 LangChain 版本 API 差异，可退化为自己拼字符串历史，不依赖框架 Memory 类。

### 方向2：引用片段可视化与原文定位（易）

**背景与痛点**：现在 `/api/qa` 返回的 `sources` 只有 `{source: 文件名, score}`，前端 `ChatPanel.vue` 渲染成一排小标签——用户看到答案却不知道"它凭什么这么答"，想核对原文得自己去翻文件，可信度打折。

**创新点**：把溯源从"文件名"升级为"证据链"：每条来源附上命中的原文片段预览（前 200 字）与相似度，前端按片段折叠展示；点击某条来源，通过**已存在**的 `GET /api/notes/<id>` 拉取全文，在原文中定位片段并滚动高亮。全部改动都建立在现有接口之上，不新增后端能力之外的任何服务。

**方案设计**：后端只需改 `qa_service._sources`：为每个去重后的来源聚合其 top-k 命中的 `page_content` 截断片段，输出 `sources: [{source, score, snippet, chunk_count}]`（`ask` 与 `ask_stream` 的 `done` 事件共用此结构，不破坏既有字段）。前端：`ChatPanel.vue` 在每条消息的"来源"标签下加可展开的"参考片段"卡片列表；点击卡片调用 `api.js` 新增的 `getNote(id)`（包装现有 `GET /api/notes/<id>`），打开原文预览抽屉，用 `indexOf(snippet前50字)` 定位首行并 `highlight` 背景闪烁。

**落地步骤（MVP 1~1.5 周）**：第 1 周：后端 `_sources` 加片段字段并补测试（断言 snippet 来自真实 chunk 文本）；同步改前端来源区为可折叠片段。第 2 周（半周）：原文抽屉与定位高亮。

**实用价值**：任何"引用必须可信"的场景都愿意用——学生对照讲义核验、老师检查 AI 回答是否断章取义、答辩时现场演示"答案出处可点开验证"。这是参赛/答辩演示中最直观的加分项，也是后续做"引用级评估"的数据基础。

**风险与备选方案**：片段与原文因切分边界（`keep_separator=True` 保留分隔符）可能无法精确 `indexOf` → 退化为取片段首句定位或全文顶部展示；同一片段被多条来源重复 → 按片段文本去重后再合并计分。

### 方向3：笔记在线编辑与单篇增量索引（中）

**背景与痛点**：目前改一个错别字只能"删文件 → 重传 → 全量重建"：`delete_note()` 会连带删除整个 FAISS 索引，`build_index()` 对全部笔记重新切分并重新调用嵌入模型——库一大，每次小改都要付全量嵌入成本与等待时间。

**创新点**：给笔记加"在线编辑 + 保存后单篇增量更新"：后端重切分被修改的那一篇，用稳定的 `chunk_id` 定位并删除旧向量、追加新向量（`VectorStoreManager.add()` 已支持追加，只需补"按 id 删除"），实现"改一篇只算一篇"。

**方案设计**：
- 给 chunk 建立稳定标识：`splitter.py` 输出的 Document 在 `build_index()` 入库前按 `note_id + 序号` 写入 `metadata["chunk_id"] = f"{note_id}#{i}"`；`langchain_community` 的 FAISS 支持 `add_documents(..., ids=...)` 与 `delete(ids)`。
- `vectorstore.py` 新增 `update_note(note_id, new_docs)`：从 `data/index_manifest.json`（新增的"笔记 → chunk_id 列表"映射，由 `build_index` 与增量更新共同维护）读出旧 id 并 `delete`，再 `add` 新 chunk 并刷新 manifest。
- 后端路由：`PUT /api/notes/<id>`（接收文本，覆盖写文件，复用 `_safe_name` 校验）；`POST /api/index/update`（遍历有"脏标记"的笔记执行 `update_note`；首次可将"脏标记"简单定义为 mtime 晚于 manifest 记录值，零状态即可实现）。
- 前端：`NotePanel.vue` 每行加"编辑"按钮，弹出 textarea（内容来自现成 `GET /api/notes/<id>`），保存后依次调用 PUT 与 update 并回填状态区。

**落地步骤（MVP 2~3 周）**：第 1 周：`chunk_id` 落 metadata + manifest 读写 + `update_note`，先用脚本级单测验证"改一篇后检索新内容、旧内容不再命中"；第 2 周：PUT 路由 + 脏标记判定；第 3 周：编辑 UI 与自动更新提示、回归全量重建流程不受影响。

**实用价值**：笔记是高频修改资产（补课、改错、续写），这是真实使用者每天都会触发的路径；增量更新同时大幅降低 API 费用与重建等待，也是把项目从"教学 demo"推向"可日常使用"的工程分水岭。

**风险与备选方案**：`FAISS.delete` 后 `.pkl` 文档存储与 `index.ntotal` 同步是常见坑 → 先写单测覆盖"删除后再检索"；若框架版本行为不稳，备选方案是"按笔记拆分子索引目录，单篇重建仅重做该子索引 + 检索时多索引 merge"，代价是检索多一次拼接，收益是彻底绕开 id 删除问题。

## 二、智能升级：从"被动回答"走向"主动学习辅助"

### 方向4：检索置信度判定与追问引导（易）

**背景与痛点**：对库外问题（比如笔记里根本没有的内容），`chain.py` 提示词虽要求"明确告知未找到"，但复杂问题时模型仍可能基于通用知识硬答甚至编造；且每次答完对话就断了，用户不知道下一步该问什么，冷启动期尤其劝退。

**创新点**：双保险改造问答出口——(a) 检索侧置信度门控：`qa_service._retrieve` 拿到 `similarity_search_with_score` 的得分后，若最相关片段得分差于阈值，直接短路输出"笔记中可能没有相关内容，建议换个问法或补充上传"而不调用生成模型；(b) 生成侧追问推荐：正常回答结束后，让同一模型以极小 `max_tokens` 再生成 2~3 个与上下文相关的追问，随 SSE 的 `done` 事件一并下发，前端渲染成可点击的提问 chip，点击即自动发送。

**方案设计**：`config.py` 增加 `RETRIEVAL_SCORE_THRESHOLD` 与 `SUGGEST_COUNT`（.env 可调）；`qa_service.ask/ask_stream` 中：检索得分先经门控判断（短路分支返回 `{"answer": "...", "type": "no_hit"}` 结构）；回答完成后追加一次 `get_llm(temperature=0.2)` 调用，Prompt 为"基于下面笔记片段与刚才的问题，给出 2~3 个值得继续深挖的问题，每行一个，不加编号"；SSE 增加 `{"type": "suggestions", "items": [...]}` 事件。前端 `ChatPanel.vue`：收到 suggestions 渲染 chip 行，点击后走现有 `send()` 流程；`no_hit` 类型消息换一种样式并提示上传引导（引导文案可复用 `NotePanel` 的上传提示）。

**落地步骤（MVP 1~2 周）**：第 1 周：门控短路 + 参数配置 + 单测（构造库外问题断言不触发生成）；第 2 周：追问生成与 SSE 事件、前端 chip 渲染与点击发送。

**实用价值**：直接降低幻觉投诉率（库外问题有了明确交代），同时把"一次提问"变成"一串提问"，提升使用时长；对刚上传第一篇笔记的新用户，追问 chip 是零成本的功能引导。此改动触及每个回答的出口，收益面覆盖全部用户。

**风险与备选方案**：得分阈值对 embedding 分布敏感，不同语料可能误杀 → 阈值默认置空表示关闭，另提供"库内自相似度分位数"校准工具；追问生成多一次模型调用 → 固定 `max_tokens=80` 并允许配置关闭；若代理不稳定，备选纯规则追问（提取答案中的实体/小标题），零成本但质量略糙。

### 方向5：知识点卡片与间隔复习（高）

**背景与痛点**：RAG 解决"查得到"，不解决"记得住"。学生的真实闭环是"笔记 → 理解 → 测验 → 记忆"，当前系统在"测验与记忆"环节完全缺失，考完即忘。

**创新点**：在索引之上叠加"卡片学习层"：用现有 LLM 把高价值 chunk 批量转化为「问答卡片」（问题 + 标准答案 + 出处），存库后用自研轻量间隔重复算法（纯 Python 实现的简化 SM-2，无需新依赖）按遗忘曲线排期，前端提供"复习模式"面板：逐卡自测 → 先想答案再展开核对 → 自评"记住/模糊/忘记"三档反馈 → 调度器决定下次出现日期；配复习统计（每日到期数、正确率、薄弱笔记分布）。

**方案设计**：新增 `services/card_service.py` 与 SQLite 库 `data/card.db`，表 `cards(id TEXT PK, note_id TEXT, chunk_id TEXT, q TEXT, a TEXT, created REAL, ease REAL DEFAULT 2.5, interval_days INTEGER DEFAULT 1, due REAL, last_grade INTEGER)`。生成链路复用现有嵌入索引：写一个"产卡"任务对每个 note 的 chunk 做一次批量 Prompt（输出严格 JSON 数组，解析失败重试 1 次），执行入口放在 `note_service.build_index()` 后异步触发或 `POST /api/cards/generate?note_id=xxx` 按需触发。路由：`GET /api/cards/due`（到期队列）、`POST /api/cards/<id>/review {grade}`（更新调度）、`GET /api/cards/stats`。调度用简化 SM-2：`interval = round(interval * ease)`，grade 档位映射 `ease` 增减。前端新增第三个主面板 `CardsPanel.vue`（与现有 `NotePanel/ChatPanel` 同列布局，复用 `style.css` 设计变量）。

**落地步骤（MVP 3~4 周，先窄后宽）**：第 1 周：卡表 + JSON 生成 Prompt + 对单篇笔记"产卡"的接口与手工校验（质量差就调 Prompt/换限产策略）；第 2 周：复习面板 MVP（显示问题 → 点开答案 → 三档反馈）＋ 简单 `due=today` 排队，不接调度；第 3 周：SM-2 调度与统计接口；第 4 周：到期提醒（后端返回待复习数，前端导航角标）、`build_index` 时自动对新增 chunk 产卡的开关。

**实用价值**：面向备考人群（考研、期末、语言学习）时，这是与"笔记问答"互补的强需求功能——把 200 页讲义变成每天 20 张自测卡，是此类工具最能产生"非用不可"黏性的形态；产出物（卡片包）还可配合方向 10 的知识包导出分享。

**风险与备选方案**：难度高在"卡片质量"与"调度正确性"两处——卡片质量不稳则退化为"只对用户收藏/高频检索的 chunk 产卡"，或输出限定为术语释义/填空两种模板；模型调用成本可配置"按笔记限量"。若模型 API 贵或离线场景，免费替代：把 `OPENAI_BASE_URL` 指向本机 Ollama（`langchain-openai` 兼容 OpenAI 协议，`config.py` 已预留 base_url，零代码改动切换），embedding 同理换 `bge-m3` 本地服务。

### 方向6：主题聚类与知识地图（中）

**背景与痛点**：笔记多了以后（几十篇论文/课程讲义），用户自己都不知道库里有什么、哪些主题占比大，只能"想起什么问什么"，没有全局导航入口。

**创新点**：给知识库做一张"地图"——用 FAISS 自带的 KMeans（`faiss` 库内置 `Kmeans` 类，无需 sklearn 等新依赖）对全部 chunk 向量聚类，每簇挑出离簇心最近的 3 个 chunk 作为代表，让 LLM 为每簇生成 8 字以内的主题名与一句话摘要；结果落盘 `data/topics.json`；前端首页新增"主题导览"栏，展示主题列表与各自笔记数，点选某个主题后问答只在该主题簇内检索（top_k 放大后按簇过滤再排序）。这相当于把"黑盒索引"变成可浏览的知识目录。

**方案设计**：新增 `services/topic_service.py`：`rebuild()` 从 `VectorStoreManager` 暴露的底层索引读取全部向量（`index.reconstruct_n(0, ntotal)` 或先 `load()` 后取 `vs.index` 的向量与 `vs.docstore`），聚类后持久化 `topics.json: {topics: [{id, name, summary, note_ids, center_id}], chunk_to_topic: {chunk_id: topic_id}}`；`vectorstore.py` 增加只读方法 `all_vectors_with_text()`（返回向量 + 对应 chunk 文本与 chunk_id，注意先给 chunk 落 `chunk_id`，见方向 3，二者天然协同）。路由：`POST /api/topics/rebuild`、`GET /api/topics`；`/api/qa` 请求体加可选 `topic_id` 过滤。前端：`App.vue` 在两栏中间或 `NotePanel` 下方加"主题"区；问答区在选中主题时展示"当前浏览：主题X"标识。

**落地步骤（MVP 2~3 周）**：第 1 周：聚类与代表 chunk 提取，落盘结构与刷新接口，先不做 LLM 命名（簇标题用 `collections.Counter` 高频词兜底）；第 2 周：LLM 命名与摘要、主题列表 UI；第 3 周：主题过滤问答与联调。

**实用价值**：对"库大而杂"的真实用户（研究生文献库、教师课程资料库），主题地图解决"回溯知识库结构"的痛点，比全文列表直观得多；答辩演示时"看，我的系统能自动把 60 篇笔记整理成 9 个主题"极具展示力。

**风险与备选方案**：KMeans 的 k 与聚类质量受文本分布影响 → 提供"主题颗粒度"参数（k=笔记数平方根上下浮动），代表 chunk 命名失败时用高频词兜底；中文簇名可能重复 → 生成时让 LLM 参考已有主题名去重。若追求更高精度且允许开源依赖，可引入免费的 `jieba` 做分词后再喂 LLM。

## 三、架构工程化：从 demo 走向可扩展系统

### 方向7：向量 + 全文关键词混合检索（中）

**背景与痛点**：纯向量检索对语义相关性强，但对"精确信号"弱——人名、编号、公式、API 名（如 `OpenAIEmbeddings`、`CHUNK_SIZE=800`）这类必须字面命中的内容，embedding 召回常排在后面甚至漏掉；而个人笔记里恰恰大量是这种术语。

**创新点**：双路召回 + RRF 融合——向量路沿用 FAISS，关键词路用 Python 标准库 `sqlite3` 的 **FTS5 全文索引**（零新依赖）对 chunk 文本建索引，两路各自取 top-k×2，再用 RRF（`score = Σ 1/(60 + rank)`）融合排序。实现后"语义找相关、关键词找精确"互补，术语类问题命中率显著提升；同时检索日志记录命中方式，可量化验证收益。

**方案设计**：新增 `services/chunk_store.py`（或并入 `note_service`）：每次 `build_index` 切分后，把 chunk 序列化写入 SQLite 表 `chunks(chunk_id TEXT PK, note_id TEXT, seq INTEGER, text TEXT, char_count INTEGER)`，并建 FTS5 虚表 `chunks_fts(chunk_id UNINDEXED, text)`，用 `INSERT ... SELECT` 同步（中文字符串在 FTS5 的 unicode61 分词下按整段匹配较弱，可叠加查询词按标点/空格切分后的逐词 OR 策略，或引入免费开源的 jieba 建独立关键词表）。新增 `services/hybrid_retriever.py` 实现 `retrieve(query, k) -> [(chunk_id, rank_score)]`，供 `qa_service._retrieve` 替换 `VectorStoreManager.similarity_search`（保留原方法作对照）。为公平对比可加 `_qa_mode: vector|hybrid` 临时开关，用 `tests/` 下 20 问人工集对比。

**落地步骤（MVP 3 周）**：第 1 周：chunks 表 + FTS5 写入链路（改 `build_index`），检索函数单测通过；第 2 周：RRF 融合替换 `_retrieve` 并跑通 /api/qa 全链路；第 3 周：术语小评测集（20 问×2 模式）对比 + 前端在来源区标注"语义命中/关键词命中"标签（数据已由后端带回）。

**实用价值**：用户存代码片段、文献引用、课程术语时这是刚需改进；从技术含金量看，"混合检索 + RRF"是 RAG 生产化的标准动作，写入简历/答辩都是硬通货。

**风险与备选方案**：中文 FTS5 分词效果不理想是最大风险 → 免费备选路径：a) 查询端把连续中文按 2-gram 拆分再走 FTS 的短语匹配；b) 用 `jieba`（免费开源）在写库与查询两端统一分词；c) 若时间紧，可将本方向退化为"向量检索 + 编辑距离/子串后置过滤"的简易融合。SQLite 文件与 FAISS 的 `data/` 目录同管，备份时注意把 `.db` 一并纳入（可复用方向 10 的知识包）。

### 方向8：轻量多用户与登录隔离（高）

**背景与痛点**：项目是单用户平铺设计：`data/notes/` 一个目录、`data/vector_store/` 一份索引、所有接口无鉴权——局域网里任何访问者都能看、删、改别人的笔记；想给班级/小组用无从谈起。

**创新点**：不加重型框架，用标准库实现"账号 + 口令哈希 + 会话令牌"的最小多用户：注册/登录后，令牌经 `hmac`（Python `hashlib`/`hmac` 标准库，用 `.env` 中的 `SECRET_KEY`）签名；每个用户的笔记目录与 FAISS 索引按 `uid` 分片（`data/notes/{uid}/`、`data/vector_store/faiss_index_{uid}`），所有业务路由经 `before_request` 钩子解析令牌并注入当前用户。改造的关键不是加功能，而是把散落在 `note_service/vectorstore` 里的硬编码路径全部参数化为"按用户解析"。

**方案设计**：SQLite 库 `data/app.db`：`users(id INTEGER PK AUTOINCREMENT, username TEXT UNIQUE, pass_hash TEXT, salt TEXT, created REAL)`（口令用 `hashlib.pbkdf2_hmac` 加盐）；`config.py` 增加 `SECRET_KEY` 并新增 `user_dir(uid) -> Path` 帮助函数；`note_service.list_notes/save_note/build_index/index_status` 与 `VectorStoreManager` 构造均接收 `uid`（目录与索引名带 uid 后缀）；`routes.py` 新增 `POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`、`POST /api/auth/logout`，其余路由组加 `@require_user` 装饰器（解析 `Authorization: Bearer <token>`）。前端：`api.js` 拦截 401 跳登录态，`App.vue` 增加登录/注册视图（复用现有 CSS 变量即可）；会话令牌存 `localStorage`。

**落地步骤（MVP 3~4 周）**：第 1 周：users 表 + 注册/登录/登出接口 + 令牌签发与校验单测；第 2 周：note/vector 路径按 uid 参数化（最核心也最易回归，务必保留单用户兼容：`uid=None` 时回落旧路径）；第 3 周：前端登录页与请求拦截；第 4 周：双账号隔离的端到端验证（A 删不了 B 的笔记、索引互不可见）并加测试。

**实用价值**：直接解锁"小团队/班级共用一套服务"的场景（各自笔记互不可见、共享同一模型代理与机器），是实训平台、课程大作业组队演示、甚至小型知识服务的最短路径；对想走部署方向的学生，这也是权限设计的入门必修课。

**风险与备选方案**：自己写鉴权有安全隐患（令牌泄露、无防爆破）→ 定位为"内网半信任环境"，并在文档中声明边界；免费增强：登录接口加固定延迟与失败次数上限。若评审/使用者要求更标准方案，免费替代是把登录换 `itsdangerous`（Flask 生态、开源免费）签发 JWT，或前置 Nginx `auth_basic`，业务代码零侵入。本方向与方向 3/7 涉及 `chunk_id`/SQLite 的改动相互独立，可分人并行。

## 四、落地与商业化：真正被别人用起来

### 方向9：用量统计与成本估算看板（易）

**背景与痛点**：每次问答背后是代理模型的真实计费（嵌入 + 生成），但系统对用量零感知：个人自费 API 可能某天突然超额，平台运营者无法了解谁的调用多，答辩/演示时也缺少"业务数据"可讲。

**创新点**：在问答出口埋点记账——优先读取 LangChain 响应的 `usage_metadata`（OpenAI 兼容代理通常回传），缺失时用项目已有的 `tiktoken` 依赖估算；每次问答落一条记录（输入 token、输出 token、耗时、命中的笔记数、会话），并提供"近 7 日趋势 / 单会话成本 / 估算费用（按 `.env` 中的单价常量）"接口；前端加一个极简统计面板。

**方案设计**：新增 `services/stats_service.py` 与 `data/stats.db`（sqlite3）：表 `qa_logs(id INTEGER PK AUTOINCREMENT, ts REAL, question TEXT, prompt_tokens INTEGER, completion_tokens INTEGER, latency_ms INTEGER, note_hit INTEGER, session_id TEXT)`；埋点在 `qa_service.ask` 与 `ask_stream`（流式结束事件处统一写库，避免逐 token 写）；`config.py` 增加 `TOKEN_PRICE_PER_1M_IN`/`OUT`（默认按常见代理价给常量，.env 可改）与 `EMBEDDING_PRICE_PER_1M`。路由：`GET /api/stats/overview`（今日次数/tokens/估算成本、近 7 日数组）、`GET /api/stats/recent?limit=20`。前端：新增 `StatsPanel.vue`（或作为 `ChatPanel` 底部折叠区）：今日与近 7 日调用量柱状（纯 CSS/`<div>` 高度即可，不必引图表库）、本次回答消耗（可从 SSE `done` 事件带 `usage` 字段直接渲染在消息下方）。

**落地步骤（MVP 1~1.5 周）**：第 1 周：日志表 + `ask/ask_stream` 埋点 + 统计接口；第 2 周（半周）：前端迷你看板与消息级用量展示。

**实用价值**：个人用户看预算余量、决定是否换更便宜的模型；班级场景给老师看"哪些笔记被问得最多、谁在用"——这些数字既是运营证据，也是答辩中"我们不止做了功能，还做了数据"的例证。

**风险与备选方案**：代理不返回 `usage_metadata` 时估算有偏差 → 标注"估算值"并用 tiktoken 精确计算输入侧（输入文本完全可控），输出侧按字符数折算，误差通常在 10% 内；单价是静态常量 → 注明需按实际代理报价改 `.env`。

### 方向10：知识包导入导出与分享（中）

**背景与痛点**：笔记与索引都躺在 `data/` 目录里，换电脑/换部署环境只能手动拷贝、重传、重建——重建又要重付一遍嵌入费用；想把自己的学习库分享给同学也缺少干净的交付形态。

**创新点**：定义"知识包"格式：`notes/`（原文）+ `vector_store/`（FAISS 索引，附 manifest 记录版本与文件哈希）+ `pack.json`（元信息：生成时间、笔记清单、模型与索引参数）打包成单个 ZIP；导出一键下载，导入一键还原且**向量索引直接可加载、无需重新嵌入**（因为 FAISS 的 `.faiss/.pkl` 本来就是按相对路径持久化的，`vectorstore.py` 的 `chdir` 设计已天然适配解压目录）；导入时对重名笔记自动改名，杜绝覆盖。

**方案设计**：新增 `services/pack_service.py`（`zipfile` + `hashlib`，纯标准库）：`export()` 在 `backend/` 下建临时目录，把 `data/notes`、`data/vector_store` 拷入并写 `pack.json`，`zipfile.ZipFile(..., ZIP_DEFLATED)` 落盘 `backend/packs/notes-pack-<时间戳>.zip`；`import(f)` 流式解压前先校验每个 `member` 文件名（拒绝 `..`/绝对路径穿越，防 ZIP 炸弹则限制总大小与数量），解压到 `data/imports/<随机目录>`，校验 manifest 后按"冲突改名"合并进 `data/notes`，并提示是否把导入向量索引切换为当前库。路由：`POST /api/pack/export`（返回下载 URL/直接 `send_file`）、`POST /api/pack/import`（multipart）。前端：`NotePanel.vue` 工具栏加"导出包 / 导入包"两个按钮（导入走现有 upload 模式，导出用 `window.location` 或 fetch blob 下载）；导入成功后引导调用 `/api/index/status` 刷新。

**落地步骤（MVP 2 周）**：第 1 周：export/import 后端 + 路径安全校验 + "导出→清空目录→导入→检索命中"的往返单测；第 2 周：前端两按钮、导入后状态刷新与冲突改名提示。

**实用价值**：换机迁移、答辩前备份（本地一份包即可演示完整还原）、同学互享"复习包"（可继续叠加方向 5 的卡片包，形成可交易的"课程知识包"雏形）——是走向"知识可携带、可分发"的最小商业化形态。

**风险与备选方案**：FAISS 索引跨机器加载要求 `faiss-cpu` 主版本一致且 `.pkl` 文档存储反序列化安全（本项目已用 `allow_dangerous_deserialization=True`）→ 只接受自己平台导出的包，manifest 记录 faiss 版本号，不匹配时提示"仅导入笔记并重建索引"（兜底路径仍是"纯 notes 导入 + 重建"，功能不失效）；中文文件名在 zip 内编码需统一用 UTF-8（Python 3.11 默认），前端测试时以中文名笔记重点回归。

## 落地优先级建议

面向 2~4 周出 MVP：推荐先做**方向 2 → 方向 4 → 方向 1**——三者均为纯增量改造、不动索引架构，叠加后体验从"能问答"跃迁为"可信、连续、引导式问答"；第二梯队按目标取舍：求技术深度选方向 7，求产品黏性选方向 5，需多用户/迁移则选方向 8/10。
