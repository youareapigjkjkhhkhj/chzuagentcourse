# 研究报告生成器 · 可拓展创新方向

> 本文档面向训练营学生团队：输入研究主题，系统自动走完「规划 → 多论文源检索 → PDF 阅读 → 本地混合 RAG → LLM 分析 → 结构化写作 → Markdown/PDF 导出」8 阶段流水线。每个方向都锚定现有真实代码（文件/函数名可直接检索），只做"跳一步但够得着"的扩展：复用已有依赖与架构，不引入付费外部服务。难度自评：易（现有技能 1~2 周）、中（需小重构 2~3 周）、难（需系统性改造，有分步路径）。

## 一、项目定位与现有能力清单

**定位**：面向研究者/工程师/学生/知识工作者的 Multi-Agent 研究工作台——输入主题自动产出带证据与参考文献的 Markdown/PDF 综述报告。现有能力：① `planner→search→reader→RAG→analyst→writer` 六代理流水线，8 阶段进度可轮询（`api/app.py` `_run_report_job`）；② 检索支持 arXiv/Semantic Scholar/Europe PMC/Crossref/综合并集五通道（`tools/paper_sources.py`），中文主题自动生成英文检索词变体（`search_agent.py`：LLM 翻译 + 22 组词典 + ASCII 兜底）；③ 本地零依赖 RAG——512 维哈希特征向量（`vectorstore/embeddings.py`）+ FAISS 内积 + 自实现 BM25 + 词覆盖率按 0.42/0.43/0.15 融合（`vectorstore/faiss_store.py`），证据以 `[Evidence N]` 块 + 相关度标签输出；④ LLM 客户端多服务商（DeepSeek/OpenAI/自定义兼容）+ 本地响应缓存（`runtime_cache/llm/`，`llm_client.py`），无 Key/断网自动降级抽取式报告；⑤ Vue3 工作台（表单/进度时间线/论文卡/证据列表/报告预览，`frontend/src/`），服务端同源托管，DOMPurify 消毒渲染；⑥ `save_report/save_pdf` 落盘 `generated_reports/{job_id}/`（Playwright 出 A4 PDF）；⑦ 12/12 单元测试（离线）+ 12/12 冒烟测试。已知短板（即创新起点）：任务状态全内存（重启即丢）、正文无引用编号、检索只取第一个非空变体、RAG 库随任务销毁、报告一次性生成不可局部修改。

## 组 A · 功能增强

### 方向1：报告档案库——重启不丢、可搜可管的成果档案（易）

**背景与痛点：** `JobStore` 全内存存储，后端重启后前端任务列表即空（`00-README` 明确写"属预期行为"），而真正有价值的报告文件已落盘 `generated_reports/{job_id}/`，却没有任何浏览/搜索/删除入口，只能手动翻目录。

**创新点：** 把文件系统变成"成果档案库"：为每份报告落一个 `metadata.json`（job_id/topic/paper_source/years_back/language/created_at/文件路径），启动时扫描目录自动重建索引——不改任务存储也能让历史报告"复活"。

**方案设计：** ① `utils/file_utils.py` 新增 `save_metadata(report_dir, meta)`，在 `_run_report_job` 写文件处一并调用；② `api/app.py` 新增 `_scan_archive()`（遍历目录解析 metadata，内存缓存）与端点 `GET /api/archive?q=&source=&limit`（按主题模糊搜索）、`DELETE /api/archive/{job_id}`（删文件 + 索引），并把 `GET /api/reports/{job_id}` 扩展为：内存无记录时按 metadata 组装只读 job（report 全文懒读取，避免一次全量载入）；③ 前端 App.vue 新增"历史报告"标签页，复用现有列表/预览组件。

**落地步骤（2 周）：** W1 定义 metadata schema、写入 + 扫描 + 搜索接口与单测；W2 前端历史页 + 从档案恢复详情与下载、删除按钮与确认。

**实用价值：** 写论文的人会连续几周生成同一主题的多版综述——隔天要找昨天的报告、对比不同论文源的产出，档案库是刚需；也让"重启丢列表"这一最劝退的 demo 缺陷消失。

**风险与备选：** 文件元数据与任务记录两份数据可能不一致——约定 metadata.json 为唯一事实源，任务记录只读不复用；删除需级联清 `runtime_cache` 无关文件。备选：不删只归档（加 `archived` 标记），先规避误删风险。

### 方向2：引用级溯源——让每个论断都能点到出处论文（易）

**背景与痛点：** 现有报告正文与 `## References` 互相独立、没有编号对应；证据列表只截取 700 字符（`_slim_evidence`），用户无法确认"这句结论出自哪篇论文"，信任度是 AI 综述工具的第一道坎。`02-项目目标` 的范围外清单也点名了"引用级溯源与证据高亮"。

**创新点：** 双保险的引用标注管线：writer 按要求在论断句尾写 `[[E:n]]`，后处理校验器把 `[[E:n]]` 替换为正文 `[引用编号]`，并生成 citations 映射表驱动前端高亮与定位。

**方案设计：** ① 证据链路已有天然锚点：`build_rag_context` 里 Evidence N 与 chunk 的 `paper_index` 一一对应，而 `paper_index` 就是 `references`（papers）的下标；② `_run_report_job` 在调用 `write_report` 前据此生成 `ref_by_evidence` 映射（`{1: 3, 2: 3, 3: 7, …}`），写入 prompt；③ writer prompt 增加"在每条论断句尾用 [[E:序号]] 标注证据，禁止标注不存在的 E 编号"；④ 新增 `utils/citation_annotate.py`：解析正文全部 `[[E:n]]`，越界/重复则剔除并记 warning，替换为 `[参考文献序号]`，把包含 `[[E:n]]` 的句子切片为 `citations: [{sentence, evidence_id, ref_no}]` 存入 job；⑤ `file_utils.py` 的下载 `kind` 扩展预留 docx/bib 场景；⑥ 前端 ReportPreview 对句尾引用上标染色、点击 `scrollIntoView` 定位 EvidenceList 对应卡片（给每条 evidence 加 `id` 锚点）。

**落地步骤（2 周）：** W1 prompt 约定 + 标注解析器 + 越界剔除单测；W2 接入流水线、job 返回 citations、前端染色与定位。

**实用价值：** 学术诚信是硬需求——导师/审稿人只问一句"这个结论哪来的"；综述初稿能逐句对回原文，是学生交作业、研究员写 related work 时最想要的功能。

**风险与备选：** LLM 可能漏标/乱标——校验器一律兜底为删标记并 warn（宁可无标注不可错标注）；编号随重排漂移——以证据在 rag_context 中的顺序号为准（构建期稳定）。备选：最低配只做"Evidence Excerpts 段首加论文链接"，两天可完成。

### 方向3：大纲先行——人机协同的分节写作（中）

**背景与痛点：** `planner_agent.plan_task` 返回的是 5 条英文模板步骤，规划形同虚设；报告由 writer 一次 prompt 全篇生成，章节结构用户无法干预，输出"一次定型"不可控。而真实写综述/开题的工作流是"先列提纲、反复调结构、再逐节填内容"。

**创新点：** 把静态规划升级为"大纲协商"：LLM 按主题产出结构化大纲（复用 `invoke_llm`，无 Key 时降级为默认大纲），用户在前端增删/调序/改标题后确认，writer 按大纲逐节写作再拼接。

**方案设计：** ① 新增 `POST /api/reports/plan`（body: topic, language）返回 `{outline: [{section_no, title, focus, questions[]}]}`，`planner_agent` 增加 `plan_outline(topic, llm_config)`；② `ReportRequest` 增加可选 `outline[]`，`_run_report_job` 检测到 `outline` 时进入逐节模式：每节独立 prompt（携带本节 title/focus + 全局 rag_context 裁剪后的对应证据），`write_report` 增加 `outline_sections` 参数，节间插入 LLM 生成的过渡段，最后统一拼 `References`；③ 前端在表单与提交之间插入"大纲编辑器"步骤：可编辑标题/删除/上下移（上下移用手写箭头按钮，避免引拖拽库），并可"保存为我常用大纲"。

**落地步骤（3 周）：** W1 大纲生成接口 + planner 结构化输出 + 前端大纲编辑 UI；W2 writer 逐节模式与拼接、引用编号跨节统一；W3 大纲模板收藏、无 Key 降级回归测试。

**实用价值：** 面向真实写作习惯：开题报告/课程综述先有骨架再填肉；用户可把老师给的目录直接贴成大纲，系统按框生成——"我能控制它写什么"是用户愿意把生成结果当初稿的前提。

**风险与备选：** 逐节调用 token 上升、节间风格/衔接不稳——每节 prompt 携带"上一节末句摘要"并要求首句承接；若成本敏感，备选做"大纲可编辑但保持一次性写作"（难度降为易），只收获结构可控。

## 组 B · 智能升级

### 方向4：多变体并集召回 + 本地混合重排（中）

**背景与痛点：** `search_agent._query_variants` 生成多组检索词变体，但主循环"遇到第一个非空结果就返回"——同一主题的不同表述（如"图神经网络"的翻译、缩写、同义词）只覆盖其中一条通道，召回显著不足；`all_open` 并集也只做字段级去重，不做相关性排序。

**创新点：** 让所有变体都真正参与检索：逐变体取回结果后按论文身份归一化去重（DOI / arXiv ID / 标题小写折叠），再用**现有本地能力**重排——把每篇论文的 title+abstract 拼成文本，走 `HashingEmbeddingModel`+BM25 的混合打分（复用 `faiss_store` 的 0.42/0.43/0.15 权重思路），叠加元数据加成（近 3 年、有开放 PDF、被引数可选项），取用户要求的 max_results。

**方案设计：** ① `tools/paper_sources.py` 新增 `merge_papers_by_identity(list)`（归一化键按 doi → arxiv_id → 小写标题折叠，保留来源标签）；② `search_agent.py` 重构主流程：`for candidate in variants` 全部执行并累计，超时/失败的变体静默跳过，最终 `merge + rerank + top_k`；③ 新增 `tools/rerank.py`，签名 `rerank(papers, topic) -> papers`，内部复用 `vectorstore/embeddings.tokenize_for_retrieval` 做 BM25 计数打分（论文量小，不必建 FAISS）；④ API 形状不变，`all_open` 源自动获得该排序；⑤ 前端 PaperCard 展示"召回命中变体/来源"徽标，便于用户感知提升。

**落地步骤（2~3 周）：** W1 并集与身份归一化去重 + 单测（构造两源同篇样例）；W2 本地打分重排与元数据加成；W3 变体命中徽标、对五通道回归冒烟。

**实用价值：** 检索质量决定报告的下限——调研越深对漏检越敏感的用户立刻受益；改动前后同一主题的论文列表肉眼可见变准，是答辩中最好讲的"对比实验"素材。

**风险与备选：** 请求数 ×变体数，Semantic Scholar/Crossref 免费限额低——变体上限收敛到 3 条并沿用现有串行失败静默；混合打分对中文主题弱——保留 topic 原文与翻译双通道即可。备选：先只合并"LLM 翻译变体 + 原文"两条通道，验证收益后再全量放开。

### 方向5：个人文献库——上传自有 PDF，缓存复用，跨任务检索（中）

**背景与痛点：** 每次任务 `reader_agent` 都重新联网下载 PDF 再抽取（慢、重复、浪费流量），进程结束后向量索引即销毁；更关键的是系统只能检索检索到的论文——用户手里导师发的 PDF、中文学位论文、会议材料（arXiv 之外的世界）完全无法进入证据链。

**创新点：** 新增本地文献库层：读过的 PDF 文本落盘缓存（按 URL 哈希命中即跳过下载），支持用户上传 PDF 入库，任务检索时把"文献库语料 + 当次网络语料"混合进同一个 RAG。

**方案设计：** ① 目录约定 `data/library/{paper_id}/`：`original.pdf + extracted.txt + meta.json`（title/source_url/source/added_at）；② `reader_agent` 加缓存层：下载前查库，命中直接读 `extracted.txt`；③ 新增 `POST /api/library/upload`（multipart，扩展名/大小白名单 ≤20MB）与 `GET /api/library`、`DELETE /api/library/{paper_id}`；PDF 文本抽取抽成独立函数复用 `tools/pdf_reader` 逻辑（若仅支持 URL 则补本地路径分支）；④ 新增 `LibraryStore`（`vectorstore/library_store.py`）：`save/load_all` 走 JSON 文本落盘，加载时重建 `ResearchVectorStore`——论文量小（几十篇级），重建成本可忽略，无需序列化 FAISS，天然规避索引格式漂移；⑤ `ReportRequest` 增加 `corpus: Literal["network","library","both"]="both"`，`rag_agent.build_rag_context` 改为两路语料合并切块检索，证据条目带 `corpus` 徽标；前端在新建任务表单旁放"管理我的文献库"入口。

**落地步骤（3 周）：** W1 文件布局 + 下载缓存层 + `LibraryStore` 加载重建 + 单测；W2 upload/list/delete 接口 + 前端上传入口；W3 双语料混合检索与徽标、清理接口与回归。

**实用价值：** 让工具服务"用户自己的文献"而非只服务 arXiv——中文学位论文、组会分享的 PDF、老师划重点的综述都能成为证据源；同一批论文反复生成多版报告只下载一次，速度与费用双降。

**风险与备选：** 恶意/损坏 PDF 拖慢流程——大小与扩展名白名单、单文件超时、抽取失败仅存 meta 并 warn；语料污染检索——Evidence 卡展示 corpus 来源，支持从任务中排除文献库（corpus=network）。备选：MVP 只做"下载缓存"不做上传（读者态即可复现，周期减半）。

### 方向6：检索质量离线评测台——给每次改进配上数字（中）

**背景与痛点：** `faiss_store` 的融合权重（0.42/0.43/0.15）、相关度阈值（0.72/0.48/0.25）都是拍出来的，后续谁改动 BM25 或换 tokenizer 都没有标尺，可能悄悄伤害旧场景；课程答辩也缺"改进前后对比"的硬数据。

**创新点：** 建一个离线基准集 + 评测脚本：人工标注若干主题的"期望命中的证据段落"，脚本算 recall@k / precision@k / 命中位次，产出一份 Markdown 评测报告存档对比——延续 `tests/test_unit_rag.py` 的"本地、无网络、确定性"传统。

**方案设计：** ① 新增 `benchmark/cases.json`：`[{topic, corpus: {title, text}[] 若干段, gold_chunk_ids: [...]}]`（语料用内置 fixture 文本而非网络检索，保证离线与确定性）；② 新增 `tools/evaluate_rag.py`：对每个 case 走 `chunk_papers → ResearchVectorStore → search`，按 chunk id 判命中，汇总 recall@k（k=3/5/8）、命中平均位次，输出 `bench_result/{timestamp}.md`（表格 + 失败样例的 gold vs 实际 top 段，便于查原因）；③ 在权重/分词/融合策略改动前后各跑一遍形成对照，可顺手把检索断言补充进 `tests/test_unit_rag.py`。

**落地步骤（2~3 周）：** W1 编写 5 个主题 × 每主题 8~10 段的标注 fixture（可直接裁剪现有已生成报告的 evidence 素材）+ 评测脚本；W2 输出报告与失败样例定位、接入 CI 式一键命令（`python -m tools.evaluate_rag`）；W3 做 2 组对比实验（如改 BM25 k1、加中文字符权重的消融）沉淀结论文档。

**实用价值：** 使用者就是本项目后续的每个开发者：改动前先看数字，回归有兜底；对学生团队则是答辩"硬通货"——recall@k 的提升曲线比任何形容词都有说服力。

**风险与备选：** 人工标注主观——在 rubric 里写清判定口径（"含核心方法或结论即算相关"）；fixture 需覆盖中英文。备选：不做统计指标，只在 `tests` 里加"确定性断言集"（改了权重旧用例仍绿），难度降为易。

### 方向7：章节级追问改写——"只重写方法对比那一节"（难）

**背景与痛点：** 报告是一次性全篇生成的：用户看完想"把方法对比写细一点/补充反方观点/语言再学术化"，只能带着新想法整题重跑（重检索、重下载、重花钱、重新等）；llm 本地缓存按完整 prompt 哈希，改一句旧缓存全部作废。这与论文返修的真实节奏（导师意见逐条改）完全脱节。

**创新点：** 把"报告"从字符串升级为"节清单 + 版本"：job 内持久化 `report_sections: [{id, heading, body, evidence_ids}]`，提供"对指定节按指令重写（可选补充检索取证）"的接口，不动其他节，节版本留档可对照。

**方案设计：** ① `writer_agent` 增加结构化模式 `write_report_sections(...) -> sections[]`（prompt 要求输出节 JSON，无 Key 走兜底切分：按 `##` 标题切原文并继承证据）；`_run_report_job` 在完成时把全文切成节存 job；② 新增 `POST /api/reports/{job_id}/refine`，body `{section_id, instruction, re_retrieve: bool}`：后端组装该节原文 + 用户指令 + （可选）用该节 focus 词对当次语料重跑 `build_rag_context` 取新证据，生成该节 v2 追加到 `section_versions`，全篇拼接后重新 `save_report`（PDF 再生失败仅 warn）；③ 前端 ReportPreview 每节标题栏加"改写"按钮：弹出指令输入框与"重检索证据"开关，完成后展示 v1/v2 对照（`difflib` 标准库做行级 diff 即可，无需引库）。

**落地步骤（4 周）：** W1 节清单切分/结构化存储与回归；W2 refine 单节后端 + 节版本存档；W3 前端节级操作与 diff 对照；W4 跨节编号一致性处理（引用编号按全篇重算后同步）与稳定性测试。低配先行：W1 就做"整篇重写但复用已有 papers/rag 证据（跳过检索阅读）"——立省大头 token，也先解决"改一句全重来"的一半痛点。

**实用价值：** 面向返修/润色阶段的真实作者：导师说"对比部分再展开"，用户只动那一节，其余稳定不动——这是把生成器从"玩具"推向"写作工具"的关键一步。

**风险与备选：** 节间指代失联（"如上所述/前文方法"）——重写 prompt 携带全局章节标题清单约束措辞；证据过期——`re_retrieve: true` 强制换证，false 则沿用原文证据提示模型不要新编。备选见落地步骤的低配版。

## 组 C · 架构工程化

### 方向8：任务状态落库与失败重跑（中）

**背景与痛点：** `JobStore` 用进程内 dict + 锁，后端一重启任务列表全丢，运行中任务直接蒸发；`02-项目目标` 风险表把"重启丢失"列为预期行为，但对课堂演示、多开部署都是尴尬点；失败任务只能原参数整单重新提交，无重试入口。

**创新点：** 用 Python 标准库 `sqlite3`（零新依赖）把 JobStore 换成持久化实现，方法签名（create/get/list/update/log/warn）保持不变——既有轮询接口与前端零改动；再加"失败重跑"端点。

**方案设计：** ① 新建 `db/jobs.sqlite`，表 `jobs(job_id TEXT PK, topic TEXT, params_json TEXT, status TEXT, stage TEXT, progress INT, logs_json TEXT, files_json TEXT, created_at TEXT, updated_at TEXT)`，papers/evidence/report 大字段按需懒加载（单独列或拆表 `job_details(job_id, key, value)`，避免列表接口全量读库）；② 重写 `api/app.py` 的 JobStore 为 SQLite 实现，保留 `threading.Lock` 串行化写；启动时把 `status='running'` 的记录置为 `interrupted`（线程无法续跑，诚实标注）；③ 新增 `POST /api/reports/{job_id}/retry`：按 `params_json` 原样重建任务入队（topic 相同且已有 files 时前端先确认覆盖），`/api/reports` 列表默认过滤 interrupted 或加 `?include=all`；④ 前端任务卡加"重跑"按钮。

**落地步骤（2~3 周）：** W1 JobStore 换 SQLite 实现并保持全部接口测试绿（WAL 模式 + 写锁）；W2 启动恢复 interrupted + retry 端点 + 单测；W3 前端重跑按钮与"上次失败原因"展示。

**实用价值：** 服务端形态的分水岭：重启不丢 + 可重跑后，才能放心开给小组/班级共享使用（也是后续多用户化的地基）；对开发者自己，调试时 kill 掉进程不再有心理负担。

**风险与备选：** 与方向 1 的 metadata 双轨并存易混乱——明确职责：job 表管"执行态"，档案库管"成果态"，二者通过 job_id 关联不互写；SQLite 并发写——WAL + 单连接串行化即可，量级远未到瓶颈。备选：不引 SQLite，用 JSONL 追加日志重建内存态（更轻，但查询/更新不如 SQL 顺手）。

### 方向9：LLM 调用记账与缓存治理（易）

**背景与痛点：** `llm_client._log_provider_cache_usage` 已拿到 `prompt_tokens/cached_tokens` 等数据却只 `print`；本地响应缓存好用的同时带来治理盲区——改完 prompt 后旧缓存无法精准清理（只能手删 `runtime_cache/llm/`），用户对"一次报告花了多少 token/钱"完全无感。

**创新点：** 给每次 LLM 调用记账落盘 + 两个管理端点 + 前端用量面板：缓存命中率、tokens、费用估算与"本次报告成本"可见，并支持一键清空缓存重新验证。

**方案设计：** ① `llm_client.invoke_llm` 增加可选 `meta: {job_id}` 参数（agents 调用处传入），每次调用（含缓存命中与 miss）append 一行 `{ts, provider, model, hit, prompt_tokens, completion_tokens, cached_tokens, latency_ms, job_id}` 到 `runtime_cache/usage.jsonl`（上限 1 万行，超出裁半轮转）；② 新增 `GET /api/usage`：汇总总调用数/命中率/总 tokens/按 job 归因 + 模型单价表（可配 JSON）估算成本；`DELETE /api/usage/cache`：清空缓存目录（前端 confirm 后调用）；③ 前端加"用量"抽屉：本次报告成本 + 近 N 次调用柱状图（原生 div 宽度即可，不引图表库）。

**落地步骤（1~2 周）：** W1 记账写入与轮转、命中/未命中两类单测；W2 两个端点 + 前端面板与"重新生成以验证新提示词"引导按钮。

**实用价值：** 共享 Key / 课程预算场景的直接刚需：一个主题大概烧多少心里有数；调 prompt 的人需要"改完就清缓存重测"的按钮，否则永远在验证旧结果。

**风险与备选：** JSONL 无限膨胀——条数上限轮转即可；topic 等隐私内容不落库（只记 job_id 关联）；估算价仅是参考。备选：若方向 8 已落地，usage 直接复用其 SQLite 连接建 `usage` 表。

## 组 D · 落地商业化

### 方向10：学术模板 + BibTeX/DOCX 多格式导出（中）

**背景与痛点：** 报告章节结构由 `writer_agent` prompt 内置固定一套（background/findings/methods/limitations/future/conclusion），换用途就得靠用户自己改 prompt 之外无处下手；References 是网页链接式富文本，进不了 Zotero/Overleaf，交课程论文还得人工誊抄文献格式。

**创新点：** 引入"写作模板"概念：不同用途（课程论文/开题报告/英文综述）对应不同节骨架与风格约束，模板化后报告真正"一篇多用"；参考文献导出为标准 `.bib`（零新依赖，纯字符串拼接），可选 Word（`python-docx`，免费开源）输出。

**方案设计：** ① 新增 `backend/templates/`（每模板一个 JSON）：`{id, name, description, sections: [{key, title_zh, title_en, hint}], word_limit, style_note}`，内置 4 个：`default`（与现结构逐节一致，保证向后兼容）、`course_paper_zh`（课程论文：引言/相关工作/方法/实验与讨论/结论/参考文献）、`proposal`（开题报告：选题背景与研究意义/国内外现状/研究内容与方法/进度安排）、`survey_en`；② `ReportRequest` 增加 `template_id`（默认 `default`），writer prompt 按模板节清单与字数约束生成；③ 新增 `utils/bibtex.py`：由 papers 元数据生成 BibTeX——author 字符串按 ", " 切分转 `and` 连接、arXiv 源用 `@misc{... eprint, archivePrefix}`、有 DOI 用 `@article` + `doi`，统一做 UTF-8 转义；④ 下载端点 `kind` 扩为 `Literal["markdown","pdf","bibtex"]`，`.bib` 直接响应附件；⑤ 前端新增模板下拉选择与"下载 BibTeX"按钮（DOCX 导出作为 W3 可选：按模板标题层级套用样式）。

**落地步骤（2~3 周）：** W1 模板 schema + default/course_paper_zh 两模板 + 生成单测；W2 writer 接模板 + bibtex 生成器与下载端点；W3 前端模板选择器 + docx 导出（可选）。

**实用价值：** 本科生交课程论文、研究生交开题报告的"最后一公里"被直接打通：生成 → 转 Word 排版 → 提交；BibTeX 让 Zotero/Overleaf 用户零成本接管文献——这是使用频率最高、最容易向身边同学传播的场景。

**风险与备选：** 模板系统与方向 3 的大纲编辑同源——划清边界：模板是"预设骨架（任务外复用）"，大纲编辑是"单次任务内人工调整"（两个方向可先后落地，接口天然兼容：模板可"实例化"成大纲再交给方向 3）；BibTeX 作者解析对格式怪异的元数据会出错——标注"生成的 .bib 建议人工复核"，错误条目不影响其余。备选：只做"课程论文模板 + BibTeX"（周期压到 1 周），Word 导出后置。
