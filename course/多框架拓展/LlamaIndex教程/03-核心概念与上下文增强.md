# 03 - 核心概念与上下文增强

本篇目标：建立 LlamaIndex 的心智模型——**上下文增强（Context Augmentation）**是什么、Agentic 应用有哪些特征、RAG 的五个阶段，以及 Document 与 Node 的关系。

## 3.1 什么是上下文增强

LLM 在海量公开数据上预训练，但**没有你的数据**——它们在 API 后面、SQL 库里、PDF 和幻灯片中。

**上下文增强**就是把你的数据在需要时提供给 LLM。LlamaIndex 提供从原型到生产的全套工具：接入（ingest）、解析（parse）、索引（index）、处理（process），并把数据访问与 LLM 提示组合成复杂查询工作流。

最流行的上下文增强形式就是 **RAG（检索增强生成）**：在推理时把上下文与 LLM 结合。

## 3.2 Agentic 应用的六个特征（官方定义）

| 特征 | 说明 |
|------|------|
| **LLM Augmentation** | LLM 被工具（任意可调用函数）、记忆、动态提示增强 |
| **Prompt Chaining** | 多次 LLM 调用串联，前一次输出作为下一次输入 |
| **Routing** | 用 LLM 决定应用下一步走向哪个分支或状态 |
| **Parallelism** | 能并行执行多个步骤或动作 |
| **Orchestration** | 用层级化的 LLM 结构编排更低层的动作 |
| **Reflection** | LLM 反思并校验先前步骤的输出，用来指导下一步 |

在 LlamaIndex 中，用 `Workflow` 类编排这些步骤与 LLM 调用（见 [16-Workflows工作流.md](16-Workflows工作流.md)）。

## 3.3 Agent 与 Workflow 的区别（官方定义）

| 概念 | 定义 |
|------|------|
| **Agent** | "Agentic application"的一个实例：把 LLM 与工具、记忆组合，在**推理循环**中半自主决定下一步用哪个工具（如果有） |
| **Workflow** | 一种**事件驱动**抽象，用来编排一系列步骤与 LLM 调用；可实现任何 agentic 应用，是 LlamaIndex 的核心组件 |

Agent 的典型循环：

1. 收到用户消息
2. LLM 结合历史、工具、最新消息决定下一步动作
3. 可能调用一个或多个工具
4. 解释工具输出，决定下一步
5. 不再调用工具时，返回最终结果

## 3.4 RAG 的五个阶段（核心骨架）

```
┌─────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐   ┌────────────┐
│ Loading │ → │ Indexing │ → │ Storing │ → │ Querying │ → │ Evaluation │
└─────────┘   └──────────┘   └─────────┘   └──────────┘   └────────────┘
   接入数据      向量化建索引      存索引         检索+生成       评估效果
```

| 阶段 | 做什么 | 本教程对应 |
|------|--------|-----------|
| **Loading** | 从数据源（文件/PDF/网页/数据库/API）取数据 | [04](04-数据加载与连接器.md)、[05](05-文档节点与切分.md) |
| **Indexing** | 创建便于查询的数据结构，通常是 **vector embeddings** + 元数据策略 | [06](06-模型配置Settings.md)、[07](07-索引Index.md) |
| **Storing** | 存储索引与元数据，避免重复索引 | [08](08-存储与持久化.md) |
| **Querying** | 子查询、多步查询、混合策略等利用方式 | [09](09-检索器Retriever.md)~[13](13-聊天引擎ChatEngine.md) |
| **Evaluation** | 客观衡量准确性、忠实度、速度 | [17](17-评估与部署.md) |

## 3.5 各阶段的关键术语

### Loading 阶段

| 术语 | 含义 |
|------|------|
| **Document** | 数据源的容器（一个 PDF、一次 API 输出、一次数据库查询结果的封装） |
| **Node** | LlamaIndex 中的**原子数据单位**，代表源 Document 的一个"块（chunk）"，带有关联文档与其他节点的元数据 |
| **Connectors / Reader** | 数据连接器，把不同来源与格式的数据摄入为 `Document` 和 `Node` |

### Indexing 阶段

| 术语 | 含义 |
|------|------|
| **Indexes** | 便于检索的数据结构；通常生成向量嵌入存进**向量存储（vector store）**，也可存各类元数据 |
| **Embeddings** | 数据的数值化表示；查询时把 query 也转成 embedding，由向量库找数值相近的数据 |

### Querying 阶段

| 术语 | 含义 |
|------|------|
| **Retrievers** | 定义给定查询时如何高效从索引取回相关上下文——**检索策略直接决定相关性与效率** |
| **Routers** | 决定用哪个 retriever；`RouterRetriever` 依据候选的元数据与查询选择一个或多个检索器执行 |
| **Node Postprocessors** | 对检索到的一组节点做变换、过滤或重排序 |
| **Response Synthesizers** | 用用户查询 + 一组检索文本块，生成最终响应 |

## 3.6 高层 API 与低层 API（给不同水平的用户）

官方设计：

- **高级 API**：5 行代码完成摄入与查询（[02-快速开始.md](02-快速开始.md)）
- **低层 API**：可自定义与扩展**任何模块**——数据连接器、索引、检索器、查询引擎、重排模块

本教程的结构正是沿着这条线：先用高层，再逐步下探到各模块。

## 3.7 五种典型应用形态（官方）

| 形态 | 说明 |
|------|------|
| **Agents** | 由 LLM 驱动的自动决策者，通过工具与世界交互，动态决定步骤 |
| **Workflows** | 事件驱动编排，可实现任何 agentic 应用 |
| **Structured Data Extraction** | 用 Pydantic 抽取器按精确结构从非结构化数据中提取，类型安全 |
| **Query Engines** | 端到端问答流，输入自然语言查询，返回响应 + 参考上下文 |
| **Chat Engines** | 端到端对话流（多轮来回，而非单轮问答） |

## 关键概念速查

| 概念 | 一句话 |
|------|--------|
| Context Augmentation | 把你的数据适时提供给 LLM |
| Document | 数据源容器 |
| Node | 数据原子单位（= Document 的一个 chunk） |
| Index | 便于检索的数据结构（含向量与元数据） |
| Retriever | 定义"怎么检索" |
| Router | 决定"用哪个检索器" |
| Postprocessor | 检索后的过滤/重排 |
| Response Synthesizer | 用上下文生成答案 |
| Agent | 推理循环 + 工具的半自主软件 |
| Workflow | 事件驱动的编排抽象 |

## 注意事项

- Node 的切分质量直接决定检索质量——**过度切分破坏语义，切分不足带来噪声**。
- 索引类型（向量/摘要/知识图谱）应在**摄入之前**确定，否则更换策略常常需要重新切分与重建索引。
- 检索性能是"整个技术栈"的涌现属性（向量库、解析器、LLM 共同决定），不是框架的单独承诺。
