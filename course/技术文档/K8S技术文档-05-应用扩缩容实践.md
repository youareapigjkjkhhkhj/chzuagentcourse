## 1. 扩缩容核心概念

### 1.1 为什么要扩缩容

```
流量增加:
  1 个 Pod → 响应慢/超时 → 用户体验差
  扩容到 4 个 Pod → 分担流量 → 正常响应

流量减少:
  4 个 Pod → 资源浪费
  缩容到 2 个 Pod → 节省资源
```

### 1.2 三层扩缩容

Kubernetes 提供三个层次的自动扩缩容：

```
┌─────────────────────────────────────────┐
│  Cluster Autoscaler (CA)                │  ← 节点层：增加/减少节点
│  ┌───────────────────────────────────┐  │
│  │  HPA (Horizontal Pod Autoscaler)  │  │  ← Pod 层：增加/减少副本数
│  │  ┌─────────────────────────────┐  │  │
│  │  │  VPA (Vertical Pod Autoscaler)│  │  │  ← 资源层：调整 CPU/内存
│  │  └─────────────────────────────┘  │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

| 扩缩容器 | 层级 | 作用 |
|----------|------|------|
| HPA | Pod 水平 | 调整 Pod 副本数 |
| VPA | Pod 垂直 | 调整 Pod 资源 requests/limits |
| Cluster Autoscaler | 节点 | 增加/减少集群节点数 |

### 1.3 扩缩容的本质

**扩容**：增加 Deployment 的 replicas 数量 → ReplicaSet 创建新 Pod → 调度器分配节点 → kubelet 启动容器

**缩容**：减少 replicas 数量 → ReplicaSet 终止多余 Pod → 释放资源

```
扩容 (1 → 4):
Deployment (replicas: 1 → 4)
  ↓
ReplicaSet 创建 3 个新 Pod
  ↓
调度器分配节点
  ↓
Pod 1  Pod 2  Pod 3  Pod 4  (全部运行)
```

## 3. ReplicaSet 与副本管理

### 3.1 ReplicaSet 工作机制

```
ReplicaSet (期望: 4 副本)
       ↓ 持续监控
   当前 Pod 数 = 4?
       ↓
   是 → 无操作
   否 → 创建 Pod (不足) 或 终止 Pod (过多)
```

### 3.2 自动维持副本数

如果手动删除一个 Pod，ReplicaSet 会自动创建新 Pod：

```bash
# 删除一个 Pod
kubectl delete pod <pod-name>

# ReplicaSet 立即创建新 Pod
kubectl get pods -w
# 可以看到新 Pod 正在被创建
```

### 3.3 Deployment 与 ReplicaSet 的关系

```
Deployment (replicas: 4, image: v1)
  ↓ 创建
ReplicaSet-v1 (replicas: 4)
  ↓ 创建
Pod-1, Pod-2, Pod-3, Pod-4 (image: v1)
```

更新镜像版本时：
```
Deployment (image: v1 → v2)
  ↓
ReplicaSet-v1 (replicas: 4 → 0)  ← 逐步减少
ReplicaSet-v2 (replicas: 0 → 4)  ← 逐步增加
  ↓
Pod-5, Pod-6, Pod-7, Pod-8 (image: v2)
```

## 4. 负载均衡原理

### 4.1 Service 负载均衡

当 Service 关联多个 Pod 时，流量会被负载均衡到所有 Pod：

```
         Service (ClusterIP: 10.96.0.10)
                    ↓
              kube-proxy
           (iptables/IPVS 规则)
                    ↓ 负载均衡
    ┌────────┬──────┴───────┬────────┐
    ▼        ▼              ▼        ▼
 Pod 1    Pod 2          Pod 3    Pod 4
```

## 5. 水平 Pod 自动扩缩容（HPA）

### 5.1 HPA 工作原理

HPA 根据**观察到的指标**自动调整 Deployment 的副本数：

```
Metrics Server / Custom Metrics API
       ↓ 提供 CPU/内存/自定义指标
HPA Controller
       ↓ 计算: desiredReplicas = ceil(currentReplicas × (currentMetric / targetMetric))
调整 Deployment replicas
       ↓
ReplicaSet 创建/终止 Pod
```

### 5.2 HPA 计算公式

```
期望副本数 = ceil(当前副本数 × (当前指标值 / 目标指标值))

示例:
  当前: 3 副本, CPU 使用率 90%
  目标: CPU 使用率 70%
  期望 = ceil(3 × (90/70)) = ceil(3.86) = 4 副本
```

当指定多个指标时，HPA 对每个指标分别计算，取**最大值**（避免缩容不足）。

### 5.3 HPA 前置条件

```bash
# 安装 Metrics Server（Minikube）
minikube addons enable metrics-server

# 验证 Metrics Server 运行
kubectl get pods -n kube-system | grep metrics-server

# 查看资源使用
kubectl top pods
kubectl top nodes
```

### 5.4 HPA 基础配置

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-frontend
  minReplicas: 3              # 最小副本数
  maxReplicas: 50             # 最大副本数
  metrics:
  # CPU 指标
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization     # 利用率百分比
        averageUtilization: 70
  # 内存指标
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
```

```bash
# 应用 HPA
kubectl apply -f hpa.yaml

# 查看 HPA 状态
kubectl get hpa
```

### 5.5 HPA 高级配置（行为控制）

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-frontend-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-frontend
  minReplicas: 3
  maxReplicas: 50
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Pods                # 自定义 Pod 指标
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: '20'    # 每个 Pod 20 请求/秒
  behavior:
    # 扩容行为：快速扩容
    scaleUp:
      stabilizationWindowSeconds: 0    # 立即扩容
      selectPolicy: Max
      policies:
      - type: Percent
        value: 100                     # 每分钟最多翻倍
        periodSeconds: 60
      - type: Pods
        value: 10                      # 每分钟最多加 10 个 Pod
        periodSeconds: 60
    # 缩容行为：缓慢缩容
    scaleDown:
      stabilizationWindowSeconds: 300  # 5 分钟稳定期
      selectPolicy: Max
      policies:
      - type: Percent
        value: 50                      # 每分钟最多减 50%
        periodSeconds: 60
```

### 5.6 HPA 指标类型

| 指标类型 | 来源 | 示例 |
|----------|------|------|
| Resource | Metrics Server | CPU、内存利用率 |
| Pods | Custom Metrics API | 每秒请求数、队列长度 |
| Object | Custom Metrics API | Ingress QPS |
| External | External Metrics API | SQS 队列深度 |

**使用自定义指标（需要 Prometheus Adapter）**:

```yaml
metrics:
# 基于 Prometheus 自定义指标
- type: Pods
  pods:
    metric:
      name: http_requests_per_second  # 来自 Prometheus
    target:
      type: AverageValue
      averageValue: "100"

# 基于外部指标（如消息队列深度）
- type: External
  external:
    metric:
      name: sqs_queue_depth
      selector:
        matchLabels:
          queue: my-queue
    target:
      type: AverageValue
      averageValue: "30"
```

## 6. 垂直 Pod 自动扩缩容（VPA）

### 6.1 VPA 工作原理

VPA 根据**历史使用模式**自动调整 Pod 的 CPU/内存 requests 和 limits：

```
VPA Recommender (收集 Pod 资源使用数据)
       ↓ 分析历史使用模式
推荐合适的 requests/limits
       ↓
VPA Updater (驱逐需要调整的 Pod)
       ↓
VPA Admission Plugin (在 Pod 创建时注入新资源值)
       ↓
Pod 使用新的 resources 配置启动
```

### 6.2 VPA 组件

| 组件 | 功能 |
|------|------|
| Recommender | 收集指标，计算推荐资源值 |
| Updater | 驱逐需要调整的 Pod |
| Admission Plugin | 在 Pod 创建时注入推荐值 |

### 6.3 VPA 配置

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: my-app-vpa
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind: Deployment
    name: my-app
  updatePolicy:
    updateMode: "Auto"      # Auto | Initial | Off
  resourcePolicy:
    containerPolicies:
    - containerName: '*'
      minAllowed:
        cpu: 100m
        memory: 128Mi
      maxAllowed:
        cpu: 1000m
        memory: 1Gi
```

### 6.4 VPA 更新模式

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| Auto | 自动推荐 + 驱逐重建 Pod | 需要自动调整 |
| Initial | 仅在 Pod 创建时应用推荐 | 新部署优化 |
| Off | 仅推荐，不修改 | 观察阶段、调参 |

### 6.5 VPA 使用建议

- **先用 Off 模式观察**，确认推荐值合理后再切 Auto
- VPA 调整资源需要**重启 Pod**
- **避免与 HPA 同时使用 CPU 指标**（会冲突）
- VPA 适合：难以预测资源需求的批处理/分析任务
- HPA 适合：流量驱动的无状态服务

## 7. 集群自动扩缩容（CA）

### 7.1 CA 工作原理

Cluster Autoscaler 在**节点层**自动扩缩容：

```
扩容触发:
  Pod 处于 Pending（资源不足无法调度）
       ↓
  CA 检查是否有节点组可以容纳这些 Pod
       ↓
  向云平台请求新节点
       ↓
  新节点加入集群 → 调度器分配 Pending Pod

缩容触发:
  节点资源利用率低（低于阈值）
       ↓
  CA 检查节点上的 Pod 是否可以迁移
       ↓
  驱逐 Pod → 删除节点
```

### 7.2 扩容触发条件

| 触发条件 | 说明 |
|----------|------|
| Pod 无法调度 | 因资源不足导致 Pod 处于 Pending |
| 节点亲和性不满足 | 需要特定节点类型 |
| 拓扑分布约束 | 需要特定可用区的节点 |

### 7.3 缩容保护

| 保护机制 | 说明 |
|----------|------|
| 低利用率 | CPU+内存利用率低于阈值（默认 50%） |
| 可迁移性 | 节点上所有 Pod 可迁移到其他节点 |
| 持续时间 | 低利用率持续一定时间（默认 10 分钟） |
| 无 Pending Pod | 没有等待调度的 Pod |
| PDB 保护 | PodDisruptionBudget 阻止驱逐关键 Pod |

### 7.4 CA 关键配置参数

| 参数 | 说明 | 生产推荐 |
|------|------|----------|
| scale-down-delay-after-add | 添加节点后冷却时间 | 10 分钟 |
| scale-down-unneeded-time | 空闲多久后移除 | 10 分钟 |
| scale-down-utilization-threshold | 节点利用率阈值 | 0.5 (50%) |
| max-node-provision-time | 新节点超时 | 15 分钟 |
| balance-similar-node-groups | 跨节点组均衡 | true |

### 7.5 Karpenter（新一代节点扩缩容）

Karpenter 是 AWS 开源的下一代集群自动扩缩容工具：

| 对比项 | Cluster Autoscaler | Karpenter |
|--------|-------------------|-----------|
| 节点组 | 基于预定义节点组 | 动态选择最优实例 |
| 扩容速度 | 较慢（分钟级） | 快速（秒级） |
| 配置 | 需要预先配置 ASG | 自动选择最佳实例 |
| 云支持 | 多云 | 主要 AWS |

## 8. HPA + VPA + CA 协同策略

### 8.1 协同工作流程

```
流量增加
    ↓
1. HPA: 增加 Pod 副本数
    ↓ (节点资源不足)
2. CA: 添加新节点
    ↓ (新节点就绪)
3. 调度器: 将 Pending Pod 调度到新节点
    ↓ (使用模式稳定)
4. VPA: 优化 Pod 资源配置

流量减少
    ↓
1. HPA: 减少 Pod 副本数
    ↓ (节点利用率降低)
2. CA: 移除空闲节点
```

### 8.2 HPA + VPA 兼容策略

| 策略 | HPA 配置 | VPA 配置 | 适用场景 |
|------|----------|----------|----------|
| 指标分离 | 自定义指标（RPS、延迟） | CPU 和内存 | API 服务 |
| 仅推荐 | 标准 CPU/内存 | updateMode: Off | 分析阶段 |
| 资源分区 | CPU 指标 | 内存指标 | 内存密集型应用 |

### 8.3 协同最佳实践

1. **HPA 用自定义指标**，VPA 用 CPU/内存，避免冲突
2. **VPA 先 Off 模式**收集数据，确认后切 Auto
3. **设置 PDB** 防止 CA 驱逐关键 Pod
4. **预留资源余量**，让 HPA 突发扩容时节点有空间
5. **设置 PriorityClass**，高优先级 Pod 优先调度

## 9. 扩缩容实战

### 9.1 实战场景：部署可自动扩缩容的 Web 应用

```yaml
# 1. 部署应用（带资源请求）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        resources:
          requests:
            cpu: 200m
            memory: 256Mi
          limits:
            cpu: 500m
            memory: 512Mi
        ports:
        - containerPort: 80
---
# 2. 创建 Service
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
---
# 3. 配置 HPA
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Percent
        value: 50
        periodSeconds: 60
```

### 9.2 压力测试触发扩容

```bash
# 部署压测工具
kubectl run load-generator --image=busybox:1.36 \
  -- /bin/sh -c "while true; do wget -q -O- http://web-service; done"

# 观察 HPA 扩容
kubectl get hpa -w
# CPU 使用率上升 → HPA 自动扩容

# 观察 Pod 数量变化
kubectl get pods -w
```

### 9.3 停止压测试触发缩容

```bash
# 删除压测工具
kubectl delete pod load-generator

# 观察缩容（需要等待 stabilizationWindowSeconds）
kubectl get hpa -w
```

## 10. 生产环境最佳实践

### 10.1 资源配置原则

```yaml
resources:
  requests:
    cpu: "200m"        # 基于 P95 使用量设置
    memory: "256Mi"    # 基于 P95 使用量设置
  limits:
    cpu: "500m"        # 2-3 倍 requests
    memory: "512Mi"    # 接近 requests，避免 OOM
```

**原则**:
- requests 是调度和 HPA 的基础，必须准确
- CPU limit 可以宽松（允许 burst）
- 内存 limit 接近 requests（防止 OOM Kill 影响稳定性）
- 使用 VPA Off 模式收集数据来优化 requests

### 10.2 HPA 调优建议

1. **优先使用自定义指标** 而非 CPU（网络密集型服务）
2. **设置合理的 minReplicas** 覆盖基线流量
3. **扩容快、缩容慢** 避免抖动
4. **设置 stabilizationWindowSeconds** 防止频繁缩扩
5. **监控 HPA 状态** 确保正常工作

### 10.3 突发流量处理

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0    # 立即扩容
    policies:
    - type: Percent
      value: 200                     # 每分钟最多增加 200%
      periodSeconds: 60
    - type: Pods
      value: 10                      # 或增加 10 个 Pod
      periodSeconds: 60
  scaleDown:
    stabilizationWindowSeconds: 300  # 5 分钟后才缩容
```

### 10.4 PDB 保护

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2            # 至少保持 2 个 Pod 可用
  # 或: maxUnavailable: 1   # 最多 1 个 Pod 不可用
  selector:
    matchLabels:
      app: web
```

> PDB 在节点维护、CA 缩容时保护应用可用性。

### 10.5 扩缩容检查清单

```
□ Metrics Server 已安装并运行
□ Pod 设置了准确的 resources.requests
□ HPA minReplicas 覆盖基线流量
□ HPA maxReplicas 不超过集群容量
□ scaleDown stabilization window 设置合理
□ 配置了 PodDisruptionBudget
□ 监控 HPA 状态和事件
□ VPA 先用 Off 模式观察
□ CA/节点组有足够余量应对突发
```

## 11. 常见问题排查

### 11.1 HPA 显示 unknown

```bash
kubectl get hpa
# TARGETS: <unknown>/70%
```

**原因**: Metrics Server 未安装或未运行

**解决**:
```bash
# Minikube
minikube addons enable metrics-server

# 验证
kubectl top pods
kubectl top nodes
```

### 11.2 HPA 不触发扩容

**排查步骤**:
```bash
# 1. 查看 HPA 状态
kubectl describe hpa <name>

# 2. 检查 Conditions
# ScalingActive: True 表示正常监控
# ScalingLimited: True 表示达到限制

# 3. 检查当前指标
kubectl top pods -l app=web

# 4. 检查 Pod resources.requests
kubectl get deployment <name> -o yaml | grep -A5 requests
```

**常见原因**:
- Pod 没有设置 resources.requests（HPA Utilization 依赖 requests）
- CPU 使用率未超过目标值
- 已达到 maxReplicas

### 11.3 扩容后 Pod 一直 Pending

```bash
kubectl describe pod <pending-pod>
```

**原因**: 节点资源不足

**解决**:
- 检查节点资源: `kubectl describe nodes`
- 添加更多节点（CA 或手动）
- 减小 Pod 资源请求
- 检查节点 Taint/Affinity 约束

### 11.4 VPA 不更新 Pod

```bash
# 检查 VPA 模式
kubectl get vpa <name> -o yaml | grep updateMode

# Off 模式: 仅推荐，不更新
# Initial 模式: 仅新 Pod 应用推荐值
# Auto 模式: 会驱逐并重建 Pod
```

### 11.5 CA 不添加节点

```bash
# 检查 CA 日志
kubectl logs -n kube-system deployment/cluster-autoscaler

# 常见原因:
# 1. 节点组已达到最大数量
# 2. Pod 的资源请求超过单节点容量
# 3. Pod 的调度约束无法满足
```

## 12. 小结与下一步

### 核心知识点回顾

1. **手动扩缩容**: `kubectl scale --replicas=N` 调整副本数
2. **ReplicaSet** 自动维持期望副本数，Pod 故障自动重建
3. **Service 负载均衡** 将流量分发到所有健康 Pod
4. **HPA** 基于 CPU/内存/自定义指标自动调整 Pod 副本数
5. **VPA** 自动调整 Pod 的 CPU/内存 requests
6. **Cluster Autoscaler** 自动增减集群节点
7. **三层协同**: HPA（Pod 数）→ VPA（Pod 资源）→ CA（节点数）

### 关键命令速查

```bash
kubectl scale deployment <name> --replicas=N   # 手动扩缩容
kubectl get deployments                         # 查看副本数
kubectl get rs                                  # 查看 ReplicaSet
kubectl autoscale deployment <name> --min=3 --max=10 --cpu-percent=70  # 命令行创建 HPA
kubectl get hpa                                 # 查看 HPA
kubectl top pods                                # 查看 Pod 资源使用
kubectl top nodes                               # 查看节点资源使用
```
