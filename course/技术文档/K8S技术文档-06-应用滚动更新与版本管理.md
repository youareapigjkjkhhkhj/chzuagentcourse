## 1. 滚动更新核心概念

### 1.1 为什么需要滚动更新

用户期望应用**全天候可用**，开发者需要**每天多次部署新版本**。传统更新方式会导致停机：

```
传统更新:
  停止旧版本 → 部署新版本 → 启动新版本
  ↑ 这段时间用户无法访问

滚动更新:
  逐步替换旧 Pod → 新 Pod → 旧 Pod → 新 Pod ...
  ↑ 全程无停机
```

### 1.2 什么是滚动更新

滚动更新（Rolling Update）允许 Deployment 更新时**零停机**，通过**逐步替换**当前 Pod 实例为新版本来实现：

```
初始状态:
  Deployment (v1)
  ├── Pod-1 (v1) ✓
  ├── Pod-2 (v1) ✓
  └── Pod-3 (v1) ✓

更新中:
  Deployment (v2)
  ├── Pod-1 (v1) ✓     ← 仍提供服务
  ├── Pod-2 (v1) ✓     ← 仍提供服务
  └── Pod-4 (v2) ✓     ← 新 Pod 启动

继续更新:
  Deployment (v2)
  ├── Pod-1 (v1) ✓     ← 仍提供服务
  ├── Pod-4 (v2) ✓     ← 新 Pod 就绪
  └── Pod-5 (v2) ✓     ← 新 Pod 就绪

更新完成:
  Deployment (v2)
  ├── Pod-4 (v2) ✓
  ├── Pod-5 (v2) ✓
  └── Pod-6 (v2) ✓
```

### 1.3 滚动更新的优势

| 优势 | 说明 |
|------|------|
| 零停机 | 全程有 Pod 在提供服务 |
| 版本控制 | 每次更新都有版本记录 |
| 可回滚 | 可随时回滚到任意历史版本 |
| 渐进式 | 逐步替换，降低风险 |

### 1.4 前置条件

> **重要**: 滚动更新需要**多个副本**。单副本更新会有短暂不可用。

```bash
# 确保有多个副本
kubectl scale deployment/kubernetes-bootcamp --replicas=4
```

## 2. 滚动更新原理

### 2.1 Deployment → ReplicaSet → Pod 的版本管理

```
更新前:
Deployment
  └── ReplicaSet-v1 (replicas: 4, 状态: Active)
        ├── Pod-1 (v1)
        ├── Pod-2 (v1)
        ├── Pod-3 (v1)
        └── Pod-4 (v1)

更新中:
Deployment
  ├── ReplicaSet-v1 (replicas: 3, 逐步减少) ← 旧版本
  │     ├── Pod-1 (v1)
  │     ├── Pod-2 (v1)
  │     └── Pod-3 (v1)
  └── ReplicaSet-v2 (replicas: 1, 逐步增加) ← 新版本
        └── Pod-5 (v2) ✓

更新完成:
Deployment
  ├── ReplicaSet-v1 (replicas: 0, 保留用于回滚)
  └── ReplicaSet-v2 (replicas: 4, Active)
        ├── Pod-5 (v2)
        ├── Pod-6 (v2)
        ├── Pod-7 (v2)
        └── Pod-8 (v2)
```

**关键点**:
- Deployment 为每个版本创建一个新的 ReplicaSet
- 旧 ReplicaSet 缩容到 0 但**不被删除**（用于回滚）
- 更新过程中新旧版本共存，Service 将流量路由到就绪的 Pod

### 2.2 默认更新参数

```
默认: maxUnavailable = 25%, maxSurge = 25%

4 个副本时:
  最多 1 个不可用 (25% of 4 = 1)
  最多 5 个总数 (4 + 25% of 4 = 5)

更新流程:
  4 个 v1 → 1 个 v2 (总数 5) → 终止 1 个 v1 → 2 个 v2 → ...
```

### 2.3 Service 在更新中的作用

```
Service
  ↓ 通过 Endpoints 监控 Pod 就绪状态
  ↓
新 Pod readinessProbe 成功 → 加入 Endpoints → 接收流量
旧 Pod 终止 → 移出 Endpoints → 停止接收流量
```

> Service 只将流量发送到就绪的 Pod，确保用户在更新期间持续访问应用。

## 3. 实战：执行滚动更新

### 3.1 前置准备

```bash
# 确保应用已部署且有多个副本
kubectl get deployments
kubectl get pods

# 如果需要重新创建
kubectl create deployment kubernetes-bootcamp --image=gcr.io/google-samples/kubernetes-bootcamp:v1
kubectl scale deployment/kubernetes-bootcamp --replicas=4

# 创建 Service
kubectl expose deployment/kubernetes-bootcamp --type="NodePort" --port 8080
```

### 3.2 查看当前版本

```bash
# 查看 Deployment
kubectl get deployments

# 查看 Pod
kubectl get pods

# 查看当前镜像版本
kubectl describe pods | grep Image
# Image: gcr.io/google-samples/kubernetes-bootcamp:v1
```

### 3.3 执行滚动更新

```bash
# 更新镜像到 v2
kubectl set image deployments/kubernetes-bootcamp \
  kubernetes-bootcamp=docker.io/jocatalin/kubernetes-bootcamp:v2
```

**命令格式**: `kubectl set image deployment/<name> <container-name>=<new-image>`

## 5. 回滚操作

### 5.1 模拟更新失败

```bash
# 故意使用不存在的镜像版本
kubectl set image deployments/kubernetes-bootcamp \
  kubernetes-bootcamp=gcr.io/google-samples/kubernetes-bootcamp:v10
```

### 5.2 查看失败状态

```bash
kubectl get deployments
```

输出（可用副本数不足）：
```
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
kubernetes-bootcamp   3/4     1            3           15m
```

```bash
kubectl get pods
```

输出（新 Pod 拉取镜像失败）：
```
NAME                                   READY   STATUS             RESTARTS   AGE
kubernetes-bootcamp-644c5687f4-4hjvf   1/1     Running            0          5m     ← v2 仍在运行
kubernetes-bootcamp-644c5687f4-hs9dj   1/1     Running            0          5m     ← v2 仍在运行
kubernetes-bootcamp-644c5687f4-wp67j   1/1     Running            0          5m     ← v2 仍在运行
kubernetes-bootcamp-7d6f85b5b6-x9yza   0/1     ImagePullBackOff   0          1m     ← v10 拉取失败
```

```bash
# 查看失败详情
kubectl describe pods | grep -A5 Events
# Events: Failed to pull image "gcr.io/google-samples/kubernetes-bootcamp:v10"
```

### 5.3 执行回滚

```bash
# 回滚到上一版本
kubectl rollout undo deployments/kubernetes-bootcamp
```

### 5.4 验证回滚

```bash
# 查看 Pod 状态
kubectl get pods
# 所有 Pod 恢复为 v2

# 查看镜像版本
kubectl describe pods | grep Image
# Image: docker.io/jocatalin/kubernetes-bootcamp:v2

# 查看更新历史
kubectl rollout history deployments/kubernetes-bootcamp
# REVISION 1 和 2 → 3 (回滚创建新 revision)
```

### 5.5 回滚到指定版本

```bash
# 查看历史版本
kubectl rollout history deployments/kubernetes-bootcamp

# 回滚到指定版本
kubectl rollout undo deployments/kubernetes-bootcamp --to-revision=1
```

### 5.6 rollout 命令总结

```bash
# 查看更新状态
kubectl rollout status deployment/<name>

# 查看更新历史
kubectl rollout history deployment/<name>

# 查看特定版本
kubectl rollout history deployment/<name> --revision=2

# 回滚到上一版本
kubectl rollout undo deployment/<name>

# 回滚到指定版本
kubectl rollout undo deployment/<name> --to-revision=1

# 暂停滚动更新
kubectl rollout pause deployment/<name>

# 恢复滚动更新
kubectl rollout resume deployment/<name>

# 重启（触发滚动更新，不改变镜像）
kubectl rollout restart deployment/<name>
```

## 6. 更新策略详解

### 6.1 RollingUpdate（默认）

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1    # 更新时最多允许 1 个 Pod 不可用（数字或百分比）
      maxSurge: 1          # 更新时最多允许超出期望副本数 1 个（数字或百分比）
```

**参数说明**:

| 参数 | 默认值 | 说明 |
|------|--------|------|
| maxUnavailable | 25% | 更新过程中允许的最大不可用 Pod 数 |
| maxSurge | 25% | 更新过程中允许超出期望副本数的最大 Pod 数 |

**不同配置的效果**:

```
# 配置: maxUnavailable=0, maxSurge=1 (零停机 + 多一个临时 Pod)
4 副本 → 5(4v1+1v2) → 4(3v1+1v2) → 5(3v1+2v2) → ... → 4(0v1+4v2)
↑ 全程至少 4 个可用 Pod

# 配置: maxUnavailable=1, maxSurge=0 (不增加临时 Pod)
4 副本 → 3(3v1+0v2) → 4(3v1+1v2) → 3(2v1+1v2) → ... → 4(0v1+4v2)
↑ 全程至少 3 个可用 Pod，但不超出 4 个

# 配置: maxUnavailable=0, maxSurge=25% (生产推荐)
4 副本 → 5 → 4 → 5 → 4 → ... → 4
↑ 全程零停机
```

### 6.2 Recreate（重建）

```yaml
spec:
  strategy:
    type: Recreate
```

```
Recreate 策略:
  先终止所有旧 Pod → 再创建所有新 Pod
  ↑ 有停机时间！
```

**适用场景**: 不支持多版本并行的有状态应用（如单副本数据库）

### 6.3 策略对比

| 特性 | RollingUpdate | Recreate |
|------|--------------|----------|
| 停机时间 | 零停机 | 有停机 |
| 资源使用 | 更新时需要额外资源 | 不需要额外资源 |
| 新旧共存 | 是 | 否 |
| 回滚速度 | 中等 | 快 |
| 适用场景 | 无状态服务 | 有状态/单副本 |

### 6.4 生产推荐配置

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0        # 生产必选：确保零停机
      maxSurge: 25%            # 允许 25% 额外 Pod 加速更新
```

## 7. 蓝绿部署

### 7.1 蓝绿部署原理

```
蓝绿部署: 维护两套完全独立的环境

切换前:
  ┌─────────┐     ┌─────────┐
  │ Blue (v1)│ ←→ │  DB     │
  │ 3 Pods   │     │         │
  └─────┬───┘     └─────────┘
        │
     Service (selector: version=blue)

切换后:
  ┌─────────┐     ┌─────────┐
  │ Green (v2)│ ←→ │  DB     │
  │ 3 Pods    │     │         │
  └─────┬────┘     └─────────┘
        │
     Service (selector: version=green)

  Blue 环境保留，随时可回滚
```

### 7.2 K8S 实现蓝绿部署

**方式一：修改 Service selector**

```yaml
# Blue Deployment (当前运行)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
      version: blue
  template:
    metadata:
      labels:
        app: myapp
        version: blue
    spec:
      containers:
      - name: app
        image: myapp:v1
---
# Service (当前指向 Blue)
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp
    version: blue        # ← 切换到 green 即可
  ports:
  - port: 80
    targetPort: 8080
```

```bash
# 部署 Green 环境
kubectl apply -f green-deployment.yaml

# 验证 Green 就绪
kubectl get pods -l version=green

# 切换流量到 Green
kubectl patch svc myapp-service -p '{"spec":{"selector":{"version":"green"}}}'

# 验证
curl http://<service-ip>

# 如需回滚，切回 Blue
kubectl patch svc myapp-service -p '{"spec":{"selector":{"version":"blue"}}}'
```

### 7.3 蓝绿部署特点

| 优点 | 缺点 |
|------|------|
| 即时切换，秒级回滚 | 需要双倍资源 |
| 完整环境验证 | 数据库兼容性挑战 |
| 新旧完全隔离 | 切换是全量的（无灰度） |

## 8. 金丝雀发布

### 8.1 金丝雀发布原理

```
金丝雀发布: 逐步将流量导向新版本

阶段 1: 95% v1 + 5% v2
  ┌──────────┐    ┌──────────┐
  │ v1 (95%) │    │ v2 (5%)  │
  │ 19 Pods  │    │ 1 Pod    │
  └──────────┘    └──────────┘
       ↓               ↓
       └──── Service ────┘

阶段 2: 90% v1 + 10% v2
阶段 3: 50% v1 + 50% v2
阶段 4: 0% v1 + 100% v2
```

### 8.2 K8S 实现金丝雀发布

**方式一：多 Deployment + 调整副本数**

```yaml
# 稳定版本 Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-stable
spec:
  replicas: 9                      # 90% 流量
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        version: stable
    spec:
      containers:
      - name: app
        image: myapp:v1
---
# 金丝雀版本 Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-canary
spec:
  replicas: 1                      # 10% 流量
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        version: canary
    spec:
      containers:
      - name: app
        image: myapp:v2
---
# Service (同时选择两个版本)
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp                     # 选择所有版本
  ports:
  - port: 80
    targetPort: 8080
```

```bash
# 逐步增加金丝雀流量
kubectl scale deployment myapp-canary --replicas=5    # 33%
kubectl scale deployment myapp-stable --replicas=5    # 50%

# 最终全量
kubectl scale deployment myapp-canary --replicas=10
kubectl scale deployment myapp-stable --replicas=0
```

**方式二：使用 Istio 精确流量切分**

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: myapp-vs
spec:
  hosts:
  - myapp
  http:
  - route:
    - destination:
        host: myapp
        subset: v1
      weight: 90                   # 90% 流量到 v1
    - destination:
        host: myapp
        subset: v2
      weight: 10                   # 10% 流量到 v2
```

### 8.3 金丝雀发布特点

| 优点 | 缺点 |
|------|------|
| 风险最小化 | 实施复杂 |
| 渐进式验证 | 需要流量管理能力 |
| 可自动回滚 | 需要强大监控体系 |

## 9. 高级发布策略

### 9.1 A/B 测试发布

```
基于用户特征的流量路由:
  Cookie/Header 包含 "beta=true" → v2
  其他用户 → v1
```

```yaml
# Istio VirtualService 基于请求头路由
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
spec:
  http:
  - match:
    - headers:
        user-type:
          exact: premium
    route:
    - destination:
        host: myapp
        subset: v2         # premium 用户 → v2
  - route:
    - destination:
        host: myapp
        subset: v1         # 其他 → v1
```

### 9.2 影子流量（Shadow Traffic）

```
生产流量 → v1 (正常响应)
           ↓ 镜像复制
           v2 (不影响用户，仅观察)
```

```yaml
# Istio 镜像流量
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
spec:
  http:
  - route:
    - destination:
        host: myapp
        subset: v1
    mirror:
      host: myapp
      subset: v2            # 镜像到 v2
    mirrorPercentage:
      value: 100.0          # 100% 镜像
```

### 9.3 使用 Argo Rollouts 进行渐进式交付

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: myapp
spec:
  replicas: 10
  strategy:
    canary:
      steps:
      - setWeight: 5            # 5% 流量
      - pause: { duration: 10m } # 观察 10 分钟
      - setWeight: 20           # 20% 流量
      - pause: { duration: 10m }
      - setWeight: 50           # 50% 流量
      - pause: { duration: 5m }
      - setWeight: 100          # 全量
  template:
    # ... Pod 模板
```

**Argo Rollouts 优势**:
- 自动化渐进式发布
- 基于指标自动回滚
- 支持蓝绿和金丝雀
- 与 Prometheus 集成

### 9.4 策略对比总表

| 策略 | 零停机 | 回滚速度 | 风险 | 成本 | 流量控制 | 复杂度 |
|------|--------|----------|------|------|----------|--------|
| 滚动更新 | ✅ | 中 | 中 | 低 | 无 | 低 |
| 蓝绿部署 | ✅ | 即时 | 中 | 高 | 全量切换 | 中 |
| 金丝雀 | ✅ | 快 | 最低 | 中 | 精细 | 高 |
| A/B 测试 | ✅ | 快 | 低 | 中 | 基于特征 | 高 |
| 影子流量 | ✅ | N/A | 最低 | 高 | 镜像 | 高 |

### 9.5 选型决策

```
什么策略适合你?

需要简单 + 安全?
  → 滚动更新 (K8S 原生)

需要即时回滚 + 能承受双倍资源?
  → 蓝绿部署

高流量 + 高风险 + 需要灰度?
  → 金丝雀发布

需要渐进式 + 自动化?
  → Argo Rollouts + 金丝雀
```

## 10. 零停机部署关键要素

### 10.1 就绪探针

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 3
  failureThreshold: 3
```

**作用**: 新 Pod 就绪后才加入 Service Endpoints，旧 Pod 终止后才移出 Endpoints。

### 10.2 存活探针

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10
  failureThreshold: 5
```

**作用**: 确保运行中的 Pod 健康可用。

### 10.3 优雅终止

```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command:
          - "/bin/sh"
          - "-c"
          - "sleep 10 && nginx -s quit"
```

**优雅终止流程**:
```
1. Pod 标记为 Terminating
2. 从 Service Endpoints 移除（停止接收新请求）
3. 等待 preStop 钩子执行（sleep 10 让连接排空）
4. 发送 SIGTERM 给容器
5. 等待 terminationGracePeriodSeconds (默认 30s)
6. 如果超时，发送 SIGKILL
```

### 10.4 maxUnavailable: 0

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0     # ← 生产必选
    maxSurge: 1
```

**作用**: 确保更新过程中始终有足够数量的 Pod 可用。

### 10.5 完整零停机配置

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: zero-downtime-app
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0          # 零停机
      maxSurge: 1                # 临时多一个 Pod
  template:
    spec:
      terminationGracePeriodSeconds: 60
      containers:
      - name: app
        image: myapp:v2
        ports:
        - containerPort: 8080
        readinessProbe:          # 就绪探针
          httpGet:
            path: /ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 3
          failureThreshold: 3
        livenessProbe:           # 存活探针
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 10
          failureThreshold: 5
        lifecycle:               # 优雅终止
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 10 && app --graceful-shutdown"]
        resources:
          requests:
            cpu: 200m
            memory: 256Mi
```

## 11. 生产环境最佳实践

### 11.1 发布前检查清单

```
□ 多副本部署 (至少 2+ 副本)
□ maxUnavailable: 0 (零停机保障)
□ 配置 readinessProbe 和 livenessProbe
□ 配置 preStop 钩子和 terminationGracePeriodSeconds
□ 设置 resources.requests 和 limits
□ 测试镜像在预发环境可正常拉取
□ 数据库迁移使用向后兼容方式 (Expand → Migrate → Contract)
□ 准备回滚方案
□ 监控告警就位
```

### 11.2 数据库迁移安全

```
安全模式: Expand → Migrate → Contract

1. Expand: 新增列/表（向后兼容）
2. Migrate: 迁移数据到新结构
3. Contract: 删除旧列/表（下一版本）

不安全: 部署代码同时修改数据库结构
```

### 11.3 监控指标

部署后应监控：
```yaml
# Prometheus 查询示例
- p99 延迟: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
- 错误率: rate(http_requests_total{status=~"5.."}[5m])
- Pod 重启次数: kube_pod_container_status_restarts_total
- CPU/内存异常: container_cpu_usage_seconds_total, container_memory_usage_bytes
```

### 11.4 保留历史版本数

```yaml
spec:
  revisionHistoryLimit: 10    # 默认 10，保留 10 个历史 ReplicaSet 用于回滚
```

### 11.5 使用 Change Cause

```bash
# 创建时记录变更原因
kubectl create deployment myapp --image=myapp:v1 --record

# 更新时记录
kubectl set image deployment/myapp myapp=myapp:v2 --record

# 查看历史
kubectl rollout history deployment/myapp
# REVISION  CHANGE-CAUSE
# 1         kubectl create deployment myapp --image=myapp:v1 --record
# 2         kubectl set image deployment/myapp myapp=myapp:v2 --record
```

### 11.6 紧急操作

```bash
# 紧急暂停更新
kubectl rollout pause deployment/myapp

# 排查问题后恢复
kubectl rollout resume deployment/myapp

# 紧急回滚
kubectl rollout undo deployment/myapp

# 回滚到指定版本
kubectl rollout undo deployment/myapp --to-revision=3

# 记录回滚原因
kubectl annotate deployment/myapp rollback-reason="接口兼容问题"
```

## 12. 常见问题排查

### 12.1 更新卡住

```bash
# 查看更新状态
kubectl rollout status deployment/myapp

# 查看 Pod 状态
kubectl get pods

# 查看 Deployment 事件
kubectl describe deployment myapp
```

**常见原因**:
- 新 Pod 拉取镜像失败（ImagePullBackOff）
- 新 Pod 健康检查失败（CrashLoopBackOff）
- 资源不足导致 Pod Pending
- maxUnavailable: 0 但新 Pod 一直不就绪

### 12.2 新版本 Pod 健康检查失败

```bash
# 查看日志
kubectl logs <new-pod-name>

# 查看事件
kubectl describe pod <new-pod-name>

# 手动测试就绪端点
kubectl exec -it <new-pod-name> -- curl http://localhost:8080/ready
```

### 12.3 回滚失败

```bash
# 查看历史版本
kubectl rollout history deployment/myapp

# 检查历史 ReplicaSet 是否存在
kubectl get rs

# 如果历史 ReplicaSet 被删除，无法回滚
# 解决: 重新 apply 旧版本 YAML
kubectl apply -f old-version-deployment.yaml
```

### 12.4 更新期间服务不可用

**原因**: maxUnavailable 设置过大或没有 readinessProbe

**解决**:
```yaml
strategy:
  rollingUpdate:
    maxUnavailable: 0    # 设置为 0
    maxSurge: 1
```

确保 readinessProbe 配置正确。

### 12.5 Pod 终止慢

**原因**: 应用未处理 SIGTERM 信号 或 preStop 钩子耗时

**解决**:
```yaml
# 增加 grace period
terminationGracePeriodSeconds: 60

# 在 preStop 中等待连接排空
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 15 && app --shutdown"]
```

## 13. 小结与下一步

### 核心知识点回顾

1. **滚动更新** 通过逐步替换 Pod 实现零停机更新
2. **Deployment** 为每个版本创建新 ReplicaSet，旧版本保留用于回滚
3. **rollout 命令**: status（查看状态）、history（查看历史）、undo（回滚）、pause/resume（暂停/恢复）
4. **更新策略**: RollingUpdate（默认零停机）、Recreate（有停机）
5. **maxUnavailable: 0** 是生产环境零停机的关键配置
6. **蓝绿部署**: 双环境 + Service selector 切换，即时回滚
7. **金丝雀发布**: 渐进式流量切分，风险最低
8. **零停机三要素**: readinessProbe + preStop + maxUnavailable:0

### 关键命令速查

```bash
kubectl set image deployment/<name> <container>=<new-image>  # 更新镜像
kubectl rollout status deployment/<name>                     # 查看更新状态
kubectl rollout history deployment/<name>                    # 查看历史
kubectl rollout undo deployment/<name>                       # 回滚到上一版本
kubectl rollout undo deployment/<name> --to-revision=N       # 回滚到指定版本
kubectl rollout pause deployment/<name>                      # 暂停更新
kubectl rollout resume deployment/<name>                     # 恢复更新
kubectl rollout restart deployment/<name>                    # 重启（触发更新）
```
